## Goal
PR #83's "License check" step (the first time it's ever actually run, since earlier CI bugs masked it — see ST-034/035/036) flags ~17 packages, but most are false positives caused by the checker script only matching exact single SPDX identifiers against `pnpm licenses list --json`'s license strings, not compound expressions or non-standard formatting. Fix the parser so it correctly evaluates these without weakening the actual policy.

## Context (read before starting)
- The checker script lives inline in `.github/workflows/subtrack-ci.yml`'s "License check" step. It builds an `allowed` Set of SPDX ids and rejects anything not an exact match.
- CI log (PR #83, run 36629412709) — false-positive patterns to fix:
  - Compound `AND` expressions where every component is already allowed, e.g. `Apache-2.0 AND MIT` (`@swc/core-linux-x64-gnu`), `(Apache-2.0 AND MIT)` (`@web3-storage/multipart-parser`) — should PASS since both components are on the allowlist.
  - Compound `OR` expressions where at least one component is already allowed (dual-licensed, consumer's choice), e.g. `(Unlicense OR Apache-2.0)` (`@zxing/text-encoding`), `(MIT OR CC0-1.0)` (`type-fest`), `(BSD-2-Clause OR MIT OR Apache-2.0)` (`rc`), `(BSD-3-Clause OR GPL-2.0)` (`node-forge` — BSD-3-Clause is already allowed, so this one passes even though GPL-2.0 alone would not).
  - Non-SPDX-normalized formatting: `Apache 2.0` (`qrcode-terminal`) should normalize to `Apache-2.0` (already allowed).
  - Ambiguous bare `BSD` (`readline@1.3.0`) — look up the package's actual licence file/npm registry metadata to determine whether it's BSD-2-Clause or BSD-3-Clause, then either normalize confidently or leave it failing with a clear reason if genuinely ambiguous.
  - `MIT-0` (`@csstools/color-helpers`, `@csstools/css-syntax-patches-for-csstree`) is not on the allowlist yet — it's the OSI-approved "MIT No Attribution" licence, strictly more permissive than plain MIT (public-domain-equivalent). Add it to the allowed set directly — this is an unambiguous permissive addition, not a new risk category.
- **Do NOT touch the allowlist for these — leave them failing exactly as today; they need a separate founder decision (D-11) currently pending on Telegram, tracked outside this task:**
  - `@img/sharp-libvips-linux-x64`: `LGPL-3.0-or-later`
  - `axe-core`: `MPL-2.0`
  - `lightningcss` / `lightningcss-linux-x64-gnu`: `MPL-2.0`
  - `caniuse-lite`: `CC-BY-4.0`
  - `make-plural`: `Unicode-DFS-2016`
  - `valid-url`: `Unknown`
  If your parser fix would incidentally cause any of these six to start passing, that's a bug in your fix — stop and reconsider, don't let it through.
