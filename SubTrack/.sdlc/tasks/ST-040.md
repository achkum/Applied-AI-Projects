## Goal
Define the complete Prisma schema for identity, household, invitation, consent, and audit_log tables with Row-Level Security policies enforcing the privacy model. Schema must support subsequent OTP, BankID, sessions, and household management tasks.

## Context (read before starting)
- ST-007 (API NestJS skeleton) is DONE; Prisma client is initialized
- `docs/product/ASSUMPTIONS.md` §A1–A3: privacy model (per-member Open book, transactions/balances never shared, per-subscription Always private)
- `docs/architecture/ADR-*.md`: seed architecture and RLS patterns
- ST-048 will define visibility policy logic; this task defines the schema contracts it operates on

## Acceptance criteria
- AC1: Given a developer migrates the new schema, when they inspect the database, then they see five tables (identity, household, invitation, consent, audit_log) with correct nullable/unique/foreign-key constraints and RLS enable=true
- AC2: Given a backend developer reads the schema comments, when they reference a table, then they understand its purpose, ownership model (user/household), and RLS scope
- AC3: Given a developer runs prisma generate, when they inspect the generated Prisma Client types, then types for create/read/update/delete operations match the schema constraints
- AC4: Given security reviewer reads the migration SQL, when they trace a Scope member's data access, then RLS policies enforce: identity rows belong to one user; household members can see only their own household's invitations; audit_log is readable only by household admins; consent is per-user, not shared

## Out of scope
- Implementation of OTP service, BankID adapters, session tokens, or household member operations
- Visibility policy logic (ST-048); this task defines tables only
- Data seeding or fixtures
- DevOps deployment or backup strategies

## Technical notes
- Prisma schema lives at `apps/api/prisma/schema.prisma`; generator in `package.json` is already configured
- RLS policies must match the privacy model: household members see only their own data; audit_log is append-only and readable by admins only
- Use advisory locks or application-layer consistency to prevent race conditions on household member counts and invitations
- Comments in schema file must include table purpose and RLS intent; this is your contract for downstream tasks

## Handoff — v1

### What was built
- `apps/api/prisma/schema.prisma` — complete Prisma schema with 5 models (Identity, Household, HouseholdMember, Invitation, Consent, AuditLog) and 6 enums. Each model carries inline RLS-scope documentation comments showing the exact PostgreSQL USING clause.
- `apps/api/prisma/migrations/0001_identity_household_rls/migration.sql` — hand-authored migration that:
  - Creates all 5 tables with correct nullable/unique/FK constraints
  - Enables RLS on all 5 tables (`ALTER TABLE … ENABLE ROW LEVEL SECURITY`)
  - Installs per-table policies keyed on `current_setting('app.current_user_id')::uuid`
  - Enforces partial unique index on `household_member (identity_id) WHERE left_at IS NULL` (one active membership per user)
  - Makes `audit_log` append-only by omitting UPDATE/DELETE policies

### AC verification
- AC1: Migration SQL creates five tables with expected constraints and RLS enabled.
- AC2: Every model in schema.prisma has a comment block describing purpose, ownership, and USING clause.
- AC3: `npx prisma@6.19.2 validate --schema=prisma/schema.prisma` → "The schema at prisma\schema.prisma is valid 🚀". `prisma generate` runs in CI (requires pnpm in PATH; not available in local dev shell).
- AC4: RLS policies trace: identity rows → self only; household_member → household peers (SELECT), admin only (UPDATE); invitation → inviter | invitee | household admin; consent → self only; audit_log INSERT → self, SELECT → self + household admin, UPDATE/DELETE → denied (no policy = deny under RLS).
