## Goal
Add a deterministic, reusable domain function that normalizes a bank transaction descriptor and resolves it to a merchant from an injected catalogue. This supplies the rules-and-alias-table first stage required by PRODUCT_SPEC §F5.2 and gives the recurring detector (ST-080) a stable merchant identity without adding a dependency on the catalogue package or changing architecture.

## Context (read before starting)
- PRODUCT_SPEC §F5.1–F5.3 and §F5.7
- DATA_MODEL.md, “Catalogue & detection”
- CATEGORIES.md
- ADR-0005
- ST-064 catalogue types and alias data
- ST-067 ingestion record; it preserves the original description and raw payload
- Current implementation exposes `BankTransaction` and `IngestionRecord` from `@subtrack/domain/bank` and `@subtrack/domain/ingestion`; neither currently performs merchant matching.

## Acceptance criteria
- AC1: `@subtrack/domain/merchant` exports a descriptor normalizer and a merchant matcher. Inputs are typed locally or structurally; implementation does not add a runtime dependency on `@subtrack/catalog` or `@subtrack/synthetic`.
- AC2: Descriptor normalization is deterministic and locale-independent: apply Unicode NFKC normalization, trim leading/trailing whitespace, collapse consecutive whitespace, and compare case-insensitively. Preserve punctuation and other characters; do not strip arbitrary suffixes, tokenize, use edit distance, substring/prefix matching, or infer an alias.
- AC3: Matcher compares the normalized transaction description for exact equality against each catalogue merchant's canonical name and explicit aliases. It returns the matched stable merchant key and canonical name (and the matched field/source if useful), or `null` when there is no exact match.
- AC4: Matching never selects arbitrarily when normalized catalog entries collide across different merchants. Such a descriptor returns `null`; duplicate normalized entries belonging only to the same merchant still resolve to that merchant.
- AC5: A transaction is not mutated and its original description remains available unchanged. The matcher has no persistence, logging, network, ML, or LLM behaviour.
- AC6: Unit tests cover case and whitespace normalization, canonical-name and alias hits, unmatched descriptions, punctuation preservation (including `.COM`), collision behavior, deterministic repeated calls, and empty/whitespace-only input.
- AC7: `pnpm --filter @subtrack/domain test` and `pnpm --filter @subtrack/domain typecheck` pass.

## Out of scope
- Fuzzy, substring, regex, token, ML, or LLM merchant resolution; PRODUCT_SPEC §F5.2's second-stage suggestions and review queue are a separate follow-up.
- Mutating ingestion records, persistence/schema changes, transaction grouping, recurring detection/confidence/reasons (ST-080), plan recognition (ST-080/ST-081 follow-up), or API/UI work.
- Editing catalogue data or changing ST-064, ST-067, or the backlog board.

## Technical notes
- Inject a narrow structural catalogue shape (stable key, canonical name, aliases) so domain code does not depend on the catalog package. The current catalog exports `CatalogMerchant` with `key`, `canonicalName`, and `aliases`.
- Expose a small result type containing the matched stable key and canonical name. Keep category and plan recognition outside this task.
- Matching is exact after the narrowly defined normalization in AC2. For example, `NETFLIX.COM` resolves only when that exact normalized form is a catalogue alias; `.COM` is not globally removed.
- Local implementation choice (Type 2b): NFKC + case-insensitive comparison + whitespace trimming/collapse provides a stable equality key while preserving punctuation. PRODUCT_SPEC §F5.2 requires deterministic rules and aliases but does not specify broader descriptor rewriting; any broader rewrite needs a separately specified follow-up.
- Keep the normalization utility pure. Do not use `toLocaleLowerCase`, current date/time, provider-specific fields, or hidden global catalogue state.
- No new dependency is expected; if the implementation proves one essential, stop and hand back rather than expanding allowed paths or changing architecture.
