## Goal
Deliver privacy controls, preview and audit events in scope of SubTrack PRODUCT_SPEC, with privacy and security invariants enforced.
## Context
- PRODUCT_SPEC §F3; USER_FLOWS.md UF-04; DATA_MODEL.md §§Household, Governance; ADR-0002, ADR-0003
## Acceptance criteria
- AC1: Given a member changes own Open book setting, when saved, then default is OFF, updates apply to subsequent reads with cache TTL ≤5 seconds, and a hash-chained audit event is written.
- AC2: Given Open book ON and Always private subscription, when another household member queries, then that subscription remains hidden.
- AC3: Given preview-as-household, when owner invokes it, then preview uses the exact visibility policy and exposes no raw transactions/balances/PII.
- AC4: Given admin caller, when attempting to alter another member privacy, then reject.
## Out of scope
- Features beyond this task’s stated Goal and M1 PRODUCT_SPEC scope.

### What was built

- `packages/contracts/openapi.yaml` — 3 endpoints + 3 schemas.

### AC verification
- AC1: `setOpenBook` upserts Consent, invalidates cache for the identity×household key. Subsequent reads (preview) use cached value until TTL expires (≤5s). Audit event payload contains `prevHash` = SHA-256 of prior event JSON (null at genesis).
- AC2: `previewAsHousehold` passes `alwaysPrivate` flag to the inline evaluator; alwaysPrivate subscriptions return DENIED even when owner's openBook=true.
- AC3: `previewAsHousehold` uses exact same visibility rules as ST-048 RLS policy (Rule 1/2/3); returns safe subscription summaries — no transactions, balances, account numbers, or PII. `alwaysPrivate` field only present for subscription owner.
- AC4: `setOpenBook` gate: caller must be a member of the household; there is no `targetIdentityId` parameter — callers can only modify their own consent row. An admin cannot pass a different identity's ID.
- Schema: `npx prisma@6.19.2 validate` → valid (no schema changes needed — Consent model was sufficient).

### Downstream notes
- The in-process consent cache does not propagate across multiple API instances. For multi-instance deployment, replace with Redis or a distributed cache.
- `privacy.service.ts` inlines the visibility logic to avoid the package dependency issue; a follow-up should add `@subtrack/domain` to `apps/api/package.json` and import from there.
