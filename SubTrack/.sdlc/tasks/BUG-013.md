## Problem and constraints
Read-only BUG-008 inventory identifies a mismatch: accepted DATA_MODEL and API helper use `app.user_id`, while all accepted SQL policies read `app.current_user_id`. Keep canonical `app.user_id` per DATA_MODEL and never rewrite unknown applied migrations. Propose binding both keys to exactly the same verified RequestContext userId, transaction-local, before any callback operation. This is compatibility of an existing helper, with no auth module/controller exposure and no database/schema/migration application.

## Acceptance criteria
1. Independent platform/security pre-review approves the dual-key binding as preserving canonical and historical policy access semantics before implementation. Do not silently replace the canonical spec key or alter SQL policies.
2. Both settings receive the exact same RequestContext principal through parameterized SQL within the existing transaction and `set_config(...,true)` local lifetime. No operation occurs before successful binding; blank context rejected before transaction.
3. Preserve all existing tests/assertions. Add meaningful setting consistency, callback ordering, failed-setting/no-callback and per-request identity binding tests without requiring unavailable migrations. No raw credentials/data logging, no unsafe interpolation/suppression.
4. API lint/typecheck/unit tests pass. Independent postimplementation architecture/security review and QA approve; full required CI before merge.
5. Document this narrow compatibility layer and unresolved SEC-FU1 authenticated-principal/module-registration constraints. No production-readiness or end-to-end database RLS claim from mock tests.
