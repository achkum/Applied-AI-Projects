## Goal
Provide a correct, audit-ready `@subtrack/money` arithmetic layer for the sharing and settlement features (ST-102, ST-103). All operations use BigInt to avoid floating-point rounding errors; largest-remainder allocation guarantees the sum of split parts equals the original total.

## Context
- ST-102 (share/split API) and ST-103 (settlement compute) depend on this package
- ST-056 added `formatMoney`/`minorUnitExponent` to this package; ST-100 extends it with arithmetic
- ASSUMPTIONS.md §A1–A3: subscription amounts are stored as minor-unit integers (öre for SEK)
- docs/product/PRODUCT_SPEC §F4: splitting must be deterministic (same inputs → same outputs)

## Acceptance criteria
- AC1: `money(minorUnits, currency)` constructs a `Money` value; `add`, `subtract`, `multiply` operate on it with BigInt; `multiply` rounds half-up for positive, half-down for negative.
- AC2: `allocateEvenly(total, n)` and `allocateByWeights(total, weights)` use the largest-remainder method; sum of parts equals `total` exactly.
- AC3: Currency mismatch in binary ops throws `MoneyError`; bad weights/n throw `MoneyError`.
- AC4: `assertValidCurrencyCode` and `assertSafeMinorUnits` guard at system boundaries (API input validation).
- AC5: Vitest suite: ≥ 30 cases covering arithmetic, allocation (even and weighted), predicates, conversion, and validation.

## Out of scope
- Forex/exchange-rate conversion.
- Persistence or Prisma models.
- Settlement computation logic (ST-103).

## Technical notes
- `Money.minorUnits` is `bigint` — all arithmetic is exact.
- `fromMajorUnits`/`toMajorUnits` bridges to the `number` world (JSON layer); `assertSafeMinorUnits` guards the entry point.
- Branched from ST-056 so the package.json scripts/devDeps are already correct.
