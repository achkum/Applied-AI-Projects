## Problem
The installed i18n-js4.5.3 exports a named I18n constructor, not the default singleton used by the mobile provider. A local runtime export check proves default is undefined; the legacy ambient declaration hides the mismatch. Existing component tests mock the provider, so compilation/test passes do not prove the app can mount.

## Goal and constraints
Use the installed library's public typed instance API; remove only the obsolete i18n-js ambient declaration and preserve unrelated declarations. Preserve shared/mobile-local catalogs, English fallback and asynchronous stored preference behavior. No dependency/lockfile, UI design, backend/authentication or new translation change. Do not log locale-storage exception payloads that could contain user data; keep errors generic if touched.

## Acceptance criteria
1. Real provider imports and mounts with actual installed i18n-js; English and Swedish translations work, including merged signature strings and interpolation.
2. Stored valid locale selects matching translations; missing/invalid stored locale falls back to English; rejected storage read finishes loading with English. Switching locale updates t() and persists the preference; failure semantics remain intentional and tested.
3. Remove false default-singleton declaration; strict TS resolves the library's real bundled typings. Provider instances do not leak locale through shared mutable translation state.
4. Meaningful regression imports the real provider/library, mocking only native storage as needed, and fails on the old code. Test both language changes, async initialization/failure and instance isolation. Changed provider coverage >=80%; full mobile tests, lint and typecheck pass.
5. Independent architect-client review, QA and required full CI pass before merge. No new auth exposure or task/milestone readiness claim.
