## Goal

Deliver the authenticated API boundary for listing owned detections, reviewing detections, and moving subscriptions through the approved lifecycle, with review feedback recorded for later classification. Keep all subscription and transaction access scoped to a trusted caller identity and the approved visibility/RLS policy. Do not expose a controller or write subscription data until the prerequisites below are complete.

## Context (read before starting)

- PRODUCT_SPEC F5.4 lists Confirm, Not a subscription, Edit, and Merge; F5.5 describes `DETECTED → ACTIVE → (PAUSED) → CANCELLED`, with TRIAL and ARCHIVED states, and says cancellation after more than 1.5× a missed cadence requires user confirmation.
- UF-06 requires every review action to be undoable for 10 seconds and feedback to be stored as classifier labels. UF-08 offers pause, mark cancelled, and archive actions.
- API_CONTRACT lists `GET /v1/subscriptions`, `GET /v1/subscriptions/:id`, `PATCH /v1/subscriptions/:id`, `POST /v1/subscriptions/:id/review`, and `GET /v1/review-inbox`. It also requires cursor pagination, RFC 9457 errors, and an `Idempotency-Key` for mutating POSTs.
- DATA_MODEL defines owner, active-share, or household open-book visibility with `always_private` override; raw transactions are never visible to other users. It describes `detection_feedback` but the current Prisma model does not define it.
- Current Prisma `Subscription` fields do not yet fully match DATA_MODEL; `SubscriptionCharge` is present in one migration but absent from Prisma. Two different migration directories with numeric prefix `0002` define overlapping subscription objects. BUG-008 is BLOCKED and is a hard prerequisite for schema or migration work.
- SEC-FU1 in BUG-009 blocks registering auth/session-protected routes until trusted authenticated-principal binding and RLS request-context enforcement pass separate review. `AppModule` currently does not register AuthModule or SessionsModule.

## Acceptance criteria

- AC1: OpenAPI 3.1 is updated first for only the approved subscription list/detail, review inbox, review action, and lifecycle fields; generated TypeScript/Zod artifacts and contract tests are regenerated and pass. Preserve existing endpoint paths and use RFC 9457 stable problem codes. All mutating POSTs require `Idempotency-Key`.
- AC2: Every route obtains identity only from the authenticated principal established by the reviewed guard/session integration. It ignores/rejects caller identity supplied by headers or body. The module is not registered until SEC-FU1 is complete. Reads and writes use a transaction-scoped RLS context matching the reconciled migration setting, with RLS enabled in PostgreSQL integration tests.
- AC3: The subscription list and detail obey the single DATA_MODEL visibility policy (owner OR active explicit share OR active household membership plus open_book and not always_private). Review inbox and review mutation access are owner-only for the transaction/detection owner. A non-owner never receives raw transaction data, account identifiers, or a private detection through household visibility.
- AC4: Review inbox is cursor-paginated and only includes actionable `DETECTED` records owned by the trusted caller. It returns only the approved safe card fields: subscription/merchant display identity, amount as a decimal string of integer minor units, ISO currency, cadence, confidence/reason codes, category, and catalog plan suggestion. It does not return raw transaction description or account data.
- AC5: Confirm/reject/update operations validate current status and apply only architecture-approved transitions atomically. The baseline explicit actions are `DETECTED → ACTIVE` on confirm and `DETECTED → REJECTED` on Not a subscription. Preserve immutable transition/feedback evidence as approved; repeated/conflicting transitions return the stable problem response rather than silently applying another action.
- AC6: Lifecycle behavior supports the approved transitions for TRIAL, ACTIVE, PAUSED, CANCELLED, ARCHIVED, and REJECTED. Cancellation by missed charge is not inferred from request-time state alone: implement a worker/trigger only if separately approved with a due-date definition and integration tests; the current API task must support the user-confirmed cancellation path from the reviewed state machine.
- AC7: Review actions and edits store only the minimal approved feedback label and identifiers needed for model training. No raw descriptors, prompts, or transaction narrative is copied into feedback. Feedback labels, visibility, retention, correction, and deletion behavior are defined by architecture/security review before storage is implemented.
- AC8: UF-06's 10-second undo is demonstrable with an explicit reviewed API contract. An undo after expiry or by a non-owner is rejected. No undo path may erase audit/security evidence. If the review decides this requires a follow-up contract, this AC moves to that task and ST-081 may not claim full UF-06 completion.
- AC9: Amounts remain integer minor units/BigInt in storage and arithmetic. JSON never serializes a JS `bigint` or converts money to floating point; the approved wire representation is a base-10 integer string and generated OpenAPI/client schemas enforce that. Include large-value round-trip coverage beyond `Number.MAX_SAFE_INTEGER`.
- AC10: Tests cover owner vs peer/household visibility (open_book on/off, explicit share, always_private), RLS principal setting, owner-only detection review, all approved state transitions and rejected transitions, feedback persistence/minimization, merge semantics, undo at 10 seconds/expiry, missing/invalid idempotency key, same-key replay, conflicting-key payload, concurrent repeat, pagination, and BigInt serialization. At least the RLS/ownership assertions run against disposable PostgreSQL with the reconciled migrations.
- AC11: API lint, strict typecheck, unit tests, generated contract checks, and disposable-DB integration tests pass. No live bank, ML/LLM, external service, or real user data is used.

## Review questions (must be resolved before READY)

1. API_CONTRACT/USER_FLOWS require 10-second undo, but API_CONTRACT defines no undo operation. Should a dedicated undo endpoint be added, and what persisted receipt/expiry semantics should it use?
2. API_CONTRACT says `mergeWith?` but does not identify source/target ownership or post-merge lifecycle. Is `:id` the surviving subscription and `mergeWith` the source, or the reverse? Should source rows be archived, and how are any charge/feedback relations consolidated without deleting evidence?
3. TRIAL, ARCHIVED, and REJECTED are statuses but their allowed incoming/outgoing transitions are unspecified. Confirm a transition table, including whether `TRIAL → ACTIVE` and which statuses may be archived/restored.
4. F5.5 says cancellation after >1.5× a missed cadence and user confirmation, but the model/source for expected due dates and charge history is incomplete. Is scheduled missed-charge evaluation a separate task? Define cadence windows and manual confirmation behavior.
5. DATA_MODEL names `detection_feedback.label` but not label enum, ownership/visibility, or retention. Approve the minimal values and whether the table should be user-owner-only and deletable/correctable by that user.
6. API_CONTRACT requires idempotency keys but specifies no storage/replay rules or existing middleware/table. Confirm same-key/same-payload replay and same-key/different-payload conflict semantics and where the key record lives.
7. BigInt has no JSON-native representation. Confirm decimal integer strings for minor-unit fields as the public wire contract, including generated Zod validation.
8. Request transaction helper sets `app.user_id`, while checked-in historical subscription migrations use `app.current_user_id`; BUG-008 must identify the authoritative setting before API implementation. Confirm visibility query and mutation RLS parity after reconciliation.
