## Goal

Expose the real registered `POST /v2/auth/browser-nonce` route behind an explicit development-only enable flag. Use the existing nonce and reservation cores with one narrow `browser-bootstrap-origin` request-coordination scope. Do not represent the scope as user identity, browser-chain authority, authentication, or authorization.

## Existing interfaces and narrow changes

- `BrowserNonceGuard` in `apps/api/src/auth/browser-nonce/browser-nonce.ts` has `issue(purpose, evidence, previousCookieSecret?)` and returns `{ nonce, cookieSecret, expiresAt }`. It validates purpose, allowlisted canonical origin and TLS/development evidence; `InMemoryBrowserNonceStore.bootstrap(record, previousCookieHash, now)` invalidates the old cookie chain when the corresponding secret is supplied. Reject an observed binding cookie unless it matches the existing 43-character base64url secret grammar before calling `issue`, so malformed evidence cannot cause fresh secret generation or chain mutation.
- `IdempotencyReservationRepository` exposes synchronous `reserve(input): IdempotencyOwner` and `settle(input, ownerHandle, outcome)`. `InMemoryIdempotencyGuard` requires a 32-byte key, a TTL from 1ms through 24h, and currently admits only `browser-chain`/`verified-principal`. Add the explicit `browser-bootstrap-origin` kind, constrained at runtime and in types to `createV2BrowserNonce` + `web`; preserve existing kinds and operation behavior. The adapter may create its branded authority input only after ST175 evidence and exact configured-origin validation, deriving the digest via a dedicated-domain HMAC of the canonical origin with a separate server key. Never construct it from raw/untrusted Origin, IP, forwarded headers, request body, or cookie data.
- `extractV2BrowserEvidence` in `apps/api/src/auth/http/v2-browser-context.ts` already supplies canonical allowed Origin, direct-socket TLS/development evidence and at most one observed binding cookie. Treat these as transport observations, not identity. Keep ST175 changes intact.
- `config.ts` currently has broad `AUTH_V2_ENABLED`, origin/cookie settings and loopback policy. Add a separate `AUTH_V2_BROWSER_NONCE_ENABLED` flag, default false. `true` must require `NODE_ENV=development`, `AUTH_V2_ENABLED=true`, and all required configuration; reject it in `test` and `production`. Validate two distinct key fields (idempotency storage key and bootstrap-origin HMAC key), each as exactly 64 hexadecimal characters / 32 decoded bytes. Require presence and shape only; never check in or emit usable values. Document placeholder key names and 64-hex shape in `.env.example` without supplying real material. Preserve no-echo config errors.
- `AppModule` currently does not register `AuthModule`; avoid importing that broad module. Register a small browser-nonce module only when the validated route flag is true, passing explicit validated config. If this needs `main.ts` changes, coordinate them after ST175 acceptance. When disabled, the route must not be registered (404) and default startup must remain compatible.

## Acceptance criteria

1. **Opt-in boundary:** route flag defaults false; route is registered only for explicit `development` enablement. `validateConfig` rejects enablement in `NODE_ENV=test` and `production`, missing keys, malformed key lengths/hex, same key for both domains, missing origins/cookie configuration, and HTTP origins outside explicit loopback development. Disabled defaults require no new keys.
2. **Request evidence:** require exactly one canonical configured Origin and the direct TLS or explicit local loopback evidence from ST175. Reject null/lookalike/malformed/duplicate Origin, malformed/duplicate recognized binding-cookie evidence, and unsupported purpose. Do not trust forwarded headers. If a single binding cookie is present, validate its exact secret grammar before reservation or nonce issuance.
3. **Reservation scope:** the new scope kind is valid only for `createV2BrowserNonce` on web. Digest the canonical configured Origin with the separate bootstrap HMAC key and domain separation. Bind operation, transport, purpose, canonical origin/scope, and a canonical request digest. Reject malformed idempotency keys using existing guard grammar. No client IP or claimed user identity is used for reservation or throttle keys.
4. **Ordering and no replay:** enforce throttles before issuance; reserve the opaque idempotency key before `BrowserNonceGuard.issue`. On successful issue, settle `completed` successfully before writing any response body or cookie. If issue or settlement fails, return a generic safe failure, do not send nonce/cookie secrets, and settle as `failed` best-effort when still pending. Duplicate pending/completed/failed key returns generic `409 AUTH_RESTART_REQUIRED`, never replays either secret or bypasses throttles. A new key plus the currently presented valid cookie invalidates its prior chain; without a cookie, issue a fresh chain but make no claim to invalidate an unpresented chain.
5. **Bounded throttling:** maintain bounded process-local fixed-window counts for both canonical allowed origin and one global bucket. Enforce both. Define/test limits, window expiry, capacity behavior, and generic response. No IP/user rate-identity claim. State resets on process restart; document this limitation. Do not retain raw keys, cookies, nonce, or other secret material in diagnostics.
6. **Wire behavior:** valid route returns only the contracted public nonce JSON, sets a distinct host-only `Secure; HttpOnly; SameSite=Lax` binding cookie with configured `Path` and no `Domain`, and inherits `Cache-Control: no-store` and `Pragma: no-cache` on success and error. Do not log Origin values, idempotency keys, cookie values, nonce, or response secrets.
7. **Tests/review:** config specs prove disabled, dev-enabled and test/prod-rejected cases without usable key material. Core specs prove scope-kind/operation constraints and no replay. Actual HTTP integration against the conditionally registered controller covers success, invalid Origin/TLS/cookie/purpose, duplicate idempotency key with no secret replay, fresh-key prior-cookie invalidation, throttle behavior, cache headers on errors, and disabled route absence. Obtain independent actual-source architect-platform and security-privacy review plus scoped checks and exact-head CI before merge.

## Explicit limits and follow-on gates

This development reference uses process-local nonce, idempotency and throttle state; process restart loses reservations and nonce chains, and throttling is per allowed origin plus global only. Origin is a browser partition signal after validation, not authenticated identity and forgeable by non-browser callers. The task does not establish distributed abuse resistance or production no-replay durability.

Production remains disabled pending confirmed deployment origins, cookie name/path/host, TLS termination and exact trusted proxy hops; approved production key delivery; database inventory; durable atomic reservation/nonce/throttle storage review; and separate security/privacy sign-off. Provider verification and session issuance remain separate gates. ST174 remains deferred. Do not record concrete deployment values until confirmed.
