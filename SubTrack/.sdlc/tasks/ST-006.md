## Acceptance criteria
- AC1: Given the package is installed in the ST-003 workspace, when its documented generation command runs twice without source changes, then it produces the same TypeScript fetch client with no uncommitted generated diff on the second run. ## Architect Type-2a decision (2026-09-27; accepted for ST-006)

- **Decision:** Use Orval **8.38.0** as the single pinned OpenAPI 3.1 code generator, with two outputs from the same local `openapi.yaml`: a native `fetch` TypeScript client and Zod 4 schemas. Pin `zod` **4.6.5** as the generated schema runtime and `@redocly/cli` **2.54.3** for OpenAPI validation; use exact versions plus the frozen pnpm lockfile. All three npm packages report permissive MIT licenses. Orval requires Node **>=22.18.0**; use that runtime for generation/CI and document the requirement. Do not silently rely on the workspace root's weaker `node >=20` declaration.
- **Developer configuration/commands:** Put `orval.config.ts` and generated files within `packages/contracts/`. Configure two named outputs against `./openapi.yaml`: `client: 'fetch'`, `mode: 'single'`, `target: './generated/client.ts'`; and `client: 'zod'`, `mode: 'single'`, `target: './generated/schemas.ts'`, `override.zod.version: 4`. Use package scripts `generate: orval --config ./orval.config.ts` and `contract:validate: redocly lint openapi.yaml --extends=spec`. Run through `pnpm --filter @subtrack/contracts generate` / `contract:validate` from the workspace root. Keep generation offline/local, output paths stable, no timestamps or remote inputs, and verify a second run leaves no tracked generated diff. Add a malformed-OpenAPI negative check. If an empty-operations skeleton yields no meaningful Zod output, do not fabricate a domain schema merely to force one; use the approved ops operations or report the generator limitation.
- **Ops scope:** `API_CONTRACT.md` explicitly names only `GET /healthz`, `GET /readyz`, and `GET /v1/version` in its Ops section. These three paths/methods are approved for the ST-006 foundation skeleton, **not required** to be implemented by ST-006. No auth, domain, ML, request body, or provider endpoint is approved for this skeleton. The accepted API contract specifies no ops response payload/status semantics, so do not assert a version shape, readiness algorithm, status code, or server behavior without a separate accepted contract; a minimal OpenAPI response description with no content schema is permissible. `openapi.yaml` remains the source of truth.
- **Options considered:** Orval fetch + Zod (chosen: one maintained generator and no Axios runtime; requires Node 22.18+); `openapi-zod-client` (rejected: Axios/Zodios runtime and no verified full OpenAPI 3.1 support); raw YAML/validation only (rejected: cannot satisfy AC1). Verification is AC1–AC3, including generated-client/schema imports, repeat-generation diff, positive/negative lint, and an exact-paths assertion.
- **Scope dependency for Conductor:** Installing these packages will update `SubTrack/pnpm-lock.yaml`, outside the current `allowed_paths`. Before re-dispatching implementation, add that lockfile path to ST-006 scope (and any root/CI Node-baseline file if a change there is required); the architect did not edit outside the current scope. No generator dependencies or feature code are installed in this decision handoff.
