## Goal
Establish a verified, reviewable migration history and a non-destructive reconciliation plan for the duplicate subscription definitions in the Prisma migration directory before any migration is changed or applied.

## Context (read before starting)
- Repository evidence: both `0002_banking_catalogue_subscription` and `0002_subscription_visibility` share the `0002` prefix and define overlapping subscription objects. The former creates `subscription_status`, `subscription`, and `subscription_charge`; the latter creates `subscription_cadence`, `subscription_status`, `subscription`, and `subscription_share` with RLS policies.
- The canonical Prisma schema defines subscription enums/tables and maps `subscription_share`.
- Current onboarding diagnostics include Prisma engine download failures. Those errors do not establish which migrations have been applied to any database.
- This task is a future migration-history investigation. It is BLOCKED until a read-only inventory of each relevant database's `_prisma_migrations` state is available and architect-platform/security-privacy agree on the target schema.

## Acceptance criteria
- AC1: Produce a read-only evidence record in this task's Progress/Handoff identifying the duplicate names, overlapping SQL objects, canonical Prisma models/enums, and the ordering conflict. Include file/statement references without copying sensitive database contents.
- AC2: Verify migration application state using read-only queries for each relevant local/dev/test/staging database before proposing changes. If access or state is unknown, remain BLOCKED and list exactly what is missing; do not infer that a migration is unapplied.
- AC3: Architect-platform and security-privacy review and approve the reconciliation plan before any SQL or schema change. If the plan could delete/alter data or change access policy, stop and escalate under DECISION_RULES; no destructive action is authorized by this contract.
- AC4: Any eventual reconciliation must preserve existing data and RLS behavior, must not edit an already-applied migration, must not reset databases, and must not use `DROP`, destructive table/type replacement, or force migration commands. Prefer an explicitly reviewed forward-only migration if evidence requires a schema change.
- AC5: Validate the final migration sequence and Prisma schema against a disposable test database or equivalent clean migration environment, with before/after schema and RLS parity evidence.
- AC6: No migration file is changed or applied until the evidence and review gates in AC2–AC4 pass. If safe reconciliation cannot be established, return BLOCKED with the conflict rather than attempting a repair.

## Out of scope
- Applying migrations to production/staging or any database with user data.
- Deleting, renumbering, rewriting, squashing, or force-applying migration history.
- Schema feature changes beyond aligning the two existing subscription definitions to the reviewed canonical schema.
- Workarounds for unavailable Prisma binaries/network access.

## Technical notes
- Duplicate numeric prefixes alone are not sufficient evidence of database state; inspect the migration table and repository history.
- Preserve RLS policies and subscription visibility invariants from DATA_MODEL.md and ST-048.
- This status remains BLOCKED until the preconditions are met. Do not set READY solely because a disposable database can be created.

## Test plan
- Inventory only through read-only migration-history queries for existing databases.
- On a disposable database, run the full Prisma migration sequence from an empty state and compare resulting schema/policies against `schema.prisma` and policy parity tests.
- Include the exact reviewed plan, read-only evidence summary, disposable validation commands, and any remaining blockers in the HANDOFF/v1 block.
