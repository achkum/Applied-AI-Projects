## Goal
Internal executable restricted OTP producer with atomic in-memory dev/test reference. Verify server-owned challenge before restricted proof issuance. Parent remains incomplete pending trusted BankID, durable storage, transport and HTTP/client integration.
## Acceptance criteria
- Challenge provisioning is internal trusted-server boundary, explicit server metadata purpose enroll_identifier or otp_step_up, pre-normalized identifier hash, channel sms/email and verified transport bindings. Generate unpredictable challenge IDs and six-digit codes; no rawidentifier storage. No caller-supplied purpose/identity/principal/verifiedresult on verification.
- Use mandatory >=32-byte keyed HMAC with domain and challenge binding; constant-time digest compare. Repository atomically compares context, expiry, attempt bound (five), code and consumes; successful race one winner. Clone/freeze metadata, no rawcode persisted, key not logged or devdefault. TTL bounded and injectable clock; invalid/expired/replayed/missing/wrongcontext generic failure, wrongcode correct-context attempts lock at five. Invalidcontext must not burn another challenge.
- Producer derives purpose enrollment/stepup and fullbinding from atomically consumed immutable server record, issues via existing ProofStore. OTP never issues login/account-delete proof or identity/session fields. Repo/proof errors generic; issuancefailure consumes challenge and requires restart.
- Meaningful boundary/concurrency/purpose/context/expiry/attempt/tamper/replay/error/no-rawsecret tests, >=80 changedTS coverage, lint/TS and independent platform/security approval with exact-head CI beforemerge.
- No v1 edits, delivery/HTTP/controller/module wiring, database/schema/migration/dependency/provider changes or productionready claim. In-memory reference is dev/test only.
