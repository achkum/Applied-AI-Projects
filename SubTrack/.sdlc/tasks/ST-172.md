# Proposed follow-on: gated, read-only mobile demo household

## Architecture decision

Proceed with mobile UI implementation using the accepted public `@subtrack/money` `formatMinorUnits(bigint, currencyCode, options)` API, guarded by a runtime capability probe. The probe must run on the executing JS runtime before any demo amount is formatted or rendered. A failed, throwing, malformed, or unsupported probe produces a localized unavailable state with no amount; there is no float or legacy-number fallback.

This is a defense-in-depth gate and permits development of the route while Hermes QA is outstanding. It does **not** revise ST-171's explicit requirement that Expo/Hermes support be separately validated before mobile adoption. Native-device/simulator execution of the probe plus rendered screen remains required before merge/adoption of the mobile caller. Node, component tests, Expo Web, and Metro bundle success do not satisfy this requirement. If the native gate fails on a supported target, the amount stays hidden there and the feature is blocked pending a new exact-formatting architecture decision; do not weaken the gate or silently substitute output.

The runtime probe should be a small pure, unit-testable capability function called at demo-screen entry. Verify BigInt exists, the target locale's `Intl.NumberFormat` accepts BigInt in `formatToParts`, and the public `formatMinorUnits` operation handles a SEK value above `Number.MAX_SAFE_INTEGER`, a negative subunit, and the supported demo locale (`sv`/`en`) without throwing or losing/reordering integer/fraction information. Also exercise 0-, 2-, and 3-digit currency exponents (JPY, SEK, KWD) in focused non-device tests. Probe output is internal and never shown as a demo amount; don't log it. Any mismatch returns unsupported. The gate is not a backend authorization or tenant-isolation check.
