## Goal
Deliver subscription visibility policy and RLS parity in scope of SubTrack PRODUCT_SPEC, with privacy and security invariants enforced.
## Context
- PRODUCT_SPEC §F3; DATA_MODEL.md Visibility rule; ADR-0002, ADR-0003
- Review substitution: architect-data independently reviews architecture because architect-platform owns this task; security-privacy and conductor also review.
## Acceptance criteria
- AC1: Given random owners, household membership, shares, open_book and always_private states, when policy evaluates a subscription, then access is granted iff owner OR active explicit share OR active household membership with open_book=true and always_private=false.
- AC2: Given raw transaction, balance, non-subscription transaction or full account number, when any other member requests it, then deny access regardless of sharing.
- AC3: Given generated policy cases, when equivalent queries execute through PostgreSQL RLS, then RLS decisions match policy for every case.

## HANDOFF/v1
- **Location**: `packages/domain/policy/` — imports via `@subtrack/domain/policy`
- **Exported functions**: `canViewSubscription(viewerId, ctx)`, `canViewBankingData(viewerId, ownerId)`, `canReadAuditLog(viewerId, householdId, memberships)`
- **canViewSubscription rules** (evaluated in order):
  1. GRANT if `viewerId === ctx.ownerId`
  2. GRANT if active explicit share exists (`ctx.shares`)
  3. GRANT if shared active household + owner open_book=true + `alwaysPrivate=false`
  4. DENY otherwise
- **canViewBankingData**: always DENY for non-owner (ASSUMPTIONS.md §A2)
- **canReadAuditLog**: GRANT only to active ADMIN members of the household
- **AC3 parity**: `test/visibility.spec.ts` includes a `sqlEquivalentCanView` mirror function that replicates the expected SQL RLS USING clause — all 11 cases assert `canViewSubscription === sqlEquivalentCanView`
- **ST-102 note**: explicit shares (`SubscriptionShare`) are included in the type model but not produced until ST-102; policy already handles them correctly
