## Authorized outcome and measured bottleneck

Deliver signed Android feature updates without rebuilding/transferring unchanged signing tools or resetting keys, backend or tester data. Existing first-publication tooling couples APK/tools source heads, always requires a fresh tools stage, mixes current execution and retained import authority, rejects an existing public file, and derives old publication from mutable latest signing history. These are measured blockers to version3, not user permission blockers.

Current live version2 stays available until a reviewed, verified successor is atomically activated. The immutable ST251 feature source is commit 55e2ffbc302bfe537066d18b31e6ca3241fdfdde. Actual successor APK source must be an exact reviewed integration descendant on the existing delivery branch; record it before build. Keep existing workflow/build/draft branch guards unchanged. Existing tools artifact source is 1655c14f4ae25ce5e8d6f5c38b1033589532aebe/run38647750948-1; imported tooling authority cef1143a8dd6452e419d6c7b9d97586dbf02e307; current execution source may change independently with exact helper hashes. Existing certificate, identity and backup remain required and unchanged. No private key access, initialization, backend/DB recreation, account, spending, production/store release or real integration delivery.

## Frozen ownership and implementation contracts

Signer/desktop author owns sign-android.sh, download-android.ps1 and android-transfer-receipt.mjs/test only. Gateway author owns image-import-binding.cjs and activation-contract.test.cjs only. Conductor owns task/evidence/backlog, integration, actual operations and sole CI observation. One consolidated independent platform/security review covers the stable slice.

Separate APK SourceHead from explicit retained ToolsSourceHead; separately bind current SignerExecutionHead and retained SigningToolingHead. Reuse tools only after exact retained manifest/receipt/archive/import/image/tool-version verification and equal raw pinned signing Dockerfile digest at old tools and new APK source. Do not relabel imports/history or silently accept arbitrary mixed heads. A dedicated StageApk/reuse-tools lane copies only fresh APK/custody files, verifies retained tools and refuses foreign stages. Existing first-build lane remains strict.

Before successor signing, retain the genuine version2 signed-history bytes in its owned hosting-run directory. A qualified hosted run reads its immutable exact history snapshot; latest signer history remains monotonic and is never reset. Successor signing retains a new immutable run history as well. Maintain exact tuple checks against receipt, APK manifest, cert and run identity.

Dedicated successor qualification validates current predecessor ledger/index/public file and approved candidate receipt/source/tool reuse evidence. Retain exact predecessor metadata and bytes exclusively. Publish a fresh verified 0444 candidate with guarded atomic replacement of the fixed file; existing gateway file bind keeps its old inode until gateway-only activation. Promote qualified metadata with retained provenance. Root activates only gateway-live and qualifies trusted HTTPS bytes/page plus resumed backend readback and unchanged API/DB IDs. Rollback restores retained predecessor publication/metadata and gateway configuration without resetting latest signer history or backend. Foreign/stale predecessor, substituted toolchain, partial/malformed evidence, version downgrade and mismatched cert fail closed. No blanket overwrite or deletion of publication history.

## Validation and acceptance

Focused meaningful tests must cover retained tools with distinct APK source, unchanged strict first-build path, wrong source/tool bytes/import/execution authority, monotonic version/history and original certificate; successor activation with exact retained predecessor, stale/foreign or absent predecessor, immutable snapshots, atomic old-inode serving, failed promotion and rollback. Prefer executed source-block/Linux filesystem tests over text-only assertions for mutation behavior.

Do not repeat ST251 UI/Money tests. Do not rebuild signing tools. Source checks and independent review do not establish actual signed/hosted/installed acceptance. Root operations remain gated on final review and applicable checks. Actual Android installation and iOS signing/installed acceptance remain pending ST250. Record compact checkpoints and exact source/receipt hashes.
