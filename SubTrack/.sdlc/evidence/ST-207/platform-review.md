1. **Make core purpose enforcement representable.** `IdempotencyReservationInput` currently has operation/transport/authority/request digest/key but no purpose. The guard cannot inspect purpose inside either opaque digest. Specify a future internal discriminated input branch carrying exactly `enroll_identifier` for `anonymous-enrollment-otp`, with runtime validation and binding of that discriminator on reserve and settle. Restrict this branch to startV2Otp/verifyV2Otp + mobile, preserving existing branches. An HMAC domain alone cannot prove that its producer enforced the purpose. This adds no wire field; verify derives it from trusted metadata.

2. **Name the metadata boundary and coherence requirement.** `OtpChallengeRepository` exposes insert and verifyAndConsume only; no bounded metadata lookup exists. The existing web code sink stores code/purpose/origin/chain/expiry and cannot supply identifierHash/channel for the proposed verify HMAC. Explicitly identify the required future repository/adapter port or separate bounded metadata store and its ownership. Require immutable challengeId/purpose/transport/identifierHash/channel/issuedAt/expiresAt metadata to agree with the record atomically consumed by the producer before a proof can be disclosed. State whether a future implementation must extend the producer/repository boundary or provide an equivalent reviewed coherence mechanism; do not imply current ports already provide this guarantee. Lookup must not expose code material or establish principal authority; missing, expired, consumed or incoherent metadata fails generically.

3. **Specify binding key isolation and lifecycle.** The proposal says server HMAC without choosing a namespace/key boundary. Require a mandatory dedicated >=256-bit anonymous binding key, distinct as decoded bytes from idempotency, OTP-code, rate, browser and credential keys; copied/frozen configuration, no fallback or caller-provided key. State that one captured binding/input is used through settlement, and key/store lifetime/rotation must preserve retained global key burns and cannot revive consumed challenges. Process-local development restart limitations should be explicit; no distributed or durable one-use claim follows from this proposal. Configuration names and wiring can remain future implementation details.

4. **Specify failure cleanup independently of settlement.** Current producer provision inserts a challenge before returning code; verify consumes before proof issue. Define allowed bounded orphans on metadata insertion, producer/proof issue, completed settlement, sink publication and response failure. A sink publish that fails after partial mutation must not leave code available; metadata/code are invalidated or removed on terminal consumption/fault while challenges/proofs are never revived. Completed settlement must stay completed if publication fails; a subsequent failed-settle attempt cannot undo it. Preserve proof confidentiality and generic response even when cleanup fails, with bounded expiry as the fallback. These are protocol invariants, not a request to implement cleanup now.

The TLS and graph direction is appropriately narrow: direct encrypted socket, no forwarded HTTPS trust, explicit development opt-in absent from default/production, standalone module first, separately reviewed web/mobile discrimination. Finding 3 is resolved with a dedicated copied >=256-bit key distinct as decoded bytes from other security keys, separate framed domains, no live rotation, whole process-local state replacement on restart, fresh client challenge and separate durable/rotation review. Global burns are therefore bounded to retained state within that process lifetime; restart clears them and no durable/distributed one-use guarantee is inferred.

The stated atomicity/terminal lifecycle and fail-closed disclosure invariants establish the proposal direction; fault/concurrency tests must demonstrate them later.
