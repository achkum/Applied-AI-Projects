## Evidence and assessment

Read AGENTS.md, ST-207/ST-177 task contracts, Constitution, DECISION_RULES, ADR-0010/0019/0020, API_CONTRACT.md, accepted OpenAPI mobile OTP envelopes/responses, ST-177 security evidence, idempotency-guard.ts, otp-proof-producer.ts, proof-store.ts, otp-http.ts and mobile-deletion-otp-authority.ts. No network, runtime edits, tests, dependency jobs, deployment, or provider calls were performed.

- Anonymous reservation binding is expressly server request isolation, not a verified principal. Identifier, IP, key and challenge possession acquire no account/session authority. Existing deletion authority requires verified credential/current session/registered contact and cannot substitute for anonymous enrollment.
- A distinct anonymous digest brand and discriminated input with literal enrollment purpose require both type narrowing and core runtime validation of kind/operation/mobile transport/purpose. Existing browser/principal inputs and binding bytes are preserved. Merely enlarging AuthorityKind or asserting TrustedAuthorityDigest is explicitly insufficient.
- Dedicated copied minimum-256-bit server HMAC key is separated as decoded bytes from OTP/rates/core/origin/credentials. Start and verify have separately framed domains and all operation/transport/purpose/identifier/channel fields; verify additionally binds challengeId from trusted metadata. Keys are process-local with whole-state restart, no implicit durable/live-rotation design. Stored reservation bindings/key indexes remain keyed digests; full strict request hashing includes verify code without retaining it.
- Existing core global key uniqueness and owner settlement remain within the process and retention period; restart clears burns without claiming durable one-use. One captured immutable input is used through settlement, with mandatory configuration and no fallback. Pending/completed/failed duplicates disclose no challenge, code or proof. Synchronous reserve precedes producer mutation; successful settlement precedes publication/disclosure and stays completed on later publication/response failure. Uncertain responses need fresh challenge/random key, and consumed state is never revived.
- Metadata is an immutable internal enrollment/mobile tuple with five-minute validity and terminal lifecycle, maintained from producer issuance rather than client input or web sink authority. Bounded publication capacity and synchronous atomic metadata/sink visibility prevent partial publication. Post-await validity/coherence, producer atomic consume, success cleanup even on failed settlement, and undisclosed bounded orphans are mandatory future fault/concurrency gates. Existing repository exposes no metadata read; review makes no claim that this adapter already exists.
- Enrollment proof remains challenge/identifier/purpose/mobile bound. Producer maps enrollment only to restricted enrollment proof; proof-store login/account-delete purpose and identity/session requirements remain distinct. OTP cannot establish login, choose/create identity, authorize deletion, or replace BankID. Anonymous mobile step-up remains rejected.
- Exact accepted mobile bodies/headers and success fields, including nextBrowserNonce:null, are preserved. Mixed browser/credential headers, ambiguous framing and proxy TLS spoofing are rejected. Direct socket TLS, development-only standalone registration, disabled/default/production absence and separately reviewed combined middleware prevent a no-Origin browser bypass.
- Existing ST-177 limits are the intended baseline: 10 starts/direct-IP/minute, 5 starts/HMAC-identifier/15 minutes and 60 combined starts/verifies/direct-IP/minute, with 10,000 active buckets. Reservations retain at most 10,000 records/24 hours; challenges/proofs/sink/metadata must be bounded and pruned. Five attempts remain producer-controlled. Clock regression/capacity/expiry behavior must be proven in the future adapter, not inferred from current code. Process-local state does not claim distributed abuse resistance.
- Test-only code sink, no public retrieval/delivery/logging, no-store generic errors, mandatory negative HTTPS/concurrency/fault/proof-purpose tests, contract follow-up, native/device/provider inventory and release gates remain open implementation obligations.

## Initial findings and resolution

The initial draft omitted explicit dedicated copied key separation and an enforceable internal purpose discriminator despite enrollment-only prose. It also left exact nullable mobile response fields implicit. Reviewer requested these concrete requirements; revised ADR adds them, separates anonymous wording/brand, and expressly acknowledges current core/producer limitations. These proposal-readiness findings are resolved at the hash above; they are not claims of implemented fixes.

The revised ADR additionally names metadata lifecycle/publication/cleanup and requires a narrow API_CONTRACT follow-up only after explicit adoption. Accepted ADR-0010/current contract remain authoritative while this ADR is Proposed. No unresolved proposal-readiness blocker was identified in the revised bounded model.

Final clarifications were re-read and included in the hash-bound review: cleanup failures suppress disclosure and render records unusable; an extended producer/repository boundary or equivalent independently reviewed mechanism must prove the metadata tuple agrees with the consumed challenge. Copying client fields alone is insufficient.

Founder option A adopts only this model and permits a separately reviewed development-only implementation task. Option B retains the block and accepted authority model. Recommend A within these exact bounds; runtime/source approval requires independent review of the later implementation and its actual evidence.
