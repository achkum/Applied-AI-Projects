## Required changes before plan approval

1. **Preserve the owner's ability to revoke a share after leaving a household.** The plan currently requires active owner membership for `INSERT/UPDATE/revoke`. An existing active share may continue exposing the subscription to remaining active household members under the accepted SELECT rule even after its owner leaves. The owner must be able to revoke that grant regardless of current household membership, or membership departure must atomically revoke/disable it. Grant creation may require active owner membership as a conservative assumption, recorded explicitly because DATA_MODEL's SELECT rule does not require it. Restrict share UPDATE to permitted revocation fields and make `subscription_id`, `household_id`, `shared_by` and other authority fields immutable at the database boundary. RLS `USING`/`WITH CHECK` alone cannot compare old and new field values; specify column grants, a trigger, or another DB-enforced mechanism. Test leave-then-revoke and attempted retargeting.
2. **Specify the privileged lookup boundary.** The proposed `SECURITY DEFINER` helper needs owner-private consent and membership reads while the caller's RLS would hide or recurse on those rows. Ordinary SELECT grants to a distinct non-owner do not bypass RLS. The plan must name the bounded mechanism (for example, narrowly owned tables/functions or a dedicated non-login role with only the required bypass capability), identify who owns the function and referenced tables, and state which RLS policies are bypassed for lookup. Keep the application role non-owner and without `BYPASSRLS`; revoke default `PUBLIC` EXECUTE; use schema-qualified objects and a fixed trusted `search_path` with no writable schema; expose only Boolean decisions; accept no caller-selected principal. Independently review the exact function SQL, grants and policy dependency graph before implementation. Verify the function fails closed with unset/malformed principal and cannot be invoked to enumerate consent or membership.

## Gates for the amended implementation

- Create every referenced table before installing its policy. Current `0001` references `household_member` before creation; current subscription policy references `subscription_share` before creation. The `household_member` policy self-queries, and subscription/share policies query each other. Compile and exercise the repaired policies through PostgreSQL, including household and invitation paths.
- Use explicit command-specific `SELECT`, `INSERT`, `UPDATE` and `DELETE` policies with owner and target-row checks. Current `invitation_access` is a permissive all-command policy; adding the `0004` policies combines access by OR and can undercut intended invitation mutation limits. Test unauthorized mutations, forged cross-owner foreign keys, owner ID changes, share retargeting, and subscription/charge/transaction isolation.
- Preserve BUG-013's same-principal transaction-local `app.user_id` and `app.current_user_id` binding and require an authenticated HTTP principal before any protected operation. The custom setting is not authentication on its own. Prove missing context, rollback and pooled connection reuse fail closed.
- Compare the full clean-installed schema, enums, constraints, grants, RLS policies and Prisma mappings against an independent target checklist. Execute ST-048 parity cases on disposable PostgreSQL 16 with separate migration and runtime roles, verifying runtime `rolsuper=false`, `rolbypassrls=false` and non-ownership or equivalent `FORCE ROW LEVEL SECURITY`. Current TypeScript SQL-equivalent tests are not PostgreSQL RLS evidence. No persistent-database, reset, `DROP`, force or deployment operation is approved here.

## Rereview of security corrections — plan-only approval

The 2026-10-10 `Security review corrections` subsection in the reconciliation plan resolves both initial plan findings. It makes owner revocation possible after household departure, forbids share retargeting/revival and owner reassignment at the database boundary, and states that new grants require owner membership. Its later, specific revocation rule supersedes the earlier broad table-row wording that required membership for every share mutation. The implementation diff must make that precedence unambiguous.

The proposed dedicated `subtrack_visibility_lookup` role names a viable PostgreSQL RLS bypass boundary: `NOLOGIN`/`NOINHERIT`/`BYPASSRLS`, no application role membership or `SET ROLE`, exact column-level read grants, Boolean `SECURITY DEFINER` functions owned by that role but no table ownership, fixed trusted search path, schema-qualified relations, revoked `PUBLIC` EXECUTE and runtime-only function grant. A role's `BYPASSRLS` attribute is powerful; this approval depends on its lack of login, membership, schema creation, broad table grants and generic query functions. The actual SQL, role grants, function bodies and policy dependency graph require independent security review before acceptance. The application role remains non-owner, non-superuser and non-`BYPASSRLS`.
