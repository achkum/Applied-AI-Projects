# BUG-008 Phase A exact-schema platform/data review

2026-10-10 · independent architect-platform/data review · `REVIEW/v1`

**Verdict: APPROVE Phase A schema target for Phase B SQL authoring only.** No Phase A blocker found in the exact artifacts reviewed. This is approval of the Prisma shape and the independent expected-target checklist, not approval of migration SQL, a database state, RLS behavior, provider persistence, or BUG-008 completion.

Reviewed exact SHA-256 inputs: `apps/api/prisma/schema.prisma` `EE08405408AD04D5917263FEDE3FF09604EAFEFD40ED37DD1811669D92E20AEC`; `apps/api/prisma/reconciliation-target.json` `3FB7C637EE7EFBC7AFF6422428EEA6338550FE153F14B11CFD4605F0F8911FC4`. Both hashes were independently recomputed. Review also compared the schema diff and `phase-a-verification.md` with `DATA_MODEL.md`, amended BUG-008, accepted ADR-0016, `reconciliation-plan.md` including its security corrections, `security-plan-review.md`, ST-060/ST-067, and both conflicting `0002` migration sources. The founder's current inventory is recorded as **none** in `founder-inventory.md`; that statement is an attestation, not this reviewer's database query.

The schema restores the six absent models: bank connection, bank account, raw transaction, merchant, catalogue plan, and subscription charge. It retains banking, catalogue, transaction, and captured-charge capability from the old banking migration while keeping the existing identity, household, OTP, session, invitation, consent, audit, subscription and share shapes. The canonical seven-status subscription, six-cadence model, `catalogue_plan` physical table, `catalog_plan_id` link, merchant alias JSON, and old captured charge amount/currency/date have a coherent target mapping. The former `region`/`active` and subscription first/last-seen metadata have no identified current consumer in this bounded target; their omission is not a removal from an applied database.

Composite `(id, identity_id)` references constrain account→connection, transaction→account, subscription→paying account, and charge→subscription/transaction to one owner. Bank, transaction and charge details remain owner-only in the stated target. These FKs do not themselves make owner IDs immutable or implement RLS. The target correctly leaves that work to SQL and its database tests. Catalogue public read and restricted writer access likewise require grants; lack of RLS alone does not establish read-only access.

Money columns use Prisma `BigInt`/target `BIGINT` minor units and three-character currency. The provider enum is the canonical `TINK_SANDBOX|SYNTHETIC|TINK_LIVE`, with no invented `TINK`/`MOCK` alias. Nullable provider connection ID, booking instant, value date, original amount/currency, catalogue verification/source URL, and next charge date avoid manufacturing absent source facts. A required transaction event date plus explicit `PENDING|BOOKED` status can represent ST-067 pending ingestion; its numeric input still needs exact Money conversion before persistence. `OTHER` account type still requires an explicit upstream mapping. No provider storage is activated by this schema, and raw provider payload storage remains outside Phase A pending its access and purge boundary.

The checked `phase-a-verification.md` reports successful Prisma validate/generate, API typecheck, JSON parse and diff check. Those are syntax and type-compatibility evidence. This review did not rerun them or contact PostgreSQL. The JSON target records expected columns, enums, keys, FKs and SQL-only obligations independently of a generated SQL file; it is a future real PostgreSQL comparison oracle, not proof that the current migration chain creates those objects. In particular, there is no claim here of executable policy compilation, RLS parity, immutability, role grants, rollback, pooling isolation or least-privilege behavior.

**Mandatory gates for Phase B and later acceptance:** author SQL against these reviewed hashes or obtain a fresh exact review if either target changes; resolve linked charge capture agreement with its source transaction or approve an explicit independent write meaning before accepting charge writes; implement and review command-specific owner/visibility policies, immutable authority fields, active-share uniqueness, confidence and nullable-pair checks, catalogue grants, and the bounded visibility helper and role privileges in the security corrections. Preserve accepted BUG-013 binding of both principal settings to one verified request principal. Apply the full repaired chain only to a disposable PostgreSQL 16 database with separate migration and verified non-superuser, non-`BYPASSRLS` runtime roles. Compare actual objects, constraints, grants and policies with this fixture and run owner/cross-owner, household/share, pending, mutation, missing-context, rollback and pooled-reuse cases. Security/privacy must independently review exact SQL, function bodies and grants; QA must review the PostgreSQL evidence. If any existing database is discovered, stop the clean-install path and inventory its migration history before proceeding.
