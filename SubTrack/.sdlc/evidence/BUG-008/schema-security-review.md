Reviewed `apps/api/prisma/schema.prisma` (SHA-256 `EE08405408AD04D5917263FEDE3FF09604EAFEFD40ED37DD1811669D92E20AEC`), `apps/api/prisma/reconciliation-target.json` (SHA-256 `3FB7C637EE7EFBC7AFF6422428EEA6338550FE153F14B11CFD4605F0F8911FC4`), their Phase A diff/evidence, BUG-008 amendment, the corrected reconciliation plan and its prior security review, DATA_MODEL, ST-048, BUG-013, and ADR-0016. This was source review only. I did not edit SQL or schema, connect to a database, run migrations, or independently repeat the author's Prisma checks.

The schema uses physical `identity_id` ownership on bank connection, account, raw transaction, subscription, and charge. Its `(id, identity_id)` unique references and composite relations link account to connection, transaction to account, subscription paying account to account, and charge to both subscription and transaction under the same owner. Transaction provider IDs are unique per account and linked charge transaction IDs are unique when present. These are suitable relational keys for the planned database constraints. The charge has its own owner field and no household relation; subscription visibility does not automatically extend to charge or transaction detail. Subscription's existing seven statuses, six cadences, `always_private`, and share shape remain. The target fixture retains owner/open-book/share SELECT semantics and owner-only mutation, with explicit shares allowed to reveal an always-private subscription by owner action.

The banking models are schema definitions only. No provider route, credential ingestion, raw provider payload table, purge job, or retention workflow is activated. Nullable connection provider ID and booking instant avoid invented provider facts. The target has no global SE market default or fabricated confidence/charge date. The schema retains merchant aliases in JSON rather than silently losing the earlier seed path. These choices are consistent with the bounded plan; catalogue semantics and data mapping still need architect/data review.

**Required exact-SQL review and PostgreSQL gates before acceptance:**

- Enforce immutable `identity_id` on subscription, banking, transaction and charge rows. Composite foreign keys must actually be present in the installed database. Test forged cross-owner references and owner reassignment, including nullable paying-account and transaction links.
- Install command-specific owner-only SELECT/INSERT/UPDATE/DELETE for connection, account, transaction and charge, including correct UPDATE `USING` and `WITH CHECK`. Charge details must never inherit household subscription visibility. Protect encrypted credentials from household paths and restrict catalogue writes by grants, not an assumption that absent RLS makes a table read-only.
- Limit new share grants to the subscription owner who is an active member of the target household. Permit that owner to revoke after leaving. Enforce immutable share `subscription_id`, `household_id`, `shared_by` and other authority fields, with no revival or redirect; a partial active-share unique index is still required. Review both share-row visibility and subscription visibility for active membership, revoked grants, open-book and `always_private` behavior.
- Review the exact `subtrack_visibility_lookup` role/function/policy SQL and privilege graph. The dedicated definer may carry `BYPASSRLS` only within the narrowly scoped Boolean lookup boundary stated in the corrected plan: NOLOGIN/NOINHERIT, no runtime or service membership or `SET ROLE`, exact column SELECT grants, no protected-table ownership or trusted-schema CREATE, fixed trusted `search_path`, schema-qualified relations, no caller-selected principal or dynamic query, revoked PUBLIC EXECUTE and runtime-only EXECUTE. Verify no consent/membership enumeration or recursive policy path. The ordinary runtime role must be non-owner, non-superuser and non-`BYPASSRLS`.
- Add the fixture's SQL-only checks: confidence bounds, original-amount/currency pairing, charge match pairing and linked captured-value agreement or an independently reviewed write contract. Require source-backed transaction and charge dates. Neither Prisma validation nor this review proves these constraints.
- Build tables before dependent policies and prove the full clean migration chain on disposable PostgreSQL 16 using distinct migration and least-privilege runtime roles. Test actual authenticated-principal binding through BUG-013's identical transaction-local settings, missing/invalid context, rollback and pooled reuse; owner, unrelated, household, departed, revoked, multi-household and always-private cases; unauthorized mutations; and grants. No database or RLS execution is claimed by Phase A.
