# BUG-008 clean-install reconciliation plan for independent review

Status: **proposal only, 2026-10-10**. No Prisma schema, migration SQL, database, or runtime change is authorized by this note. The founder's current-environment attestation is recorded in [founder-inventory.md](./founder-inventory.md): there are no local, dev, test, staging, or production SubTrack databases. The older empty local Compose observation in the task remains historical evidence. There is no known applied migration to preserve or forward-migrate. If an existing database is discovered, stop this clean-install path and inventory its `_prisma_migrations` before any schema action.

## Governing target and scope gate

`DATA_MODEL.md` and the Constitution govern money and privacy; ST-048 and the current Prisma `Subscription`/`SubscriptionShare` shape establish subscription visibility; accepted ADR-0016 makes charge details owner-only and accepts the BUG-013 dual transaction-local principal setting. ST-060 requires banking, catalogue, transaction, and charge tables, despite those six models being absent from current `schema.prisma`. ST-067 currently has an in-memory ingestion store, so this plan does not activate provider persistence or retention jobs.

BUG-008 currently excludes rewriting, renumbering, or replacing migration history and schema feature changes beyond the subscription conflict. Before implementation, amend its permitted scope narrowly to allow repair of **unapplied source migrations** and addition of the six missing Prisma models while retaining the ST-060 banking/catalogue/transaction/charge capability. Obtain independent architect/platform-data and security/privacy approval of this exact target before schema or SQL edits. Preserve the original SQL in Git history and an evidence diff; do not erase provenance. No `DROP`, database reset, force command, existing-database application, or production deployment follows from this plan.

## Canonical relational target

All new rows have UUID primary keys and `created_at`/`updated_at` timestamptz columns, per `DATA_MODEL.md`. All monetary amounts are `BIGINT` minor units with a three-character currency; application conversion must use the Money contract, never JavaScript `number`. `identity_id` is the physical name for the DATA_MODEL owner `user_id`, matching the established identity schema. Owner IDs must be immutable after insertion. Nullable fields below represent genuinely absent provider or manually entered facts; do not synthesize source facts to satisfy `NOT NULL`.

## RLS and privilege contract

Protect bank connection, account, raw transaction, provider payload when introduced, and subscription charge with owner-only SELECT/INSERT/UPDATE/DELETE. `subscription_charge` must **never inherit** the household-visible `subscription` predicate from the old banking migration. Charge owner policy reads its own immutable `identity_id`; composite ownership constraints prevent a forged cross-owner association. Household peers receive only authorized subscription rows or aggregates, never transaction, account, bank credential, charge-detail, or raw payload rows. `merchant`/`catalogue_plan` are public SELECT; a separate narrowly granted service/migration role writes them. Absence of RLS on catalogue tables does not itself enforce read-only access: prove database grants.

Subscription SELECT is owner OR active explicit share into a household where requester is active OR owner open_book in a common active household while `always_private=false`. Explicit sharing can expose an always-private subscription by deliberate owner action; open_book cannot. Subscription mutation is owner-only. Sharing mutation is owner-authorized and household-bound. Existing `consent` is owner-private; a household policy cannot depend on a normal requester read of another owner's consent. Review a narrowly scoped `SECURITY DEFINER` visibility helper or equivalent that returns only a Boolean, obtains the principal exclusively from transaction-local `app.current_user_id`, validates active owner/viewer membership and active share/open_book internally, uses schema-qualified relations with fixed `search_path`, grants EXECUTE only to the runtime role, and is owned by a dedicated non-login role with only necessary table privileges. The helper must not accept a caller-selected principal or expose consent/other private rows. Its function/body, role grants and RLS behavior need explicit security review; avoid self/circular RLS recursion (notably `household_member` self-reference and `subscription`↔`subscription_share`) through carefully staged dependency order and tested privileged lookup boundaries. Install referenced tables before policies, then prove policy compilation and execution. Do not make a general bypass-RLS service account the application role.

All request queries use one verified `RequestContext.userId`. As ADR-0016 records for BUG-013, the transaction helper already binds both `app.user_id` and `app.current_user_id` transaction-locally to that same snapshot. The current source path must still be proven under the actual HTTP principal and least-privilege DB role. Missing/unset/invalid context must fail closed; pooled connection reuse must not carry a former principal.

## Review requests and present limits

### Security review corrections (2026-10-10)

The initial security review requested changes, retained in security-plan-review.md. New share grants require subscription ownership and active target-household membership. Owner revocation does **not** require current household membership: leaving a household must never prevent removing an earlier grant. Share subscription_id, household_id and shared_by are immutable after creation, enforced at the database boundary; UPDATE is revocation-only, with no grant revival or redirect. Subscription/banking/transaction/charge owner IDs are likewise immutable. The implementation must test departed-owner revocation and rejected share/owner reassignment explicitly.

For a concrete lookup privilege design, propose a dedicated `subtrack_visibility_lookup` role: NOLOGIN, NOINHERIT, BYPASSRLS, with only schema USAGE and column-specific SELECT on the exact membership, consent, subscription and share fields required by the reviewed predicates. It owns only narrowly scoped Boolean SECURITY DEFINER functions, not protected tables. Runtime and service roles receive no membership in it, no SET ROLE access, no private-table SELECT through it, and no CREATE in its trusted schema. Revoke PUBLIC function EXECUTE and grant only the runtime role; fix search_path to trusted schema/pg_catalog and schema-qualify every relation. A function accepts at most the target object ID, never a caller-selected principal/owner; it derives the requester exclusively from the trusted transaction-local context, and returns only whether that requester is authorized. No dynamic SQL, arbitrary query port, row payload, raw consent getter or mutation is permitted. This explicit BYPASSRLS mechanism is confined to definer execution and must be reviewed against the exact SQL and role grants before acceptance; ordinary SELECT grants alone are not a bypass mechanism. Verify that the runtime role itself is non-owner, non-superuser and non-BYPASSRLS, cannot SET ROLE to this helper, cannot replace its functions/schema, and cannot invoke a generic private lookup. Invalid/unset context returns false or fails closed. No role is provisioned by this plan.

These corrections define the proposed mechanism for rereview; they do not claim security approval or executed PostgreSQL proof. If the exact role/function design is rejected, revise it before any schema/migration edit.

Security/privacy should challenge the helper role, fixed search path, EXECUTE grants, recursion avoidance, immutable owner IDs, share authority, charge/transaction isolation, catalogue grants and failure on missing principal. Architect/data should confirm the column/enum mapping, pending event/date representation, source-backed captured charge fields, merchant alias preservation and the catalogue naming alias. The proposed repair is blocked until the BUG-008 scope amendment and these independent reviews; no actual PostgreSQL proof or implementation is claimed here.
