# ST-199 platform plan review

**Decision: Approve the proposed narrow internal core as Type 2a, with mandatory plan amendments below.** The accepted ADR-0010 already explicitly permits development-only OTP deletion reauthentication, requires a distinct deletion-only proof, and separates server-owned proof producers from HTTP integration. ST-199 does not add a new security model if it remains internal, gated, and incapable of authorizing deletion itself. Treating the branded authority assertion as authentication or adding any HTTP/wiring path would change the decision and require a Type 1 founder decision under DECISION_RULES §1/§2 (security model, data deletion; D-12 if uncertain).

The current `OtpProofProducer` is purpose-limited to enrollment and step-up. It consumes repository state before awaiting proof issue, and its proof bindings omit identity/session for those purposes. `ProofStore.issue` validates an `account-delete` binding only when identity and session are nonempty; it does not authenticate whoever supplied them. Therefore the core must strictly validate the authority assertion's runtime shape and compare its complete scope against stored challenge state, while trusting the boundary that supplied the assertion. This follows the existing CSRF-core pattern: a branded type plus strict validation/scope checks is an internal assertion, not an authentication or provenance verifier. Only a future separately reviewed adapter may assert authority after resolving a genuine current principal and registered contact. The core must not add an exported mint helper, HTTP path, principal-grant behavior, or a second authentication layer. `ProofRepository.insert` is asynchronous by interface, so proof insertion failure after OTP consumption is expected and terminal; it must never restore the challenge. The returned proof is useful only to future separately reviewed orchestration.

Required amendments before authoring:

1. Define `TrustedDeletionOtpAuthority` as an opaque, runtime-validated internal assertion. The caller boundary is trusted to have resolved a genuine current v2 principal and server-owned registered contact; only a separately reviewed future adapter may make that assertion. The core validates its shape and checks scope only. It must not infer or mint identity/session, export a mint helper, grant principal authority, expose HTTP, or act as an authentication/provenance verifier. A cast/brand alone grants no special behavior. Snapshot own enumerable data properties only; reject accessors, symbols, unexpected keys, non-plain objects, and malformed UUIDs/hashes/transport fields before state mutation. State explicitly that possession of this assertion does not authenticate a caller or authorize account deletion.
2. Store and compare the entire immutable authority scope in each challenge: identity, session, identifier hash, channel, and exact transport binding (mobile with no browser fields; web with exact HTTPS origin and nonempty server chain). Wrong owner/session/scope must not consume, decrement attempts, or otherwise burn the challenge. Do not accept raw identifiers or caller-selected owner IDs.
3. Make successful verify, exact-scope check, code comparison, and one-use consume one synchronous/atomic transition before the first await. The existing proof issue call must bind `purpose: account-delete`, action `delete-account`, same identity/session, identifier hash, challenge and full supported transport binding, and must never issue login/enrollment/step-up. `ProofBinding` has no channel field, so compare channel in the stored challenge scope and leave the accepted ProofStore contract unchanged. Any issue/insert failure leaves the OTP consumed and returns no proof; it causes no deletion. Recheck monotonic/fresh clock and expiry before issue and after its await; fail closed on regression/expiry and never restore state. Document that a successfully inserted proof with a lost response is an orphan that expires within the existing five-minute proof TTL.
4. Enforce the stated hard bounds without live-entry eviction: at most 10,000 challenges and 10,000 rate buckets, pruning expired entries only; reject capacity before committing challenge/rate counters where feasible. Apply per-identity 5 starts/minute and global 300/minute atomically with challenge insertion. Use fixed five-minute challenge TTL, five wrong-code attempts, and fail-closed clock validation. The accepted HTTP contract separately requires Idempotency-Key, current authenticated principal, CSRF for web, and throttles; the internal core must make no claim to implement or bypass those HTTP guarantees.
5. Keep explicit development mode, `AUTH_DELETE_OTP_DEV_ONLY=true`, copied server key (minimum 32 bytes), proof store, and clock mandatory. No default production wiring, HTTP module, delivery, database, provider, account deletion, principal minting, or mutation of the existing OTP producer. Start may return code only to the internal local development sink and must never expose it on wire or logs.
6. Add meaningful tests for complete scope binding and purpose isolation, wrong-scope non-burning, atomic one-use behavior under concurrent verification, wrong-code limit/expiry/replay, bounded-map and rate-limit capacity, defensive snapshots/config accessors, key copying, clock regression, and proof insertion failure with no restoration. Avoid PII and secrets in fixtures. Follow the task's required root QA and independent security review before merge.

The plan remains within the accepted development-only deletion reauthentication model only while all six constraints hold. Any future HTTP exposure or use of this proof to execute deletion is a separate task and security review; it cannot be inferred from this approval.
