# ST-199 independent security plan review

**Decision: APPROVE WITH CONDITIONS**

**Classification: Type 2a (architecture), within the accepted Type 1 security decision.** ADR-0010 already accepts the development-only OTP deletion reauthentication path under explicit development mode plus `AUTH_DELETE_OTP_DEV_ONLY=true`, and requires a separately consumed deletion-only proof. ST-199 is an internal implementation of that accepted boundary, with no endpoint, deletion action, provider, deployment, or production rollout. It therefore does not itself change product scope or the accepted security model. Any expansion beyond that narrow path—including production use, real OTP delivery, account establishment, authentication/step-up, or changing deletion authorization—would be a Type 1 change and must return for founder decision and an ADR. Security review remains a merge gate.

The core decomposition is acceptable: keep the existing restricted OTP producer unchanged; put the new deletion-only producer in its own internal module; accept only a server-minted, explicitly branded authority assertion; synchronously match the complete challenge scope and consume it before asynchronously issuing the existing purpose-bound proof. The brand is a type-level marker, not authentication. The core must not resolve identity, trust client selectors, mint principals, expose HTTP, or perform deletion.

Conditions for implementation and security approval:

1. Make the trusted-adapter boundary enforceable in module structure. Keep the trusted authority as an internal assertion, like the accepted CSRF brand, and do not export a minting helper. The core validates its shape and challenge scope but does not authenticate the assertion. The future trusted HTTP adapter must establish the genuine current principal, server-owned registered contact, and exact transport before creating it.
2. Bind challenge authority to the same identity, session, identifier hash, channel, and exact transport, and compare all of that scope before mutation. Bind the resulting `account-delete`/`delete-account` proof using only the existing ProofBinding fields: purpose/action, identity, session, identifier hash, challenge, and full transport. Do not add channel to ProofBinding or modify the existing proof store; the channel is enforced by the core challenge match. Reject malformed/accessor-bearing inputs before mutation. Wrong scope must neither consume nor count as a wrong-code attempt. Do not accept raw identifier values or caller-selected owners.
3. Keep verification, attempt accounting, and terminal consume synchronous and atomic before calling `ProofStore.issue`. Once consumed, no failure, timeout, expiry, or clock regression may restore the challenge or code. An issue failure can leave only an unusable/orphaned proof within the existing proof TTL; it must not trigger deletion or return any other proof purpose.
4. Enforce the development and feature gates on every construction, capture validated configuration/key/proof-store/clock values without invoking attacker-controlled getters, and use a copied server key of at least 32 bytes. Keep code digests domain-separated HMACs; never retain or log plaintext codes. The six-digit code, five-minute TTL, five failed attempts, challenge/rate-map capacities, and per-identity/global start limits must be hard bounds, with no live-entry eviction or overwrite. Capacity rejection must not partially commit a challenge or charge a rate count where feasible.
5. Keep start output internal for a future local development sink. Do not wire HTTP, account deletion, delivery, production configuration, or idempotency claims in this task. A future HTTP adapter still needs current-principal resolution, verified registered contact, accepted idempotency behavior, and its own accepted rate/throttle controls.
6. Include meaningful tests for scope binding and wrong-scope non-consumption; purpose isolation; atomic concurrent consume; attempt and expiry limits; gate/config/key validation; rate and capacity behavior; clock regression; and proof insertion failure after consume. Tests must demonstrate that no failure path restores a consumed challenge. Use synthetic values only.

The plan is narrowly bounded enough to proceed as Type 2a. If implementation cannot preserve the trusted-adapter boundary or terminal-consume ordering, stop and revise the plan before merging; those are security invariants, not implementation preferences.
