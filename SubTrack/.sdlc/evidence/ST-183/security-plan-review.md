# ST-183 security preimplementation review

**Decision: APPROVE WITH CONDITIONS**

The proposed boundary is sound for an unwired development/test resolver: require the concrete v2 verifier, bind verifier and reader methods once, derive `userId` only from verified `sub`, pass `sid` plus that frozen owner scope to exactly one current-owner read, and return only a frozen `{identityId, sessionId}` copy. The existing v2 access-token verifier already enforces canonical v2 token structure, issuer/audience, UUID subject/session, version 2, fixed 900-second lifetime, and expiry at its own clock. ST-182’s record shape supplies the relevant session and transport fields. This remains separate from the v1 resolver.

Conditions for implementation approval:

1. Keep the reader interface narrowly typed to `readSession(sessionId, frozenOwnerContext, nowMs)` and capture the own data method descriptor once; require a callable data value and invoke it with its original receiver. Do not accept a generic `verify`, repository query, or an adapter that can choose an unscoped lookup. The one read must be a single current-consistent owner snapshot, including active-owner and unrevoked/unexpired-session checks.
2. Validate the verifier result and reader result as hostile adapter output: plain expected record shape, own enumerable data properties only, no symbols/hidden keys/accessors/extras, copied once before inspection, and strict field/value validation. Reject malformed values and exceptions uniformly as `UnauthorizedException('Unauthorized')`; do not attach causes, details, or log input/token/record data.
3. Validate trusted transport context before calling collaborators. Require exact mobile transport-only shape; web requires exact canonical HTTPS origin and nonempty browser-chain ID. Match the session record’s transport and, for web, origin and chain exactly. Reject mobile records that include web-only keys, even when their values are `undefined`.
4. Sample and validate the clock before verification/read, then sample it again after awaiting the read. Re-run token validity at the second sample and check the copied session record’s `createdAt <= freshNow < expiresAt`. Also reject a backward clock (`freshNow < initialNow`); otherwise a clock rollback during the await could make an expired token or session appear live again. Unsafe, negative, throwing, or non-number clock values fail closed.
5. Build the owner scope solely from verified `sub`, freeze it, and pass the verified `sid` exactly once. Do not derive identity/session authority from transport input, caller JSON, record fields, environment fallbacks, v1 credentials, or a second read. Freeze and return only the minimal principal copy.
6. Treat the post-read result as authorization at the reader’s linearization point. It does not guarantee ownership remains active after that point, so any future request integration must retain owner-scoped data access and recheck its own transaction rules. Keep resolver unwired and development/test-only; no HTTP, module, DB/provider, refresh, production, or public API surface.

Relevant reference facts: `apps/api/src/auth/sessions-v2/v2-access-token.ts` has `urn:subtrack:auth:v2:development`, `urn:subtrack:api:v2:development`, `ver: 2`, and `TTL_SECONDS = 900`, and its `verify` already samples its configured clock. `apps/api/src/auth/sessions-v2/v2-session-issuer.ts` defines `SessionRecord` as identity/session/family IDs, generation 0, 64-hex refresh hash, transport, optional web origin/chain, device name, and creation/expiry times; the memory reader scopes by `context.userId`, active owner, and session expiry. The task explicitly says ST-182 is pending, so the implementation must conform to its accepted interface once available and must not silently change ST-182.
