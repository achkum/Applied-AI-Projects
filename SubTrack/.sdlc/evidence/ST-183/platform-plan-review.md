# ST-183 platform preimplementation review

**Decision: APPROVE the design in the task contract, subject to the implementation constraints below.** This is a source/interface review only; no code or QA was run. The existing legacy `PrincipalResolver` shows the established NestJS failure shape (`UnauthorizedException('Unauthorized')`) and owner-scoped reader pattern, but ST-183 should remain in its separate `sessions-v2` path and must not reuse its v1 `JwtService`.

## Concrete interface and implementation

Add only `apps/api/src/auth/sessions-v2/v2-principal-resolver.ts` and its adjacent spec. Define a local `V2SessionReader` with `readSession(sessionId, context, nowMs): Readonly<SessionRecord> | null | Promise<Readonly<SessionRecord> | null>`. The current `InMemoryV2SessionRepository.readSession` satisfies this sync-compatible contract structurally. Import `RequestContext`, `SessionRecord`, and `V2AccessToken` as types where possible. Constructor config is exactly `{ environment: 'development'; enabled: true; accessTokens: Pick<V2AccessToken, 'verify'>; reader: V2SessionReader; clock: () => number }`.

Use descriptor-based exact snapshots like the ST-182 `snapshot` helper: require ordinary plain objects, exact own keys (including rejecting symbols and non-enumerable extras), own enumerable data properties only, and read each property value once. Bind the captured `verify` and `readSession` functions to their source objects once in the constructor. Freeze internal wrappers. For each `resolve`, first validate token and snapshot trusted transport context before collaborators; accept exactly `{transport:'mobile'}` or `{transport:'web', exactOrigin, browserChainId}`. Web origin must be canonical HTTPS origin and chain ID nonempty. The caller is responsible for passing server-derived transport data; this resolver is intentionally unwired.

Call the captured verifier once and immediately copy its exact own-data claim set. Revalidate all claim invariants locally: fixed ST-180 v2 development issuer/audience, `ver === 2`, canonical lowercase UUID `sub` and `sid`, nonnegative safe-integer `iat`/`exp`, exact 900-second interval, and `iat <= floor(nowMs/1000) < exp`. Do not trust a structurally supplied verifier result without snapshotting it.

Create and freeze `{userId: sub}` and invoke the captured reader exactly once as `readSession(sid, context, nowMs)`. Await either return form. Snapshot its record strictly before validating fields. Require exact ST-182 fields plus only the two allowed web metadata fields; enforce canonical identity/session/family UUIDs, `sid !== familyId`, generation 0, 64 lowercase hex refresh hash, transport/device constraints, safe nonnegative timestamps, exact 24-hour expiry, `createdAt <= freshNow < expiresAt`, and identity/session equality with claims. For mobile, reject presence of either web key even if undefined. For web, require exact origin and chain equality with the trusted transport snapshot and `deviceName === null`. Return only a newly allocated frozen `{identityId: sub, sessionId: sid}`.

After the awaited read, call the resolver clock again and repeat the full access-token lifetime check and session time checks with that fresh value. Clock failure, rollback that makes `iat` future, or either expiry reached while the read is pending must fail closed. Collapse verifier, clock, reader, and validation exceptions into `UnauthorizedException('Unauthorized')` with no cause, detail, or logging. This fits the legacy resolver's public failure shape while preserving v1 implementation untouched.

## Snapshot and deletion semantics

The existing in-memory reader checks the active identity set and owner scope while synchronously reading, and returns a frozen record copy. Its read operation is the authorization linearization point: deletion that completes before the read yields `null`; deletion after a successful read can race with the resolver returning its principal. No two-file resolver can close that post-read race, nor promise distributed consistency. Document that the reader must provide one current-consistent scoped snapshot and that authorization reflects ownership at that read's linearization point. Protected request handling will need a fresh scope check in the data transaction; this dev-only unwired resolver does not establish permanent ownership or RLS guarantees.

## Focused tests

Tests should establish: strict constructor/context/claim/record shape handling without invoking getters; captured receiver and callable references; invalid input rejected before verifier/reader as applicable; one verifier and exactly one owner-scoped reader call; active owner and exact record/transport binding; v1-shaped or malformed credentials never fall back; generic Unauthorized for all failures; and principal immutability/independence from source objects. Include deferred async-reader cases where the clock advances to access-token or session expiry before resolution, plus deletion-before-read returning null and deletion-after-read illustrating the documented linearization limit. Exercise simulator proof → ST-182 issuer → real `V2AccessToken` → resolver for mobile and web using ephemeral keys only. No HTTP, module wiring, database, refresh, provider, or production claims belong in this change.

## Source observations

- `V2AccessToken.verify` already returns frozen claims with strict issuer/audience/version/UUID/900-second validation and its own clock check. Resolver-side snapshot and post-await recheck remain necessary because this class's clock runs before the repository await.
- ST-182 `SessionRecord` fields are identity/session/family/generation/hash/transport, optional web `exactOrigin` and `browserChainId`, `deviceName`, and created/expiry timestamps. Its `readSession` is synchronous and checks current active-owner membership at read time.
- The v1 `PrincipalResolver` already produces a frozen minimal principal and generic Nest unauthorized response after a scoped reader call. Keep this behavior isolated from the new v2 verifier and development-only namespace.
