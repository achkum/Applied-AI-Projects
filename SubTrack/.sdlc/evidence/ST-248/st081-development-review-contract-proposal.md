# ST081 bounded development review contract proposal

Status: **proposal for independent platform/privacy review, not an implementation or production policy**. This narrows the existing ST081 delivery group to one Synthetic owner inbox with Confirm, Not a subscription, and Undo. Edit, Merge, automatic cancellation, real providers, training, export delivery, and full UF06/ST081 completion remain outside this slice. Source anchors: accepted ADR-0016, ST081 readiness, existing detector/lifecycle cores, canonical subscription/charge tables, ST248 owner bank store, and current private-mobile authority. Existing manual and bank behavior remain equality gates.

## Local/test-only contract

Use disposable local PostgreSQL and owned Synthetic fixtures only. Test-created review/feedback/receipt state is destroyed with the fixture/database; this temporary test lifetime is **not** an approved production retention duration or UF11 owner-erasure proof. The test harness owns the disposable database, limits access to its existing ordinary runtime/observer roles, verifies fixture identity before teardown, and treats failed teardown as a failed qualification with no reused fixture. No default-enabled endpoint, persistent production rows, new grants, provider/account execution, external training/export, or deployed erasure job follows from this proposal.

1. An owner-bound detection composition reads only booked debit Synthetic raw rows from an unpurged generation through named, parameterized SQL in the existing current-owner transaction. Group by the accepted deterministic merchant key **and account and currency**; reject unresolved/mixed groups. PostgreSQL BIGINT values enter as canonical integer strings and are parsed directly to `bigint`; no money value passes through `Number`, including values beyond `Number.MAX_SAFE_INTEGER`. The narrow domain port below feeds the existing detector algorithm and Money helpers unchanged. Convert resulting Money through existing canonical base-10 integer-string wire rules, never floating-point JSON. Persist candidate identity from the stable owner/generation/account/merchant/currency/cadence tuple and a fixed versioned detector identity; use a deterministic digest over those typed fields, with a unique owner+generation+digest key and collision conflict (never coalesce distinct tuples). Keep a separate unique owner+candidate+raw-transaction source link for the detector's selected booked transactions. Repeat sync may update evidence only for an undecided candidate in that same source generation and never recreate or overwrite a reviewed candidate. A changed source charge does not silently rewrite a reviewed decision. Exact named SQL and collision/rollback proof are frozen below.
2. A strict private-mobile, Bearer/current-owner/Just-me read returns only owner `DETECTED` candidates, stable cursor order, bounded terminal pagination, canonical amount/currency, confidence and allowlisted reason codes. No raw descriptions, account IDs, transactions, owner selector, or household feedback. The native inbox displays reasons and Confirm / Not a subscription; after each action it re-reads authoritative owner state. Logout/rotation/blur hide obsolete rows and failures retire authority as in current Core behavior.
3. Confirm and Reject accept an exact candidate ID, expected revision and caller idempotency key, with no client-supplied owner/source/status/transaction selector. Under the current-owner lock and transaction, require `DETECTED` and the expected revision; apply ADR-0016 lifecycle `ACTIVE` or `REJECTED`, append one closed binary feedback label, and create one owned atomic receipt/audit event. Minimum receipt/inverse allowlist: owner ID, operation `confirm|reject`, candidate ID, canonical request digest and scoped key hash, receipt ID, exact pre/post revisions, prior state `DETECTED`, resulting state `ACTIVE|REJECTED`, server completion/undo deadline, consumed-at marker, and the response's bounded status/revision/receipt/deadline fields. Undo needs no raw charge IDs, amount, account, prior row snapshot or merchant text. Feedback permits owner, candidate, closed label, created timestamp, superseded-by/undone-by event reference only; no optional transaction ID in this slice. Exclude raw transactions, descriptions, account/provider identifiers, credentials, and broad row snapshots. Replay checks current principal and owner **before** receipt lookup; same owner/operation/resource/key/digest returns original bounded result without a second transition; changed digest conflicts. Unknown commit causes current readback, not automatic retry.
4. Every successful review returns server-issued `receiptId` and `undoUntil`. The server sets deadline to completion time + 10 seconds; `now < undoUntil` is required. Undo uses a fresh key and current same-owner authority, locks receipt and candidate, checks post-action revision and unconsumed receipt, then appends a compensating feedback/audit event and restores `DETECTED` with a new revision atomically. It never deletes old evidence or overwrites an intervening edit. The original feedback's superseding reference has a composite same-owner/same-candidate FK to the new receipt; a unique original-to-Undo relationship prevents a second successful compensation. After all awaited writes and authority/session/epoch fences, the last synchronous precommit guard reads the same trusted server clock again and requires `now < undoUntil`; equality or advancement past deadline rolls back subscription, feedback and both receipts. Expired, consumed, stale, foreign, or otherwise invalid undo fails with the accepted closed conflict/expiry surface. Same-key successful undo replay returns its original bounded result after fresh authority/ownership checks, without a new transition or renewed deadline. Native Undo is shown from the server deadline and success is established only by readback; a client timer never authorizes it.
5. Correction before expiry is the compensating Undo; a later contradictory decision cannot silently relabel `REJECTED` or `ACTIVE`. Any later correction needs a separately reviewed owner workflow. Only current, non-undone binary feedback can be considered for **future separately authorized** training; this slice does not train or export. A future production erasure design must remove personal review/feedback/receipt/source-link rows within UF11's hard-delete bound; append-only evidence is not an erasure exemption. This disposable fixture's teardown does not prove that owner erasure flow. An audit remnant, if any, can contain only already-approved pseudonymous fields. Data export purpose and shape are undecided, so no export path is enabled here.

## Bank-source dependency and proof

Source associations must stay owned and generation-scoped, without reassignment on Merge or crossing a household boundary. The proposed source link uses composite owner/transaction foreign keys with `RESTRICT`; a linked transaction blocks ST248's accepted raw-transaction DELETE atomically. Detection must **not** silently cascade or detach links to make purge pass. In the local proof, an unlinked revoked generation purges normally; a linked generation returns the existing closed conflict and remains intact, including its account/transaction counts and receipts. A usable production review-plus-purge flow needs a separately reviewed unlink/erasure contract or another source-association design; this proposal does not change the frozen two DELETE statements, role grants or cleanup authority.

## Frozen domain and storage path roster for a later source task

Domain-only money port: `packages/domain/detection/types.ts` adds a bigint-minor transaction/series type; `packages/domain/detection/detector.ts` factors one shared internal algorithm and adds a distinct `detectRecurringBigint` entry with a bigint-only validator. The existing `detectRecurring(TransactionSeries)` public signature and `assertSafeMinorUnits(number)` validation stay exact for legacy callers; both entries use the same Money constructors, cadence/amount thresholds, tie breaks and reason construction. `packages/domain/detection/index.ts` exports the additive bigint entry/types; `packages/domain/test/detection.spec.ts` or one adjacent focused spec proves legacy goldens unchanged, bigint parity for safe values, exact >MAX_SAFE_INTEGER processing, mixed-currency rejection and no float/Number bridge. For API runtime import, add a narrow `packages/domain/tsconfig.detection-runtime.json`, `package.json` `./detection-runtime` compiled export and `build:detection` task, then use `@subtrack/domain/detection-runtime`; do not point Node at the TS source export or fork the algorithm. Existing `packages/money` code, mobile Metro bridge, legacy detection subpath and workspace pins stay unchanged.

Storage design to freeze before implementation: additive migration owns a candidate identity unique key, owner+candidate+raw-transaction link with composite owner FKs and RESTRICT, minimal owner feedback, and minimal receipt/event tables with FORCE RLS for ordinary runtime. Named read/lock/upsert/insert/consume statements enforce both current owner GUCs and typed parameters. The review transaction locks current owner/candidate and scoped receipt key, checks current principal before replay, conditionally changes one revision, appends feedback/event and receipt, then fences the current session before commit. Undo locks the same resources in one fixed order, checks owner/deadline/post revision/consumed marker, conditionally restores DETECTED at the next revision, appends superseding evidence and consumes the prior receipt atomically. No generic statement, SQL literal caller input, bypass role, global DELETE or global grant is permitted. Any minimal table-specific privilege needed by the ordinary runtime role requires exact independent review and proof before source GO.

Required source/actual proof before any runtime acceptance: reconciled migration and exact SQL statement review; least-privilege non-superuser FORCE RLS with both current GUCs; cross-owner/household isolation; deterministic repeat sync and bigint parity beyond safe-number range; canonical Money roundtrip; concurrent same/different-key review and undo; server deadline equality; stale revisions; rollback and post-commit readback; source-link/purge conflict; preserved manual and bank receipts. Actual owner-erasure proof belongs to a separately authorized production-bound contract, not disposable fixture teardown. Installed native proof must use the real owned fixture and current session, never preset acceptance flags.

## Open policy decision and classification

2026-10-14 exact-contract amendment: `st081-017-ddl-proposal.sql` and `st081-named-sql-contract-proposal.md` freeze proposed DDL, quote-free named parameterized SQL, and synchronous final-precommit Undo guard. Add generated original feedback_id as a minimal receipt inverse field with same-owner/same-candidate FK and unique owner/feedback relationship; supersede by exact event identity, never timestamp equality. Candidate INSERT SELECT proves account belongs to selected active/unpurged/synced Synthetic generation with currency/paying-account agreement. They supersede the earlier optional undecided rescan-evidence update: this initial slice compares and skips an existing candidate and never updates candidate tuple, source links or subscription evidence on rescan. Merchant display/key/category must be one unambiguous trusted catalogue or fixed server-owned Synthetic roster match using existing matchMerchantDescriptor; normalized raw descriptor output is not a safe display fallback. Fixed Synthetic canonicalName alone may occupy custom_name when no catalogue UUID exists. Known Undo expiry propagates409 only after confirmed successful rollback before any COMMIT attempt; uncertain rollback/commit, unknown/async guard and regressing clock remain generic500. These are review proposals, not runtime changes or executed qualification.

ADR-0016 already decides the local reversible status table, minimal feedback labels and 10-second undo. Designing and proving this **test-only** strict contract in disposable owned fixtures is a bounded Type2a architecture exercise, pending independent privacy review; no Founder decision is required to choose the fixture's lifetime and cleanup for that local proof. It does not authorize default-enabled durable production review persistence. Before production/default enablement, an explicit product/privacy decision must set bounded retention and deletion scheduling for feedback, audit and idempotency/undo receipts (including post-expiry replay), their account-erasure/correction behavior, and whether/how current labels may enter user export or model training. The present documents specify no such duration or training/export authorization. A source-association versus bank-purge user flow also needs a reviewed contract. Founder policy input is required only if these production choices change product purpose or deletion rights; platform/privacy reviewers cannot infer a production period or consent from the accepted local semantics.
