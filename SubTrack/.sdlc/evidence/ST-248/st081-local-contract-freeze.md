# ST081 Synthetic review: local contract freeze for independent privacy/storage review

**Proposed Type2a development fixture contract only.** No runtime/source edit, migration execution, production retention, export/training, provider execution, new ticket, or ST081 completion follows from this document. It narrows the accepted ADR-0016 review model to Synthetic Scan → Inbox → Confirm/Reject → 10-second Undo, after ST248 bank qualification. The companion `st081-development-review-contract-proposal.md` supplies purpose and open-policy boundaries; this file freezes the concrete next source roster.

## Exact private-mobile wire proposal

All routes are `POST` over the existing direct development HTTPS private-mobile host, exact path/no query, one JSON body of at most 8192 bytes, current Bearer/session and complete profile + persisted Just me. The existing closed bank parser is not widened; a detection-only strict flat parser may admit only the required string members. Unknown/duplicate/escaped duplicate/prototype keys, coercions, arrays, numeric JSON money, mixed credentials, cookies, Origin and bodyless/malformed framing fail closed. No client owner, account, raw transaction, bank generation, source, status, or scope field.

| Route | Exact request body | Key | Exact success response |
| --- | --- | --- | --- |
| `/v2/private/mobile/detections/scan` | `{}` | 16–255 printable ASCII Idempotency-Key | `200 {scan:'complete'}` after durable readback; no candidate count or raw data |
| `/v2/private/mobile/detections/read` | `{}` or `{cursor:string}` with existing bounded opaque cursor grammar | absent | `200 {items:Candidate[],nextCursor:string|null}`; max 50 and terminal pagination |
| `/v2/private/mobile/detections/confirm` | `{candidateId:uuid,expectedRevision:canonicalPositiveInt64String}` | required | `200 ReviewResult` |
| `/v2/private/mobile/detections/reject` | same | required | `200 ReviewResult` |
| `/v2/private/mobile/detections/undo` | `{receiptId:uuid}` | required fresh key | `200 ReviewResult` |

`Candidate` has exactly `id`, `revision`, `displayName` (bounded accepted canonical merchant label, never raw descriptor), `categoryCode`, `cadence`, `expectedAmountMinor` (canonical base-10 integer string), `currency`, `confidence` (existing bounded decimal policy), `reasons` (allowlisted reason-code strings only), `status:'DETECTED'`. No raw transaction IDs, amounts of individual charges, account ID, provider fields, free-text reason params, private audit, or household visibility. Stable descending `(created_at,id)` owner cursor uses the existing signed/opaque cursor pattern; duplicate/cycle/overlong cursors fail. `ReviewResult` has exactly `candidateId`, `status:'ACTIVE'|'REJECTED'|'DETECTED'`, `revision`, `receiptId`, `undoUntil` (`RFC3339 UTC` for Confirm/Reject, `null` for Undo). Same-key replay returns the same stored bounded response. All responses `no-store`; invalid wire 400, missing/current-invalid principal 401, invisible candidate/receipt 404 indistinguishable from missing, wrong mode/stale/review conflict 409, expired undo 409 `UNDO_EXPIRED`, storage/unknown commit masked 500 and mandatory fresh readback. No automatic client retry or preselected success state.

`scan` is local-fixture-only and idempotent by owner+source-generation+algorithm version; it selects the server-known one active, unpurged, synced Synthetic connection and never lets a caller nominate a connection. If none exists, return a closed setup/conflict state; if more than one active generation appears, fail unavailable rather than guess. A separate minimal `scan_receipt` atomically records owner, generation, scoped key hash, canonical empty-body request digest and the closed `scan:'complete'` result; same-key replay checks current owner and current generation first, and a key reused after generation change conflicts. A second new key may rescan without changing reviewed candidates or source links. Source text used for merchant normalization stays inside the current server transaction and is never persisted in detection feedback or sent in review payloads.

## Frozen local schema and SQL contract

Disposable additive `apps/api/prisma/development-auth/017-private-mobile-detection.sql` is proposed after 016 in the owned local migration loader only. It creates `st081_detection.candidate` keyed `(identity_id,subscription_id)`, with `connection_id,account_id,merchant_key,currency,cadence,algorithm_version,candidate_h` as its closed identity tuple, `(identity_id,connection_id,candidate_h)` unique and typed FK `(subscription_id,identity_id)` to `public.subscription`, `(connection_id,identity_id)` to `st248_bank.generation`, both `ON DELETE RESTRICT`; the digest is SHA-256 of a versioned length-delimited owner/generation/account/merchant/currency/cadence tuple. Equal hash with unequal stored tuple is a hard conflict, never coalescence. `source_link` keyed `(identity_id,subscription_id,raw_transaction_id)` has composite FK to candidate and to `public.raw_transaction(id,identity_id)`, both RESTRICT. Source links are immutable after initial creation; rescan does not delete/reassign them. A linked transaction causes the frozen ST248 purge DELETE to fail atomically, with unchanged rows, generation and receipts. No cascade/unlink/global DELETE or bank grant change.

`feedback` contains only `id,identity_id,subscription_id,label,created_at,superseded_by_event_id` with closed `CONFIRMED_SUBSCRIPTION|NOT_SUBSCRIPTION` labels and an owner/candidate FK; Undo's newly appended receipt is the compensating event and marks the prior label noncurrent without deleting it. No optional transaction FK, narrative, amount or account. `review_receipt` contains only `id,identity_id,subscription_id,operation(confirm|reject|undo),key_h,request_h,pre_revision,post_revision,prior_status,result_status,completed_at,undo_until,consumed_at,undo_of_receipt_id,result_response` where `result_response` is the closed `ReviewResult` fields; `undo_until` is completion+10 seconds only on originals. Unique `(identity_id,operation,subscription_id,key_h)`, owner/candidate and owner/original-receipt composite FKs, a composite owner FK from feedback.superseded_by_event_id to the compensating undo receipt, and one unique successful undo-to-original relationship serialize replay. `scan_receipt` contains only `identity_id,connection_id,key_h,request_h,completed_at,result_status` with unique owner/key and owner/generation FK. No raw key, payload, bank/charge identifier or broad prior snapshot is allowed. All five tables use FORCE RLS for the existing ordinary runtime role with both transaction-local owner GUCs; only exact table/column privileges justified by the named operations are proposed, never a global grant or bypass role. These are proposed DDL fields/constraints, not executable SQL approved in this document.

The only proposed SQL operation names are `detectionModeRead`, `detectionActiveGenerationLock`, `detectionBookedRows`, `detectionScanReceiptRead`, `detectionScanReceiptInsert`, `detectionCandidateLookup`, `detectionSubscriptionInsert`, `detectionCandidateInsert`, `detectionSourceLinkInsert`, `detectionInboxPage`, `detectionReceiptLock`, `detectionCandidateLock`, `detectionCompareUpdate`, `detectionFeedbackInsert`, `detectionFeedbackSupersede`, `detectionReceiptInsert`, `detectionReceiptConsume`, and `detectionFinalFence`. Each statement is fixed/parameterized and registered in the current owner transaction, with `$1::uuid` equal to both `app.user_id` and `app.current_user_id`; joins to generation/account/raw transaction and every mutation include matching `identity_id`. `detectionBookedRows` requires `SYNTHETIC`, fixture institution/version, `ACTIVE`, unpurged, synced, `BOOKED`, debit negative, nonrefund, account/currency agreement, fixed deterministic `(account_id,transaction_date,raw_transaction.id)` order and a fail-closed bounded result. `detectionInboxPage` selects only own `DETECTED` candidate rows, joins canonical merchant display only, orders `(created_at,id) DESC`, and returns 51 to form a max-50 page. No generic SQL, owner selector, stored procedure, security definer, arbitrary UPDATE or new DELETE belongs to the roster.

Transaction order: enter existing verified current-mobile authority → mode check → owner/generation lock (scan) or receipt scoped-key lock (review/undo) → candidate owner lock → compare revision/status → exact side effects + feedback/receipt → `detectionFinalFence` rechecks current session/owner before commit. Receipt lookup/replay cannot precede authority/mode and owner checks. Confirm and Reject use existing pure lifecycle `DETECTED→ACTIVE|REJECTED` and increment one revision; never alter manual rows. Undo locks original receipt and same candidate in one fixed order, requires server `now < undo_until`, original unconsumed and current revision exactly original post revision, then compensates to `DETECTED` at a new revision, supersedes binary feedback and consumes original receipt atomically. After all awaited mutation, feedback and receipt writes, the final precommit fence rechecks the same trusted server clock and still requires `now < undo_until`; equality or expiry rolls back every effect. Later mutation/expiry/equality conflicts. Same-key replay of a committed original or undo returns its immutable bounded result only after fresh current authority and owner proof. Rollback includes receipt and all effects; unknown commit forces readback rather than retry.
