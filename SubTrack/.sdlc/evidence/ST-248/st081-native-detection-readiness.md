# ST-081 native detection inbox readiness (source reconnaissance)

The smallest coherent next slice, after ST-248 bank qualification, is one **owner-only Synthetic detection review**: sync provides booked raw transactions; a bounded server job groups a current owner's eligible rows into deterministic merchant/currency/account series, runs the accepted `detectRecurring` core, persists stable `DETECTED` subscriptions, and a native inbox reads them with confidence/reason codes and Confirm / Not a subscription actions. Each action rereads the authoritative status; manual subscriptions and bank rows/digests remain unchanged. This would be a partial ST-081 delivery, not Edit/Merge, full UF-06, real-provider/ML quality, automatic cancellation, household sharing, or production release.

Reusable source is concrete: `packages/domain/detection/detector.ts` handles booked debit cadence/amount patterns and emits reason codes; `subscription-lifecycle.ts` maps `DETECTED` Confirm→`ACTIVE` and Reject→`REJECTED`; `detection-merge.ts` is a decision helper only. The canonical `subscription` table has `source`, `status`, confidence and reason JSON, and owner-scoped RLS. Existing subscription read projection filters reason params/raw evidence, and OpenAPI has a **default-unavailable v1** owner-only review page with immutable cursor ordering. ST-248 has current private-mobile Bearer/Just-me authority and a durable Synthetic bank store. None of these is yet a native detection persistence/review endpoint or an owned, proven bank-to-detector grouping pipeline. The v1 review contract is not activated and cannot be reused as a native Bearer route by assumption.

Required contract/store boundaries before implementation: strict private-mobile read page and Confirm/Reject mutation schemas with no owner/scope/transaction selector; current authority and owner locks before replay; terminal pagination and stable order; canonical integer-string Money and reason-code-only output. A named SQL composition must select only current-owner booked Synthetic rows, define deterministic merchant grouping from the accepted merchant normalization/match core, reject mixed accounts/currencies and unsafe bigint→number conversion, then upsert stable candidate identities without duplicating previously rejected/confirmed decisions on repeat sync. Candidate-to-source charge association and purge dependency must be explicit: ST-248 purge currently refuses linked subscription charges, so review must neither silently cascade bank rows nor block purge without a specified user flow. Review mutations need atomic owner-scoped status, feedback/audit, replay receipt, revision check and final session fence, with non-superuser FORCE RLS/rollback/concurrency proof. UI must hide stale results on logout/rotation and show genuine post-mutation readback.

**Readiness blocker:** accepted ADR-0016 requires 10-second server-timed compensating undo for every review action and says feedback/receipt persistence remains blocked until bounded retention, erasure/correction and export/training purpose are recorded and privacy-reviewed. The current schema has no `detection_feedback` table or review receipt/undo/merge link. That contract must be resolved before Confirm/Reject can be called an executable review slice. ADR-0016 also retains reconciled migration/least-privilege PG proof gates; ST-248's owned Synthetic proof does not automatically discharge them for new detection SQL. Preserve the existing manual and bank receipts as separate equality gates in any later actual PG/device qualification.
