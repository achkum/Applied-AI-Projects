# ST194 security plan review

**Decision: Approve as Type 2a, with mandatory conditions below.** The proposal implements the already accepted `DELETE /v2/me/sessions/{id}` web branch using existing session authority and repository operations. It is a bounded, opt-in development HTTP slice. It does not change the API contract, so ADR-0010's Type 2a contract decision does not itself authorize production exposure or a security-model change. Keep the default app route at 404 and leave runtime wiring unchanged.

The authority sequence is sound if preserved exactly: validate the access JWT, snapshot only its own-data claims, and derive `sub`/`sid` solely from those verified claims. The synchronous `webContextForCurrentSession(sid, {userId: sub}, bindingHash, exactOrigin, time)` call is only a transport lookup. It does not authenticate the final principal. Await the shared principal resolver, require its identity/session to equal the verified claims, then take a fresh nonregressing clock and synchronously recheck the owned live row, complete binding, and current context before mutation. This closes deletion, expiry, and context-change races across the await.

Require direct TLS and one canonical exact Origin; reject ambiguous credentials, body/framing, query, duplicate raw headers/cookies, bearer/mobile material, any refresh cookie, and all CSRF aliases. The accepted protected-web credential selector requires exactly one access cookie and zero refresh cookies. The naturally sent `st_v2_refresh` cookie is path-scoped to `/v2/auth`, so it should not reach `/v2/me`; if present, fail closed instead of ignoring it. Verify the canonical session CSRF token before revocation. Call the existing atomic owner-scoped `revokeForCurrentSession`; never use the path ID as an owner selector. Keep foreign and missing targets indistinguishable. Do not add an idempotency header: the accepted DELETE contract has none. Listing GET's absent-Origin behavior is a separate review and must not relax this route's Origin rule.

On confirmed self-revocation, invalidate only the requesting principal's CSRF state after repository commit. If invalidation fails, return a generic no-store failure and do not claim rollback or restore the session. Sibling revocation must not invalidate caller CSRF. The target sibling's CSRF entry may remain as bounded inert state: active current-row validation rejects it. Do not claim target-chain cleanup, TTL guarantees, delivery/socket atomicity, or safe retries. A lost response remains committed; stale self credentials fail current-row validation.

Mandatory implementation evidence: actual-TLS tests with accepted bootstrap and refresh modules plus the new module; sibling, self, foreign, and missing revocation; bad-CSRF no-mutation; races deleting/expiring the caller during principal resolution; raw ambiguity and malformed-input rejection; capacity preservation and consumed-history neighbors; no-store parser/errors; and default 404. Keep the four proposed new files and metadata-only scope. No production-readiness claim.
