# ST194 platform plan review

**Decision: Type 2a, approve with the requirements below.** This is a reversible, opt-in development HTTP adapter for the already accepted `DELETE /v2/me/sessions/{id}` contract. Its isolated module, explicit development enablement, default 404, and four new files do not change the credential model, public contract, provider, database, or runtime wiring. Source work remains hard-gated on accepted ST193 main/tree/CI evidence; the development module is not evidence of API or rollout readiness.

The caller authority sequence must remain strict: validate the access JWT with `accessTokens.verify`, derive `sub` and `sid` only from those verified claims, then call `webContextForCurrentSession(sid, {userId: sub}, bindingHash, exactOrigin, observedAt)` synchronously. That ST191 port returns only the live, owned, bound web context; it is a lookup, not principal authority. Await `principal.resolve` with that context and require its identity/session to equal the verified claims. After the await, read a fresh non-regressing clock and synchronously recheck the owned live row, full binding/current context, and target eligibility before mutation. No additional await may open a race before revocation.

Verify the shared session CSRF token before state change. The repository revocation operation must atomically recheck the current caller row and target ownership/liveness, preserve refresh-history capacity, and revoke only the requested target. For self-revocation, invalidate only the requesting principal's CSRF state after confirmed commit. If invalidation fails after commit, return generic 500 without restoring the session or claiming rollback; sibling revocation must not invalidate caller CSRF. Target CSRF cleanup is not implied. Stale self cookies must fail current-row checks. Preserve the contract's no-idempotency behavior and indistinguishable missing/foreign result.

Retain the proposed strict raw credential/header/cookie parsing, direct TLS and exact-Origin evidence, and bounded throttle. The existing `selectV2CredentialTransport` protected web branch requires `refreshCookies.length === 0`; therefore reject any `st_v2_refresh` cookie on DELETE, even though its `/v2/auth` path normally keeps it off `/v2/me`. Do not silently ignore it or let the new adapter diverge from the shared selector. Tests should exercise real TLS with the accepted bootstrap/refresh stack, including all refresh-cookie cases, deletion/expiry while principal resolution awaits, CSRF failure with no mutation, sibling/self/foreign/missing targets, commit followed by CSRF invalidation failure, and default-route 404. Do not claim atomic socket delivery, rollback after an unknown commit, cookie clearing, or cleanup of another chain's CSRF state.
