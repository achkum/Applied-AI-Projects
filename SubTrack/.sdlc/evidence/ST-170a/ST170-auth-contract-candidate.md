# ST170 — Auth wire contract candidate v2

**Status: proposal only (Type 2a).** These are proposed `/v2` interfaces, not accepted behavior or implementation authority. Preserve `/v1` route bytes and semantics; inventory deployments and consumers before any rollout, and make no rollout-safety claim. Keep BankID provider protocols and payloads outside this contract.

| Operation | Proposed request | Proposed response / behavior |
|---|---|---|
| `POST /v2/auth/browser-nonce` | Same-origin browser JSON request `{purpose}`; exact allowlisted `Origin` | `200 {nonce}` plus a distinct host-only `Secure; HttpOnly; SameSite=Lax` binding cookie; nonce is public and sent by JS in a custom header. |
| `POST /v2/auth/otp/start` | `{channel, identifier, purpose, transport}`; purpose=`enroll_identifier` or `otp_step_up` | `202 {challengeId}` with generic status/body/timing; never selects or creates a principal. |
| `POST /v2/auth/otp/verify` | `{challengeId, code}` plus browser nonce header when web | Returns a purpose-bound enrollment/step-up proof, never a login bootstrap by itself; one-use. |
| `POST /v2/auth/session` | `{transport, loginProof, deviceName?}`; proof is bound to that transport | Web sets access/refresh cookies and returns `{sessionId, csrfToken}`; mobile returns `{accessToken, refreshToken, sessionId}` once for OS secure storage. `no-store`. |
| `POST /v2/auth/refresh` | No body; web uses refresh cookie, mobile `Authorization: Refresh <opaque-secret>` | Rotates in the same transport; web refresh response also supplies a separate readable session CSRF token. `no-store`, `Pragma: no-cache`. |
| `GET /v2/me/sessions` / `DELETE /v2/me/sessions/{id}` | Authenticated caller; no identity selector | List or revoke only caller-owned sessions; delete returns `204`. |
| `POST /v2/me/reauth/otp/start` | Authenticated caller; `{channel}` only, no identity/identifier/environment selector | Development only: resolve caller-owned registered identifier server-side, enforce `AUTH_DELETE_OTP_DEV_ONLY` + explicit development mode; create same-principal/session account-delete challenge; generic `202 {challengeId}`. |
| `POST /v2/me/reauth/otp/verify` | Authenticated same principal/session; `{challengeId, code}`; web exact Origin + session CSRF | Same dev-only server gate; verify/consume caller-owned account-delete challenge atomically and return `{reauthProof}` bound to that principal/action, never a login proof; no-store. |
| `DELETE /v2/me` | `{reauthProof}` | `204`; consume proof atomically for same-principal account deletion only. |

## Proposed identity, proof, and session rules

- BankID verification is mandatory for account enrollment. OTP verifies an identifier first in the accepted UF01 enrollment order; its proof permits only the BankID continuation and cannot create/select an identity. Account enrollment completes only after verified BankID. OTP step-up alone cannot log in. Login requires verified BankID, or a server-verified registered mobile passkey/biometric assertion plus OTP. Only a server-owned verified result can establish `loginProof`.
- Proof records bind purpose, identity when established, normalized identifier hash where relevant, initiating challenge, selected transport, intended action, and browser nonce chain where applicable. Use opaque random values; store hashes only. Five-minute proof TTL is a proposed policy. Redeem once atomically. `dev_delete_reauth` is deletion-only and same-principal; production deletion requires recent BankID. Permit verified OTP deletion only with server-side `AUTH_DELETE_OTP_DEV_ONLY=true` and explicit development mode; fail closed elsewhere. No client field selects environment or method.
- Browser bootstrap binds nonce and secret-cookie pair to exact allowlisted Origin, purpose, and challenge/proof chain. Rotate at transitions and return each next public nonce in the response; do not require reuse of a consumed cookie value. Reject mismatch, expiry, replay, `Origin: null`, wildcard, and reflected credentialed CORS. Authenticated unsafe cookie calls use a distinct session-bound readable CSRF token, supplied with the session/refresh web response and rotated with lifecycle; require exact Origin always. Bearer calls need no cookie CSRF.
- Transport is selected explicitly and proof-bound; redemption cannot switch mode. Protected mobile calls use only `Authorization: Bearer <access JWT>`. Refresh uses only the opaque refresh secret via `Authorization: Refresh <opaque-secret>` for mobile, never body/query; reject any refresh body and cookie-plus-Authorization. Reject cookie-plus-bearer protected calls; no fallback between modes. OpenAPI may document `Refresh` as a custom `apiKey` header scheme; do not describe it as an IANA standard.
- Web cookies are host-only (`Domain` omitted), `Secure; HttpOnly; SameSite=Lax`: names `st_v2_access` with `Path=/v2` and `st_v2_refresh` with `Path=/v2/auth`; neither uses a `__Host-` prefix because paths are narrower than `/`. Deployment supplies actual host/origin values; placeholders are not allowlisted hosts. Require HTTPS outside local development, edge HSTS, and trust forwarded host/proto only from configured proxy hops. Fail closed on insecure production configuration.
- Keep 15-minute access and 30-day refresh lifetimes. Repository interface atomically consumes one active refresh hash and creates one same-identity, same-family successor; concurrent losers create none; consumed-token reuse atomically revokes the family. Retain consumed hashes through the applicable refresh lifetime. Unknown, expired, or revoked credentials reveal no ownership. List/revoke are owner-scoped.
- Use separate `/v2` auth validation and distinct v2 issuer/audience/key namespace; never accept v2 credentials in v1 or fall back to v1 identity headers. Derive `{identityId, sessionId}` only from an active server-validated session; bind transaction identity from that snapshot. Missing/invalid auth returns stable generic RFC 9457 `401`; CSRF failure is `403`; use `application/problem+json`; redact credentials and PII from errors/logs.
- Normalize channel/identifier, throttle by IP and identifier, and make OTP responses non-enumerating; `202` does not assert delivery or account existence. Idempotency must not replay codes/proofs or bypass throttles; use `Idempotency-Key` only where the accepted API contract requires it.

## Decision and gates

Propose opt-in `/v2` because identity, proof, and credential semantics change; retain `/v1` unchanged pending deployment/consumer inventory. No migration/schema or provider change is proposed. Before implementation: update OpenAPI first and review it; complete security/privacy review of nonce, CSRF, proof binding, storage and rotation; inventory databases before schema work; confirm exact deployment origins, cookie host, proxy hops, production keys, and development-only deletion configuration. Verify RLS only with disposable PostgreSQL and a qualified non-superuser, non-`BYPASSRLS` role. These gates are not claims of current deployment or provider behavior.

Proof-producer integration is a separately required ST170b slice: verified BankID adapter/simulator login and production account-delete reauth must issue server-owned proofs through reviewed adapter interfaces; no client-facing BankID/provider fields are invented here. Session exchange is not client-ready until that slice passes its gates. DELETE /v2/me requires current authenticated same-principal session plus exact Origin and session CSRF for web; deletion proof is independent. Caller-issued proofs cannot satisfy these guards.
