# ST203 platform plan review

**Decision: APPROVE_PLAN, conditional on an explicit new founder decision before any source work. Classification: Type 1 (security model / one-way door), pending that decision.** The verify adapter consumes a one-use challenge and exposes an account-delete-only reauthentication proof over HTTP, adding a live capability path. ADR-0010 is contract-only, and ADR-0012 plus the ST201 founder receipt expressly approve START only and exclude VERIFY. ST201's narrower Type 2a review does not transfer. No founder approval for ST203 is present; the Conductor must obtain and record a separate decision under DECISION_RULES §§1–2 (D-12) before implementation. This review does not grant that approval.

The proposal is bounded and consistent with the existing contract and accepted components if implemented as written. It uses the exact `{challengeId, code}` request and `{reauthProof}` success body for `verifyV2DeleteOtpReauth`, preserves generic failures and no-store behavior, and limits the adapter to the explicitly registered development mobile branch. It reuses the existing authority resolver, deletion-only proof producer and `verifyV2DeleteOtpReauth` idempotency operation. It adds no authority kind, credential mode, default registration, database/provider, contract change, client/UI behavior, or deletion action.

Keep these conditions in the task contract:

- Require exact development, enabled, and `authDeleteOtpDevOnly` gates; register the module explicitly and keep it out of default wiring. Accept only one canonical Bearer credential over direct TLS, reject cookies and competing credential/request selectors, and require a strict body with exactly the two contract fields. Preserve generic status/error mapping and no-store headers on every response path, including parser/framing failures.
- Resolve authority only through the existing trusted resolver and validate identity, session, registered-contact hash/channel, and mobile transport. Immediately before invoking core verify, synchronously reverify claims/freshness and the full current owned session row, with no await before invocation. Require the core's native promise. After it resolves, synchronously recheck current authority before settlement and again before disclosing the proof. Do not claim a transaction across core, guard, and HTTP response boundaries.
- Bind the existing reservation to verified-principal authority and the canonical `{challengeId, code}` digest. Reserve before core verify; duplicates, changed-body retries, and uncertain outcomes return generic `409 AUTH_RESTART_REQUIRED`, never a saved proof. Do not keep raw code or proof in replayable state. The core consumes the challenge before awaiting issuance, so proof-store failure, authorization change, settlement failure, or response loss can leave a consumed challenge and/or committed proof. Never retry, replay, restore, or guess cleanup; require a fresh challenge.
- Keep validation focused on actual HTTPS behavior using the existing resolver, producer, proof store and idempotency guard. Cover malformed transport/body before reserve/core, indistinguishable verification failures, duplicate and parallel attempts, revocation at awaited boundaries, proof issuance failure after consumption, and settlement/response failure. No provider delivery or actual deletion is exercised. Require independent security/platform source reviews and the stated QA/CI gates after the Type 1 decision.

No plan defect requires redesign. The blocking prerequisite is the separate founder decision; preserve the proposal-only status until that decision is recorded. Scope expansion into new authority/proof semantics, default wiring, provider or persistence work, contract changes, or deletion behavior requires reclassification and renewed review.
