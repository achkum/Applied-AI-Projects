# ST203 proposal: development mobile deletion OTP verification adapter

**Disposition: proposal only; no implementation or authorization is implied.** ST203 is separate from ST201 and must be classified independently. ADR-0012 explicitly approves the challenge-start branch only and excludes verify. The founder receipt for ST201 likewise approves only `/start`. ST203 would consume a one-use challenge and return a deletion-only reauthentication proof, so this proposal recommends **Type 1 pending an explicit founder decision** under `DECISION_RULES.md` §1 and §2 (security-model ambiguity / D-12). The ST201 security review's Type 2a classification concerns its narrower start adapter and cannot be extended to verify. Do not infer founder approval from the existing route/schema or from ADR-0012. If the architect and security reviewer can establish that verify is only a reversible integration of already accepted authority/proof semantics with no security-model change, they may state a separate Type 2a position; conflicting/uncertain classification remains Type 1. No source work should begin before that decision and independent plan reviews.

## Contract and existing implementation

The existing OpenAPI operation is `POST /v2/me/reauth/otp/verify`, operationId `verifyV2DeleteOtpReauth`. The request is exactly `{challengeId, code}` (`DeleteOtpVerifyRequest`, no additional properties); the response is exactly `{reauthProof}` (`DeleteOtpVerifyResponse`). Success is `200`, no-store. The proof is opaque and one-use, account-delete-only. Existing documented error responses are `401`, `403`, `409`, plus default V2 problem. Idempotency retries must never replay proof; a duplicate or uncertain committed one-use operation returns generic `409 AUTH_RESTART_REQUIRED`, without code/token/proof, and restarts with a fresh challenge. No OpenAPI change is proposed.

The accepted core is `DevelopmentDeletionOtpProofProducer.verify({challengeId, code, authority})`. It validates canonical 43-character challenge id and six-digit code, rechecks the trusted authority scope against the challenge, consumes a wrong-attempt budget, and deletes a correct challenge synchronously before awaiting proof issuance. It issues `purpose: account-delete` bound to that challenge, mobile transport, verified identity, session and registered identifier hash; after the await it validates expiry and opaque proof format. All failures collapse to `Deletion OTP verification unavailable`. This gives a critical failure window: proof-issue failure after a correct code leaves the challenge consumed; a later HTTP/session/settlement/response failure may leave both challenge consumed and proof committed. Never retry, restore, replay, or guess cleanup. The client must start a fresh challenge. A returned proof remains independent of session authorization and is not sufficient for deletion by itself.

The current ST201 HTTPS adapter already implements the direct-TLS mobile Bearer branch, strict framing/raw-header checks, current-principal resolver, HMAC verified-principal idempotency, no-store/problem responses, and bounded per-principal/global request throttling. Its development-only module is explicitly registered, not in default app wiring. The verify adapter should follow those local patterns while remaining a separately registered module. Reuse the actual `DevelopmentMobileDeletionOtpAuthorityResolver`, existing access-token/session/contact readers, `InMemoryIdempotencyGuard` with its already-supported `verifyV2DeleteOtpReauth` operation, and the accepted proof producer. Do not add authority kinds, auth modes, fallback branches, global defaults, providers, database/schema work, client/UI behavior, real delivery, public deployment, or deletion behavior.

## Exact HTTP behavior

Register only with exact `environment: development`, `enabled: true`, and `authDeleteOtpDevOnly: true`; capture and validate strict own data properties and bound methods at registration/constructor time. Require exactly one canonical `Authorization: Bearer <v2 access token>`, no Cookie header of any kind, direct TLS socket and `request.secure === true`, exactly one canonical positive Content-Length within 4096 bytes, JSON content type, no transfer-encoding, duplicate/raw-header ambiguity, query, Origin/nonce/CSRF/XSRF, identity/contact/environment/method selectors, extra body fields, or caller-selected transport. Keep errors and success `Cache-Control: no-store` and `Pragma: no-cache`.

Parse the body as a strict plain object with exactly two own fields. `challengeId` must be canonical unpadded base64url for 32 bytes (43 characters); `code` must match `^\\d{6}$`. No identifier, channel, proof purpose, principal, or session comes from the body. Malformed framing/body/credential ambiguity returns generic `400 AUTH_REQUEST_UNAVAILABLE`; invalid or stale access credential/current principal returns generic `401 AUTH_REQUEST_UNAVAILABLE`; a valid principal with a challenge/code/scope mismatch returns indistinguishable generic `403 AUTH_REQUEST_UNAVAILABLE`; duplicate/pending/committed idempotency returns generic `409 AUTH_RESTART_REQUIRED`; unexpected trusted-port/capacity/response failures return generic `500 AUTH_REQUEST_UNAVAILABLE`. Emit no challenge existence, attempt count, registered contact, code, proof, or trusted error detail. The generic `403` for all core verification failures avoids distinguishing absent, expired, exhausted, wrong-code, and wrong-principal challenges; proof-store/system failures are also currently indistinguishable because the accepted producer collapses all failures.

Success is exactly HTTP `200` JSON `{ "reauthProof": "<opaque one-use account-delete proof>" }` with no-store headers. Never include challenge id, code, session/token, expiry, cookie, or any extra field. Do not log proof or code. A duplicate key cannot return prior success; response loss requires a fresh challenge and verification.

## Required ordering and failure windows

1. Validate raw request/transport and exact body before any throttle, reservation, or proof call. Resolve the current authority through the existing trusted resolver using the verified token; require its identity/session match the verified claims and its registered server-side contact hash/channel and mobile transport to be valid. Never accept a fabricated or request-derived authority.
2. Apply a bounded local verify request throttle before reservation (recommend same bounded 5 per verified principal/minute and 300 global/minute envelope used by ST201, with capped buckets and monotonic clock); return only generic 429 if selected. The core's wrong-attempt limit remains authoritative for each challenge. This adapter throttle is not an idempotency bypass and does not alter the core.
3. Build `verified-principal` authority digest with the existing keyed/framed pattern over identity id, session id, registered identifier hash, and channel. Hash canonical JSON `{challengeId, code}` with SHA-256; the guard HMACs the binding before storage. Do not store raw code/proof in idempotency state. Reserve `verifyV2DeleteOtpReauth` over mobile transport before calling verify. Reservation duplicates map to generic 409 and never replay a proof.
4. Immediately before the unsafe core call, synchronously reverify token claims, freshness, and full owned current mobile-session row. Invoke `otpProofs.verify({challengeId, code, authority})` once; do not place an await between that final ownership check and invocation. Require a strict native promise and validate the resolved proof as canonical opaque `v2.` plus 43-character secret, without retaining it in replayable state.
5. After the producer await, synchronously recheck current token/session before any later unsafe effect or disclosure. Settle the known reservation `completed` synchronously, then make a final current-principal/session check immediately before emitting 200. Do not claim a cross-system transaction: the proof can be issued before the post-await check or settle; the challenge is already consumed before proof issuance. If authorization changes or a later operation fails, suppress the proof response and do not attempt proof/challenge cleanup. Best-effort `failed` settlement is allowed only for the known owned pending reservation and cannot mask the primary outcome; never overwrite a completed reservation.
6. Any uncertain outcome after core verification, completed settlement, or response writing is non-replayable. A retry with that key returns generic 409; the caller starts a fresh challenge and verifies again. Do not retry core verify, restore quota/attempts/challenge/proof, or return a saved proof. If headers were sent, do not write a second response.

## Required adversarial HTTPS checks

Use an actual local CA HTTPS server and the production-shaped dev module with fixed synthetic identity, real accepted token/session/principal/contact resolver, `InMemoryIdempotencyGuard`, and `DevelopmentDeletionOtpProofProducer` plus local proof store. Verify exact wire success and no-store; no proof/code/challenge on failures; wrong code, expired/unknown challenge, wrong principal/session and exhausted attempts all have indistinguishable generic 403; invalid/stale token and owner revocation/deletion deny; malformed JSON, extra keys, duplicate headers, cookies (including unrelated cookies), Origin/CSRF, query, bad framing, noncanonical challenge, non-six-digit code, and non-TLS fail before reserve/core; different idempotency keys cannot bypass core wrong-attempt limits; duplicate same key or changed body never replays proof; parallel verification yields at most one proof; owner/session changes during deferred resolver and proof-store issuance suppress proof; proof-store failure after challenge consumption requires a fresh challenge; reservation, settle, and response failures leave no replay and no guessed cleanup; capacity and hostile synchronous/thenable/getter ports fail closed; parser errors retain no-store; logs contain no code/proof/PII. Assert the existing account-delete proof binding and prove it cannot redeem as login/step-up proof. No real SMS/email or actual account deletion is exercised.

Require independent platform and security **plan** dispositions before source work, then independent frozen source reviews, focused HTTPS/API QA, full required API QA and CI before merge. Any High/Critical security issue blocks merge. Evidence must state this is development-only adapter acceptance, not production readiness or delivery readiness.
