1. ADR-0010 requires isolated v2 issuer/audience/key and mutually exclusive credential modes. No v2-to-v1 bridge, token export, alternate identity header, issuer replacement, or V1 fallback is authorized.
2. For each future v2 read POST/PATCH, parse raw cookies/header multiplicity; require exactly one `st_v2_access` plus the distinct binding cookie, reject Authorization and `st_v2_refresh` as route credentials. Verify access to derive `sid/sub`, hash the observed binding cookie, call `webContextForCurrentSession(sid,{userId:sub},hash,origin,now)`, then pass its chain and origin to `DevelopmentV2PrincipalResolver.resolve`; compare returned owner/session to the verified claims before attaching server-only `RequestContext`. The resolver does **not** check binding-cookie hash or return a chain; its chain check uses the trusted port's result.
3. `extractV2BrowserEvidence` currently requires exactly one allowlisted `Origin` and direct TLS. An ordinary same-origin browser GET can omit Origin and script cannot set it. The concrete Type 2a remedy proposed in client review is `POST /v2/subscriptions/{id}/read` with empty JSON `{}`, cookie-only current web authority, exact Origin, binding/chain and one session `X-Session-CSRF`; it performs no mutation, CSRF rotation or idempotency reservation (ADR-0010 reserves that for mutating POST). Do not silently relax the extractor or claim a browser can supply Origin manually.

Both routes must require exact allowlisted Origin, direct HTTPS, current cookie/chain binding and one valid `X-Session-CSRF` for that same verified identity/session; reject duplicate/mixed headers, query identity selectors and unknown body fields. The read POST must not consume/rotate CSRF or write subscription state. No `Access-Control-Allow-Credentials` widening or wildcard origin.
