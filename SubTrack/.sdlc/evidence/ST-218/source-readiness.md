`ADR-0010` mandates additive v2 isolation; `ADR-0023/0024` bind v1 lifecycle to its existing current-session Bearer authority. Browser cookies do not reach `/v1` by Path and must never be copied into an Authorization header or accepted through a fallback. `ST-050b` remains IN_PROGRESS, `ST-050c` proves only enrollment OTP browser transport, and no accepted evidence establishes an enrolled signed-in browser account, persistent v2 session issuer/reader, or real provider. Existing owned PG fixtures are synthetic and do not create a user account.

Browser read envelope gap: accepted `extractV2BrowserEvidence` (`apps/api/src/auth/http/v2-browser-context.ts`) requires exactly one `Origin`; an ordinary same-origin GET may have none, and JavaScript cannot set this forbidden header. The [WHATWG Fetch origin-header algorithm](https://fetch.spec.whatwg.org/#append-a-request-origin-header) makes this browser behavior, not a client implementation choice. Do not weaken that extractor or invent a GET exception.

Readiness: **NOT_READY** for ST-217 client implementation or user-facing detail. The smallest safe next slice is a contract-only additive `POST /v2/subscriptions/{id}/read` with strict empty `{}` body, cookie-only current web principal, exact allowlisted Origin and session-bound `X-Session-CSRF`; it is a pure bounded read with no nonce/session/CSRF mutation. ADR-0010 requires idempotency for *mutating* POST, so this read requires no Idempotency-Key. Status-only `PATCH /v2/subscriptions/{id}` remains a separate future contract/runtime step. Later runtime must derive current session ID from verified access credential, hash the observed browser binding cookie and call accepted `webContextForCurrentSession(sessionId, {userId}, bindingCookieHash, exactOrigin, observedAt)`, compare its returned chain with `DevelopmentV2PrincipalResolver.resolve(access, {transport:'web', exactOrigin, browserChainId})`, then construct `RequestContext`. Its browser proof can use an internally issued simulator proof for a pre-registered synthetic fixture identity; it must not label that a usable onboarding flow. Durable account/session integration and actual signed-in browser onboarding remain separate blocked prerequisites before user-facing activation.
