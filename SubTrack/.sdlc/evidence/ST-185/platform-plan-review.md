# ST185 platform design review

**Decision: APPROVE with the conditions and limits below.** This is a preimplementation design review of the internal development v2 refresh service in `.setup/ST185-task-draft.md`. Source work remains gated on formal ST184 acceptance.

## Assessment

The proposed service boundary fits accepted ST184's in-memory lifecycle seam and ADR-0010's contract-only v2 authentication scope. It correctly treats the raw refresh secret as possession proof: canonical validation and domain-separated hashing happen in the service, while the repository receives only hashes and authenticates the principal from stored lifecycle state. The service must not accept identity, session, or family selectors. The accepted repository's `rotateRefresh` is the only atomic state transition; do not add a separate lookup, retry, or second store.

The captured dependency interface and receiver preservation are important here. At construction, validate exact plain own-data configuration and capture only callable data descriptors for the repository and token issuer, preserving their receivers. Reject accessors, hidden/symbol/extraneous fields, and malformed ports before use. Snapshot the exact mobile-only or canonical HTTPS web transport before calling collaborators, then pass a frozen copy. The request shape likewise stays exact own-enumerable-data `{ refreshToken, transportContext }`; getters, symbols, hidden fields, and extra keys fail closed.

Before any repository call, require the canonical `v2r` 32-byte base64url secret grammar and round-trip encoding, a safe nonnegative millisecond clock value, and exactly 32 random bytes. Copy generated bytes before hashing; domain-separate the hashes and reject a successor hash equal to the current hash without burning the active token. Generate the successor before the single `rotateRefresh` call. Its exact input is the two hashes, snapshotted transport, and observed time. Awaiting the port is appropriate for deferred/fault tests, but the memory implementation remains synchronous and atomic.

Only an exact own-data `rotated` outcome with canonical stored identity/session/family IDs and bounded fixed expiry can advance to access-token issuance. Treat `invalid`, `reused`, malformed/unknown outcomes, thrown ports, and extra/accessor outcome fields as generic failures with no credentials. Validate a fresh clock after rotation, require it to be nondecreasing and strictly before stored expiry, issue exactly one isolated v2 access token for the stored identity/session, validate its bounded string result, and check the clock again after synchronous signing. Return only frozen `{ sessionId, accessToken, refreshToken }` after all checks succeed.

After a validated rotation, any subsequent clock, signing, or response-validation failure must attempt exact tuple cleanup using the stored owner and successor hash. `revokeRotatedFamily` must be given a frozen owner context and exact `{ identityId, sessionId, familyId, refreshTokenHash }`; ignore false/throw outcomes and return no credentials. Never restore the consumed credential or retry rotation. Unknown, throwing, or malformed repository outcomes do not establish a cleanup tuple and must not produce credentials. As ADR-0010 specifies, uncertain orphan state expires normally; durable transaction/fault semantics need separate design review.

The concurrency model is coherent: a competing reuse may revoke the family after the first call's commit point, so successful issuance does not promise ongoing authorization. The shared resolver remains responsible for current authorization on each request. Keep the validation on one real shared issuer/repository/refresher/resolver path: replaying an old token must yield no credentials and invalidate old and current access tokens for that family while a neighboring family and identity remain usable. Exercise web and mobile bindings, wrong-context no-burn, collision/capacity/deletion/expiry behavior, captured receivers, clock rollback and deferred expiry cleanup, token-issue failure cleanup, and unknown or malformed adapter results without leaking secrets.

## Conditions and limits

1. Begin source only after ST184 is formally accepted and its independent approval evidence is present. The ST184 task is currently marked `IN_PROGRESS`; the plan draft alone is not that acceptance gate.
2. Keep the implementation limited to the specified internal development service, accepted in-memory repository, and v2 issuer. No HTTP, CSRF, idempotency, cookies, provider, database, client readiness, or production-auth claim follows from this approval.
3. Keep all failures generic and credential-free, and keep raw secrets only in local service variables and the successful frozen return. Repository state remains hash-only.
4. Preserve ADR-0010's bounded unknown-orphan behavior; do not invent retry or restoration semantics.
