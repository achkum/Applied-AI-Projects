# C19 iOS zero-arrival identifier investigation and proposed diagnostic

Read-only source/config/harness inspection following actual C16 iOS failure. No source edit, dependency/configuration change, device run or rerun. No concrete TLS/network/UI/configuration fault is established.

Source findings:
- Existing native workflow supplies EXPO_PUBLIC_MOBILE_ENROLLMENT_ENABLED=true and fixed HTTPS loopback URL to both matrix jobs. Enrollment client reads static process.env.EXPO_PUBLIC_* references, the form Expo inlines. Driver child environment inherits process.env; prebuild, xcodebuild and private Metro inherit it. No source-visible iOS override or EAS invocation exists in this path; EAS development's disabled flag is not used by this local workflow. Static graph preflight also forces these same fixed env values, but compilation proves neither values executed in the installed bundle nor request success.
- Client baseUrl rejects nondevelopment/web/disabled/missing or malformed HTTPS configuration before a request. freshKey then calls Expo crypto and validates exactly 32 bytes before fetch. Either stage can produce zero fixture arrivals. Fetch failure is separately mapped to restart. Actual zero arrivals cannot distinguish any of these from form submission/normalization failure.
- IdentifierEntry normalizes the current native controlled text value and disables Continue until valid; valid submit invokes EnrollmentProvider.start, which accepts only identifier phase, publishes starting, calls startMobileEnrollment, and commits otp only for current mounted generation after validated accepted response. Failed start restores identifier/error. The main Maestro flow successfully reached the OTP-field wait; it did not establish which submit/client stage executed. Reusing Android's prior successful identifier as proof of iOS text/input/submit behavior is invalid.
- Owned harness listens only on IPv4 loopback; public fixed URL is localhost. Leaf certificate has DNS localhost SAN, serverAuth EKU, RSA3072/SHA256 and one-day validity, verifies hostname against the owned explicit CA. iOS build calls simctl add-root-cert on the same owned simulator before private Metro launch. These are source intentions and successful build steps; actual iOS transport/ATS/TLS acceptance remains unobserved. No justification exists to change hostname, bind publicly, bypass certificate checks or invent a certificate failure.
- Android debug trust is a separate explicit narrow CA plugin plus adb reverse; its successful entry does not prove iOS trust/transport behavior. Existing probes report exit-other and cannot establish absent/present UI. Native proof tooling does not explicitly qualify the macOS timeout executable, so its execution path is also not proven by source; current closed bucket does not identify that as the cause.

Smallest proposed next diagnostic (independent plan review and task-roster amendment before implementation): an explicitly owned-proof-only, native development-gated passive closed stage sink shared by existing IdentifierEntry/EnrollmentFlow/mobileEnrollmentOtp. No new endpoint, UI label, request, retry, wait, timeout or acceptance flag. Default entirely off. An explicit proof flag must be statically inlined and set only in existing private workflow; no release/EAS profile enables it. Reject web/nondevelopment/disabled instrumentation. Emit fixed stages only, never method arguments, identifier/channel/value/key/URL/path/response/error object or generation IDs.

Stage roster sufficient to distinguish this failure: submit-valid/submit-invalid; start-accepted/start-ignored; config-accepted/config-rejected; entropy-accepted/entropy-rejected; fetch-entered/fetch-rejected; response-accepted/response-other; contract-accepted/contract-rejected; flow-committed/flow-obsolete. Emit only on original existing execution branches, never wrap/retry/alter fetch or timing. Configuration marker must not expose URL or bypass original baseUrl validation; entropy marker must not retain bytes or key. Response-other is a closed status-family category at most, not a body. Observe start path only, never OTP verify/resend secrets; if additional starts occur publish bounded zero/one/multiple counts rather than individual values. A generation/reset clears RAM stage state; no storage or telemetry.

Existing Metro log remains private. Driver failure-only parser for exact identifier phase reads bounded fixed private log and projects only known stage presence/count buckets; unknown/missing/malformed data remains withheld and does not imply nonexecution. If actual console delivery cannot be observed from owned Metro, report diagnostic unavailable rather than fabricate UI state. Companion Node/client/mounted tests must cover inactive production/web/default, malformed/private canaries, original request/authority semantics unchanged, each genuine stage, no mutation retries, stale generation and strict parser100 coverage. Task paths required: existing IdentifierEntry.tsx/test, EnrollmentFlow.tsx/test, mobileEnrollmentOtp.ts/test, one narrow privateRuntime diagnostic helper/test, existing runtime driver/parser/tests, existing native workflow for explicit proof-only flag. This is a proposal only, not installed evidence or current repair authorization.

A reviewed client stage sink is orthogonal to C18's enrollment child-execution repair and is necessary before another unchanged iOS cold run can answer the zero-arrival cause.
