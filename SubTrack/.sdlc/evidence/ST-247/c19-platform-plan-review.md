# C19 iOS client-stage proposal: platform plan review

Verdict: **amend before source GO**. The proposal preserves the accepted request, authentication, timeout, and native proof boundaries, and no iOS transport/configuration fault is established. The proposed Metro parser needs a positive delivery calibration before absence of a stage can have diagnostic meaning.

The installed React Native 0.74.5 `setUpDeveloperTools.js` forwards JavaScript console events through HMRClient only under development, a polyfilled console, and a working HMR connection; `HMRClient.log` silently ignores send failures. `private-runtime-build.sh` writes the owned `expo start --localhost` process output to private `metro.log`, but a running Metro server does not prove that this iOS simulator's JavaScript markers reached that file. Add a fixed, proof-only, nonprivate calibration marker on the mounted identifier view before submission. Parse it under the same bounded private-log rules. If absent, emit only `diagnostic-unavailable`; do not classify missing submit/config/fetch markers as negative observations. Even when calibrated, markers describe only the single observed execution and must not replace fixture arrival/OTP/installed acceptance gates.

Freeze the exact owned roster before editing: `IdentifierEntry.tsx` and its mounted test for normalized submit decisions; `RegistrationScreen.tsx` and test if a callback-forwarded marker is used at its existing `onValidIdentifier` bridge; `EnrollmentFlow.tsx` and test for phase and generation decisions; `mobileEnrollmentOtp.ts` and test for original config, entropy, fetch, response and contract branches; one narrow default-off proof marker helper/test; the existing bounded driver/parser/tests and native workflow for an explicit local-proof-only compile-time flag. Keep the marker sink disabled in web, nondevelopment, default, and release/EAS paths. Emit only fixed tokens, no argument/object/string interpolation, URL, input, key, error, status number, or response body.

The existing macOS identifier probes call `spawn('timeout', ...)`. Their `exit-other` result establishes a child `close` with a non-null code, so it does not by itself indicate a missing `timeout` executable. It cannot distinguish timeout utility status 125/126/127 from another tool exit without a closed code bucket. Do not install or change tools on that inference. A bounded diagnostic-only bucket may be added if independently reviewed; leave `exit-other` inconclusive otherwise. Preserve the probe deadlines and every acceptance wait.
