## Containers, keys and resource envelope

Pin PostgreSQL, API base/final image and Caddy by verified digest; do not invent digests. Build the API outside the VPS using the frozen lockfile and actual required workspace packages, then start only the reviewed `sandbox/main` entrypoint. The existing API Dockerfile boots Nest and is not a qualified substitute. Non-root API and gateway users, read-only roots, dropped capabilities, `no-new-privileges`, bounded writable tmpfs, explicit PID/CPU limits and stop timeouts are required. Run PostgreSQL as its supported postgres UID with writable owned data volume; do not blindly apply a read-only layout that prevents normal initialization. Caddy's certificate/config volumes must be writable only by its designated non-root UID.

Enforce local Compose limits rather than relying solely on Swarm-only settings: PostgreSQL 256 MiB, API 384 MiB and gateway 96 MiB initially, with finite PID limits and total bounded rotated container logs. PostgreSQL connection/buffer settings and API pool/concurrency must fit those budgets. Measure current available memory before future execution; fail preflight when insufficient instead of affecting other services. The source author must document the total envelope and writable volume/log growth. Global/per-owner data ceilings remain a runtime prerequisite; memory limits do not bound persistent disk usage.

Only the founder/devops role creates actual sandbox values. Use a separate host secret directory, mode 0700; no real values in `.env`, Compose interpolation output, shell command arguments, build layers/args, logs or artifacts. Mount individual secret files read-only with permissions/ownership allowing only the designated container UID to read. A blanket host-owned 0600 file is not sufficient if it makes the non-root worker unable to read; explicitly verify effective mount ownership and access without printing contents. PostgreSQL uses a password file; runtime credentials, migration credentials and API signing/identity/session material are separate. Mount no migration key into the API or gateway. Caddy's ACME account and certificate keys stay in its dedicated persistent volume, outside APK/gateway artifacts.

## Concrete HTTPS ingress plan

The approved design uses the verified IPv4 `198.44.116.159`, no invented domain and no purchase. Recommend Caddy **2.11.7**, then independently resolve its official image digest and validate the actual pinned binary/config before later execution. Its official release is dated 2026-10-03; older bare-IP issuance regressions make an unqualified old pin unsuitable. Explicitly configure only the Let's Encrypt ACME issuer at `https://acme-v02.api.letsencrypt.org/directory` with `profile shortlived` for `https://198.44.116.159`. No internal/self-signed issuer, ZeroSSL/paid fallback, on-demand arbitrary host issuance or disabled certificate verification. Start with gateway-internal HTTP 8080 / HTTPS 8443 so a non-root process needs no privileged bind capability; only a later reviewed public profile maps host TCP 80/443. Validate the adapted pinned configuration's ACME challenge listeners/port mapping. Leave UDP/HTTP3 unpublished in this first slice.

Keep persistent Caddy account/certificate storage so restart and renewal work. The actual future release must verify the trusted chain, IP subjectAltName, expiry and renewal behavior from outside the VPS and on both phones. Obtaining an ACME account automatically for this approved certificate is normal certificate custody, not permission to register a paid hosting service. If issuance/renewal fails, stop exposure and report the exact cause; the legacy runbook's self-signed staging fallback is unsuitable for public testers.

Caddy accepts only the canonical host. No reflected CORS or arbitrary catch-all proxy route. Until the exact sandbox route roster is approved, API proxying remains disabled; explicit unavailable responses must not fabricate health/product success. The future proxy discards client-supplied forwarding authority and supplies its own source metadata over the isolated trusted hop. Application validation trusts only that hop and derives owner solely from validated credentials; no owner headers. Caddy admin port is disabled or container-loopback-only, never published. Use finite header/body/read/write/upstream deadlines, no request body/capability logging, and short HSTS only after trusted HTTPS is established. Static download links stay unavailable until real verified artifact destinations exist.

## Verification scope and deployment handoff

The preparation checks are Bash syntax, Compose configuration without displaying interpolated secret values, pinned Caddy adaptation/validation and inspection of namespace/ports/mounts/users/resource bounds. They do not establish public TLS, backend readiness, identity isolation or installed-phone acceptance. API image build waits for the real approved sandbox source; reserve the shared heavy-job slot before any build. A future deployment checklist must separately require identity adoption, independent source/deployment review, applicable CI, validated migrations, durable two-owner/restart/revocation readback and actual artifact availability before publication. No infrastructure-only passing check may bypass those gates.
