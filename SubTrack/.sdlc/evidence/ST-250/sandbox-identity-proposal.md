# ST-250 — Public sandbox identity proposal

Status: Proposed; founder adoption and independent implementation review pending. This document authorizes no runtime exposure. Prepared by independent security/platform review, 2026-10-14.

## Decision to adopt

**A — Recommended:** Adopt a separate, explicitly simulated sandbox guest model with one private workspace per installation, protected by a durable possession credential. Permit its separately reviewed implementation and zero-additional-cost deployment on the existing VPS. This exception applies only to the isolated tester sandbox; production enrollment and login retain mandatory BankID. No real OTP delivery, banks, new third-party accounts, spending or public store release is authorized.

**B:** Retain the currently accepted private simulator model. Continue infrastructure, packaging and other development, but keep public interactive sandbox access blocked until a separately approved identity boundary exists. Shared Alice access is prohibited under either option.

## Exact identity and credential semantics

1. The sandbox server creates a random internal owner UUID and a cryptographically random 32-byte installation capability. Neither a phone number, email, device identifier, supplied owner UUID nor chosen Alice/Bob name supplies authority. Display names are editable presentation data only. The workspace begins with synthetic data; the UI persistently says verification and integrations are simulated and asks testers to use fictional inputs.
2. The capability is disclosed once, only after its owner/digest record commits successfully over publicly trusted HTTPS. The phone saves it only in native secure storage. The database stores its domain-separated digest, creation/expiry/revocation state and owner binding; it never stores the raw capability. Capability values, access/refresh tokens, private inputs and request bodies are excluded from logs, feedback URLs, crash reports and analytics. No browser/clipboard/export capability transport is provided.
3. Initial admission is a narrowly named **anonymous sandbox bootstrap** operation, not anonymous OTP, a verified subject, BankID or an existing principal. Its one-use reservation binds operation, sandbox transport, request digest and a globally keyed idempotency key. It creates no client-selected principal. Duplicate or uncertain bootstrap returns a generic restart result and never replays credentials. Lost initial disclosure leaves an inaccessible bounded orphan; retry with a new key creates a fresh workspace. No destructive compensation follows uncertain commit.
4. Returning-device admission presents the installation capability to a dedicated sandbox resume endpoint. The server resolves its owner from the durable digest record, checks non-revocation and expiry, then issues a new owner-bound session only after commit. It does not accept an accompanying owner selector. This is possession authentication for a simulated workspace, not person verification. Initial capability lifetime is 30 days from creation without sliding renewal; access-token lifetime is 15 minutes and session/refresh lifetime is at most 24 hours, always capped by capability expiry. These finite defaults are implementation assumptions for review, not production policy changes.
5. Sandbox tokens have distinct issuer, audience, key IDs/signing material and credential namespace. Production, private-proof and sandbox credentials cannot authenticate each other. Every business read, write and replay requires a current unrevoked same-owner durable session plus the accepted owner/RLS checks. No credential embedded in the shared test/download link authenticates a workspace.
6. Refresh remains atomic, same-family and one-use; consumed refresh reuse revokes that family. An uncertain refresh response retires local session credentials without retry. A still-current installation capability can resume a new sandbox session; unknown older sessions remain bounded by expiry. This is an explicit sandbox-only recovery exception, not a change to production's fresh verified-login requirement.
7. Logout revokes the installation capability and every session for that workspace atomically. The app clears capability and session credentials after known success and retires them after uncertainty; it cannot promise server-side revocation until acknowledged. Restart before logout resumes the same workspace and reads persisted data. Restart after logout creates a new workspace. No cross-device recovery or migration is included: reinstall, lost secure storage, logout or capability expiry loses access to the old workspace. Do not erase workspace data as logout compensation.
8. Persist owner, capability digest, sessions, revocation and business state in the isolated sandbox PostgreSQL volume. A process restart preserves access/readback; immutable sandbox environment/database/role/epoch checks fail closed on wrong composition. Separate keys and databases prevent any synthetic principal from entering production. Do not adapt the disposable fixture harness into a production launcher or weaken its private loopback gates.

## Bounded public operation

The shared test link is discovery and download access, not a secrecy boundary. Admission must remain safe if the link is indexed or forwarded. Before exposure, freeze concrete limits in the implementation contract: maximum active workspaces, per-owner rows/bytes, sessions/reservations, bootstrap and resume attempts, concurrency, pool size, body size and request duration. Enforce capacity atomically before creation and business writes; report generic 429/capacity failures without issuing credentials. Rate-limit by server-observed source address using only explicitly trusted proxy hops, with bounded short-lived keyed state; source address is never owner authority. Per-source limits alone cannot control distributed abuse, so the global storage/admission ceiling is mandatory. No automatic paid scale-up occurs. Resource limits must preserve unrelated VPS services.

Only reviewed sandbox routes are public. Private Alice/Bob login and enrollment, web handlers, debug/OTP diagnostics, legacy export/deletion handlers and real provider adapters remain absent. PostgreSQL and API container ports stay private; the reviewed HTTPS gateway is the public entry point. Use an independently renewed publicly trusted certificate, not the CI self-signed CA. OpenClaw application/software/services/deployment directories are not used.

No new retention/deletion job is bundled with this proposal. Capability expiry disables access; any later purge policy needs its own explicit retention/deletion contract and review. Clearly tell testers that this is temporary test data, not durable production storage.

## Why the existing approval is insufficient for this one boundary

The founder already authorized a public tester sandbox on the existing VPS without extra cost. That covers the sandbox delivery direction, public-link audience and isolated hosting; asking for those approvals again is unnecessary.

However, [ADR-0010](../../../docs/architecture/adr/ADR-0010.md) explicitly says: “Enrollment still requires verified BankID before an account is established.” It also requires fresh verified login after uncertain refresh. [ADR-0006](../../../docs/architecture/adr/ADR-0006.md) adopts simulator mode with “fixed demo identities” and says it is never enabled with production data. The present private mobile composition completes enrollment as Alice and provides selector-free Alice login behind development/loopback restrictions. Public access cannot safely reuse that identity.

This proposal establishes a new synthetic workspace from possession rather than BankID and permits capability resume after uncertain refresh. Those are concrete sandbox authority semantics; they are not merely choosing a deployment port. [DECISION_RULES §1–2](../../../docs/governance/DECISION_RULES.md) assigns security-model changes to the founder. Approval A adopts this narrowly isolated exception without replacing production BankID or enabling real integrations. Implementation, independent reviews, applicable CI and actual public/native acceptance still follow; proposal adoption is not security sign-off for an unbuilt system.

## Focused release evidence

Before public exposure, demonstrate two independent installed clients with distinct owners: foreign read/write/replay and credential-namespace rejection; restart durable readback; resume/expiry/revocation; refresh reuse and uncertain-response behavior; global/per-owner capacity and bounded ingress; no raw credentials or inputs in operational output; and absence of private/debug/real-provider routes. Review the actual composition, grants, proxy boundary, certificate renewal and deployment rollback. Preserve accepted Money and privacy gates; mock proofs or passing fixture tests do not establish installed-app acceptance.
