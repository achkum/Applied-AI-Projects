## Runnable custody and loader
A manually dispatched dedicated GitHub workflow uses the existing pinned Node22/PNPM toolchain and an isolated PostgreSQL16 service. Its bootstrap login is exactly subtrack_sandbox_bootstrap and its database exactly subtrack_sandbox. Disposable service administrative authority is used only to install the two unchanged reviewed DDL files, set migration SHA/manifest settings, assign a random API-login password and verify resulting catalogue/privileges. No connection to a supplied remote database, arbitrary query text or fallback database is accepted. Secrets are ephemeral workflow-private files mounted/read at the existing exact /run/secrets paths with regular-file, mode and size custody; signing and HMAC material generated locally, never printed or uploaded. The actual loadSandboxConfig compiled module computes the manifest and DDL hashes; no duplicate manifest implementation or key logging.

The shell launcher refuses non-disposable markers and unexpected cwd/database/server-major/role tuple, executes only the named harness, sets bounded timeout and performs cleanup first in a finally path. The harness builds the existing API using the unchanged compiler, invokes actual main entrypoint in a bounded child process, uses ordinary subtrack_sandbox_api_login pool role for all runtime operations, and sends HTTP to loopback4000 with exact canonical Host and privately retained gateway/source headers. Origin / secrets remain the production-shaped sandbox tuple; loopback/private harness is not a publicly valid test link. Bootstrap/admin connections are closed before runtime scenarios. All resulting data is newly generated synthetic state, not Alice/Bob private fixture data.

## Ordered runtime scenarios
1. Actual compiled startup succeeds with installed manifest, roles, migration hashes and forced RLS. Catalogue checks prove NOLOGIN/non-BYPASS owner, app-login SET role graph excludes owner/bootstrap, public schema USAGE only as reviewed, both SECURITY DEFINER ownership/fixed search paths/PUBLIC execute revocation and composite receipt FKs.
2. Two distinct real HTTP bootstrap calls create two empty owners, separate capabilities/sessions and bounded access credentials. The successful reservation/identity/session inserts necessarily execute guard_growth; the successful scoped creation and subsequent business call execute lock_owner. No simulated flags substitute for success/readback. Credentials remain private memory.
3. For both owners: profile update/read, Just Me selection/read and manual creation using canonical amount minor string and a real idempotency UUID. Owner pagination returns only that owner's exact created synthetic subscription. Idempotent manual replay returns the original result after current authority checks. Native Month is derived client behavior and is not claimed by this proof.
4. Stop the real compiled process and its pool cleanly; restart the same compiled main against the same database/key/epoch/manifest, without loader or reset. Resume each capability with fresh keys and read profile/mode/owner data back exactly. Persisted owner/subscription IDs may be compared only in private memory.
5. Real manual edit/status behavior for each owner, including version conflict and foreign resource denial in both directions. Runtime ordinary-role SQL isolation checks set both trusted owner GUCs and mismatched GUCs in dedicated transactions: across all relevant public subscription/receipt/profile and auth owner tables, foreign reads return no rows, foreign writes fail/affect zero, and cleanup resets/discards connections. No direct mutation of existing business rows to fabricate a scenario.
6. Real refresh rotates credentials once; new access succeeds. Reusing consumed old refresh returns restart and revokes that family; its access is denied. Separate unaffected owner remains usable. Wrong gateway, raw duplicate keys, malformed body and private-namespace credentials fail before disclosure.
7. Real logout from the unaffected owner revokes workspace capability/all sessions, denies old access and resume, while durable stored profile/manual rows remain in database. A fresh third bootstrap starts empty rather than reclaiming any existing owner.
8. Shutdown child processes/pools, remove ephemeral private material and destroy disposable database/service custody. Only then emit the exact schema below if every scenario succeeded. Known cleanup uncertainty prevents a qualified receipt.

## Accepted custody refinement and process semantics
Platform and privacy accept a launcher-owned uniquely labelled PostgreSQL16 Docker container/network instead of a GitHub service stanza. This avoids displaying generated bootstrap material during service creation. The approved PG16-bookworm image is pinned to docker.io/library/postgres@sha256:0ea6700a3b4f0ae6ce746519073558aed4d88a79d8d07622a9a644946c7319c4. Both independent reviewers accepted this refinement; executable paths are unchanged. Container/network IDs and unique labels are checked before exact removal; successful Docker list calls must subsequently confirm absence, preventing daemon failure from masquerading as deletion. The persistent database resides solely in container tmpfs. Exact secret files, private logs/envfile/key material and hostname mapping are removed/restored before closed receipt publication; no raw artifacts.

Root also accepted SIGTERM/wait of the exact compiled main child as realistic process restart, preserving the same DB/key/epoch; the harness never claims main.close was invoked. Child PID/command custody is checked and live owned child stopped on failure; only successful process, pool, Docker database/network and private material cleanup permits receipt.
