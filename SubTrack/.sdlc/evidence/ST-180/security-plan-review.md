# ST-180 security preimplementation review

**Decision: APPROVE WITH MANDATORY TASK-BOUND CONDITIONS**

This approval covers only an unwired internal dev/test Ed25519 v2 access-token core. It does not approve integration, production readiness, or changes to v1. The implementation and its tests must meet every condition below before this review can support merge.

1. Keep the API limited to issue and verify. Require explicit dev/test mode and an explicit enabled flag. Do not read environment variables, generate/fallback to keys, select algorithms dynamically, call the v1 JwtService, add exports/barrels/modules/configuration, or connect HTTP, sessions, persistence, authorization, or providers.
2. Fix issuer and audience to v2-only constants in the implementation. Use the proposed exact development values `urn:subtrack:auth:v2:development` and `urn:subtrack:api:v2:development`; do not accept caller-selected namespace values. Make no claim that constructor inputs prove global separation from v1 keys. Require private and public KeyObjects with asymmetricKeyType `ed25519`, the respective private/public type, and prove they form a pair (for example, derive/export the private key's public key and compare canonical SPKI DER bytes with the supplied public key).
3. Issue only canonical lowercase RFC UUIDs, versions 1–8 with the RFC variant, for both identity and session IDs. Treat those arguments as server-owned inputs; reject malformed values. Validate the injected clock result as a safe nonnegative integer millisecond timestamp before flooring to seconds. Use the exact 900-second TTL with safe integer arithmetic.
4. Emit only the exact header `{alg:"EdDSA",typ:"subtrack-v2-access+jwt"}` and exact payload keys `iss,aud,sub,sid,iat,exp,ver` with `ver:2`. Verification must reject all missing or extra own keys and require exact fixed issuer, audience, version, UUID, time, and TTL values. Require `iat <= nowSeconds` and `nowSeconds < exp`; allow no clock skew or future-issued token. Validate verifier clock results the same way as issuer clock results. Never use an unverified header to choose verification behavior.
5. Bound the token to at most 4096 ASCII characters before decoding or cryptographic work. Require exactly three nonempty segments, canonical unpadded base64url by decode/re-encode equality, valid UTF-8 JSON objects with plain-object prototypes, and a 64-byte Ed25519 signature. Define duplicate-key rejection explicitly: after decoding and parsing each JSON object, require the original decoded UTF-8 bytes to equal `Buffer.from(JSON.stringify(parsedObject), "utf8")`. This rejects duplicate keys, whitespace, alternate escapes, and noncanonical representations; tests must cover duplicate header and payload keys. If implementation chooses a different mechanism, it must reject duplicate names before values can be overwritten.
6. Collapse malformed input, invalid claims/signatures/keys, and clock failures to one generic verification failure. Do not include token text, claims, key material, or parser/crypto detail in errors or logs. Return only a frozen minimal validated claims object; do not log or store tokens/claims.
7. Tests must use generated ephemeral Ed25519 fixtures only and cover actual issue/verify; v1 JWT rejection even with a deliberately shared fixture key; wrong/mismatched key types and pairs; namespace/version/header/algorithm mismatches; missing, extra, and duplicate keys; invalid UUIDs and clocks; unsafe/negative timestamps, incorrect TTL, future issue and expiry boundary; malformed/noncanonical/oversize tokens; and tampered/wrong signatures. Do not place literal private keys or real personal data in fixtures.

The verifier's output is only a validated credential payload. It is not proof of an active session, current ownership, authentication context, or authorization. Any later runtime must separately validate the current session and owner in a reviewed v2 resolver. Keep all HTTP/session/authz/refresh/CSRF/idempotency, durable storage, schema, dependencies, provider, deployment, and production work out of this task.

The legacy JwtService accepts a different JWT header/payload contract and loose base64url parsing. Preserve it unchanged; the v2 verifier must reject its tokens semantically even where a test deliberately shares a signing key. ADR-0010 is contract-only and requires an isolated v2 issuer, audience, and key namespace; this review does not expand that acceptance into rollout or runtime approval.
