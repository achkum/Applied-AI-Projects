New qualified SQL012 may add a separately purposed bounded `login_proof` table, executor-only table RLS/grants, and the exact functions frozen in `platform-readiness.md`: `reserve_login(h,h,h,h,text,text,text,h,ms)`, `issue_login(login_scope,h,h,uuid,h,h,ms)`, `login_material(login_scope,h)`, `consume_login(login_scope,h,uuid,uuid,uuid,h,h)`, `fail_login_burn(login_scope)`, `prune_login(text,h,ms)`. Exact SQL bodies, grants, RLS and catalog pins must be frozen before source GO. ## Required login contract

Use direct private `https://localhost:3443`, loopback Host/TLS, exact configured Origin, one unambiguous host-only `st_v2_binding` cookie, canonical 43-character nonce header, session purpose, same chain/binding/epoch and one `Idempotency-Key` per mutating POST. Bootstrap a **fresh** session-purpose nonce; an enrollment nonce/proof/continuation/OTP or current session cannot be cast to login authority. `POST /v2/auth/login/simulator/verify` may accept exactly `{transport:'web',demoIdentity:'alice'|'bob'}` as a closed *simulator fixture choice*. It must not accept UUID, HMAC, subject, contact, asserted provider result, method, timestamp or prior-session selector. The trusted server verifier invokes the selected fixed fixture, checks method, exact expected fixture name/subject digest and fresh canonical `verifiedAt` after the await, then resolves only a live registered identity by that verified subject. Missing/deleted/foreign subject and failed verification collapse to safe generic failure with no account-existence oracle. The current verifier is Alice-only, so a narrow reviewed enrollment fixture choice for Bob is needed to create the second owner naturally; do not seed an identity/session to satisfy isolation.

The verify operation reserves a globally unique keyed burn in an independent short committed transaction, then issues a one-use `login/authenticate` proof with immutable verified owner, subject, issue/expiry and web binding. It consumes the original **unbound** session-purpose nonce and creates a successor **session-purpose** nonce with `authority_h=proof_h` on the same chain/cookie/Origin/epoch; return `200 {transport:'web',loginProof:'v2.<32-byte secret>',status:'verified',nextBrowserNonce}` under no-store. Both proof and successor nonce expire no later than five minutes after issuance; verification cannot renew an expired predecessor. `POST /v2/auth/session` accepts exactly `{transport:'web',loginProof}` with that successor nonce and its own globally unique burn. A duplicate key, pending/consumed proof, wrong purpose, stale/cross-chain/cross-cookie/Origin/epoch nonce, or mismatched owner must never produce credentials. Reject duplicate/framed headers, mixed cookies/Bearer, duplicate/trailing JSON, extra fields and query strings before authority work. No client-supplied owner identity enters the trusted SQL inputs. Align the proposed private errors with the platform note: closed 400 `INVALID_LOGIN_REQUEST`, 403 `AUTH_ORIGIN_REJECTED`, generic 409 `AUTH_RESTART_REQUIRED` for authority failures (including absent/deleted subject), 404 `LOGIN_UNAVAILABLE` only for disabled route and 500 `INTERNAL_ERROR` for unexpected adapter faults; contract/client reviewers must sign the exact outward matrix.

After trusted server subject resolution, terminal login rechecks the stored proof and bound nonce under locks, takes a live owner `FOR UPDATE` lock under `subtrack_runtime` with both equal transaction-local owner GUCs, and creates a fresh family/session/current refresh credential/current session CSRF. Proof+nonce deletion, owned burn completion and all session inserts commit **in the same transaction**. The proof issuer and terminal issuer may be separate requests/transactions; consumption and session issuance may not be separately committed. Do not use SQL010 enrollment issuance or the test fixture path. Access remains 15 minutes, session/refresh at most 24 hours, and CSRF is distinct from pre-auth nonce. Return the existing host-only Secure/HttpOnly/SameSite=Lax access/refresh/chain cookies plus in-memory readable CSRF and session ID only after an observed successful COMMIT and clean pool reset. Never return private profile, mode or subscriptions in the issuance response.

Lock order is frozen across reserve/verify/terminal and cleanup: **epoch → owned reservation → nonce digest(s) → login proof → verified-subject advisory lock if used → live identity → family/session/credential/CSRF**. Issue locks the old unbound nonce before proof/successor insert; terminal locks the successor nonce before proof. `login_material` and `consume_login` retain their locks on one connection and transaction. Provider/simulator work occurs outside locks; after each await, rematch source proof, nonce, clock, epoch and owner. Capacity is bounded to the adopted 10,000 live-state limit, with locked admission and safe expiry-only pruning. DB clock and persisted watermark govern validity; process clock rollback, key/manifest mismatch, missing bundle or pool role/GUC contamination fails closed. The separately committed reservation remains globally burned on known rollback; only its owned failed state may be settled after known rollback. On uncertain COMMIT, lost response or failed post-commit pool check, disclose no credential/CSRF, perform no compensating delete or mutation retry, and require a new bootstrap and verified login. Any orphan session expires or is later owner-managed. Log no raw secret, subject digest, PII, fixture personnummer, cookie or proof.

Only after a known new session does the client perform separate current-authority reads of persisted profile and persisted mode. A complete profile plus explicit `just-me` may mount ST-238 owner list/detail/status; missing/incomplete profile or absent mode resumes those existing explicit steps with no subscription call. Recheck current session/CSRF/owner on every private operation. Reload and `ENROLLMENT_LOGIN_REQUIRED` clear volatile proof/CSRF/private UI and offer fresh verification; no silent CSRF recovery or browser storage of bearer/proof/CSRF. Empty owner list remains truthful; no household/peer disclosure.

## Returning same-browser cookie predicate

The accepted `private-enrollment-http.ts` parses cookies and rejects every name other than `st_v2_binding` **before** dispatching `/v2/auth/browser-nonce`. A returning browser automatically sends its existing `st_v2_access`, `st_v2_refresh` (on `/v2/auth/*`) and `st_v2_chain` cookies, so that blanket predicate would prevent a fresh session-purpose bootstrap. Security approves this **narrow Type 2a wire correction within the same fresh-verification model**: only `POST /v2/auth/browser-nonce` with strict `{purpose:'session'}`, `POST /v2/auth/login/simulator/verify`, and `POST /v2/auth/session` may parse a unique, bounded, syntax-valid cookie roster containing `st_v2_binding`, `st_v2_access`, `st_v2_refresh`, `st_v2_chain`. The three old session cookies are inert on these pre-auth login routes: do not verify or look them up, derive owner/chain/CSRF from them, compare them to a prior session, or use them as proof. For bootstrap, any old binding cookie is also inert and replaced by a newly issued binding cookie; verification and terminal exchange require that new binding matched to the fresh nonce/proof. Missing old session cookies are allowed. Duplicate names, invalid framing/value syntax, unknown names and Authorization/Bearer alongside cookies remain rejected. The exception must be selected by exact method/path/body purpose, never by a broad `/v2/auth` prefix.

Existing enrollment/OTP cookie rejection and every authenticated current-session route's exact credential/CSRF checks remain intact. Bootstrap returns only its new binding cookie. Verify returns no session cookie. Terminal exchange sets the new access/refresh/chain cookies only after a known 201 commit; a rollback or uncertain commit never overwrites them. This correction is already within the platform roster's `private-enrollment-http.ts` and focused tests; no new role, grant, subject lookup, SQL function or security-model delta is authorized. Actual same-browser PG/TLS test must start with all three old cookies, complete fresh login, prove stale cookies cannot substitute for fresh binding/proof or authorize private reads, and inspect new cookie replacement only on known terminal success.
