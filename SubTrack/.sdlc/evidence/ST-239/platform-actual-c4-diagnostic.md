## What the C4 marker proves, and what it does not

EN light's closed receipt reports `FAIL ST237_BROWSER_CASE case=login phase=BOB_INCOMPLETE_LOGIN_PROFILE_RESPONSE navigation=200 patch=200 read=200` followed by the shell's browser failure and owned cleanup. In `startFreshLogin`, this phase is set immediately after clicking the login simulator action, while awaiting a `POST /v2/me/profile/read` **with status exactly 200**. The `read=200` field is cumulative from earlier profile responses; it is not scoped to the new Bob login. The marker therefore proves no matching fresh 200 profile response reached that wait before failure; it does **not** by itself prove that a profile request was sent, that a failed profile response occurred, or that the login session committed.

The pixel state narrows the execution path. `RegistrationFlow.runLogin` changes to `login-restart` only when it catches `LoginApiError('restart-required')`. `apps/web/lib/login-api.ts` creates that error only after strict `application/problem+json` HTTP 409 with `code=AUTH_RESTART_REQUIRED` from one of `POST /v2/auth/browser-nonce`, `POST /v2/auth/login/simulator/verify`, or `POST /v2/auth/session`. A profile read error in this same `runLogin` catch instead becomes `login-unavailable`. Thus **an auth restart on one of those three operations is source-supported by the screen**, while the exact first failing operation is not yet evidenced. A profile-read authority failure is not the leading interpretation of this C4 pixel. The old 200 profile/mode reads, Bob's enrolled default profile and the contact snapshot barrier do not prove the subsequent login operation succeeded.

`private-login-http.ts` maps `AUTH_RESTART_REQUIRED` to the same 409 for verification or session and masks internal cause. `DurableDevelopmentLogin` uses that one fail-closed signal for nonce/scope/reservation, trusted subject lookup, proof issue/consume, transaction rollback or unknown outcome. The separate bootstrap transaction can also produce restart at `browser-nonce`. `private-enrollment-http.ts` explicitly permits inert old session cookies for the returning-session bootstrap; that branch is relevant because Bob starts fresh login in the existing browser context after natural enrollment, but cookie presence alone establishes no defect. The fixture verifier and SQL012 `reserve_login`/`issue_login`/`consume_login` provide multiple possible 409 conditions. Choosing one as a fix without operation evidence would be a guess. The qualified PG login integration is gated after the browser case in the current proof shell, so C4's browser stop does not expose its later negative matrix.

**RLS lookup hypothesis independently ruled out at this exact head.** The checked-in C4 `verifySimulatorLogin` resolves `SELECT id,external_id FROM public.identity WHERE external_id=$1` under `this.tx('subtrack_identity_provisioner', ...)`, not `subtrack_runtime`. Business migration 0002 grants that role SELECT on exactly `(id,external_id)` and installs `identity_provisioner_select ... USING (true)`; the private launcher pins its role membership, ACL and policy. No owner GUC is needed for this narrowly privileged subject lookup. The later session transaction does switch to `subtrack_runtime`, but first gets trusted login material, sets both owner GUCs, and only then locks the live owner row. A missing GUC on the lookup is therefore **not** a source-supported C4 fix candidate; do not change roles or broaden RLS on that premise. This is a source conclusion, not a fresh PG result.
