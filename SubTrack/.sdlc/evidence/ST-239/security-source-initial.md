# ST-239 independent security source review — initial, blocking

2026-10-11. Scoped source review of the current uncommitted SQL012 and unfinished login API/HTTP. SQL012 SHA-256 **c91a4d806277da08ea14790a5dba494fa94b46834a9f82b9d6c59113bc07a631** at inspection. Accepted base is `85f8134b9fd2a79ab572825766a7928171c9801e`. This is **not** exact-head approval or an actual PostgreSQL/browser proof. I changed no product source and ran no tests.

## Findings, ordered by severity

1. **BLOCKER — live-owner row locks cannot execute under the present executor grants.** SQL012 `issue_login` lines 182–183 and `consume_login` lines 224–225 use `SELECT ... FROM public.identity ... FOR UPDATE` inside SECURITY DEFINER functions owned by `subtrack_auth_executor`. Accepted SQL010 lines 30–33 grant that role only `SELECT(id,external_id,deleted_at)` and a `FOR SELECT` owner-GUC RLS policy. PostgreSQL `SELECT FOR UPDATE` requires UPDATE privilege and applicable UPDATE RLS policy. The issuer therefore cannot perform its required live-owner lock; terminal consumption cannot either. The API's runtime row lock at `durable-development-login.ts:232–234` does not repair the issuer's separate transaction. Resolve within the frozen owner-scoped boundary and prove actual qualified PG issuance/consumption. If a new executor privilege is proposed, classify its exact access delta before adoption; do not widen identity enumeration or grant executor membership to the login role.

2. **MAJOR — expired-nonce pruning conflicts with the new proof FK unless cleanup is ordered.** SQL012 line 37 adds `login_proof.terminal_nonce_h` referencing `nonce(nonce_h)` (deferred FK). Accepted SQL007 `prune_nonces` lines 77–82 deletes every expired nonce; SQL012 `prune_login` lines 287–304 deletes expired proofs. Running the existing nonce pruner first while an expired proof still references its terminal nonce makes COMMIT fail. The current login API does not call `prune_login`. Define and exercise proof-before-nonce cleanup in every relevant path, with actual PG regression and capacity recovery. Deferred checking postpones the failure to COMMIT; it does not make the deletion valid.

## Scoped observations

SQL012 creates one separately purposed `login_proof` table with forced RLS and executor-only table grants. Its six named functions grant reserve/fail/prune to producer and runtime as frozen, issue only to producer, and material/consume only to runtime; no direct proof-table grant to either caller role was seen. `reserve_login` uses the global reservation primary key and pending state; `issue_login` and `consume_login` settle their owned burn in the same transaction as their proof/nonce changes. The issue and terminal functions fence epoch, manifest, DB clock/watermark, purpose, chain, binding, origin, proof expiry and stored owner. `consume_login` repeats a live subject comparison and performs family/session/credential/CSRF inserts plus proof/nonce deletion in one function transaction. These are source observations, not executable validation.

The unfinished API derives subject from the trusted verifier and provisioner lookup, obtains material under the proof/nonce locks, sets both owner GUCs, then asks SQL to consume. The private HTTP body and header parsers reject extra/duplicate JSON fields, duplicate header/cookie names, query strings, Bearer and unknown cookies; the three old session cookies are inert on the exact new login routes. Session cookies and readable CSRF are only sent after `createV2Session` reports committed; a post-commit token-issuer failure produces a generic 500 and no new credential response. The API source was explicitly unfinished at this checkpoint, with its first typing failure patched but not rerun and no tests yet. No broader verdict is implied.

Source verdict: **BLOCK** this SQL hash and API boundary until finding 1 is repaired and finding 2 has an executable cleanup order. Re-review the changed SQL hash, grants/RLS/catalog pin, and actual PG/browser evidence before any security approval.

## Narrow remediation classification (reviewed proposal, not installed bytes)

The storage author proposed an SQL012-only `GRANT UPDATE(id) ON public.identity TO subtrack_auth_executor` and a `FOR UPDATE` RLS policy whose `USING` requires **both** transaction-local owner GUCs to equal `id`, with `WITH CHECK (false)`. I agree this is the minimal row-lock remedy for the stated functions. Before it, executor can read the GUC-scoped owner but cannot lock that identity row. After it, executor can request a lock on only that GUC-scoped row; the false check denies an actual UPDATE result. The login role still cannot SET executor or query this table through executor membership. This is a concrete, bounded **Type 2a amendment** to the accepted trusted executor capability, not an arbitrary-principal lookup or general identity mutation grant. It must be source-reviewed and proven against qualified PG, including positive row lock and negative UPDATE. A suggested API runtime prelock would acquire identity before reservation and nonce, contrary to the frozen lock order, so I did not approve that alternative.
