# ST-239 C5 login SQL/source compatibility audit

2026-10-11. Read-only platform audit at exact C5 head `f915e34cbe9cfc5e4eb68ad9aaddd3e3f916bb32`, while the closed auth-status diagnostic run is pending. ST-239 remains `IN_REVIEW`; this is **not** a runtime diagnosis, source fix, source GO or qualified PG result. I inspected the committed `DurableDevelopmentLogin`, SQL001/003/004/005/007/008/010/012, enrollment subject hashing, private launcher composition/catalog pins and the qualified login integration source. No SQL, application source, backlog or status was edited for this audit.

| Boundary | Exact source comparison | Finding |
| --- | --- | --- |
| Legacy nonce and bootstrap purpose | SQL001 `nonce.purpose` admits `session`; SQL008 `issue_bootstrap_nonce` has its fixed `session` request hash; bootstrap transaction/port submit a session-purpose nonce; SQL003 `peek(...,'session')` selects that purpose. Login `witness` calls `peek` with `session`, matching the SQL012 issue/material/consume purpose checks. | No purpose/schema mismatch found. A live nonce can still fail on expiry, binding, epoch, manifest or watermark; source alone does not show which occurred in C5. |
| Reservation operation compatibility | SQL001 `reservation.operation` checks only nonempty text. SQL004's bootstrap uses `createV2BrowserNonce`; SQL012 `reserve_login` inserts `verifySimulatorLogin` or `createV2Session` with `authority_kind='login-chain'`, and `issue_login`, `login_material`, `consume_login` check the matching operation before settling. SQL005 pruning is expiry-based, not a hardcoded operation roster. | The older reservation table permits both new operation names; no static CHECK failure or operation-name mismatch found. |
| Key, scope and configuration | Login hashes nonce/binding with the same domain-form as enrollment, uses length-framed HMAC with `epoch.enrollmentKeys`, and the launcher passes the same verifier/key set, epoch, manifest and origin to enrollment/login. Login's `scope()` fields align in count/order with SQL012 `login_scope` and the `$1…$11` composite. `reserve_login` and all SQL012 transition functions compare the same epoch/origin/manifest and observed clock. | No obvious field-order, hash-key, origin or manifest mismatch found. Clock/epoch/capacity predicates can still legitimately deny a particular run; a closed actual operation is needed before narrowing them. |
| Trusted subject lookup and ACL | Enrollment stores `this.h('person','subject',[personnummerHmac])` as `identity.external_id`; login computes the same domain with the same `epoch.enrollmentKeys`. SQL010 grants `subtrack_identity_provisioner` SELECT `(id,external_id)` under `identity_provisioner_select USING(true)`. Committed login lookup uses that provisioner role. SQL012 `issue_login` then independently checks the live owner and subject under executor RLS after both server-derived owner GUCs are set. | The previously suggested unscoped `subtrack_runtime` lookup defect is ruled out by exact C5 source. The `source=MANUAL` feature has no bearing here. |
| Producer and runtime roles | SQL012 grants `reserve_login`/`peek` to the producer, `issue_login` to producer only, and `login_material`/`consume_login` to runtime only. Login source uses producer for witness/reserve/issue, and runtime for material/consume; before runtime owner lock it derives the owner from `login_material` and sets both GUCs. Launcher pins login role memberships and function/table ACLs. | No obvious caller/EXECUTE mismatch found. The existing integration source asserts cross-purpose role denials and a natural owner login, but the C5 browser stop occurs before that gated qualified PG matrix runs. |
| Proof and cleanup lifetime | SQL012 issues a terminal `session` nonce and `login_proof`, with the latter FK-cascading on terminal nonce deletion. SQL007 nonce prune selects only expired nonces; SQL012 material requires unexpired proof and nonce and consume removes both in one transaction. SQL005 reservation prune removes only expired burns. | No deterministic early-prune conflict appears in the source. Actual timing, capacity and a possible 409 route remain unknown. |

The C4 masked restart screen and `BOB_INCOMPLETE_LOGIN_PROFILE_RESPONSE` marker support a 409 restart on bootstrap, simulator verification or session before a matching fresh profile 200. They do **not** identify which operation or SQL predicate failed. C5's diagnostic is designed to emit only closed per-route status enums. If it shows `nonce=409`, inspect bootstrap issuance/reservation predicates; if `nonce=200,verify=409`, inspect login witness/reservation/subject/issue; if `verify=200,session=409`, inspect terminal nonce/proof/material/consume. This audit finds **no source-proven compatibility defect to fix ahead of that receipt**. Preserve the existing no-retry, one-use and unknown-commit behavior; any concrete change needs its own narrow evidence and independent security/QA review.
