## Client contract to freeze with platform and security

Use a real visible Log in link on Welcome in both locales and a real **Log in instead** action from the existing-subject enrollment stop. Both enter the same fresh login start with `POST /v2/auth/browser-nonce` `{purpose:'session'}` and a new binding chain. The agreed private simulator call is `POST /v2/auth/login/simulator/verify` with exact closed `{transport:'web',demoIdentity:'alice'|'bob'}`; `demoIdentity` is a **finite user-selected test-fixture choice**, not an asserted subject or provider result. The trusted server itself verifies the chosen fixed simulator result, fresh `verifiedAt` and live registered owner before issuing one-use authority. The client must not send a principal UUID, HMAC, asserted provider result, OTP, enrollment continuation or contact-to-owner mapping. Require unique idempotency, exact Origin, current nonce/binding, credentials and no-store; the proof producer does not issue session auth cookies. The 200 response must be exact `{transport:'web',loginProof:'v2.<secret>',status:'verified',nextBrowserNonce}`; the proof and successor nonce remain same-chain and memory-only. Then existing `POST /v2/auth/session` exact `{transport:'web',loginProof}` with successor nonce returns the known-committed 201 `WebSessionResponse` and current access/refresh cookies plus CSRF. Strict client decoding admits only these closed web responses, holds the CSRF only in a volatile ref and immediately clears the proof/nonce after exchange. Cookie secrets never enter JS, storage, URL or screenshots. Platform/security have scoped Type 2a approval of this finite-choice wire; the contract author must encode it in OpenAPI before client authoring, including exact status/problem matrix, nonce rotation and cookie paths. The natural second-owner proof must enroll the same Bob fixture that the login selector chooses; proof cannot substitute a client-supplied owner ID.

After known 201 completion, clear all login proof/nonce values, install the new volatile CSRF, then `POST /v2/me/profile/read` with `{}` and the current session cookie/CSRF. Independently call `POST /v2/me/mode/read` with `{}` under the **same** new authority; do not infer either from a prior enrollment state, login response, cookie, contact or local profile. Only `profileComplete:true` plus persisted `mode:'just-me'` may call `POST /v2/subscriptions/owner/read` `{}` and mount `PrivateSubscriptions`. For incomplete profile, show the returned existing profile in `ProfileEditor`; save only a deliberate user patch and reread before the mode gate. For `mode:null` with complete profile, present the existing explicit Just me choice; POST it only on action, reread persisted mode, then enter the list. Existing complete profile, contact and mode must never be overwritten by the login sequence. A truthful empty list still requires the authoritative `items:[]`, `nextCursor:null` response.

Reuse the accepted owner API and strict decoders: `readProfile`, `readMode`, `readOwnerSubscriptions`, `readOwnerSubscription`, `patchOwnerSubscription`. The current mode/list API requires 200 closed JSON, bounded fatal UTF-8, owner-only projection, no-store and session CSRF; login adapters need the same bounded strict response/problem parsing and explicit abort behavior. One in-flight login operation at a time; abort/generation-fence late producer/session/profile/mode responses on Back, locale navigation, restart and unmount. Duplicate clicks cannot create multiple sessions. Once a one-use login result is sent, a lost/unknown response cannot be retried or interpreted as success. Clear volatile authority and private projections, show a fresh-login restart action, and create an entirely new nonce/verification chain if chosen. Never replay a consumed login proof, refresh silently, recover a historical CSRF or announce a session from an uncertain response.

Reload must discard CSRF and private UI, and expose a keyboard-operable Log in action without carrying enrollment state. The same is required after `ENROLLMENT_LOGIN_REQUIRED`, expired current cookie, partial terminal credentials, server 401/403, deleted/missing registered subject, or malformed/untrusted result. Preserve the accepted ST-238 five cases and owner list/detail/status behavior; the return path must not route to sample `home` or sample subscription detail. Generic user-facing errors must not reveal whether an identity, account or subscription exists. A 409 login restart has a clear fresh-verification action; transient unavailable state can retry only by starting a new chain. No private profile/list/detail remains mounted after an authority stop.
