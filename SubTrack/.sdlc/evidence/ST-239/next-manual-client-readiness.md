## Complete owner journey and screen states

After fresh verified login, independently reread the complete profile and explicit `just-me` mode. Only then show the owner list and an **Add subscription** action even when the list is empty. Add opens a labelled form with name, approved category, one of five fixed cadences, SEK amount, and optional **next expected charge date**. Save is one user intent; on known commit, read the returned server ID through the authoritative owner detail endpoint, refresh the owner list, and focus a saved confirmation/detail heading. The row and detail must visibly say **Added manually** and **Expected amount**; a date is an expectation, never a paid charge. Fresh login after reload rereads profile/mode/list/detail from storage. Detail of an owner `source=MANUAL` row offers **Edit**; edit loads the exact current detail and its server revision, submits a full replacement of only the five editable fields, rereads detail/list, and keeps existing legal status actions separate. A stale edit shows a conflict, fetches the current detail, and asks the owner to review it before a fresh save; no automatic merge or overwrite. A status action must invalidate a prior edit token.

`RegistrationFlow` currently has `subscriptions-loading`, `subscriptions-list`, and `subscriptions-detail` only; `PrivateSubscriptions` renders a truthful empty message, rows, detail and legal status buttons, with no Add/Edit control. Extend the flow with explicit add/edit, validating, saving, rereading, saved, conflict and uncertain states. Keep `requestPending`, generation and AbortController discipline, and clear form, receipt key, CSRF and private projections on stop/unmount. Do not fetch mutation state from the public/static subscription detail route or infer mode from a list. Incomplete profile returns to its existing editor; absent mode returns to explicit Just me choice. No mutation form appears before both authoritative reads.

## Input and single-submission behavior

Freeze a closed contract first. Proposed body: `customName`, `categoryCode`, `cadence`, `expectedAmountMinor`, `nextChargeDate` (optional on create, explicit `null` to clear on edit), plus edit revision precondition. No owner, identity, currency selector, source, status, privacy, merchant, account, plan, charge or provider field from the browser. Name trims to 1–120 reviewed Unicode characters without controls. Category options use the approved stored taxonomy codes and existing translated category labels; cadence only `WEEKLY`, `MONTHLY`, `QUARTERLY`, `SEMIANNUAL`, `ANNUAL`. Currency is fixed `SEK`. Date accepts a real ISO calendar day or blank/null. The amount control should label **Amount (SEK)**, explain two decimal digits at most, and parse a deliberate ungrouped decimal input with string operations and `BigInt` into canonical positive minor-unit text, bounded by signed bigint max; no `Number`, `parseFloat`, `toMajorUnits`, or `fromMajorUnits` for validation. Reject zero, negative, exponent, thousands separators, excess precision, overflow and ambiguous locale input with field-specific errors. Use the reviewed contract/money parser once frozen; current `packages/money` exposes bigint arithmetic/formatting but no safe decimal-string SEK input parser, while `private-onboarding.ts` validates read-side canonical signed minor strings. Do not mistake those for the new positive write parser. Display amounts via existing `formatMinorUnits(BigInt(...), 'SEK', { locale, display: 'code' })`.

One save click allocates one high-entropy idempotency key and freezes an immutable canonical body, target and edit precondition. Disable double submit and form changes while pending. The mutation adapter must accept that key as an argument and preserve it across a same-intent recovery under current authority; `registration-api.ts` currently generates a fresh key per call and must not be reused for this behavior. On timeout, abort or masked/unknown result, never claim success or issue a new-key replay. While the same page and authority remain live, offer **Check this save** using the same key and exact request, then reread the returned ID/detail. If authority fails, clear private state and require fresh verified login. After reload the volatile key is gone: fresh login, list/detail review and a visible unresolved-save explanation precede a new Add attempt; no automatic duplicate submission. The durable receipt/server response semantics must be settled by platform/security, including same-key response status, retention and conflict code. A receipt conflict or stale revision shows a localized review state, not a guessed success. A known 400 field error retains the draft for correction with a new intent/key only after the user edits; 401/403 stops; 404 edit target returns to a safe owner-list view after reread; 409 mode/profile sends the owner through the authoritative gate. Mask unexpected response bodies and private payloads from UI diagnostics.

## Accessibility, localization and visual review

Add every string to `sv.json` and `en.json`; maintain parity and use `catalogs[locale]`. The existing `PrivateSubscriptions` component uses token CSS, semantic list/section headings, and `data-step-focus`; the new form should follow `ProfileEditor`'s native labels, `aria-invalid`/`aria-describedby`, field error alerts and focus to the first invalid control. On entry focus the form heading, on saving focus a status announcement, on conflict/uncertainty focus its alert, on confirmed reread focus the detail heading, and on Cancel restore focus to the originating Add/Edit button. Keep Enter submission and Escape/Cancel safe; busy buttons must remain visibly disabled. Test screen reader names for amount, category, cadence, date and all actions. Ensure light/dark token contrast, wrapped long names/large amounts and narrow viewport without overflow. Copy must distinguish manual entry from bank detection and expected charge from settled payment. Existing lifecycle status labels remain legal and unchanged.

## Open contract choices and readiness verdict

Platform proposes a monotonic UTC microsecond `updatedAt` token with changes to lifecycle status; security prefers a monotonic bigint revision. Client can carry either as an opaque exact server value, but the contract must choose one and prove status/edit cross-route invalidation before source GO. Likewise settle whether same-key replay returns 200 or preserves create 201, and whether list/detail expose the same provenance and revision needed by Add/Edit. The client does not synthesize revision or manual provenance from null merchant. Confirm the approved category roster and exact amount normalization in the contract, then derive form validation from it.

**Client/design: APPROVE TO PLAN, NO SOURCE GO.** A complete owner Add→persisted list/detail→fresh-login read→Edit/stale conflict→reread→legal status path is feasible within existing private screens.
