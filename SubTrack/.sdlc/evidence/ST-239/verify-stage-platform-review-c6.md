The new `VerifyStage`, `VerifyOutcome` and `VerifySqlstate` values are closed compile-time sets. `verifySimulatorLogin` creates stage/outcome/sqlstate **inside each invocation**, so concurrent login attempts do not share diagnostic state. The optional transaction callback is supplied only along this verification path (`witness`, `reserve`, subject lookup, issue), and is invoked inside `tx`'s existing catch after rollback handling. Its own exception is swallowed so a failed writer cannot replace the original fail-closed auth result. The outer catch writes one fixed-format line using only those enums and then calls the same `fail()`; it prints no identity, nonce, key, proof, cookie, CSRF, SQL, provider material, exception message or stack. The spec covers false issue, allowlisted SQL rejection, unknown commit, per-invocation reset and a throwing diagnostic writer while retaining `AUTH_RESTART_REQUIRED`.

Transaction outcomes are accurately separated: `ROLLED_BACK` is assigned only after known rollback and clean connection; `UNKNOWN_TX` covers failure before commit attempt without known clean rollback; `UNKNOWN_COMMIT` requires `commitAttempted=true` (including a lost COMMIT acknowledgement or failed post-commit clean). Existing `operate` still invokes `failBurn` only after a rolled-back operation and does so **after** the diagnostic callback has captured the original failure. Thus a cleanup failure cannot overwrite the recorded issue-stage SQLSTATE/outcome, and the burn/session proof behavior is unchanged. `RETURN_FALSE` is assigned only when `issue_login` returned false from a committed transaction. A generic reject remains `REJECT`; none of these labels claims the internal SQL predicate.

Unknown codes map to `OTHER`; absent/non-object values to `NONE`. This prevents arbitrary exception text or codes from reaching the receipt.
