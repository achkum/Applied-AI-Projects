## Recommendation and user boundary

Deliver **owner-entered manual subscription add and edit, persisted through the existing private Just me list and detail**. After fresh verified login, authoritative profile and explicit Just me gates, an owner can add an invoice/partner-card subscription without a bank connection, see it immediately in the owner list, open its detail after reload/fresh login, correct its name/category/cadence/SEK amount/optional next charge date, and use the already accepted legal status actions. An empty owner account must have a usable Add action. The UI must never imply that a manual entry was detected from a bank or that an estimated charge was paid. This is one complete F4.5/ST-086 experience, not just a write endpoint, form, or seeded fixture.

The more direct competing M1 path is My household/invites. It is important but requires shared membership/visibility, invitation acceptance, and the UF-02/03 privacy story; it is a larger trust and user boundary than the owner-only path already proven by ST-238 and being reopened by ST-239. The dashboard/review inbox depends on blocked ST-081 and other M3 work. Manual add/edit is the smallest next feature that turns the presently read-only owner subscription experience into one a private owner can populate and use. It remains within PRODUCT_SPEC F4.5 and the private/no-real-provider limits. Backlog ST-086 formally depends on ST-081, which is still `BLOCKED`; Conductor/product/architect must either define this narrower private owner child as an explicit dependency-safe predecessor, or clear the relevant ST-081 dependency. Do not silently call all ST-081 review/feedback/undo complete.

## Source basis and gap

- PRODUCT_SPEC F4.5 specifies manual subscriptions; BACKLOG_SEED ST-086 says add/edit after ST-081. API_CONTRACT already sketches `POST /v1/subscriptions (manual)` and explicitly says manual fields are future broader PATCH work, but OpenAPI currently contracts no manual creation/edit operation. The existing `/v2/subscriptions/owner/read`, `/v2/subscriptions/{id}/read`, and browser lifecycle PATCH have accepted private current-session/readback shapes.
- `Subscription` storage already has `source=MANUAL`, optional `customName`, optional merchant/account/plan/nextChargeDate, category, cadence, bigint amount, currency, status and `alwaysPrivate`. The migration has owner-matching RLS `subscription_insert`/`subscription_update` and runtime INSERT/UPDATE grants. That is storage capability, not a reviewed manual writer. Existing subscription repositories implement read and legal status transitions only. `PrivateSubscriptions` renders list/detail/status, with no Add/Edit control. ST-238's 51 rows are inserted by `tools/database/private-profile-proof.sh` as proof data, not user-created subscriptions.
- The contract and UI must start from the current ST-239 head *after* acceptance. The next slice must reuse current web authority, exact Origin/cookie/binding/chain/CSRF, independently persisted profile and mode gates, and owner-derived `RequestContext`; never accept an identity/household selector from the browser. Reload requires fresh login because historical CSRF recovery is not contracted. No real BankID, delivery, bank sync, spend, public route or production release is needed.

## Contract and data choices to freeze before source GO

Propose private `POST /v2/subscriptions/owner/manual` for create and `POST /v2/subscriptions/owner/manual/{id}/edit` for owner correction, both default-unavailable and mounted only in the pinned loopback HTTPS launcher. Contract-first Type 2a review should settle exact paths, closed request/response and problem matrix. Require the existing exact Origin/current-session/CSRF checks and a fresh `Idempotency-Key` bound to operation, request and authenticated owner on each mutation. Return a server-generated ID and current owner projection only after known commit; a lost/unknown commit response must not cause blind duplicate creation. Either implement durable idempotent result recovery under current authority or provide a safe read/reconcile UX before another attempt; simply returning a generic restart without finding a possibly committed new row would make manual create unreliable. This is a specific design gate, not an assertion that existing auth burn covers subscription writes.

Suggested smallest input is a nonblank bounded custom name, one approved category code, supported fixed cadence, positive integer minor-unit decimal string in SEK, and optional ISO date for next expected charge. Store `source=MANUAL`, `status=ACTIVE`, `always_private=true` by default; merchant/plan/paying account and charge links stay null. Edit only those manual fields on an owner-owned `source=MANUAL` row, with an explicit stale-update precondition (`updatedAt` or reviewed revision) so two tabs cannot silently overwrite each other. Validate money with `packages/money` and the approved integer-string wire; no JS floating arithmetic. If custom cadence, multi-currency, trial status, sharing, or inferred renewal computation is desired, architect/product must specify semantics before expansion. Generic 404 must hide foreign IDs; stale edits use a stable 409; malformed data 400; current authority failure 401/403 as existing private policy dictates. Confirm exact constraints and DB uniqueness/idempotency design against schema/migration before freeze.

This is not a new product-scope or real-provider decision. Contract/schema/idempotency changes are Type 2a under DECISION_RULES and need architect/platform plus security classification. A concrete expansion of who can see or change another owner's data would be a Type 1 security-model decision; the proposed owner-only RLS path does not require one by itself. Design reviews the Add/Edit flow and bilingual/focus states. No founder permission should be inferred merely from the current `IN_REVIEW` predecessor.

## Coherent acceptance and proof

Use an actual disposable qualified PG16 and the accepted ST-239 private HTTPS runtime. Naturally enroll/login a fresh owner with zero subscriptions, complete and reread profile/Just me, add one manual subscription in the UI, list and open its persisted detail, refresh via fresh login and reread it, edit its fields and independently reread, then apply an existing legal status action. Repeat for a second owner and prove the first cannot read/edit the second's row; deleted/expired/revoked authority, absent profile/mode, duplicate/foreign IDs and direct default/production routes fail closed. Prove atomic failure and concurrent duplicate create/idempotency behavior, stale edit conflict, large valid integer amount and invalid/overflow cases, RLS with both owner GUCs and pool reset. Preserve the ST-239/238 natural login and owner list/detail/status regressions, including truthful empty and 50/51 pagination. Assert no write from a read-only projection and no input-controlled owner ID. Browser QA should inspect sv/en × light/dark, keyboard focus, errors, loading, save confirmation and narrow viewport. Pin source/SQL/bundle and cleanup receipts as the accepted private proof already requires.

Provisional roster: product/architect freeze OpenAPI, generated bindings, API_CONTRACT and exact allowed paths; API author implements dedicated manual create/edit repository/service/private HTTP composition and targeted tests; storage reviewer handles only any necessary additive migration/catalog/grant pin; web author extends `PrivateSubscriptions` and `RegistrationFlow`/API adapter, both catalogs, tests and private launcher; independent platform/security/client/design/QA review exact source and actual PG/browser proof. Reuse accepted private authority and list repositories without modifying SQL001–012 or auth login unless an exact defect is demonstrated. No blanket source author path is approved by this note.

Estimate for this complete private add/edit slice: **1,600–2,600 nongenerated source/test lines, roughly L (2–4 hours of agent effort)**, low-to-medium confidence until the idempotency/SQL decision and exact roster are frozen. Many lower-level components exist, but none of those user journeys is established by the ST-239 login or this proposed manual entry alone.
