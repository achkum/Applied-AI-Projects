## Proposed closed contract to freeze contract-first

Use `POST /v2/subscriptions/owner/manual` and `POST /v2/subscriptions/owner/manual/{id}/edit`, private/default-unavailable in the pinned launcher only. Each requires one canonical `Idempotency-Key` (proposed 128-bit random UUID or equivalent 128-bit base64url; one new key per user intent), exact JSON, `Content-Type: application/json`, current CSRF and the accepted strict transport/header rules. Reject duplicate/unknown JSON keys and selector headers. A successful mutation returns only `{ "id": "<server-generated UUID>" }`, `Cache-Control: no-store`; client then performs the existing authoritative owner-detail read and refreshes the list. Initial and same-key replay may both return 200 with the same ID, avoiding a stored personal-data response snapshot. A different payload/operation/target/precondition under the same owner's key returns stable 409 `MANUAL_IDEMPOTENCY_CONFLICT`. Do not replay a 400/401/403 failure as success.

Create body has exactly `customName`, `categoryCode`, `cadence`, `expectedAmountMinor`, and optional `nextChargeDate`. Edit has those same five fields plus required `expectedUpdatedAt`; it is full replacement of the editable manual fields, with explicit `null` for clearing the optional date. `customName`: trim and require 1–120 Unicode characters after validation, with a reviewed normalization rule and no embedded control characters. `categoryCode`: exact approved `CATEGORIES.md` stored codes only, excluding listed excluded categories. `cadence`: `WEEKLY`, `MONTHLY`, `QUARTERLY`, `SEMIANNUAL`, or `ANNUAL`; `CUSTOM` needs separate semantics. `expectedAmountMinor`: canonical positive base-10 integer string, bounded by signed PostgreSQL `bigint` (1–9223372036854775807), parsed with `packages/money`/BigInt, never a JS number. Currency is fixed `SEK`. `nextChargeDate`: real `YYYY-MM-DD` calendar date or null; no inferred schedule or payment assertion. Freeze precise length/Unicode/date/amount schema in OpenAPI and generated validation before source work.

Create stores DB-generated `subscription.id`, trusted `identity_id`, `source=MANUAL`, `status=ACTIVE`, `always_private=true`, fixed currency and the accepted fields; merchant, catalogue plan, paying account, confidence/reasons and charges remain null/absent. Edit requires same owner and `source=MANUAL`, changes only the editable fields and `updated_at`; it never reactivates, detects, archives, shares, creates a charge, or changes provenance. Existing lifecycle PATCH owns status. Return identical generic 404 `SUBSCRIPTION_NOT_FOUND` for absent/foreign/nonmanual IDs. Wrong precondition is 409 `MANUAL_EDIT_CONFLICT`; invalid request is 400; auth/CSRF retains existing private 401/403 mapping; unknown storage outcome is masked 500 and the UI retains the key while live. The optional date does not mean a charge has been paid.

## Durable receipt and stale-edit mechanism

The checked-in `Subscription` Prisma model has a UUID DB default, `source=MANUAL`, `customName varchar(120)`, category `varchar(50)`, cadence enum, `expectedAmountMinor bigint`, `currency char(3)`, `nextChargeDate date`, `alwaysPrivate`, and `updatedAt timestamptz(6)`. It has **no idempotency table or revision column**. Business migration `0002_privacy_constraints` grants runtime subscription `SELECT/INSERT/UPDATE` and owner-matching insert/update RLS; private SQL011 forces RLS. `withRequestTransaction` sets both `app.user_id` and `app.current_user_id` transaction-locally. The private owner statement set already performs owner-qualified reads and status updates with `clock_timestamp()`. These are capabilities to reuse, not evidence that manual writes are approved.

Add a single append-only private `manual_subscription_mutation_receipt` table through new reviewed qualified SQL **after accepted SQL012**, with matching Prisma model only if Prisma accesses it. Proposed columns: `identity_id uuid NOT NULL`, `key_hash bytea NOT NULL` (SHA-256 of high-entropy key), `operation` closed `create|edit`, `request_hash bytea NOT NULL` (SHA-256 of versioned canonical exact-field payload, operation, edit target and expected version), `subscription_id uuid NOT NULL`, `created_at timestamptz NOT NULL`, primary/unique `(identity_id,key_hash)`. No raw name, date, amount, credential, cookie, CSRF, token, browser chain or request body goes in a receipt or log. Key uniqueness spans create and edit for an owner. FK to owner and subscription must preserve receipts for the agreed retention period; avoid cascade deletion or unrelated cleanup that could permit later duplicate replay. Choose documented retention and any pruning only after product/security review; default is no automatic prune in this private slice.

Inside one `withRequestTransaction`, the repository checks owner profile+mode and looks up the owner/key receipt first. A matching receipt returns its ID; a mismatched digest is 409. If absent, create/edit the subscription, then insert an immutable receipt with the resulting DB-generated subscription ID **in the same transaction**. No receipt can commit without its subscription effect, and a rolled-back mutation leaves no receipt. Concurrent same-key writers serialize at the unique constraint: the loser rolls back its whole transaction, then starts a fresh owner-scoped transaction to read the winner's committed receipt and compare the digest. This also resolves a race where a same-key edit initially sees a stale version because the first writer won. A failed first transaction frees the key for a legitimate retry. If the HTTP response is lost after commit, retrying the **same key and exact body under freshly verified current authority** returns that ID. Do not create a new key for an uncertain in-page attempt. After reload, when the volatile key is gone, require fresh login and owner list/detail reconciliation before presenting a new Add action; never automatically resend a new-key copy of the uncertain entry. Keep all receipt operations owner-scoped by RLS, FORCE RLS, a non-bypass runtime role, no PUBLIC access and a least-privilege SELECT/INSERT grant; no runtime UPDATE/DELETE on receipts. Pin role, policy, grants and catalog at startup and prove cross-owner and pool-reset behavior on disposable PG16.

Use existing `subscription.updated_at` as the edit token, **exposed on the owner detail response** as canonical UTC microsecond text. A client submits the exact last detail value in `expectedUpdatedAt`; inside the same owner RLS transaction, `UPDATE ... WHERE id=$id AND identity_id=$owner AND source='MANUAL' AND updated_at=$expected` changes only allowed columns and sets `updated_at=GREATEST(clock_timestamp(), updated_at + interval '1 microsecond')`. A zero-row update is classified via an owner-qualified lookup as 404 or 409, never by exposing foreign existence; before returning 409, recheck a same-key receipt in a fresh transaction so a concurrent replay can recover the winning result. This timestamp rule prevents two rapid edits from sharing a version. The existing private lifecycle status statement currently uses bare `clock_timestamp()`; it must adopt the same monotonic expression so a status action always invalidates an older edit token, including within one microsecond or after clock adjustment. Re-read detail after success or conflict. Because existing owner list/detail projection omits `updated_at`, both contract and private statement/validator must change; a UI-only token is insufficient. Qualified PG proof must exercise same-microsecond and two-tab races. If accepted ST-239 changes this storage or projection, revisit the token choice rather than assume the snapshot remains valid.
