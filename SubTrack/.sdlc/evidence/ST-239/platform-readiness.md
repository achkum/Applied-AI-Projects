## Proposed frozen private wire and state sequence

1. Welcome `Log in`, reload, and `ENROLLMENT_LOGIN_REQUIRED` enter a clean login state. `POST /v2/auth/browser-nonce` with `{purpose:'session'}`, unique `Idempotency-Key`, exact `Origin: https://localhost:3443` returns a new public nonce and distinct `st_v2_binding` Secure/HttpOnly/SameSite=Lax host-only cookie. Do not carry an enrollment continuation, proof, OTP, nonce, chain or CSRF into login. The existing endpoint and binding cookie are reused unchanged.
2. **New private development-only** `POST /v2/auth/login/simulator/verify`: exact JSON `{transport:'web',demoIdentity:'alice'|'bob'}`; exact Origin, current `X-Browser-Nonce`, binding cookie and fresh Idempotency-Key; no access/refresh cookies or session-CSRF. The server calls its allowlisted simulator outside DB locks, validates a fresh trusted result, computes the accepted subject digest and resolves only an existing registered identity using the provisioner's existing `SELECT(id,external_id)` authority. A separate ordinary owner-scoped live/deleted check is mandatory. No contact/profile/mode write. An independently committed global burn precedes simulator work. The issue transaction locks epoch/owned burn/old session-purpose nonce, rechecks clock/epoch/cookie/chain/Origin and live owner, deletes the old nonce and creates an authority-bound successor **session-purpose** nonce and a separately purposed one-use login proof. Response `200 {transport:'web',loginProof:'v2.<opaque 32-byte secret>',status:'verified',nextBrowserNonce:'<opaque 32-byte nonce>'}`; `Cache-Control:no-store`, `Pragma:no-cache`; no identity data. Proof expiry is at most five minutes and no later than trusted verification source; successor nonce keeps the existing exact five-minute TTL. Duplicate/lost issue response never replays the proof.
3. Existing `POST /v2/auth/session` in this private launcher accepts exact `{transport:'web',loginProof:'v2.<opaque 32-byte secret>'}`, successor `X-Browser-Nonce`, same binding cookie, exact Origin and new global Idempotency-Key. Its burn operation and authority kind are login-specific. A single READ COMMITTED transaction takes epoch/owned reservation/proof/successor nonce locks in fixed order, obtains only the proof's stored owner, sets *both* server-derived owner GUCs, locks and checks the live identity, then creates new family/session/current credential/current CSRF, conditionally consumes proof and nonce, and settles that burn. Concurrent redemption yields at most one committed session. Never call the simulator inside this transaction. The existing `st_v2_access` (`Path=/v2`), `st_v2_refresh` (`Path=/v2/auth`) and `st_v2_chain` (`Path=/v2`) Secure/HttpOnly/SameSite=Lax host-only cookies, plus readable session-bound CSRF in `WebSessionResponse`, are sent only after known COMMIT and clean pool state. Access remains 15 minutes/session 24 hours. A known rollback may fail only the owned burn; unknown COMMIT/lost response discards local credentials and starts fresh verified login, with no replay, retry, compensation or response cache.
4. After known login, run independent current-authority profile read (`POST /v2/me/profile/read`) and mode read (`POST /v2/me/mode/read`) with that new session, exact Origin/binding/chain and current CSRF; decode each strictly. Complete profile **and** persisted `just-me` permit ST-238 owner list/detail/status. Incomplete profile resumes the existing explicit profile step; absent mode resumes explicit mode choice after profile completion. Missing, inconsistent or failed reads disclose no subscription view. Empty list remains truthful. Reload drops volatile CSRF and private data, offering fresh login because current-session CSRF recovery is not contracted.

Use the accepted private wire parser's duplicate-header/body rejection, loopback TLS/Host gate, no-store problem+json and generic `409 AUTH_RESTART_REQUIRED` for invalid/spent/expired/deleted/cross-purpose/duplicate/unknown authority. Keep `403 AUTH_ORIGIN_REJECTED` for exact-Origin rejection, `400 INVALID_LOGIN_REQUEST` for syntax, `404 LOGIN_UNAVAILABLE` when development route is disabled, and `500 INTERNAL_ERROR` only for unexpected adapter faults; these *proposed* code names and 200/201 envelopes require contract/client/security signoff before source GO. No sensitive distinction between missing, deleted or foreign subject. The login route stays unavailable outside explicit private development HTTPS and production/default routes remain closed.

## Final signature, lock and wire freeze for source GO

The nine `reserve_login(h,h,h,h,text,text,text,h,ms)` arguments are respectively `key_h, owner_h, authority_h, request_h, operation, origin, epoch, manifest_h, observed_ms`. `login_scope` has exactly eleven ordered fields `key_h, owner_h, authority_h, request_h, nonce_h, binding_h, origin, chain, epoch, manifest_h, observed_ms`; all digest fields use `subtrack_auth.h`, observed time uses `subtrack_auth.ms`. `authority_kind='login-chain'`, `transport='web'`, exact private Origin and accepted pinned epoch/manifest are server literals. The only operation literals are `verifySimulatorLogin` and `createV2Session`; their keyed request digest includes operation, strict body, browser chain, nonce and cookie binding. There is no generic operation/purpose argument accepted by issue, material or consume. `issue_login(login_scope,h,h,uuid,h,h,ms) RETURNS boolean` takes proof_h, terminal_nonce_h, identity_id, subject_h, session_binding_h, verified_at_ms in that order. `login_material(login_scope,h) RETURNS uuid` takes proof_h. `consume_login(login_scope,h,uuid,uuid,uuid,h,h) RETURNS boolean` takes proof_h, stored identity_id, session_id, family_id, refresh_h, csrf_h. `fail_login_burn(login_scope) RETURNS boolean` and `prune_login(text,h,ms) RETURNS boolean` take respectively only the scope, and epoch/manifest_h/observed_ms. These six signatures and roles in the matrix above are the freeze; no open-ended signature choice remains.

Both issue and terminal paths use this lock order where objects exist: **epoch → owned reservation → nonce digest(s) → login proof → verified-subject advisory lock if used → live identity → family/session/credential/CSRF**. Issue locks the old unbound nonce before inserting proof/successor; terminal locks the authority-bound successor nonce before proof. `login_material` and `consume_login` keep locks on the same transaction connection; a failed rematch rolls back. Producer's subject lookup uses the existing provisioner `SELECT(id,external_id)`, then the executor's SQL010 identity SELECT only with both server-derived owner GUCs set, comparing `external_id=subject_h` and `deleted_at IS NULL` under row lock. No operation in this order calls the simulator under a database lock.

The new verify endpoint returns **200** with the exact body and no-store headers stated above. Existing private `/v2/auth/session` returns **201** and the existing `WebSessionResponse` `{transport:'web',sessionId,csrfToken}` with current cookie paths/attributes and no-store headers; it does not add identity/profile/mode fields. Private login extensions use `400 INVALID_LOGIN_REQUEST` for malformed wire/body, `403 AUTH_ORIGIN_REJECTED` for exact-Origin/host binding rejection, `404 LOGIN_UNAVAILABLE` for disabled route, `409 AUTH_RESTART_REQUIRED` for missing/deleted/foreign/expired/spent/cross-purpose/duplicate/unknown authority, and `500 INTERNAL_ERROR` for unexpected adapter failures. Do not expose SQL or owner distinctions. Existing OpenAPI default/mobile references and headers remain intact; contract edits add only the private development verify route and the precise private availability refinement to the existing web session operation, plus explicit closed simulator choice on enrollment verify. Security has concurred; client/contract signoff is the remaining cross-role wire gate.

### Same-browser stale-cookie gate and proof custody

The accepted `private-enrollment-http.ts` cookie guard currently rejects `st_v2_access`, `st_v2_refresh` and `st_v2_chain` before even handling `/v2/auth/browser-nonce`. Freeze one narrow private-login exception: only `POST /v2/auth/browser-nonce` with strict `{purpose:'session'}`, the new `POST /v2/auth/login/simulator/verify`, and the private `POST /v2/auth/session` may receive the parsed allowlist `st_v2_binding`, `st_v2_access`, `st_v2_refresh`, `st_v2_chain`. For those three routes, the old access/refresh/chain cookies are **ignored completely**: no lookup, principal resolution, chain adoption, CSRF check, expiry interpretation or credential reuse. Browser nonce bootstrap creates a fresh nonce and replaces binding; verify/session use only that new binding and nonce/proof chain. Duplicate names, unknown names, missing/invalid required fresh binding, malformed cookie framing, Authorization/Bearer and forbidden proxy/method headers still reject. The old three cookie values may be expired or noncanonical yet cannot choose an owner or affect login; they are never copied into the new chain. No new auth cookies are sent at verify or before known terminal COMMIT; the 201 session response replaces them. OTP/enrollment and current-owner route guards are unchanged. This exact exception is part of the client/security contract and Type 2a review, not a general relaxation of cookie authentication.

Add to the exact tests already rostered: same browser with old valid session cookies; old expired and malformed-canonical-value cookies; different old owner cookies; duplicate/unknown/framing/Bearer rejection; old cookie non-use before 201; new binding/proof-only owner resolution; rollback/uncertain commit preserving no disclosed new credentials.
