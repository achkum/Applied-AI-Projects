## Source verdict: BLOCK pending exact startup identity ACL/RLS gate

The two initial SQL blockers are repaired in the inspected SQL012 bytes. `GRANT UPDATE(id)` to executor plus `identity_login_executor_lock` uses both owner GUCs in its `FOR UPDATE USING` and `WITH CHECK(false)`. No login-role executor membership is added. `login_proof.terminal_nonce_h` now has `ON DELETE CASCADE DEFERRABLE INITIALLY DEFERRED`. Every proof expiry is capped at or before its bound nonce expiry; legacy `prune_nonces` deletes only expired nonces, so cascade cannot evict a live proof. `prune_login` deletes only expired proofs. The terminal consume deletes its proof before the bound nonce. This resolves the static cleanup conflict; actual PostgreSQL positive/negative proof remains required.

**Remaining source finding:** `apps/web/private-https-server.mjs` `LOGIN_IDENTITY_LOCK` checks absence of a table-wide executor UPDATE and UPDATE on only `external_id` and `deleted_at`, and checks only the named new policy. It does not enumerate all `public.identity` column grants or the full identity policy roster. A post-install executor `UPDATE(email)` grant or extra permissive identity policy can pass that startup check, violating the frozen exact ACL/RLS assertion and potentially widening the trusted executor boundary. Pin the exact `public.identity` ACL and policy set at startup (including the sole executor `UPDATE(id)` and the existing policies), then add a drift-denial startup test. Existing migration and SQL file hashes do not detect post-install catalog drift. This is a qualification gap, not evidence that SQL012 itself grants the extra access.

## Other inspected boundaries

SQL012 limits the new proof table to executor table grants; producer gets reserve/issue/fail/prune, runtime gets reserve/material/consume/fail/prune, and both caller roles have no direct proof-table grants. The issuer locks its own reservation and original session nonce before locking and checking a live owner/subject; terminal material and consume use the bound nonce and proof, then create family/session/credential/CSRF and settle the owned burn in one transaction. Function bodies, signatures, grants, auth table shape/policies, and the SQL012 source hash are compared by the launcher against its pinned inputs. The proof shell records source/build digests and compares them at finish, but these gates have not run in this review.

The API calls the closed trusted simulator verifier, computes a domain-separated subject digest, looks up a candidate only through provisioner authority, and lets SQL recheck the live owner under both transaction-local GUCs. Its terminal path derives owner from locked proof material, uses a separate runtime owner lock, and releases credentials to HTTP only after a known clean COMMIT. Unknown COMMIT discards local credentials and does not replay the mutation; known rollback may settle only its own burn. Pool cleanup discards an unclean connection. Private HTTP checks the exact Origin, body, cookie/header and nonce shape; old session cookies are inert on the two new login routes; session cookies and CSRF appear only on the 201 response after commit. These are source observations, not executable results.

It does not yet establish all required direct-call boundary, race, deleted/foreign owner, rollback, capacity, clock/epoch, pool-reset and private HTTP negative evidence.
