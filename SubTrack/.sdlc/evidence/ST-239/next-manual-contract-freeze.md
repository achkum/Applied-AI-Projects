## Append-only create receipt; revision deferred

The current private `ownerStatusCompareUpdate` sets `updated_at=clock_timestamp()`, while the older `SubscriptionLifecycleRepository.apply` sets `updated_at=NOW()`. Their disagreement matters for a future stale Edit, **not for Add-only**: this child performs no manual-field update, so it adds no `revision` column, update trigger, edit precondition, status-statement rewrite or revision projection. The later Edit child must choose a monotonic bigint revision, advanced by every manual edit **and both existing legal status mutation paths** (a reviewed database trigger is the likely minimal cross-route mechanism), rather than relying on timestamp resolution. That future proposal from the earlier full-slice note is retained as planning, without source approval or schema work now.

SQL013 creates `manual_subscription_create_receipt` with `(identity_id, key_hash)` unique/primary key, `request_hash` of a versioned canonical create payload, `subscription_id`, and creation time. Keep operation purpose fixed to `manual-create-v1` in the digest/domain so a future Edit cannot accidentally share this key space. Key hashing uses SHA-256 over the high-entropy canonical key; hash no secret, raw key, name, amount, date, CSRF, cookie or request body into logs/evidence. Receipt rows are immutable to the runtime role: only owner-scoped SELECT/INSERT, FORCE RLS, no UPDATE/DELETE, no PUBLIC rights, no SECURITY DEFINER shortcut. The digest equality check is scoped by authenticated owner; a mismatch yields the stable 409 without leaking another owner's receipt. The receipt's ID alone is the immutable success snapshot for create.

**Retention: no automatic pruning while the owner account exists.** Keep the receipt across app restart, session expiry/revocation, subscription status changes and any later subscription-row deletion, so the same key cannot create again after a lost response. Avoid an FK from receipt to subscription that cascades/deletes or blocks that lifetime; keep `subscription_id` as an immutable result reference. Owner hard erasure may remove receipts as part of the same controlled data-erasure action; the erased owner cannot authenticate to replay. If product/security later requires bounded retention, that is a separate contract change with an explicit duplicate-risk policy. An owner may retry the exact key/body under a newly verified current session; the client retains the key only while the page is live. After page reload the volatile key is gone: fresh login and list/detail reconciliation precede any new Add, with no automatic new-key resend of an uncertain attempt.

Under the current `DurableCurrentWebAuthority.transact`, the owner `identity` row is locked `FOR UPDATE` before business statements and remains locked through commit. This **serializes same-owner mutation transactions**, so the repository can read the owner/key receipt first, insert a previously unseen subscription and its immutable receipt in the same transaction. A concurrent same-key request waits on the owner lock, then sees the committed receipt and returns its stored ID; if the first rolls back, the second proceeds. Keep the unique index as a database backstop. No separate burn, compensating write, mutation replay after uncertain commit, or second transaction for success is needed. On unknown commit, disclose no success and discard the uncertain connection; a later exact-key retry reauthenticates and deterministically checks the receipt. The authority's current masked exception path is a known implementation detail: the new HTTP adapter must distinguish invalid current authority from a masked storage/commit outcome only through a reviewed typed boundary, never by exposing SQL errors or treating an uncertain commit as 401.
