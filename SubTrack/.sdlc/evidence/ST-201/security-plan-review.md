# ST201 independent security plan review

## Decision

**Classification: Type 2a (architecture), not Type 1. Plan disposition: approve the narrow development-only design, subject to the conditions below and independent implementation review.** DECISION_RULES defines Type 1 as a one-way door involving a security-model change; it does not classify every security-sensitive runtime adapter as Type 1. This proposal uses the already-established current mobile access principal, session ownership, deletion-only proof producer, idempotency guard, and accepted `/v2` contract. It adds no authentication mode, authority kind, public endpoint, default wiring, provider, or deletion behavior. The endpoint is cross-cutting runtime integration of an accepted contract, so Type 2a is appropriate. The security reviewer retains veto authority for a High or Critical finding; that does not substitute for founder approval if the design changes the security model.

The ST200 prerequisite is satisfied by `/workspace/.setup/ST200-accepted-main-receipt.json`: accepted source `fe56d65ec4b168518c64dc2c4c2c6210e4bf2a4e` is recorded on `main` at `11f6368ecead21e61d658bfe3a16dfe0c9533ab0`, with all 34 CI steps passing, 15 focused tests, 1,029 API tests, lint/typecheck/build/gitleaks passing, and platform/security source reviews approved. This clears the plan's ST200 hard gate only; it is not ST201 implementation approval or a production-release approval.

## Conditions that must remain exact

- Expose only `POST /v2/me/reauth/otp/start` from an explicitly registered development module. Require all three gates: environment is exactly `development`, feature `enabled` is exactly `true`, and `AUTH_DELETE_OTP_DEV_ONLY` is exactly `true`. Capture and validate configuration at registration and fail closed. Keep the module out of default application wiring.
- Require the accepted endpoint's JSON body to be exactly `{ "channel": "sms" | "email" }`. “No method selector” means no authentication-method or BankID-versus-OTP selector. `channel` is expressly part of the existing `DeleteOtpStartRequest` schema and is not a method selector. Resolve the registered deletion contact only from the authenticated server-side principal; require the requested channel to match that registered channel before reserve, quota charge, or challenge creation. Do not use caller-provided identity, identifier, contact, or environment values to choose authority or destination.
- Preserve the mobile transport branch as exactly one Bearer authorization value, no cookies of either kind, and no competing credential branch. Reject duplicate, malformed, mixed, or unknown credential observations. Require direct TLS (`request.secure` and TLS socket), and reject Origin/nonce/CSRF/XSRF headers, caller identity aliases, query strings, extra JSON fields, transfer encoding, duplicate/noncanonical content length, and noncanonical or oversized credential/body input before unsafe work. The facade is a development reference and is not proxy/provider/client ready.
- Resolve authority through the existing server-side V2 verifier, principal resolver, current owned mobile session row, and registered-contact reader. Preserve freshness checks and repeat current-token/current-row checks after each asynchronous boundary. A current row check must be immediately before each unsafe synchronous core operation; do not insert an `await` between that final check and the operation. Revalidate after reserve before challenge creation, after challenge creation before private sink, and before settle/response as specified. Do not claim atomicity across database, proof, or HTTP boundaries.
- Apply the bounded HTTP request throttle before idempotency reservation, then reserve before challenge/code creation. Bind reservation to operation, mobile transport, verified-principal HMAC authority (verified identity, session, server-resolved identifier hash, and channel), and canonical `{channel}` request hash. Use the existing synchronous idempotency guard without changing its replay semantics. Duplicates remain generic `409 AUTH_RESTART_REQUIRED`; never return an earlier challenge or result. The local throttle is a supplemental bound; retain the existing proof producer's core throttle.
- The start operation must remain synchronous and produce a strictly validated challenge id, six-digit code, and expiry no more than five minutes ahead. Store the code only through a private, local, synchronous development sink, with no public inbox/admin route, logging, provider, delivery, or code in any response. Return exactly `202` with `{ "challengeId": ..., "status": "accepted" }`; include no code, proof, token, expiry, cookie, or delivery assertion.
- Map only a genuine local per-identity/global quota rejection to `429`. Add a narrow typed error for that actual rejection. Do not classify port-thrown lookalike errors, capacity exhaustion, configuration/clock failures, or proof-port failures as quota; those remain generic failures. Keep malformed/raw request failures `400`, stale/invalid authentication `401`, registered-channel mismatch `403`, duplicate reservation `409`, and unexpected trusted-port/capacity/response failures generic `500`, with no secrets or PII in error details.
- Treat reserve, start, sink, settle, and response failures as potentially occurring after prior local state committed. Never roll back or restore challenge, throttle, or idempotency state; never retry, replay, clear unrelated cookies, or guess cleanup. A challenge created before a later sink/settle/response failure can remain a bounded five-minute orphan. Best-effort failed settlement is allowed only for a known owned reservation and must not mask the primary failure. If headers were sent, do not attempt a second response.

## Implementation review gates

Implement only the four proposed adapter/module/spec files and the narrowly scoped producer error export/spec change. Do not change OpenAPI, defaults, dependencies, providers, database, deletion flow, or clients under this plan.

Independent security review of the implementation must inspect transport ambiguity, strict raw HTTP validation, fresh-row ordering, throttling/idempotency ordering, quota classification, private sink behavior, failure windows, and absence of secrets/PII. Exercise the actual HTTPS module against a real local CA and existing verifier/session/contact/proof/idempotency components; test mismatch and malformed-input rejection before reserve/create, duplicate non-replay, session revocation/deletion at each awaited boundary, quota versus capacity/forged error, and sink/settle/response failures. Require repository security-source review and CI before merge. Evidence must not imply real SMS/email delivery or production readiness. Accepted prior Type 2a router work is precedent for reversible protected API integration; it does not grant production-release approval.

## Scope boundary and escalation

This plan does not authorize real SMS/email delivery, provider integration, public/private inbox exposure, actual deletion, default app wiring, client integration, or changes to accepted contract semantics. Any change that creates a new authority kind/authentication mode, changes principal or proof semantics, exposes a new public port, wires this into default runtime, or alters deletion semantics changes the security model and must stop for Type 1 founder decision under DECISION_RULES (including the applicable D-05/D-12 gate). A High or Critical security finding blocks merge unless the founder overrides it in writing under the Constitution and DECISION_RULES. Any proposed change to endpoint/body/channel interpretation, transport requirements, ordering, status mapping, or failure behavior also requires renewed review rather than a silent adjustment.
