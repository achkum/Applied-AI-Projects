# ST201 platform plan review

**Disposition: classify as Type 1 before runtime implementation; plan only.** The existing `/v2/me/reauth/otp/start` route and `{channel: sms|email}` body are already in the accepted OpenAPI contract, so this proposal does not itself require an API contract change. However, ADR-0010 explicitly leaves runtime implementation and security review for a separate task. ST201 would activate a security-sensitive authentication, idempotency, and challenge-creation path for account deletion where the accepted system currently has only a contract. `DECISION_RULES.md` §1 places changes to the security model in Type 1, which requires founder decision. The fact that the path is opt-in, development-only, and reversible reduces exposure but does not make activation of that security model a module-local implementation choice. Do not begin implementation until the founder's Type 1 decision is recorded. If the founder approves the model, its implementation details can proceed within the existing contract and explicit gates below.

The ST200 accepted-main gate is now evidenced by `/workspace/.setup/ST200-accepted-main-receipt.json`: main is `11f6368ecead21e61d658bfe3a16dfe0c9533ab0`, all 34 CI steps passed, and platform and security source reviews approved. This removes the former ST200 gate blocker. Preserve the remaining stated dependency and require the final implementation review, QA, and CI before merge.

If approved, keep the endpoint exclusively registered by the explicit development `Module.register` configuration and fail closed on every other configuration. Derive identity, session, and registered contact from the verified current mobile principal through the existing authority resolver. The only caller-selected field is `channel`, because the existing request schema requires it. Require it to equal the server-resolved registered channel; mismatch must fail before idempotency reservation, challenge creation, or quota charge. Do not use it to select a different contact. Do not add identity, identifier, environment, method, or transport selectors.

Preserve the exact mobile credential branch: one Bearer authorization header and no cookies of any kind. Retain strict request framing, direct TLS, no-store responses, and generic parser/credential failures. No default-module registration, OpenAPI/generated-client edits, provider or delivery integration, database changes, or deletion/client behavior changes belong in this slice.

The mutation ordering is a required security property: verify the current principal and owned mobile session; enforce the bounded HTTP retry throttle; synchronously reserve idempotency using the verified-principal digest and canonical `{channel}` request hash; recheck token/session; synchronously invoke the existing OTP producer; recheck token/session; synchronously store the code only in the private development sink; then recheck and synchronously settle the reservation before returning the exact 202 response. Do not insert an await or other asynchronous boundary between the last current-session check and a synchronous unsafe mutation. Preserve the existing producer's own throttle and quota semantics. Only a locally established quota rejection may map to 429; capacity/configuration/clock/proof-port failures and port-thrown lookalike errors must remain generic failures.

Failure semantics are required: reservation duplicates never replay prior results; a created challenge, consumed quota, or locally stored code is never rolled back or retried after a later failure; unknown outcomes may leave a bounded orphan; no compensating delete, fallback, or secret-bearing response is allowed. Settle failure best-effort only for the known owned reservation and never mask the primary error. The 202 body is exactly `{challengeId, status: accepted}` and must not claim delivery or expose code, proof, token, or expiry. A real SMS/email provider, public inbox, or client integration requires a separate reviewed task and any applicable founder approval.

Before merge after the Type 1 decision, require focused security review and the specified HTTPS/API QA for credential exclusivity, channel mismatch, replay, stale/revoked session, quota-versus-capacity mapping, hostile ports, and post-mutation failures. Keep the endpoint outside the default module and verify no change to the contract or account-deletion/client behavior. If implementation requires a contract or security-model change beyond the founder-approved decision, stop for another decision rather than weakening these conditions.
