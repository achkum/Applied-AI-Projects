Keep existing `POST /v2/auth/browser-nonce`, `/otp/start`, `/otp/verify`, `/enrollment/pending`, `/enrollment/simulator/verify`, `/enrollment/complete` request/response shapes in `packages/contracts/openapi.yaml`. Do not return raw private handles or invent provider fields. The trusted verifier result remains server-owned; the client sends only the contracted `transport`, `identifierProof`, `continuation` or `verifiedEnrollment` envelope. Terminal response is existing `WebSessionResponse` with session ID/current CSRF only; postcommit access/refresh go into distinct host-only Secure/HttpOnly/SameSite=Lax cookies at `/v2` and `/v2/auth`, with no refresh JSON.

Add contract-first `GET /v2/me/profile` and `PATCH /v2/me/profile` using the already accepted exact `ProfileView` and `ProfilePatch` schemas in `packages/contracts/profile.ts`; regenerate checked-in bindings and add contract tests. GET has no body and returns only the closed view. PATCH requires exactly one JSON object with at least one permitted field, returns the updated closed view, and never accepts `profileComplete`, `defaultCurrency`, owner/identity/contact/trusted names/verifiedAt/session/household fields. Server computes `profileComplete` from persisted canonical display name after write. Keep `defaultCurrency: SEK` read-only. Both operations require the current v2 access cookie, binding cookie, exact Origin and chain; PATCH additionally requires current session-bound CSRF. Responses and problem+json are `no-store`/`no-cache`, generic for unavailable authority, strict about duplicate/framed headers, query/body shape and media type. Freeze exact 400/401/403/409/500 mapping with client/security before source edits; do not infer it from UI component props. A missing in-memory CSRF after reload leads to fresh verified login under ADR-0028, with no recovery endpoint invented here.

`apps/web/lib/registration-api.ts` currently implements only the first three calls, and `registration-flow.tsx` discards the proof. Extend their strict decoders through the three existing enrollment responses, hold continuation/nonce/CSRF in component memory, fence abort/late responses and double submit, and show explicit login-required, restart and generic failure states. Do not store handles or credentials in URL, localStorage or logs. Mount a profile view/editor after committed session only; if ST-237 is still absent, implement the minimal accessible editor within this task from the accepted patch/view schemas, bilingual catalogs and existing tokens. Never imply a saved profile until a decoded server PATCH response and a fresh GET agree. Keep subscription Home/detail mock status visibly separate from this milestone; no redirect that suggests real owner subscriptions are connected.

## Private composition and data boundary

Create one explicit, opt-in, direct loopback HTTPS composition for enrollment and profile; keep default `AppModule`, normal start, production and real OTP/BankID providers unactivated. `apps/web/next.config.ts` currently rewrites browser `/api/v2/auth/*` to **HTTP** `127.0.0.1:4000`. Worse, accepted access and refresh cookies use `Path=/v2` and `Path=/v2/auth`, so the browser will not send them on `/api/v2/*`. The task must move browser calls to same-origin `/v2/*` and use a reviewed HTTPS route/proxy that keeps those exact external cookie paths and preserves Origin, host-only scope and no-store; `/api/v2/*` must not remain the authenticated browser path. The service and current authority currently hard-code `https://st233a.invalid`, qualified database `st233a_development_auth_foundation_proof` and login `subtrack_dev_auth_login`; approve an exact matching loopback host/certificate/DB configuration and update both trusted pins together. A browser may use a locally resolved named host only with actual TLS hostname validation; no Origin rewrite, reflected CORS or insecure-cookie exception. Pin epoch/manifest/independent keys from local secret custody, reject mismatches and refuse startup if competing legacy/delete/refresh writers are reachable in this qualified composition.

After ST-236 known commit, use accepted `V2AccessToken.issue(identityId, sessionId)` once and then set cookies. If cookie writing fails or the response is lost, never replay credentials or compensate by deleting the account. The access cookie establishes only claims; `DurableCurrentWebAuthority.withCurrentWebAuthority` must reread current durable session, binding/Origin/chain, live identity and CSRF under one `subtrack_runtime` transaction before profile statements. Supply a **fixed, named, audited statement set** (e.g. `profileRead`, `profilePatch`) in server composition, with parameter count/type and field allowlists; no generic SQL callback, caller-supplied owner/GUC/digest/statement name or dynamic column names. `OwnerTx` gets only values derived from parsed patch and server-known owner. Keep identity-first lock ordering and verify current CSRF again under lock before PATCH; clean role and both GUCs on pool return. The profile table already has FORCE RLS and dual-GUC owner policy in SQL010; verify actual ordinary-role SELECT/UPDATE only and foreign-owner denial. Account erasure must make profile unreadable through live-identity check; this task does not activate deletion or claim its concurrent lock proof.

The ST-236 qualified fixture disables competing deletion/refresh/legacy writers. Preserve that limitation in this composition and demonstrate they are absent at startup. Access expires after 15 minutes, session after 24 hours. No silent refresh fallback, OTP-only re-login or v1 bearer bridge. A later task that enables refresh/deletion must use the same identity/session locks, current-CSRF option A, family-only reuse revocation and erasure lock protocol under qualified PG race proof before those routes join the composition.
