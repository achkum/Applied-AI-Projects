## Exact next boundary

After ST-236 acceptance, deliver **one executable private development web path**: browser nonce and OTP start/verify → restricted pending → awaited trusted simulator → durable new identity/session → signed v2 access and current-web authority → persisted owner profile read/patch → explicit persisted `JustMeChoice` after profile completion → owner subscription detail read/status change through the same current-browser authority. A larger exception to the 600-line task rule is justified only for this complete executable boundary, with measured caps and specialist ownership before GO; if it cannot fit its time cap, split at a working, security-reviewed HTTPS account/profile boundary rather than another isolated helper.

## Existing pieces and exact gaps

- ST-229 defines wire operations `/v2/auth/enrollment/pending`, `/simulator/verify`, `/complete`, strict web evidence, no-store errors/cookies and one-use burns. ST-236 implements private typed `DurableDevelopmentEnrollment.startOtp`, `verifyOtp`, `admit`, `verifyPerson`, `complete`; it is not registered in Nest or HTTP. Its internal handles are raw 43-character secrets, while accepted HTTP continuation domains are `v2.`, `wep.`, `wev.`; the adapter must map/validate these at the boundary without widening the service's authority. Terminal `complete` returns private refresh, CSRF, identity/session and incomplete profile only after known commit; adapter must sign the v2 access token and set exact host-only cookies, never disclose refresh in JSON.
- Current `apps/web/lib/registration-api.ts` calls only browser nonce and OTP start/verify; `registration-flow.tsx` discards the restricted proof and displays a BankID-required stopping state. It needs in-memory continuation state, abort/late-response fences, strict responses and generic lost-response restart. No local storage, client owner selector, client verifier result or OTP-only login.
- ST-234 has strict `ProfilePatch`, `ProfileView`, `JustMeChoice` components and decoder but no profile or mode HTTP operation. SQL010 creates `identity_profile` with FORCE RLS and owner-dual-GUC policies only in the ST-236 qualified fixture. A trusted current-web profile reader/writer must accept only allowed mutable fields, check persisted completion before accepting explicit `just-me`, and never turn a UI mode choice into household/member/consent creation. The proposed ST-237 profile editor in `.sdlc/evidence/ST-235/parallel-private-web-execution-proposal.md` is unmounted, props-only, about 500 lines and explicitly excludes routes/API/subscriptions. Reuse it if accepted; do not duplicate it or present that PR as this feature. This checkout has no `.sdlc/tasks/ST-237.md` or local ST-237 branch; Conductor must reconcile live PRs before dispatch.
- ST-235 `DurableCurrentWebAuthority` already verifies signed access, current session, binding/Origin/chain and CSRF under one owner transaction. Browser subscription detail/lifecycle controllers/compositions already exist but use their own isolated fixture/Prisma composition. The new integrated composition must bind the enrollment-produced session to the accepted current-web authority and owner-scoped subscription repository under one named, audited server-owned statement set. Avoid fallback to v1 bearer, seed-only identity, process-local session or a parallel issuer.
- SQL010 adds `identity.verified_at/given_name/surname` and `identity_profile` only to the qualified ST-233a fixture. Ordinary migrations and Prisma `Identity`/profile mapping do not have these columns/table. `clean-migration-proof.sh` diffs normal migrations against Prisma; a schema-only mapping would fail drift, and ordinary `identity.findUnique` without a narrow `select` would query missing columns. Carry the deferred mapping only alongside a reviewed forward ordinary migration, compatible grants/RLS and clean-migration/normal-database proof. Do not treat fixture SQL010 as an ordinary migration or silently copy its private roles/functions into default runtime.

## Mandatory security predicates before source GO

1. Freeze a contract-first additive profile read/patch and explicit Just me operation in OpenAPI/generated types with exact methods, strict JSON/body/headers/statuses/no-store and both sv/en states. Existing ST-234 components alone authorize no endpoint. Confirm no Type 1 policy change; give platform/client/security/QA a single complete HTTP+storage+browser proposal before edits.
2. Adapter accepts one exact HTTPS Origin, one valid binding cookie, one canonical nonce, one global idempotency key per mutating enrollment step, no query/duplicate framing/Authorization/access/refresh/CSRF pre-auth mixture. Server owns chain, request digest, epoch and method; client cannot select subject, owner, contact, provider result, role or SQL. Fail closed on wrong purpose/binding/chain/expiry/epoch and lost/uncertain commit. Do not replay credentials or retry terminal completion automatically.
3. Session issuer bridges only a known-committed ST-236 result to accepted v2 token claims and `/v2` access plus `/v2/auth` refresh cookies; preserve binding cookie, return only sessionId/CSRF in body. Current-web owner/CSRF check must use that exact durable session and both server-derived owner GUCs, with clean pool reset.
4. Preserve SQL010's executor-only identity SELECT(id,external_id,deleted_at), dual-GUC RLS, birth/intent same-transaction attestation and runtime-only profile policy. Ordinary migration must replicate the necessary business schema/privacy predicates without broad public/executor rights. Profile patches cannot edit trusted names, verifiedAt, identity/contact/session/currency/owner fields. Verify account erasure removes or renders profile inaccessible in the same owner lifecycle.
5. ST-236 disables competing deletion, refresh and legacy identity/session writers in its fixture; an integrated route cannot claim deletion/refresh race safety until those writers take the same identity/session locks or are explicitly proven absent in the new private composition. Refresher must read durable state and coordinate family reuse/revocation and CSRF policy, or remain disabled in the qualified proof with session expiry/restart semantics stated. Deletion must lock the same live identity before erasure; terminal provisioning holds sorted subject/contact locks and live owner lock. Test races, rather than infer safety from serial mocks.
6. Keep natural-browser CSRF/Origin/cookie behavior and owner subscription invisibility under ordinary-role RLS. Assert missing/foreign subscription IDs give the same owner-invisible response, stale lifecycle pairs conflict, and no cross-owner profile or transaction/account detail leaks. Errors/logs carry no PII, credentials, private SQL or driver text.
