# Next private web client: exact executable scope proposal

Read-only architect-client assessment, 2026-10-11. This is scoping evidence for Conductor, not source GO or accepted ST-236 QA. No ST-237 task, branch or accepted editor is assumed. The first acceptance boundary is a new user completing **private HTTPS enrollment and a persisted owner profile** in a natural browser against disposable PG16. `Just me` and subscription detail are extensions only if the complete boundary fits the L240 cap and their HTTP contracts, platform composition and QA are ready. An unmounted profile form is never an acceptance substitute.

## Observed client and contract state

- `apps/web/app/[locale]/register/page.tsx` renders `components/onboarding/registration-flow.tsx`. It obtains nonce, starts OTP, verifies OTP, then erases the restricted proof and shows a BankID stopping message. `lib/registration-api.ts` has bounded response reads, abort support, strict current response decoding and fresh idempotency keys, but no pending, simulator or completion methods. Existing `test/registration-{api,flow}.test.tsx` codifies that stop.
- `apps/web/next.config.ts` rewrites `/api/v2/auth/:path*` to `http://127.0.0.1:4000/v2/auth/:path*` in development only. Accepted `st_v2_access` cookie Path=`/v2` and `st_v2_refresh` Path=`/v2/auth` do not accompany `/api/v2` browser requests. The new flow needs a reviewed, same-origin **direct HTTPS `/v2`** topology with exact browser `Origin`, binding cookie and postcommit cookie paths. Do not treat the existing HTTP rewrite as the private HTTPS acceptance route or manually set `Origin` in fetch.
- `packages/contracts/openapi.yaml` already fixes `POST /v2/auth/enrollment/pending` 201, `/simulator/verify` 200 and `/complete` 201. Required JSON bodies are respectively `{transport:'web',identifierProof}`, `{transport:'web',continuation}`, `{transport:'web',verifiedEnrollment}`; each requires exactly one `Idempotency-Key`, exact HTTPS `Origin`, `X-Browser-Nonce` and binding cookie. Responses are closed `transport/continuation/status/nextBrowserNonce`, `transport/verifiedEnrollment/status/nextBrowserNonce`, and `transport/sessionId/csrfToken`. Wire prefixes are `v2.` restricted proof, `wep.` pending and `wev.` verified handle, each with exactly 43 base64url characters after the prefix; nonce is exactly 43 characters. No proof or session secret in URL, DOM, logs or storage. ST-236 internal raw handles need server-side adapter mapping; the client must use only accepted wire values.
- `packages/contracts/profile.ts` strictly parses `ProfilePatch`, `ProfileView`, `JustMeChoice`. Patch permits only displayName, avatarColourToken, avatarEmoji, language and theme. View adds read-only `defaultCurrency:'SEK'` and `profileComplete`; `profileComplete` requires nonnull valid displayName. Just me is exactly `{mode:'just-me'}`. There is **no accepted profile read/patch or mode HTTP route**. Contract-first OpenAPI operations, generated types, exact statuses and security evidence are a dependency, not fields for the client to invent.
- `apps/web/app/[locale]/home/home-screen.tsx` and `subscriptions/[id]/subscription-detail.tsx` render mock data; detail route accepts only the literal `spotify`. Existing v2 owner detail `POST /v2/subscriptions/{id}/read` requires `{}`, cookie/binding/Origin/CSRF and returns closed owner or peer view. `PATCH /v2/subscriptions/{id}` accepts exactly `{status:ACTIVE|PAUSED|CANCELLED|ARCHIVED}`. Both are contract-only/unavailable in the default graph. Existing home has no owner list contract through this authority, so do not silently relabel mock Orbit as account data.

## Minimum web implementation, after contract and platform freeze

1. **Transport and session shape.** Update `apps/web/next.config.ts` only if needed for the private HTTPS route topology; settle this with platform before source edits. Change `lib/registration-api.ts` to use the reviewed `/v2/auth` same-origin path for the private feature. Use `credentials:'include'`, browser-generated Origin, fresh one-use idempotency key for each mutating dispatch, bounded exact-media JSON decoder, closed schema validation, and abort/late-response fencing. Do not send pre-session access/refresh/CSRF or post-session Authorization. If the browser cannot supply exactly the required Origin, the HTTPS acceptance must fail closed pending a reviewed server topology; no JS Origin spoof.
2. **Enrollment continuation.** Extend `registration-flow.tsx` after OTP to retain proof and rotated nonce in volatile component/ref state, show a localized simulator verification step, then dispatch pending → awaited trusted simulator → complete sequentially. At each success validate exact `transport`, status, handle prefix/length and next nonce; replace the preceding secret. Client sends no identity, contact, name, provider result, owner or role to these calls. The simulator UI may ask the user to begin verification only; any demo identity selection must be a separately reviewed trusted server mechanism, never an extra client authority field. Keep synchronous duplicate-submit guard. Back/unmount aborts and invalidates the generation. On any uncertain/lost/409 terminal response, erase local continuation and require fresh verified login; do not replay `complete`, infer account creation or display a signed-in claim. Known `ENROLLMENT_LOGIN_REQUIRED` must lead to a separately supported verified-login path or a safe localized stop, never OTP-only session creation.
3. **Postcommit owner profile.** After a strict 201 completion, hold only public sessionId and CSRF in memory, then fetch the profile with the new contract-first owner read operation under the **same current durable session**. Add a real `apps/web/app/[locale]/onboarding/profile/page.tsx` (final path to be frozen with design), or keep a mounted profile step within `register`, with route navigation only if session/CSRF recovery on reload is contracted. Mount `components/onboarding/profile-editor.tsx` and `.module.css` from accepted ST-237 if present; otherwise include these exact files in the integrated task. The editor receives a parsed `ProfileView`, emits `parseProfilePatch` from changed allowed fields only, handles empty/invalid/duplicate save, and parses the returned persisted `ProfileView` before success. Add `lib/profile-api.ts` for the accepted owner read/patch only; body, method, CSRF header, media type, statuses and errors follow the newly frozen operation. A completed state must survive an authoritative server reread in a separate browser navigation/session context, with no client profile cache presented as persistence. If the current session cannot be recovered after navigation because CSRF is intentionally in memory and durable refresh/current-session read is absent, keep the editor in the live enrollment page and explicitly bound acceptance to that browser session; a reload-persistence claim waits for a reviewed recovery path.
4. **Only if budget permits: mode and subscription.** Add `profile-mode-choice.tsx` and `.module.css` only with an accepted explicit Just me HTTP operation that rereads the completed profile under current owner authority and persists the choice. Add a private detail route accepting a real UUID, `lib/subscription-api.ts` and an owner-only presentation in `subscriptions/[id]/subscription-detail.tsx` only after the integrated read/PATCH routes are live in the private graph. For read, send `{}` with CSRF and render only strictly decoded `visibility:'owner'` fields; a peer projection must not expose owner actions. PATCH one allowed status target, then perform authoritative read after 409 or uncertain response; clear the private view and disable actions when reread fails. Do not derive a dashboard total/list from the current single-detail route. Existing demo/mock Home stays visibly sample-only until an owner list contract exists.

## Natural-browser acceptance that proves the minimum

- On loopback HTTPS with the private graph and disposable PG16, start as a new user, complete actual OTP simulator issuance, restricted proof admission, awaited trusted verification and terminal commit. Observe one binding cookie, exact browser Origin, nonce rotation and credential cookie paths; inspect network responses for no refresh/access secret in JSON and no cache. A wrong Origin, missing/duplicate binding/header or stale chain fails generically before any owner data.
- Continue to mounted profile form, save an allowed canonical display name plus one optional preference, and authoritatively reread persisted `ProfileView` as the same owner. Verify a separate owner cannot read or patch it, no trusted name/contact/currency/identity field is writable, and reload/navigation behavior matches the actual contracted session recovery.
- Exercise `sv` and `en`, both theme states, keyboard and screen-reader labels, busy/error announcements, 80/81-scalar and Unicode rejection, unchanged/empty patch, double submit, Back/unmount, late responses, 409 and lost completion without automatic replay or false success. Verify no proof, CSRF, contact, provider result or private error text appears in DOM, URL, local/session storage or logs.
- If extensions are included, select Just me only after persisted complete profile and verify server-reread mode persistence. Read a real owner subscription by UUID, change one accepted status, reread after a conflict/uncertain response, and verify foreign/missing IDs are identical invisible 404s. Do not count the current mock Spotify card as that proof.

Focused web unit/axe tests, contract generation, bilingual parity, exact-head HTTPS browser/PG proof and independent client/design/security/QA review are required. ST-236 real PG/CI/QA, integrated ordinary migration and profile HTTP are prerequisites, not evidence supplied by this document.
