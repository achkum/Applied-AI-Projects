## Classification and correction to the proposed boundary

**Conditional Type 2a, with no Type 1/founder hold inferred.** A private, opt-in loopback HTTPS account-to-persisted-profile composition, contract-first profile read/patch and ordinary forward business migration are reversible cross-cutting architecture/API/schema work within the accepted simulator and owner-authority policy. It does not change public exposure, real delivery/provider, retention, erasure authority, CSRF acceptance or security role model. A concrete proposal to retain erased identifiers, accept historical CSRF, widen executor/provisioner/default grants, make a public endpoint/port or activate production would be a separate security-model/public-exposure decision; none is necessary for this slice. The original platform/client proposal's `GET /v2/me/profile` and fresh-browser/reload claim require the following narrow correction before GO, rather than a new helper task.

`DurableCurrentWebAuthority.CurrentWebRequest` requires `csrfToken` for **every** operation; `withCurrentWebAuthority` calls `check_current_web` before and after its owner callback. An ordinary browser GET does not reliably supply `Origin`. A CSRF-free GET or synthesized Origin would bypass this accepted current authority. Freeze a **contract-first `POST /v2/me/profile/read` with exactly JSON `{}`**, exact browser Origin, current session-bound `X-Session-CSRF`, access and binding cookies, and no idempotency key because it is a pure read, following the accepted subscription `/read` pattern. `PATCH /v2/me/profile` uses the same current authority and allowed `ProfilePatch`; it rechecks current CSRF under the locked owner transaction. Keep the editor mounted in the live registration flow with volatile CSRF and browser chain after terminal 201. An authoritative second read in that live session proves a persisted save. It does **not** prove reload/new-browser recovery: ADR-0028 requires fresh verified login when in-memory CSRF is lost, and no executable verified-login or CSRF-recovery path is in this proposed slice. State this limitation honestly in product/UI/QA evidence. Do not add a CSRF-less current-session reader, recovery issuer, historical-token fallback or OTP-only login to solve it.

## Exact wire and private topology predicates to freeze

- Use one opt-in, loopback-only, single browser origin such as `https://localhost:3443`, with a certificate whose SAN includes `localhost`. The browser entry serves web and external `/v2/*` on that same origin. Any internal API proxy uses authenticated HTTPS with certificate chain **and hostname** validation against a task-owned local CA or exact peer public-key pin; preserve browser `Host`/`Origin` and cookie `Path`. The external browser TLS certificate must be trusted through an ephemeral, task-owned browser trust profile or narrowly scoped certificate/public-key trust mechanism, with actual hostname validation demonstrated. Keep CA/private key out of Git and discard temporary profile/key custody after proof. No persistent OS hosts/certificate-store edits, public listener, `ignoreHTTPSErrors`, `NODE_TLS_REJECT_UNAUTHORIZED=0`, reflected CORS, Origin rewrite or `Secure=false` exception. If the chosen proxy cannot validate its upstream peer or preserve headers/cookies, stop at topology freeze and select a different narrow proxy.
- Existing web development rewrite sends `/api/v2/auth/*` to **HTTP** localhost, while accepted cookies use `/v2` and `/v2/auth`; those cookies cannot accompany `/api/v2/*`. Browser dispatch must use same-origin external `/v2/*` for enrollment/profile. Require exactly one permitted Origin, binding cookie and relevant nonce/CSRF header; reject duplicates/framing ambiguity, query parameters, mixed Authorization/refresh/access modes and unsupported media/body shapes before private work. Browser JavaScript must let the browser set Origin. Host-only `Secure; HttpOnly; SameSite=Lax` cookies retain accepted access `Path=/v2` and refresh `Path=/v2/auth`; no Domain, token JSON, cacheable credential/profile/problem response or broadly credentialed CORS.
- Current ST-236 SQL010, service, `DurableCurrentWebAuthority`, qualified DB and proof pin `https://st233a.invalid`, `st233a_development_auth_foundation_proof` and `subtrack_dev_auth_login`. Preserve the existing proof pin and its acceptance; add **only** one exact new private composition pin (origin plus its named disposable DB/role/epoch/manifest) across SQL/service/current authority and harness after platform freeze. Reject every other origin, database, epoch or key mismatch at startup. Do not turn the origin into a caller-selected allowlist or silently update the qualified fixture pin. Real server-side private keys remain independent, immutable per epoch and secret-custodied; no random fallback after restart.
- Default `AppModule`, ordinary server start, production, real OTP/BankID providers and externally reachable ports stay unactivated. The composition must inventory actual registered routes/providers/writers at startup and fail if legacy enrollment, refresh or deletion writers can reach the same identity/session state. Current ST-236 proof disables those writers; this slice has **no** shared-lock race proof for enabling them. A later refresh/deletion slice must separately prove ADR-0028 current-CSRF option A, family-only reuse revocation, and shared identity/session/erasure lock order in qualified PG before activation.

## Owner, profile and data authority

The HTTP adapter maps raw private 43-character `proof/pending/verified` handles only to the already contracted `v2.`/`wep.`/`wev.` public domains; reject wrong prefix, length, alphabet, direction or state. Preserve nonce rotation, binding/Origin/chain/epoch/purpose/expiry, independent global one-use idempotency burns and no replay. The browser supplies only the accepted transport/proof/continuation/verified handle envelopes. Await the trusted simulator result on the server; neither client identity/contact/name nor provider-result fields become authority. Known terminal commit permits one accepted `V2AccessToken.issue(identityId,sessionId)` and cookie write. Failed/lost response or uncertain commit discloses nothing, triggers no credential retry/identity deletion and shows no false saved/signed-in state. Active existing subject yields only the accepted login-required state; this slice cannot fabricate a login path.

Profile read/patch must enter `withCurrentWebAuthority` with verified v2 access claims, exact Origin, binding and chain and current CSRF. It obtains the current live identity/session in one `subtrack_runtime` transaction with dual server-derived owner GUCs and identity-first lock ordering. The callback receives only the derived owner and fixed **named audited** parameterized `profileRead`/`profilePatch` statements; freeze their SQL literal, parameter count/types and field allowlist in the trusted composition. No request-provided owner, GUC, digest, SQL, statement name, column name or generic callback. Restrict PATCH to the accepted `ProfilePatch` fields; derive `profileComplete` from persisted canonical display name, keep `SEK` read-only and return only accepted closed `ProfileView`. In ordinary-role PG, prove `identity_profile` FORCE RLS, dual-GUC owner equality, own SELECT/UPDATE, foreign denial, no cross-owner update via forged inputs, and pool role/GUC reset after every outcome. A deleted identity must fail the live-identity check and make its profile unreadable; this does not activate deletion or establish its race safety.

Freeze exact OpenAPI operations, generated bindings and 400/401/403/409/500 problem mapping with platform/client/security before implementation. The read takes only `{}`; PATCH takes exactly one nonempty strict JSON object. Reject owner/session/identity/household/contact/trusted names/verifiedAt/currency/profileComplete, duplicate headers or keys, forbidden query, ambiguous cookies, extra body fields and wrong content type. Require `Cache-Control: no-store` and the accepted no-cache handling on success and problem paths. Generic authority failure must not reveal whether an account, session or profile exists. No PII, raw handles, credential hashes or private SQL errors in logs, URLs, storage, snapshots, responses or receipts.

## Ordinary migration and qualified installer remain distinct

SQL010 installs qualified private auth plus business columns/profile; it is not an ordinary Prisma migration. A single forward ordinary migration and `schema.prisma` mapping must land together for **only** the accepted business additions, with no mode field, private auth roles/functions or wider grants. Compare the two separate installation paths: fresh ordinary `0001→0002→new migration`, and qualified `0001→0002→SQL001–010` without replaying the ordinary migration over SQL010. Compare exact column type/null/default/check/FK, owner policy/FORCE RLS and grants, and verify narrow pre-migration ordinary Prisma queries do not select new columns. Preserve existing nullable unique identity/contact keys and provisioner `SELECT(id,external_id)/INSERT` plus ST-236's reviewed executor `SELECT(id,external_id,deleted_at)` and row policy. Startup must fail closed on drift; neither path may make the fixture's private auth authority available to default runtime.
