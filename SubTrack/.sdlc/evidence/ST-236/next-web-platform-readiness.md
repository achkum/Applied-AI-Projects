# Next private web platform — corrected executable readiness

Read-only architect-platform assessment, 2026-10-11. This is a proposed Type 2a task boundary for Conductor, **not source GO or product acceptance**. ST-236 C11 has qualified isolated PG success and source approvals; foundation/actual QA and exact-head acceptance remain pending. The new work starts only after ST-236 acceptance and live task/PR reconciliation. No Type 1 policy change or blanket founder hold is implied.

## Decision and precise first outcome

The first integrated task must let a new user complete the existing private simulator enrollment through a real, same-origin, loopback HTTPS browser, receive the committed v2 session cookies, edit an owner profile in the **mounted live registration component**, and observe the committed profile through a separate authoritative database read. The endpoint is a private development account/profile boundary, not production signup, a Just me choice, subscription ownership or release readiness. Do not dispatch an isolated props-only editor as this outcome. Adopt accepted ST-237 component files if they exist at GO; otherwise include the editor once in this task.

The current `DurableCurrentWebAuthority.withCurrentWebAuthority` has `csrfToken` mandatory in `CurrentWebRequest` and invokes `check_current_web` before and after every callback. A natural same-origin browser GET commonly has no `Origin`, and the accepted authority also demands exact Origin, binding and chain. Therefore the profile **read is `POST /v2/me/profile/read` with exactly `{}`**, while the write is `PATCH /v2/me/profile`. Both are current-session operations with one exact browser-generated `Origin`, current `X-Session-CSRF`, access and binding cookies, and the same current browser chain. Neither uses refresh, mobile bearer, or a new CSRF recovery route. This corrects the GET proposal in `next-web-platform-exact-scope.md` and the client scope note; those earlier notes remain historical scoping evidence. If volatile CSRF is lost on reload, the mounted component stops at a localized verified-login-required state. No supported login/recovery flow is invented. The browser proof of persistence is a distinct `POST /read` after the PATCH, through a new server query/transaction, in the live session; browser reload is tested as an honest stop, not represented as a successful authenticated reread.

## Contract-first HTTP freeze

Add both operations to `packages/contracts/openapi.yaml`, regenerate checked-in clients and validate the existing strict `ProfilePatch`/`ProfileView` parsers. Read accepts precisely one JSON object `{}`; patch accepts precisely one JSON object with at least one of `displayName`, `avatarColourToken`, `avatarEmoji`, `language`, `theme`, with no unknown keys. Canonical display-name rules are 1–80 Unicode scalars, NFC, trim stable, no control/format or surrogate code points. `profileComplete` is server computed from the persisted canonical name. `defaultCurrency: 'SEK'` is read-only. Reject trusted identity, contact, owner, verified names/time, session, household, mode and currency fields. Responses are closed `ProfileView`; neither route returns an owner selector or private credentials.

Freeze these outcome classes with security/client before source edits: 200 closed profile on each success; 400 for malformed method/body/query/duplicate or framed headers, wrong JSON media or forbidden fields; 401 for unavailable current access/session/live owner; 403 for missing/invalid current CSRF or rejected exact Origin/binding/chain; 409 generic profile-state conflict or uncertain write where a success cannot be established; 500 masked infrastructure failure. If the implementation cannot distinguish 401 from 403 without leaking authority state, freeze one generic mapping explicitly before GO and keep the same outward body for equivalent failures. No owner-existence 404. All successes and RFC 9457 `application/problem+json` failures carry `Cache-Control: no-store` and `Pragma: no-cache`; no credential Set-Cookie on errors. Body-size, content-type, single-header and no-query rules are tested at the actual ingress. Existing enrollment paths retain their accepted request/response shapes, public `v2.`/`wep.`/`wev.` handle domains and no-replay semantics; the adapter privately maps these to ST-236 raw canonical handles and never exposes a raw one.

## Exact private HTTPS composition

Freeze a single opt-in topology: `https://localhost:3443` with a certificate whose SAN covers `localhost`, one loopback-bound browser ingress, and external same-origin `/v2/*` routes beside the web app. Browser fetches use `/v2/auth/*` and `/v2/me/profile*`, `credentials: 'include'`, and the browser's own `Origin`. The current development rewrite from `/api/v2/auth/*` to `http://127.0.0.1:4000` cannot carry the accepted `Path=/v2` access cookie or `Path=/v2/auth` refresh cookie. Remove that route from this private flow and prove the external path is `/v2`; host-only Secure/HttpOnly/SameSite=Lax cookies retain those exact paths. The proxy preserves the external `Host`, exact `Origin`, cookie scope, canonical headers and no-store. If an upstream API hop is needed, it is HTTPS with pinned peer CA/SPKI **and** hostname verification. Never disable verification globally, use `ignoreHTTPSErrors`, install persistent OS trust/hosts entries, reflect CORS, rewrite Origin, relax Secure, or expose a public listener. Browser trust is confined to a disposable task-owned profile or equally narrow ephemeral trust; prove the real hostname and certificate in browser/wire evidence.

Preserve the existing `https://st233a.invalid` proof tuple and its checksum/pin behavior. Add **one** new source-controlled exact private tuple for `https://localhost:3443` with its own named disposable PG16 database, qualified login, epoch and manifest. No arbitrary origin/database/role environment allowlist. Review every current pin in SQL001–010, bootstrap material/port/transaction, enrollment service and durable current authority together; many SQL checks and code constructors currently hard-code `st233a.invalid` and the ST-233a proof database. The new tuple must be accepted at each required layer as a unit while mismatched cross-tuples fail startup and database guards. Preserve the historical proof path byte-for-byte where possible; if an original pinned SQL file must change, demonstrate the original tuple's functional/catalog and source-pin proof still passes at the exact head. The qualified private composition refuses startup unless the expected keys, epoch/manifest and role/database match, and unless competing legacy, refresh and deletion writers are absent from its actual route/worker graph. Default `AppModule`, normal start, production and real OTP/BankID provider paths stay unactivated.

After ST-236's known terminal commit, issue one accepted `V2AccessToken.issue(identityId, sessionId)` and write the two cookies. Cookie-write failure or lost response never triggers credential replay or account deletion. The client erases uncertain continuations and stops for fresh verified login. The access token supplies claims only. Each profile operation enters the unchanged current authority with current token, binding, Origin, chain and CSRF; it takes the live identity lock first, establishes server-derived equal dual GUCs under `SET LOCAL ROLE subtrack_runtime`, checks durable session/CSRF before and after the owner callback, and fences epoch/manifest. The patch must execute while that lock is held; no route may bypass this through Prisma, a generic SQL callback or client-provided owner/GUC/digest/statement name. Pool release must prove role and both GUCs clean.

The server composition installs only two audited named business statements, for example `profileRead` (owner-derived `identity_id` parameter only) and `profilePatch` (owner-derived ID plus exactly typed, parsed allowed fields). Freeze their SQL literals, parameter count/types and call sites; no dynamic column names or caller statement map. Prefer an allowlisted fixed update of editable columns with server-computed completeness and `updated_at`; unchanged fields come from a locked owner row, not client authority. The read must issue a fresh SELECT under owner RLS. Test absent/foreign row as generic unavailable/conflict without leaking another profile. Verify actual ordinary-role SELECT/UPDATE and foreign-owner denial under the SQL010 FORCE RLS/dual-GUC policy. Erasure makes profile unreadable via the live-identity predicate; this task does not enable deletion or claim a deletion race proof. Current 15-minute access and 24-hour session bounds apply; no silent refresh or v1 bridge.

## Ordinary migration versus qualified SQL010

`SQL010` installs the business columns and profile only inside the pinned development-auth fixture; it is not a Prisma migration. In the same integrated PR, add exactly one forward ordinary migration after `0002_privacy_constraints` **and** matching `apps/api/prisma/schema.prisma` mapping. Match SQL010's nullable `identity.verified_at`, `given_name`, `surname` and `identity_profile` spelling, types, lengths, defaults, checks, FK, timestamp behavior, FORCE RLS, dual-GUC owner policy and narrow runtime grants. Do not add mode or new identity/contact selectors. Preserve the provisioner's current `SELECT(id,external_id)/INSERT` and qualified executor's exact `SELECT(id,external_id,deleted_at)`; no private auth functions, roles or special fixture grants enter ordinary runtime. Inspect Prisma's generated SELECT/erasure behavior for pre-migration compatibility; fail startup on drift rather than widening queries silently.

Prove two separate paths on disposable actual PG16: ordinary `0001→0002→new migration` against schema and clean-migration/RLS tests, and qualified `0001→0002→SQL001–010` without running the ordinary migration over SQL010. Compare catalog types, null/default/check/FK, grants and policies for the business schema. Keep fixture-only auth authority and SQL010 checksum/pins qualified to the second path. Do not make SQL010 silently idempotent.
