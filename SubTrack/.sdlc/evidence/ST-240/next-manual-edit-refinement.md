## Receipt namespace and transaction ordering

Preferred separate public.manual_subscription_edit_receipt, leaving SQL013/create receipts unchanged. Unique (identity_id,key_hash) spans ALL edit targets for that owner; target id and expectedRevision are in the request digest. Create and Edit are explicitly separate receipt/key classes; do not promise global create/edit key uniqueness. Architect/security must adopt this concrete namespace/schema before GO.

Receipt stores owner, 32-byte key/request hashes, immutable subscription_id, result_revision and creation time. Runtime owner-scoped SELECT/INSERT only, FORCE RLS with both owner GUCs, no PUBLIC/UPDATE/DELETE, owner FK CASCADE for controlled hard erasure, no subscription FK and no automatic pruning while owner exists. Keep receipts after row deletion/status changes/session expiry/restart.

Same accepted owner lock/current-authority transaction: (1) verify current profileComplete+Justme, (2) owner/key receipt lookup, (3) if receipt exists compare complete digest and return original committed {id,revision} or stable key conflict, (4) otherwise lock owner-qualified MANUAL target, classify absent/foreign/detected404, compare exact revision, update only manual fields, record resulting id/revision in the same transaction, (5) preserve post-authority checks/fence/known commit and connection reset. Receipt lookup precedes target existence/precondition: replay after target deletion returns original id/revision; the following detail read returns generic404. Replay never recreates or resets a row and never bypasses current profile/mode.

Known edit and exact replay return200 {id,revision}, the original commit snapshot only. Reread authoritative detail/list immediately. A later revision or deletion means show current truth/reconciliation, not guessed saved fields or permission to resend. Different concurrent edit intents with one expected revision yield one success and one stale409. Same-key duplicates serialize and advance once. Unknown commit discloses no success, discards connection and performs no compensation/replay; explicit same-key/body checking reauthenticates and consults the receipt.
