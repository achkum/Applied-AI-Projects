# ST-237 private PG loopback topology readiness — independent platform/security review

**Conditional Type 2a readiness, not an actual PASS or full-feature acceptance.** C8 run 38146107259 installed ordinary and qualified SQL through 010 and then reported `FAIL ... phase=INSTALL step=EPOCH_SEED sqlstate=unavailable`. The current proof script creates an `--internal` Docker bridge, requests `-p 127.0.0.1::5432`, and extracts `.NetworkSettings.Ports["5432/tcp"][0].HostPort` only after the seed. That receipt does not establish whether the seed failed or whether published-port extraction failed with a stale step label. Docker Engine v28's endpoint code conditions `ProgramExternalConnectivity` on `!n.internal`; therefore the internal bridge is a credible static cause of an absent host mapping, to be confirmed by exact phase diagnostics. [Moby endpoint source](https://github.com/moby/moby/blob/v28.0.0/libnetwork/endpoint.go#L3325-L3342).

**Approve this narrow correction for a new actual proof attempt, subject to these predicates:** create one task-owned, ordinary user-defined `bridge` network with `Internal=false`, IPv4 `nat` gateway mode and network-local `com.docker.network.bridge.host_binding_ipv4=127.0.0.1`; retain the explicit sole TCP `-p 127.0.0.1::5432` mapping. Use the Docker-assigned positive ephemeral host port only after verifying the live container's exact singleton `5432/tcp -> 127.0.0.1:<port>` binding in both HostConfig and NetworkSettings. Advance `step=PORT_BINDING` before extraction, verify reachability from the host over `127.0.0.1:<port>` before key/epoch seed or browser work, and fail closed on missing, multiple, IPv6, wildcard, wrong-container or wrong-port mappings. Recheck the mapping and sole attached container during custody and cleanup. Docker documents localhost publishing and the bridge-local default bind option, but warns that Engine releases before 28.0.0 can expose localhost-published ports to peers on the same L2 segment; require Engine >=28.0.0 for this proof or stop. [Docker port-publishing documentation](https://docs.docker.com/engine/network/port-publishing/).

Keep the existing pinned PostgreSQL 16 image, fresh task name/labels/head/CID, one owned network and container, sole data tmpfs, SCRAM host authentication, private generated credentials, resource limits, no privilege/capability/device additions, and exact cleanup/absence receipt. The host Node API uses only the verified loopback port. The direct `https://localhost:3443` ingress, real TLS socket, Firefox NSS trust and browser negatives remain unchanged. This network change permits ordinary bridge egress from the disposable PG container, so it is a real relaxation of container isolation; compensate by allowing only the pinned PG image and single attachment, rejecting extra network endpoints or routing options, and keeping all credentials and synthetic data task-owned. Do not change host firewall or daemon policy or claim that a loopback mapping protects arbitrary Docker daemon configurations. The actual job must prove the mapping, host connection, SQL seed, startup, browser and custody phases at one exact head before this is accepted as working.

The correction changes only disposable development proof topology. It grants no production/public endpoint, runtime role, SQL writer, schema, credential, provider, account or founder-level security-model authority. Under the accepted ST-237 single-loopback Type 2a boundary and DECISION_RULES §§1–3, I find no concrete Type 1 founder hold for this exact proposal. A proposed non-loopback binding, reachable public host port, global daemon/firewall change, unqualified image, or weaker authentication would leave this readiness and need a new decision. An alternative with a private bridge and a host-network relay would add a second proxy/custody path; it is not the smallest correction to the current host-Node-to-PG design.
