# ST-237 manifest custody correction — security readiness

Read-only security classification at the ST-237 accepted base `fd380a353e11441cf294856a7df474da53421a57`, 2026-10-11. This narrows the manifest finding in `tuple-pin-audit.md` and the `b`×64 value in `security-exact-readiness.md`; it is a proposed source contract, not source GO, a key generation receipt, or an executed PostgreSQL/browser proof. No source, Git, provider, deployment, or test state was changed for this review.

## Exact correction and classification

ADR-0027 already requires `epoch.manifest_h` to fingerprint the mandatory immutable isolated key set. An arbitrary newly generated set will not have SHA-256 fingerprint `b`×64. Retain the historical ST-233a tuple and `a`×64 **only as its qualified fixture witness**. For the new private tuple, replace **only** the proposed `b`×64 manifest with a freshly derived lowercase 64-hex SHA-256 fingerprint. The tuple remains `(st237_private_https_profile, https://localhost:3443, subtrack_dev_auth_login, st237_private_https_v1, derived manifest)`; the manifest is one fixed value for that epoch after generation, not a caller-selected runtime parameter. Existing SQL comparisons of active epoch, manifest and Origin remain mandatory. This implements ADR-0027's existing custody requirement and is **Type 2a** within the isolated development boundary; it introduces no independent Type 1 founder hold. Changing a live key, Origin or epoch later is outside this correction and needs controlled retirement review.

Generate the mandatory keys once into a task-owned private TEMP configuration with restrictive file/directory custody and no checked-in bytes. The manifest algorithm must be specified in source and proof: SHA-256 over a versioned domain separator followed by a fixed, documented order of labelled, binary, byte-length-prefixed values. The exact input set is the bootstrap idempotency key and Origin-authority key; all nine enrollment keys (`binding`, `idempotency`, `authority`, `request`, `nonce`, `otp`, `proof`, `person`, `session`); the trusted simulator HMAC key; and the canonical DER SubjectPublicKeyInfo encoding of the Ed25519 public key used for access tokens. Verify the Ed25519 private key derives that public key before the manifest is accepted. Do not hash textual encodings, object iteration order, serialized JSON, a private-key export, optional keys, or a format-only placeholder. Require the expected key lengths/strength, exact labels/cardinality, and distinct mandatory HMAC key bytes; reject missing, repeated, malformed, aliased or extra authority material before any listener or DB seed. The public DER is included because changing the signing pair changes authentication authority; the private component is proved by pair match without exposing it in the manifest input.

Derive the fingerprint from that private file **before** the owner seeds the new active epoch. Pin the derived value in the new private epoch row and in one immutable task-local runtime configuration. On every start, independently reload and validate the same private material, recompute the fingerprint, and compare it with both the declared configuration value and the active PG row under the exact database/Origin/login/epoch tuple. Verify the row is active and singular, the schema and qualified actor are expected, and every relevant constructor receives that same derived tuple. A supplied manifest string or database name never proves the keys. Any absent file, wrong file custody, wrong key, changed pair, wrong declared hash, absent/duplicate/retired/tampered epoch row, mixed tuple, or comparison/connection failure stops startup and dispatch generically. No random fallback, live rotation, retirement, alternate origin/allowlist/membership, or caller-provided authority is added. A same-epoch restart with the identical private file must pass and preserve durable burns, one-use records, sessions and CSRF.

## Required proof and disclosure bounds

The new disposable PG16/private HTTPS proof must seed and query the actual derived manifest, exercise a same-file restart, and show startup refusal after one-key change, missing key/file, duplicate-key substitution, mismatched Ed25519 pair, altered declared fingerprint, and altered/retired/missing active PG row. Cross-pair old/new database, Origin, epoch and manifest negatives must exercise both constructor and SQL predicates. Preserve and rerun the ST-233a `a`×64 historical positive/negative exact-head proof at the changed head; do not turn that fixture constant into a production custody claim. Source pins and cleanup must cover the manifest algorithm, private file creation/consumption, schema seed and startup graph.

The manifest is a fingerprint, not a secret and not authorization by itself, but its value and all raw/keyed digests should stay out of logs, receipts, snapshots and error bodies. Report only a nonsecret tuple identifier, exact source head, generic pass/fail step, owned resource removal and key destruction. Never print private key bytes, symmetric keys, OTP material or a full config file. This correction does not relax the earlier TLS, complete enrollment→profile, current-authority, ordinary/qualified schema, QA or CI gates.
