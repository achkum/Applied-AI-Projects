## Exact mounted result and existing evidence

`apps/web/app/[locale]/register/page.tsx` already mounts `RegistrationFlow`; keep this route and component mounted through profile save and fresh read. Do **not** navigate to a separate profile route after completion: CSRF is volatile and there is no contracted reload/current-session recovery or executable verified-login flow. A direct visit, reload, or lost CSRF shows a localized verified-login-required stop without suggesting that OTP restores the session. Existing `registration-flow.tsx` ends at `accepted` after OTP and erases the restricted proof. `registration-api.ts` presently calls `/api/v2/auth/*`; `next.config.ts` rewrites that prefix to HTTP `127.0.0.1:4000`. Those requests cannot carry `Path=/v2` access or `Path=/v2/auth` refresh cookies. The private browser flow must use same-origin external `/v2/*` under `https://localhost:3443`, credentials included, real browser-emitted Origin, no JS Origin header. Platform's preferred one-process loopback HTTPS ingress dispatches `/v2` to the isolated private handler and other paths to Next, with no API upstream hop; exact TLS/trust/host proof remains a source-GO dependency. The browser must not use the old rewrite in this flow.

The exact component state progression is `identifier → otp → pending-admission → simulator-verification → terminal-completion → profile-loading → profile-editing → profile-saving → profile-confirming → profile-saved`, with terminal `restart-required`, `verified-login-required`, and generic `unavailable` states. The simulator step presents a single localized user action and busy/progress state; it sends **no** selected identity, provider result, name, contact, role, or owner. The trusted simulator result and any fixed test identity come only from server-side authority. Do not label OTP verification as signed in. A known `ENROLLMENT_LOGIN_REQUIRED` becomes verified-login-required stop; no OTP-only session. The mounted editor must receive a strictly parsed server `ProfileView`, not `projectInitialProfile` as evidence of an existing persisted row. Persisted success requires 200 PATCH **and then a distinct 200 `POST /read` in the same live browser session**, both strictly decoded, with the latter view shown as authoritative. Never infer success from local form state or from session cookies alone.

## Calls, wire decoders, and volatile state

Extend `apps/web/lib/registration-api.ts` with exact response decoders and methods for the already accepted contracts:

| Sequence | Request and expected success | Client handling |
|---|---|---|

| trusted simulator | `POST /v2/auth/enrollment/simulator/verify` 200; `{transport:'web',continuation}` and rotated nonce/new key | Closed `{transport:'web',verifiedEnrollment:'wev.' + 43 base64url,status:'verified',nextBrowserNonce:43 base64url}`. | terminal commit | `POST /v2/auth/enrollment/complete` 201; `{transport:'web',verifiedEnrollment}` and rotated session-purpose nonce/new key | Closed `{transport:'web',sessionId:UUID,csrfToken:string}`; access/refresh secrets exist only in HttpOnly cookies. Clear handle/nonce; keep public sessionId and current CSRF in volatile JS memory only. Do not replay on 409, network loss, abort, malformed 201, or unknown outcome. |
| current profile read | **New** `POST /v2/me/profile/read`, operationId `readV2BrowserProfile`, 200; body exactly `{}`, `X-Session-CSRF`, access+binding cookies, exact browser Origin; **no idempotency key** | Strict `parseProfileView`. Use once after known completion to load editor and again after PATCH as the independent persistence proof. No GET, bearer, refresh, nonce, local cache, or owner selector. |
| current profile write | **New** `PATCH /v2/me/profile`, operationId `patchV2BrowserProfile`, 200; nonempty strict `ProfilePatch` of changed allowed fields, current `X-Session-CSRF`, access+binding cookies, exact browser Origin; **no idempotency key** | Strict `parseProfileView` on 200, then separate read before saved announcement. No `profileComplete`, `defaultCurrency`, trusted names, identity, contact, session, household, or mode in body. |

All fetches use `credentials:'include'`, relative `/v2` URLs, `Content-Type: application/json`, bounded UTF-8 reads, exact status and media type, closed schema parse, and `cache:'no-store'`; optional `Accept: application/json` is not an authority check; fail closed on excess bytes, malformed JSON, extra fields, wrong handle alphabet/prefix/length, or invalid view. Verify success/problem `Cache-Control: no-store` and `Pragma: no-cache` on actual wire; response secret/body inspection remains a browser/backend gate. The accepted enrollment problem pairs are 400 `INVALID_ENROLLMENT_REQUEST`, 401 `ENROLLMENT_AUTHORITY_INVALID`, 403 `AUTH_ORIGIN_REJECTED`, 404 `ENROLLMENT_UNAVAILABLE`, 409 `AUTH_RESTART_REQUIRED` or (complete only) `ENROLLMENT_LOGIN_REQUIRED`, 429 `ENROLLMENT_RATE_LIMITED`, 500 `INTERNAL_ERROR`; accept only exact four-field `application/problem+json`, never print server detail. Contract/storage proposes profile 200 closed view, 400 malformed wire/body, 401 unavailable access/session/live owner, 403 CSRF/Origin/binding/chain failure, 409 state conflict or uncertain write, 500 masked infrastructure; freeze exact masked problem schemas and any safe 401/403 collapse with security before source GO. UI maps 400 to safe invalid/unavailable without echoing private input, 401/403 to verified-login-required or safe authority stop, 409/lost PATCH to uncertain-save state, 500/transport/malformed to unavailable. Equivalent authority failures must reveal no existence signal. No automatic replay of one-use enrollment calls or uncertain PATCH.

Use `AbortController`, a generation counter, and a synchronous `requestPending` ref across every transition, including nested pending→simulator→complete and profile save→read. Back/unmount invalidates the generation, aborts, and clears proof, pending/verified handles, nonce and CSRF; late completions cannot mount a profile or announce success. Since a server may have committed despite abort/lost response, any uncertain terminal outcome must show the verified-login-required stop, never restart/replay completion or delete the account. A lost profile PATCH response may be followed by a fresh authorized read only to show current authoritative state; it cannot label that write successful without an established 200 PATCH plus separate 200 read. If read/CSRF fails, clear the private view. Keep proof, nonce, CSRF, handles and any profile view out of URL, DOM attributes, browser storage, log/snapshot and telemetry; the six-digit OTP appears only in its user-entered input and is cleared on submit/back. A user-entered display name necessarily appears in the visible input; the secrecy check applies to credential/authority material and unrelated PII, and screenshots use synthetic names only. Existing theme preference may remain in localStorage; no auth or profile data joins it.

## Editor and design acceptance

Add `apps/web/components/onboarding/profile-editor.tsx` and `.module.css`, mounted by `registration-flow.tsx`. Use existing token variables, `@subtrack/ui` controls where applicable, and Norrsken's restrained editorial hierarchy; maintain WCAG AA contrast in light/dark and visible keyboard focus. `displayName` is editable, initially blank if server null; save is disabled until at least one allowed field actually changes and parses. `parseProfilePatch` already enforces 1–80 NFC, trim-stable Unicode scalars, no control/format/unpaired-surrogate code points and nonempty object. Optional controls are only eight accepted avatar color tokens, eight accepted emoji (or null), `sv|en`, `system|light|dark`. Ensure labels, legends, instructions, validation associations, `aria-invalid`, `aria-live` status/busy feedback, focus moved to errors or saved heading, disabled double submit, no motion dependence and reduced-motion behavior. Sensitive handles, CSRF, sessionId and contact never render in JSX or hidden fields.

Add matching `onboarding.registration` continuation/status keys and `onboarding.profile` editor/error/saved/reload-stop keys in both `packages/i18n/catalogs/sv.json` and `en.json`; remove or replace the current `acceptedMessage`/`bankIdRequired` stopping copy from the executable private path. The simulator must be plainly labeled as a **private development simulator**; never imply real BankID or public registration. The user can tell when contact verification, trusted simulator, account commit, profile saving and server confirmation are each pending/complete.
