## Findings requiring proof work

1. **Moderate — C9 loopback topology is not yet proved at its approved boundary.** `tools/database/private-profile-proof.sh` creates an ordinary bridge with a loopback default bind and the sole explicit `-p 127.0.0.1::5432`, and custody checks the live singleton mapping. But the script advances to `PORT_BINDING` and extracts the host port only **after** generating the private bundle and inserting the epoch (`EPOCH_SEED`); it never tests host reachability over `127.0.0.1:<port>` before seed. It also relies on the bridge's implicit IPv4 NAT default rather than declaring and checking `gateway_mode_ipv4=nat`. The conditional C9 topology approval explicitly required those predicates before key/epoch seed. Move port extraction, exact HostConfig/NetworkSettings singleton verification and a host loopback connection check ahead of private key/epoch work; declare/check NAT mode if that remains the chosen topology. This is a proof qualification gap, not evidence of an observed external listener.

2. **Moderate — committed terminal partial-cookie behavior remains unproved across the browser boundary.** `apps/web/test/private-profile-browser.mjs` verifies a successful three-cookie completion and an actual profile request with the chain cookie omitted; the adapter rejects that request. `registration-flow.tsx` routes a failed first profile read after completion to the verified-login stop. The mounted UI unit tests do not exercise that composition, and no actual browser case forwards one terminal completion to a known commit while delivering only part of its `Set-Cookie` header to the browser. A small additional natural-browser scenario should establish one terminal request/commit, partial cookie delivery, generic current-authority denial and the localized verified-login stop, with no terminal replay, replacement credential, credential logging or new fault API. The existing missing-chain raw HTTPS negative is useful but cannot prove that post-commit UI path. This remains an explicit ST-237 acceptance condition, not a reason to broaden the private issuer.

## Source boundary assessment

The C6 enrollment classification is resolved within the accepted Type 2a disposition: the adapter maps the durable core's deliberately collapsed invalid/spent/capacity/dependency/uncertain outcome to masked `409 AUTH_RESTART_REQUIRED`, verified active-subject login to `409 ENROLLMENT_LOGIN_REQUIRED`, and unexpected adapter/token-issuer faults to generic `500`; the updated contract prose qualifies the private path without deriving 401/429 from SQL text. The client discards continuation on terminal failure and does not replay completion.

The C6 startup weakness is substantially corrected. Before opening `127.0.0.1:3443`, the launcher checks the private tuple and bundle/key-pair/manifest, pinned SHA-256 of SQL001–010, 25 qualified function bodies/signatures/owners/configuration/grants, 43 auth policies, 115 auth columns, auth role membership/types/ACLs, profile columns/RLS/policies/grants/constraints, trusted principal functions and trigger, and the live epoch fence. The auth constraint definition projection is compared to the fixed `20d5868b5252c03b0d54b691938e860c` MD5 obtained from four C8 clean pinned qualified installs; it is not learned from the database under test. I independently recomputed the ten SQL file SHA-256 values and found they match the launcher's fixed pins. Those checks are fail-closed source guards; their runtime behavior still requires the exact-head startup refusal receipts.

The private listener retains direct TLS socket and exact loopback Host/Origin checks, a closed `/v2` route roster, raw single-header/cookie parsing, strict duplicate JSON-member rejection and generic four-field problems with no-store/no-cache. Completion writes access, refresh and host-only Secure/HttpOnly/SameSite=Lax chain cookies only after a known core commit and token issue. Profile POST read and PATCH require exact Origin, current CSRF and the access/binding/chain cookies; they call the existing current-web authority, which derives the owner from the token, locks the live identity, fences the epoch, verifies current session/CSRF before and after the fixed SQL, uses equal transaction-local dual GUCs under `subtrack_runtime`, and discards uncertain/unclean connections. The two named profile statements bind the derived owner and do not assign currency. The ordinary migration and qualified SQL010 are separate installations; startup checks the qualified catalog, while the actual ordinary/qualified equivalence remains an execution gate. The private middleware suppresses only the nonauthority locale cookie for this opt-in root; no competing refresh/delete/legacy writer is mounted.

The expanded proof source now covers same-bundle fresh-process browser restart with RAM-held CSRF, valid-key/pair/hash/tuple and epoch-row refusal, function/profile tamper refusal, browser cookie/current-authority negatives, committed PATCH response abort with one submission, deleted owner/expired CSRF, unknown COMMIT discard/no retry, immutable PG image digest, source/build finish recheck and owned cleanup. These are designed checks, not successful C9 receipts. The historical ST-233a qualified proof and exact-head natural browser/PG16 matrix, QA, applicable CI and independent platform/devops reviews remain mandatory before final acceptance. In particular, the four C8 constraint-pin installs do not turn the later C8 `EPOCH_SEED` failure into a private end-to-end PASS.
