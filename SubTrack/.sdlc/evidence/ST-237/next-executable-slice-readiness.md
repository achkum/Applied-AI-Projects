## User-visible acceptance target

An actual person enrolls through the ST-237 private loopback HTTPS natural-browser path, obtains its enrollment-created persisted owner and current session, saves a **complete** profile, and receives a separate authoritative read. The person then explicitly chooses **Just me** (`JustMeChoice` is exactly `{ "mode": "just-me" }`), receives a committed result, and separately rereads the persisted choice. In that same live session, an owner-only list displays genuine persisted subscriptions, the person selects one by its displayed row, opens its authoritative owner detail, makes one allowed status transition, and rereads the committed detail. Empty owner list is a truthful empty state, not seeded UI. For actual proof, a synthetic private development subscription record may be inserted for the enrollment-created owner into the disposable database; the identity/session must come from natural enrollment and the record must be persisted and owner scoped. No real bank/provider, household creation, peer list, consent, manual UUID entry, or fake product-complete fixture path is implied. The scope remains the accepted UF-01 steps 5–6, PRODUCT_SPEC F1.4/F1.5, and existing owner subscription read/status behavior.

An owner-only list is required for this **usable** path: current `/v2/subscriptions/{id}/read` and PATCH need a UUID that the UI cannot obtain from a persisted owner record. The existing `/v1` list contract and `SubscriptionPage` shape provide precedent, but its authority/composition cannot be silently reused. Freeze a new, narrow `POST /v2/subscriptions/owner/read` (or another exact reviewed path) with JSON `{}`, current browser CSRF/cookies/Origin/chain, no client owner/scope/filter/cursor selector, no-store/no-cache, bounded stable server ordering and `SubscriptionPage` with owner projections only. Initially cap at 50 and return `nextCursor:null` **only if all rows fit**; if more than 50 are possible, add an opaque server-owned cursor and test it before claiming list completeness. A smaller fixed page without navigation would strand rows. The owner list can include `DETECTED` and other statuses for truthful viewing, but lifecycle controls remain limited to accepted transitions. Do not expose peer/household projections through this new path; preserve existing peer-safe detail contract elsewhere without activating household access here.

## Contract, storage and authority freeze before implementation

1. **Mode contract.** ST-234's `JustMeChoice` is a component only, not an endpoint or storage license. Add exact current-browser POST choice plus authoritative POST read (or a single reviewed equivalent that proves persisted state after choice) in `packages/contracts/openapi.yaml`; regenerate bindings and strict validators. Specify exact body/header/status/problem/no-store rules, incomplete-profile 409, duplicate choice semantics, and committed versus uncertain response behavior. A sensible narrow persistence model is nullable `onboarding_mode` (`NULL` before choice, `just-me` after), attached to `identity_profile`; the explicit write must read `profile_complete=true` under the same locked current-owner transaction and reject other states. A repeated choice should not silently create a new side effect; choose and contract either same-value idempotent readback or 409, with deterministic tests. Do not infer mode from profile completion or represent My household as a created household/membership/consent. Keep future mode changes outside this slice unless the accepted spec requires a separate transition contract.
2. **Ordinary and qualified SQL.** Add one ordinary forward Prisma migration (likely `0004_...`) with matching `IdentityProfile` mapping, nullable/default/check constraint and reconciled policy/grants. The ST-237 qualified SQL010 fixture is a separately pinned snapshot: add an equivalent reviewed next qualified statement/fixture installation and explicit catalog equivalence, rather than editing executed historical SQL or treating ordinary migration as automatically installed there. Confirm `public.identity_profile` and `public.subscription` have FORCE RLS and owner policies, `subtrack_runtime` grants are no broader than needed, and the qualified installer/startup catalog rejects drift. Existing subscription schema/RLS from migrations 0001/0002 supplies owner fields/status; this slice adds no subscription table or public writer. Check merchant join visibility if projecting canonical merchant name, and never read transaction/charge/bank/detection evidence to fill a card.
3. **One current authority.** Add audited, parameterized, fixed names for mode read/conditional write, owner list, owner detail, locked status row, and compare-and-update status to the `businessStatements` installed in `apps/web/private-https-server.mjs`'s existing `DurableCurrentWebAuthority`. All run via `OwnerTx.execute`, deriving owner only from the signed current session; its transaction already fences epoch/manifest, checks live binding/Origin/chain/volatile CSRF, locks identity, sets both owner GUCs under `subtrack_runtime`, rechecks authority and commits before disclosure. Do not mount the isolated browser subscription controllers' separate Prisma/session graph, a v1 bridge, generic SQL callback, caller owner selector, seed identity, or competing refresh/delete/legacy writer. Prefer a fixed owner `SELECT ... WHERE identity_id=$1::uuid ORDER BY created_at DESC,id DESC` for list; detail restricts to same owner even though the older shared detail contract admits a peer projection. Lock owner row `FOR UPDATE`, run the existing status matrix (`ACTIVE`→`PAUSED/CANCELLED/ARCHIVED`, `PAUSED`→`ACTIVE/CANCELLED/ARCHIVED`, `CANCELLED`→`ARCHIVED`), then compare-and-update with expected status. Missing and foreign IDs yield identical 404; same/forbidden transition yields 409. Unknown commit result discloses no success.
4. **HTTP and UI.** Preserve ST-237's direct `https://localhost:3443`, exact private cookie roster and private wire parsing. Add only fixed route dispatch in that launcher; responses must be bounded, strict, bilingual where user facing, and no-store/no-cache. Reuse ST-234 strict profile/mode shape and existing subscription read/status projections, but adapt their storage to this durable authority. `RegistrationFlow` should reveal one accessible Just Me choice only after a fresh complete-profile read, wait for committed write and fresh mode read, then show the owner list. The current `home` and `[id]` pages are mock screens; the private path must render actual owner rows/detail and must never pass a handwritten UUID as a product control. Decode only the owner projection before exposing status buttons; after 409 or uncertain PATCH, perform one authoritative detail read without retrying mutation. If reread fails, clear private detail and disable actions. The registration `csrf` ref is volatile: on reload or partial terminal-cookie state, clear private view and show a fresh verified-login stop. There is no supported recovery/login re-entry in this slice. Keep original authentication protocol and the C28 honest stop. The C28 copy follow-up is nonblocking: the partial-terminal stop's reused second sentence mentions reload although no reload occurred. A generic bilingual sentence stating that a fresh verified login is required can cover both causes, provided the stop/editor absence remains.
