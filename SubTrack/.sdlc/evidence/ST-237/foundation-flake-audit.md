## Exact failing window

In `tools/database/development-auth-foundation-proof.sh`, the `prune-first` branch (around lines 1069–1090) inserts **10,000 expired reservations**. The holder then begins a transaction and runs the actual positive `subtrack_auth.prune_reservations` call with `statement_timeout='20s'`. The observer polls for `pg_stat_activity.state='idle in transaction'` with `observe_clients`' default **10,000 ms** deadline. This state is reached only after the positive pruning statement finishes and the transaction remains open. The waiter is launched only after this observation succeeds. C15 stopped at `race-holder-observe`, so it never reached the advisory-lock waiter, holder release, COMMIT, or result assertions for this case.

The pinned SQL005 function takes the epoch and advisory locks, then uses `eligible ... LIMIT 10000 FOR UPDATE` and deletes eligible rows. The 10,000-row seed deliberately exercises that full batch. A busy runner can leave the holder active beyond the observer's 10-second budget while still inside its allowed 20-second SQL budget. This mismatched deadline is the **best supported source-level explanation** for an intermittent failure at precisely this point; the passes on C10–C12 support timing sensitivity. It is an inference, not a proven duration measurement. In particular, the script sets `prune_failure_kind=timeout` before calling `observe_clients`; that label also survives an early return caused by an observer client failing to join or a holder leaving unexpectedly. `holder_sqlstate=unavailable` only rules out a captured five-character SQLSTATE in its private log at cleanup; it does not distinguish those paths.

## Narrow corrective recommendation

Ask the Conductor to obtain the task's exact source-path roster and independent Type 2a review before changing the historical proof script, which is outside the present ST-237 allowed paths. For the **prune-first, 10,000-row holder only**, give the actual SQL statement a bounded budget above measured slow-run duration (for example 60 seconds) and give the idle-in-transaction observation a shorter but adequate bounded deadline (for example 45 seconds). Keep the waiter lock observation, COMMIT and ROLLBACK variants, real clock/expiry checks, 10,000-row cap assertion, immutable snapshots, result assertions, SQL error checks, custody, and cleanup exactly as gates. Do not lower the seed count, accept an active holder as success, or turn this failure into a warning.

Before a timing change, a minimal safe diagnostic at the observer deadline can record only fixed holder state/wait-event enums, whether the holder process remains live, and coarse elapsed time. That would distinguish a genuinely slow DELETE from observer-client failure or holder exit without exporting queries, row values, private SQL, or credentials. If the holder itself reaches the longer SQL timeout or returns a SQLSTATE, treat that as a real proof failure and diagnose the database path. After an independently reviewed source change, a fresh exact-head mandatory foundation receipt is required; historical passes do not close C15.
