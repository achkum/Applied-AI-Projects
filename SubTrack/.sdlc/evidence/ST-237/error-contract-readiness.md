# ST-237 private enrollment error contract — independent security/platform Type 2a readiness

**Decision: qualified contract clarification is the smallest safe resolution of C6 finding 1; this is not final feature approval.** The accepted ST-236 durable core deliberately emits only `AUTH_RESTART_REQUIRED` for malformed, expired, wrong-binding, conflict, capacity, database, clock, and uncertain-commit failures (`.sdlc/evidence/ST-236/author-readiness.md`, typed transition section). Its implementation catches and collapses operation faults, while preserving only the verified active-subject `ENROLLMENT_LOGIN_REQUIRED` branch (`apps/api/src/auth/enrollment-v2/durable-development-enrollment.ts`). No trusted internal type currently distinguishes invalid authority, capacity, or dependency faults at the HTTP boundary. SQLSTATE, message matching, timing, or a second query would invent such authority and may disclose private state or misclassify a committed one-use operation.

The published `WebEnrollmentProblem` response description at `packages/contracts/openapi.yaml:2162` says 401 for invalid authority, 429 for capacity/throttle, and 500 for unavailable dependencies. Its exact four-field schemas at lines 1766–1840 and each enrollment operation's response list permit those statuses, but the description implies a classification this private durable composition cannot make. C6 security/platform finding 1 correctly identifies that discrepancy. The C8 adapter correction now maps unexpected adapter and access-token-issuer exceptions to generic `500 INTERNAL_ERROR`, while the accepted core's `AUTH_RESTART_REQUIRED` and verified login-required outcomes stay 409 (`private-enrollment-http.ts`, `privateEnrollmentFailure`). This fixes the independently observable adapter fault; it does not create core failure provenance.

**Exact Type 2a disposition for Conductor/architect review:** clarify the `WebEnrollmentProblem` response prose and the private operation descriptions, with regenerated contract artifacts and focused contract/adapter assertions, that ST-237's private durable core intentionally returns masked `409 AUTH_RESTART_REQUIRED` for its collapsed invalid, spent, unknown, capacity, dependency, and uncertain terminal outcomes. Preserve `409 ENROLLMENT_LOGIN_REQUIRED` only for the verified active subject, `400` for trusted wire rejection, `403` for the exact Origin policy, and `500 INTERNAL_ERROR` for unexpected faults outside the core. Retain the 401/429/500 schema pairs as permitted only when an implementation has an independently trusted source for them; do not promise that this private path emits 401 or 429. The client must treat collapsed 409 as discard-and-fresh-verified-flow, with no retry or credential replay. Keep four masked fields, no-store/no-cache, and no sensitive detail or Set-Cookie on failure. This is a reversible API documentation/contract alignment for an opt-in private development path, with no SQL, issuer, authority, public route, or production security-model change. It is Type 2a under `DECISION_RULES.md` §1, subject to architect decision and renewed independent security review, not a Type 1 founder decision by itself.

If exact 401/429/500 emission is a required product behavior rather than a listed response capability, a prose clarification is insufficient. That path needs a separately reviewed typed outcome added at the durable core's trust boundary, with provenance and pre/post-burn or unknown-commit semantics proved through actual PG tests. It must maintain the accepted privacy equivalence classes and generic uncertain-result handling; any decision to reveal previously collapsed private authority states would alter the security model and require Type 1 review. Do not relabel errors at the adapter or infer their cause from SQL text.

This decision covers only C6 finding 1.
