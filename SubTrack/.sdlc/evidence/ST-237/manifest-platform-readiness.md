# ST-237 private manifest and epoch readiness (platform proposal)

Read-only proposal at the accepted `fd380a353e11441cf294856a7df474da53421a57` baseline. This is a narrow correction to the ST-237 tuple plan, not source GO, an implemented key store, or a PostgreSQL/browser proof. ADR-0026 requires an identical pinned key epoch to survive restart and missing/mismatched keys to fail closed; ADR-0027 describes `epoch.manifest_h` as the fingerprint of the mandatory immutable isolated key set. The current proposed private identifier, literal `b` repeated 64 times in `tuple-pin-audit.md`, is merely well-formed hex. It cannot attest arbitrary newly generated keys. No SHA-256 preimage for that literal should be sought.

## Exact private tuple and custody contract

Keep the historical `st233a_development_auth_foundation_proof` / `https://st233a.invalid` / `fixture` / `a`×64 constructor and ST-233a proof semantics. For the new private tuple use database `st237_private_https_profile`, Origin `https://localhost:3443`, login `subtrack_dev_auth_login`, epoch `st237_private_https_v1`, and **manifest `M` calculated from the newly provisioned actual keys**. Replace the private `b`×64 proposal in the exact source-controlled tuple descriptor and its expected proof value with `M` through platform/security review before source GO; freeze the corresponding private bundle in task custody for that pinned source revision. The private manifest is a pinned value for that disposable installation, never a caller-selected or request-derived value. No old fixture schema, seed, digest assertion, or test receives `M`.

Create one owner-only, task-confined private configuration bundle once, before the migration authority seeds `subtrack_auth.epoch`. It contains exact schema version `1`, exact database/Origin/login/epoch fields, the mandatory key fields below, Ed25519 private PKCS#8 and public SPKI DER, and `manifestHash=M`. Generate symmetric key bytes with a CSPRNG (at least 32 bytes each), an Ed25519 pair, and no fallback on any read/parse failure. Use strict canonical base64url for serialized bytes; reject aliases, extra/missing fields, noncanonical encoding, wrong byte lengths/type, all-zero or duplicate symmetric keys, and mismatched Ed25519 pair. Keep the bundle and private key under the task-owned ephemeral secret directory, outside Git, logs, receipts, web assets and browser process; only the private API/provisioner process can read it. Provision it once with exclusive creation and restrictive filesystem permissions; restart opens the existing file without generation. Destroy it only with the owned disposable installation cleanup. The public DER may be repeated in the bundle because pair matching is required; it is not a secret. Neither the raw keys nor `M` is printed in logs or receipts; a receipt may record only the tuple identifier and pass/fail result.

Mandatory symmetric values in canonical order (each a separate isolated key): `bootstrap.idempotencyKey`, `bootstrap.originKey`; `enrollment.binding`, `enrollment.idempotency`, `enrollment.authority`, `enrollment.request`, `enrollment.nonce`, `enrollment.otp`, `enrollment.proof`, `enrollment.person`, `enrollment.session`; `simulator.simulatorHmacKey`. The final mandatory value is `access.ed25519PublicSpkiDer` derived from the supplied Ed25519 private key and byte-equal to the supplied public key's canonical SPKI DER. This list corresponds to the bootstrap material/transaction, `DurableDevelopmentEnrollment.KEY_NAMES`, `DevelopmentEnrollmentPersonVerifier`, and `V2AccessToken` constructors. There are 12 symmetric keys and one public key. The private signing bytes are not placed in the hash; the verified public key commits to the matching private key. Do not add TLS certificate keys, disposable PG passwords, random handles/nonces, or optional unused legacy keys to this auth manifest.

Canonical algorithm `st237-private-auth-manifest-v1`:

1. Start a byte buffer with ASCII `subtrack:st237:private-auth-manifest:v1` followed by one `0x00` byte.
2. Append fields in exactly this order: `database`, `origin`, `login`, `epoch`, then the 13 mandatory key labels above. For each, append unsigned 16-bit big-endian UTF-8 label byte length, the label UTF-8 bytes, unsigned 32-bit big-endian value byte length, and raw value bytes. The four tuple values use UTF-8 bytes; symmetric keys and SPKI use decoded/derived bytes. Reject duplicate labels, changed order, empty values, or values beyond the stated length bounds. No JSON serialization, base64 text, separators dependent on Unicode character counts, or environment iteration order enters the digest.
3. `M = lowercase_hex(SHA256(buffer))` (64 hex characters). The domain/version and the four tuple fields make the interpretation and installation binding explicit. Recalculate from copied, validated bytes at each startup. The private config's `manifestHash`, the one active database epoch row's `manifest_h`, and the selected private tuple's runtime `manifestHash` must all equal `M`. Never substitute `M` from a request or trust a config digest without recomputation.

## Provisioning, startup and API boundaries

Provisioning is ordered: generate and validate bundle once; compute `M`; record the bundle's `manifestHash`; install the private qualified schema in its own PG16 cluster under the existing installer `SESSION_USER` and exact source/fixture controls; seed one active row `(id='st237_private_https_v1', manifest_h=M, origin='https://localhost:3443', state='active', watermark_ms=<trusted initial DB time>)` using migration-owner authority. Do not permit runtime login, producer, or executor to insert/replace the epoch row or update its manifest. Never copy the old `fixture/a` row into the private active slot. A second setup attempt against an existing bundle or epoch must compare and resume only the identical tuple; it must not reseed or regenerate. An inconsistent partial setup fails and requires explicit owned disposable cleanup/reprovisioning, without touching the historical fixture.

At startup, a single private composition loader owns this bundle and returns a frozen, server-only `PrivateAuthEpoch` value `{database, origin, login, epoch, manifestHash, bootstrapKeys, enrollmentKeys, simulatorHmacKey, accessKeyPair}` after strict validation and recomputation. It passes the same tuple and key bytes to `development-bootstrap-material.ts`, `development-bootstrap-burn-material.ts`, `development-bootstrap-transaction.ts`, `development-bootstrap-postgres-port.ts`, `durable-development-enrollment.ts`, `durable-current-web-authority.ts`, and the verifier/token constructors. These constructors continue to validate their own inputs; the private composition must not expose an arbitrary `manifestHash`, origin, epoch, DB or key override. The existing old fixture constructors/tests remain valid on their old tuple. This is an additive private composition contract, with only the minimal exact two-database Origin/tuple allowance described in `tuple-pin-audit.md` for shared SQL/source.

Before opening HTTPS or accepting a request, the loader checks the actual PG connection's `current_database()`, `session_user/current_user`, empty dual owner GUCs, exact DB/Origin/epoch/manifest, the active epoch row, its pinned origin/state/watermark, and expected qualified schema/function/ACL version or exact source pin. Recheck the tuple/epoch/manifest at every borrowed connection and operation fence as existing functions require; pool return proves role/GUC reset. Reject missing/tampered/duplicated/wrong-version or wrong-epoch bundle, mismatched key pair, wrong row or schema, retired epoch, cross-tuple value, clock regression, and unexpected writer graph with one generic startup failure. A valid same-file/same-row restart computes the identical `M` and preserves database nonce, burn, OTP, session and CSRF authority until their normal expiry; it does not rotate keys or reset watermark. No live rotation, retirement, epoch migration, caller selector, random fallback, or plaintext key material in SQL is added.

The schema impact is deliberately small: retain ADR-0027's `subtrack_auth.epoch(id, manifest_h, origin, watermark_ms, state)` and the existing SQL comparisons; insert the computed `M` during owner provisioning and enforce the exact DB-to-Origin guard. No new key table, plaintext secret column, SQL HMAC helper, runtime epoch writer, or arbitrary manifest setter is proposed. Source candidates for later approved work are one private bundle loader/provider under `apps/api/src/auth/`, the private composition entry point, an exact private tuple descriptor consumed by the listed constructors, and the task-owned proof installer. The proof must keep its key bytes private while checking same-bundle restart, each single-key mutation, pair mismatch, bundle deletion, digest-only tamper, row tamper, wrong schema/version, cross epoch/Origin/database, and old fixture pass at the changed source head.

This is an exact implementation of accepted ADR-0026/0027 key-epoch integrity within the proposed Type 2a private storage/composition slice, not a new authentication authority or proposed Type 1 policy. Independent security review should classify the concrete custody/provisioning implementation and the exact roster before implementation. Full feature source GO still waits for the actual TLS/browser preflight and approved exact plan; this document alone authorizes no source, Git, provider, test or deployment mutation.
