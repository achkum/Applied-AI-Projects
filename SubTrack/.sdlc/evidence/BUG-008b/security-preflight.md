## Findings to resolve or prove

1. **Major — invitation service policies may fail their own table operations.** Runtime policies on `identity`, `household_member`, `invitation`, and `audit_log` omit `TO`, so they apply to `PUBLIC` (`migration.sql:248-249,260-272,275-286,300-305`). Their expressions call the Boolean functions granted only to `subtrack_runtime` (`migration.sql:240-245,369-373`), while `subtrack_invitation_service` receives table grants and separate policies. A service query can still be subject to the ordinary policy and lack `EXECUTE` on its function. Scope ordinary policies to the runtime role or grant only the helper executions needed by the service. Prove with an actual service login: SELECT pending invitation, accept/decline, insert associated member and audit entry; verify ordinary login cannot perform those transitions.
2. **Major — no non-owner identity bootstrap path is visible.** `identity_insert` (`migration.sql:249`) requires `subtrack_principal_matches(id)`, but `subtrack_principal()` queries an existing, nondeleted `identity` row (`migration.sql:169-179`). The runtime therefore cannot create a new identity, and the OTP service only receives `otp_challenge` grants (`migration.sql:365`). If new-user creation belongs to a separate trusted role, declare its narrow grant/policy and test it under that role. Otherwise registration cannot reach the owner-only steady state. Avoid granting broad `identity` INSERT to the ordinary runtime.
3. **Review least privilege — invitation service can read every identity column.** `identity_invitation_service_select USING (true)` and `GRANT SELECT ON ... identity` (`migration.sql:350,366`) permit access to all identity rows, including email, phone and external ID. Confirm which columns the accepted invitation flow needs and narrow column grants/policy where possible; prove the service cannot read unrelated identity fields if they are not needed. This is a privacy exposure if the service connection is compromised.

The inspected snapshot's `subtrack_membership_authority_immutable` trigger (`migration.sql:53-76`) now blocks role changes by a nonadmin and protects the last active admin, while allowing a member to leave. Actual PostgreSQL tests must assert self-promotion denial, self-leave success, admin role change, and last-admin departure denial. The self-promotion observation is **not** an outstanding finding against this snapshot.
