# ST126e plan review

**Decision: APPROVE the arithmetic and standalone API contract, with the documentation condition below.** This approval is limited to the reversible additive primitive described in the plan. It does not authorize a provider integration, default/caller wiring, schema or UI change, production behavior, or a claim that the existing bank/ingestion pipeline supplies the necessary billed and settled amounts.

The API can operate without changing that pipeline: a caller may pass each pair as `billed: Money` and `settled: Money`. It can report an unusual change in the pair's effective booked conversion cost only when those values are authoritative and the caller has selected an appropriate same-owner, same-service, chronological reference set. The primitive itself cannot establish provenance, authorization, grouping, chronology, whether a charge is posted, or whether a signed amount represents an eligible refund. Those remain caller responsibilities. Since fees and bank markup are already reflected in the settled amount, this signal is an effective booked conversion cost, including fees and rounding; it cannot isolate a market FX-rate movement. The current AI/ML spec asks for an “unexpected FX swing” but does not define these details or supply the pipeline contract. This is therefore an explicit, reversible Type2a heuristic, not fulfillment of the end-to-end anomaly rule or a production-quality statistical decision.

The exact-rational arithmetic is sound. For positive magnitudes, let a pair's ratio be `n/d = abs(settled.minorUnits)/abs(billed.minorUnits)`, reduced by GCD. With one homogeneous billed/settled currency pair, the currency exponent multiplier is constant for every observation and cancels from relative deviations and the median comparison. Thus minor-unit ratios preserve the relevant relative signal exactly, even when the currencies have different exponents; no absolute exchange rate is inferred. Sorting ratios by cross-products yields the ordinary median, including the exact mean of the middle two fractions for even histories. With candidate `n/d` and positive median `N/D`, `Delta = abs(n*D - N*d)` and `20*Delta > N*d` is exactly the strict test `abs(C-M)/M > 5%`. Equality is inside. For a median of 1.5, the exact boundaries are 1.425 and 1.575; both are inside, while values strictly beyond either boundary flag. Reducing fractions and bounding history at 50 are sensible controls on intermediate integer growth.

The proposed validation and boundaries are coherent: validate every candidate/history Money pair before returning for insufficient history; require nonzero bigint amounts, canonical three-uppercase-letter currencies, USD/EUR billed currency, a different settled currency, and exact currency-pair homogeneity; accept 0–3 valid references as `false`, require at least four to make a finding, allow 50 and reject 51. Normalize signed values to magnitudes only inside the math, leaving refund/direction eligibility to the caller. Snapshot property reads once, bound and snapshot the history array, and map malformed input and getter failures to one fixed MoneyError message. This is consistent with the existing `packages/money` validation style and avoids exposing caller data. Do not use `Number` for amounts or ratios.

One recordkeeping condition follows directly from `DECISION_RULES.md` §4.3: because the spec is silent, the chosen reversible assumptions must be recorded in both the task and `ASSUMPTIONS.md` with status “Assumed.” The plan calls the thresholds and minimum sample reversible heuristics and proposes documentation/ADR recording, but implementation should not begin until that specific task-file and assumptions-ledger record is present. The ADR should state the same scope limits above. Root retains the Type2a architecture decision; no founder Type1 decision is implicated by this local API alone.
