1. Undo. Future additive POST /v1/subscriptions/:id/review/:receiptId/undo, requiring current trusted same-owner principal plus Idempotency-Key. Every successful review action and UF06 Edit returns a server-issued receiptId and undoUntil. Receipt is owned, captures affected IDs, pre/post revisions and minimum approved prior state, and is committed atomically with action/feedback/audit. Window is server completion time +10seconds, valid only while server now < undoUntil (equality expired). Receipt single-use; inverse is a new compensating event, never deletion of audit/evidence. All affected revisions must still match post-action versions; later changes give UNDO_CONFLICT, expired UNDO_EXPIRED. Do not overwrite later edits. Same-key replay of a successful undo is the original bounded receipt response; new keys cannot use a consumed receipt. Ownership/current-authentication/target access is checked on replay. No schema/route yet.

2. Merge. UF06 explicitly combines two detections: :id is the source detection, mergeWith is the survivor, distinct IDs; both must be same-principal owned DETECTED records in same currency. Existing ACTIVE or cross-owner merge is not introduced. Survivor remains DETECTED with its existing display/amount/cadence/privacy fields; source becomes ARCHIVED and an append-only, owner-only merge link records both IDs. Original charge/feedback associations stay attached to their original identities; owner-only queries may resolve the reviewed merge link, with transaction visibility unchanged. No relation deletion, charge reassignment, amount sum or automatic feedback rewrite. Both records/revisions and receipt are locked/committed atomically; races or duplicate merge conflict. Undo compensates the link and restores source state only if both revisions match. No cross-owner/raw-transaction access through a visible survivor. Extension to active/manual subscriptions needs a new architecture contract, not an implicit assumption.

3. Lifecycle. Owner action table, all unlisted status changes rejected with LIFECYCLE_CONFLICT: DETECTED confirm->ACTIVE, reject->REJECTED, archive->ARCHIVED; merge handling above; edit leaves status unchanged. TRIAL activate->ACTIVE, cancel->CANCELLED, archive->ARCHIVED. ACTIVE pause->PAUSED, cancel->CANCELLED, archive->ARCHIVED. PAUSED resume->ACTIVE, cancel->CANCELLED, archive->ARCHIVED. CANCELLED archive->ARCHIVED. REJECTED archive->ARCHIVED. ARCHIVED has no ordinary outgoing transition. No automatic reopening, rejected-to-active or archived restoration; reviewed10second compensating undo is the only restoration of prior review state in this scope. TRIAL creation is outside ST081 (manual subscription ST086). Repeated non-idempotent actions conflict; idempotent replay does not repeat a transition. No self-status transitions used as successful noops. UF06 edits keep a receipt; UF08 non-review archive/cancel is not silently advertised as undoable beyond UF06's requirement.

4. Missed-charge cancellation. ST081 implements only owner-confirmed explicit cancellation from the table. No clock-based request inference or scheduled worker. F5.5's >1.5cadence reminder/evaluation remains pending under ST081 AC6 until a separate bounded task establishes authoritative expected due dates, calendar/custom cadence, booked charges and user confirmation protocol. No invented due-date arithmetic or new job; manual cancellation does not claim the automatic missed-charge flow.

5. Feedback. Minimal owner-only detection_feedback records use existing user_id/subscription_id/optional transaction_id/label/created_at shape; future migration shape not chosen here. Proposed closed labels CONFIRMED_SUBSCRIPTION, NOT_SUBSCRIPTION, EDITED, MERGED. Only first two are binary subscription-training truth; EDITED/MERGED are review events and never imply a binary label. Corrections and undo append owner-scoped compensating/superseding evidence; only current, non-undone binary labels are eligible for later authorized training. No raw descriptor/narrative, bank/account details, amount, prompt or arbitrary JSON in feedback. Household visibility never grants feedback/transaction access. Follow existing approved account-data erasure and retention policy; do not introduce an indefinite or new time-based retention period in this ADR. Because no approved explicit feedback retention duration/job was found, persistence and export/training remain BLOCKED until a bounded retention/deletion contract under ST081 AC7 is recorded and security reviewed. This resolves label/ownership/correction semantics, not that missing privacy requirement or actual deletion.

6. Idempotency. Future owner+operation+resource scoped key, canonical validated business payload digest, atomic pending/committed receipt in same DB transaction as side effects/audit. Trusted current principal/ownership required before any replay; key supplied by caller never authorizes. Same scope/key/digest returns the original bounded business response without repeating effects; different digest -> IDEMPOTENCY_CONFLICT. Concurrency must serialize through unique scoped key and lock/conditional transaction, not in-memory process maps. Failure rolls back uncommitted action and key together. Receipts exclude credentials/tokens/raw bank data; no logging of keys or payloads. Storage/TTL/schema/RLS design deferred until BUG008 reconciliation and independent DB proof; a new receipt retention duration is not invented. No cache means no current runtime change. General exactly-once across external providers is not claimed.
