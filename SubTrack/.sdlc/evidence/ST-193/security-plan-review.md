# ST193 security plan review

**Decision: Approve with conditions as Type 2a.** The proposal adds a narrowly scoped development HTTP adapter around accepted v2 session and CSRF seams; it preserves the accepted credential boundary and does not change the security model, so Type 1 is not warranted. This approval covers the plan only, not implementation or production readiness.

The consumed-refresh lookup may derive a `VerifiedWebSessionAuthority` only for CSRF verification from the matched stored refresh scope, including retained consumed history, active identity, time, and full binding. It must never establish an active protected principal. A matching consumed-token reuse must reach the accepted atomic family-revocation path. Wrong CSRF, cookie, origin, or binding must not mutate state. This matches ST-191’s security source review: the lookup is a credential/CSRF preflight and confers no principal or issuance authority; rotation independently rechecks transport and ownership. ADR-0010 retains separate session-bound CSRF and atomic same-family refresh reuse revocation.

Required conditions: frame the browser-chain HMAC with stored chain, canonical Origin, owner, and session id; do not bind it to an incorrectly verified principal. Store only canonical operation digests and refresh-token hashes, never raw secrets. Mint final CSRF only from the newly issued JWT’s current principal plus the matching owner row/hash. For known post-commit failure, conditionally revoke the exact rotated family before headers and invalidate CSRF under the same authority only after confirmed removal of that issuance; preserve advanced CSRF state. Unknown commit outcomes must not guess or restore old credentials. Reject every body through zero framing, no `Transfer-Encoding`, and undefined body; reject duplicate raw headers and validate direct TLS canonical Origin and refresh binding cookie. Ignore access cookies as refresh authority; forbid Auth/mobile and nonce paths.

Keep this dev-module-only, default-404, with explicit key/port configuration. Do not claim complete preflight/rotation/socket atomicity, provider integration, or production readiness. Type 1 applies if implementation changes the existing CSRF security model.
