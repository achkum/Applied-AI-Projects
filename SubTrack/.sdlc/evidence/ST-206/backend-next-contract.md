# SubTrack backend deployment contract review

**Status:** The current API is **not ready for deployment with authenticated identity or database-scoped requests**. The next bounded backend candidate is ready for architect choices and implementation planning; it must not be called a full-auth or deployable release.

## Evidence reviewed

Required source set: repository `AGENTS.md`, governance Constitution and Decision Rules, `.sdlc/tasks/BUG-009.md`, `SEC-FU1a.md`, `SEC-FU1b.md`, `apps/api/src/auth/sessions/principal-resolver.ts`, `sessions.service.ts`, `jwt.service.ts`, `apps/api/src/database/request-transaction.ts`, and `apps/api/src/app.module.ts`.

- `PrincipalResolver.resolve(token)` calls the existing `JwtService.verify`, builds a frozen `RequestContext` from only the signed `claims.sub`, and calls one `SessionOwnerReader.readCurrentSessionOwner(claims.sid, context)`. It rejects absent/mismatched/revoked session and absent/mismatched/deleted owner with one generic `UnauthorizedException('Unauthorized')`; it returns frozen `{identityId, sessionId}`. This is the accepted `SEC-FU1b` pure core, and its task explicitly excludes an HTTP adapter, storage adapter, transaction binding, and module registration.
- `JwtService` issues/verifies the existing EdDSA claim profile (`sub`, `sid`, `iat`, `exp`, 15-minute lifetime). SEC-FU1a/1b explicitly preserve this issuer/verifier policy and opaque IDs. The service generates an ephemeral key pair when `JWT_PRIVATE_KEY_PEM` is absent, which is documented as unsuitable for horizontal scaling; persistent production key provisioning remains a separate readiness gate.
- `RequestContext` currently contains only `userId`. `withRequestTransaction` starts a Prisma transaction, parameter-binds transaction-local `app.user_id` and `app.current_user_id`, then invokes its callback. Migration `0001_identity_household_rls` protects `identity` using `id = current_setting('app.current_user_id')::uuid`; accepted migration `0003_session` protects `session` SELECT/INSERT/UPDATE with the same user setting. `PrismaService` adds no request scoping itself.
- `AppModule` registers `PrivacyModule`, `DataRightsModule`, `OpsController`, and `PrismaService`; `appModuleFor` conditionally imports only `BrowserNonceHttpModule`. It does not import `AuthModule` or `SessionsModule`. `SessionsModule` exposes a controller that treats a nonempty `X-Caller-Id` only as a truthiness check; session creation then persists `dto.identityId` supplied in the body. Therefore that module must stay out of the reachable app graph until the trusted principal and request-scope integration is reviewed.
- Existing development HTTP adapters under `auth/sessions-v2` already implement bearer-header parsing and routes such as `/v2/me/sessions`, with `DevelopmentV2PrincipalResolver` and `InMemoryV2SessionRepository`; their modules are registered directly by integration tests and require an explicit development-only config. They validate a distinct V2 token/session profile (UUIDs, V2 issuer/audience/version, transport bindings). These are useful transport/test precedents, but are not a production adapter for the accepted `JwtService`/`PrincipalResolver` and must not be duplicated or treated as real database/RLS evidence.
- `SEC-FU1a` and `SEC-FU1b` handoffs both explicitly say that HTTP principal integration, live database ownership/RLS, key provisioning, and module exposure remain unapproved. `BUG-009` records that exact Session-schema parity was approved, with no migration changes, and requires a separate security-reviewed SEC-FU1 integration task before either auth/session module is registered.

## Bounded next candidate

Implement one internal Nest HTTP principal adapter around the already accepted resolver, plus the minimal production reader it needs. Do not add a new public route or change any wire contract in this slice. Do not use `X-Caller-Id`, a body identity, V2 development tokens, or a second credential authority.

Suggested files, all under `apps/api/src/auth/sessions/` unless noted:

- Add `prisma-session-owner-reader.ts` and `prisma-session-owner-reader.spec.ts`. Implement `SessionOwnerReader` using the existing `PrismaService` and `withRequestTransaction`. The resolver supplies its verified `claims.sub` as the sole `RequestContext.userId`; issue one scoped, read-only query joining the requested session ID to its owner identity and selecting only session `id`, `identityId`, `revokedAt`, and identity `id`, `deletedAt`. Use one database statement/snapshot for both rows. Keep the reader generic on errors; no token, ID, SQL detail, or PII in messages/logs. Do not add schema fields, SQL migrations, or an alternate owner lookup.
- Add `authenticated-principal.guard.ts` and a focused spec. Read exactly one `Authorization: Bearer <existing JWT>` credential from raw HTTP headers, reject missing, duplicate, malformed, mixed, or unsupported credentials generically, call the existing `PrincipalResolver`, then attach only its immutable verified `{identityId, sessionId}` to the request. Any request `RequestContext` exposed to downstream code must be freshly derived from `principal.identityId`, never copied from headers/body. Do not broaden the guard to V2 cookies, refresh credentials, new claims, UUID validation, or another token service.
- Add a small `authenticated-principal.module.ts` exporting the reader/resolver/guard providers for future protected controllers, but keep it unregistered from `AppModule` and `AuthModule` in this task. Alternatively, if the platform architect wants no DI module until a real route consumes it, keep provider wiring in the next route task and test the guard through a test-only Nest module. Do not add a production probe endpoint.
- Add a Nest HTTP adapter test under `apps/api/test/` that exercises the guard through a test-only probe controller. Cover missing/duplicate/malformed/non-Bearer headers; invalid JWT with zero reader calls; valid signed JWT resolving to active owner; mismatch/revocation/deleted owner and storage failure producing the same 401 response; and spoofed `X-Caller-Id`/body identity having no effect. Assert the probe receives only resolver-derived identity/session values. Keep credentials and IDs out of logs and test snapshots.
- Add a real PostgreSQL integration test for the reader under the repository's existing database-test conventions. Against a non-owner/non-bypass application role and the accepted migrations, prove that the two local GUCs are transaction-scoped, a caller sees only its own session/identity, and absent/revoked/deleted/mismatched rows fail closed. Also prove a second request cannot inherit the first request's `current_user_id`. No production database writes or schema/migration edits belong in the candidate.

This uses an actual HTTP boundary (Nest guard + header cardinality + trusted request attachment) and the accepted principal core. It advances the missing integration without reimplementing the already-complete claim validator or duplicating the V2 development endpoints. It remains internal infrastructure until a separate reviewed task applies it to a contracted protected route.

## Security contract and error behavior

The only authority for identity is the signed existing JWT plus the live session/identity snapshot. The token's `sub` is only a lookup scope before the resolver succeeds; it is not published as an authenticated context until session ID, owner, revocation and deletion checks pass. A handler may only receive `RequestContext({ userId: verifiedPrincipal.identityId })` after that point. All parse, verification, lookup, and ownership failures must have one indistinguishable generic unauthorized response and must not log credentials or principal data.

The current database policies cast `current_setting(... )` to UUID while SEC-FU1b deliberately preserves opaque IDs at the resolver boundary. Do not add UUID validation as a new credential rule. The scoped reader must fail closed for a value not accepted by the persisted identity schema/policy, and the transport must map it to the same generic unauthorized result.

## Required architect decisions for the root

1. Confirm the adapter boundary: a reusable internal Nest guard that exports a verified immutable principal, with a separate helper to derive the existing one-field `RequestContext`, or a request-scoped provider that exposes both. Recommendation: attach the minimal principal and derive context explicitly at each repository boundary; avoid ambient mutable context.
2. Confirm the transaction boundary: one `withRequestTransaction` around the reader's single current-owner statement for this candidate; every later protected handler/repository must independently use the verified context and scoped transaction. Recommendation: accept this bounded reader transaction now and keep route-wide transaction design as a separate Type 2a decision if the data-access surface requires it.
3. Confirm token transport for this adapter: one `Authorization: Bearer` header using the existing `JwtService` profile only. Recommendation: retain this because SEC-FU1a/1b preserved that core and no accepted policy grants this guard browser-cookie authority. Leave browser cookie, CSRF, refresh, issuance, and V2 transport out of scope.
4. Confirm module ownership: keep provider module unregistered by default; first consumer should be a separately contracted endpoint with OpenAPI-first changes if it adds/changing public API behavior. Recommendation: no `AppModule` or legacy `AuthModule` import in this integration task.

## Remaining blockers to actual deployment

- No production HTTP route currently consumes the accepted `PrincipalResolver`; existing legacy controllers still accept caller IDs directly, and default `AppModule` excludes the session/auth module graph.
- No concrete Prisma `SessionOwnerReader` or live non-bypass-role RLS integration evidence exists. Unit tests of the core and mock transaction tests do not prove PostgreSQL policy enforcement.
- Existing `withRequestTransaction` is an opt-in helper; `PrismaService` does not automatically scope queries, and the unscoped `SessionsService` directly calls Prisma. Any route enabled before repository-level context propagation would bypass the intended request boundary.
- The default JWT key is regenerated at process startup when no PEM is configured. Production key management/rotation and multi-instance verification are not ready.
- This work does not resolve OTP/BankID production authority, refresh/deletion lifecycle policy, cookie/CSRF design, public API contracts, database migration inventory, or production security sign-off. It does not claim full auth readiness, and none of these findings authorize deployment.

## Readiness disposition

**Scoped candidate: READY for root architecture decision and a separate explicitly scoped implementation task.** Reuse the accepted `JwtService`, `PrincipalResolver`, `RequestContext`, `withRequestTransaction`, and existing RLS policies. Preserve BUG-009's gate: no `AppModule`/`AuthModule`/`SessionsModule` registration, DB/schema/migration change, or production route exposure in this slice.

**Overall backend deployment: BLOCKED.** The principal/HTTP/RLS integration and production key/runtime/data-access proofs above remain open. No full-auth or security-all-clear claim is warranted.
