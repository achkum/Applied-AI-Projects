# ST177 plan security review

Verdict: approve the bounded Type 2a development reference in principle. This is approval of the reference design’s architecture and scope, not evidence of production safety or authorization to deploy. The decision remains contract-only under ADR-0010; implementation needs the concrete controls below and its own runtime review.

## Review basis

Reviewed `/workspace/.setup/ST177-implementation-decision.md` including its conductor corrections, `docs/architecture/adr/ADR-0010.md`, and the current browser nonce guard/store and HTTP module, idempotency repository, OTP proof producer, proof store, and shared identifier normalizer. No repository source was changed. Three shell calls were used; no tests, installs, or Git operations were run.

The central ordering is sound for these synchronous in-process repositories: exact request/header validation and throttling; non-mutating nonce preflight; derive chain authority only from the opaque trusted preflight result; synchronous idempotency reservation; synchronous atomic nonce consume/rotate with complete revalidation; then async producer work; settle idempotency before returning any challenge, proof, rotated nonce, or code sink access. Never `await` between preflight, reserve, and consume/rotate. A preflight/reservation/consume failure returns a generic failure and no secret. Once rotation succeeds, any later failure burns the nonce and reservation; the client must bootstrap a new chain. Completed and pending idempotency duplicates return generic `409 AUTH_RESTART_REQUIRED`, never a prior result.

## Required implementation details

- **Shared nonce authority:** `BrowserNonceHttpModule.register` currently constructs a guard privately, while bootstrap service defaults to its own guard. Refactor module wiring to inject one `BrowserNonceGuard` instance into bootstrap and OTP services. Add synchronous, non-mutating `validateBound` plus a store lookup that checks canonical configured Origin, explicit loopback/TLS evidence, nonce/cookie syntax and hash pair, stored purpose, chain and expiry. Return only an opaque trusted chain/origin context. Keep the existing consume-and-rotate transition atomic and make it revalidate all preflight evidence.
- **Verify purpose and chain:** verify’s request schema has no purpose. Add a synchronous server-side challenge metadata lookup, keyed by opaque challenge ID, before nonce preflight; take purpose and bound chain/origin from that record only. Unknown, expired, consumed, or mismatched challenges must produce the same generic failure and must not consult accounts or users. Bind producer verification to the same web chain and exact origin. Do not add a request `purpose` field or infer purpose from caller input.
- **Authority and idempotency:** derive the `browser-chain` authority HMAC from the validated chain ID only after nonce preflight; never cast caller data to `TrustedAuthorityDigest`. Reserve synchronously using operation, `web`, chain authority, canonical request digest, and the single validated `Idempotency-Key`. Reject duplicate/malformed key headers and extra body fields. Keep start/verify reservations distinct. Complete `settle` before any secret-bearing response or making the code available through the injected harness. If settlement fails after producer work, expose nothing; challenge/proof/nonce are burned and the key remains non-replayable/pending until expiry.
- **Bound all in-memory state:** current `InMemoryOtpChallengeRepository` does not expire/prune records or enforce capacity; current `InMemoryProofRepository` also lacks expiry pruning and a capacity bound. Add bounded stores (10,000 active records as specified) that prune expired records before insertion and fail closed at capacity. Challenge metadata must disappear on expiry and successful consumption. Ensure proof records are pruned on access/insertion. The code sink likewise retains only until expiry, caps at 10,000, prunes, and fails closed. Never retain raw identifiers or codes beyond their documented short lifetime.
- **Normalization and privacy:** map API `sms` explicitly to shared normalizer channel `phone`; `email` maps to `email`. Hash normalized identifiers with SHA-256 only for producer binding, and use a separate HMAC for identity throttling. Hash direct `request.socket.remoteAddress` with the rate-limit key for IP throttling; ignore all forwarding headers. These buckets mitigate abuse but are not authentication, principal identity, or reliable end-user identity behind a proxy. Fail closed on bucket capacity and return generic responses. Do not log request bodies, identifiers, codes, cookies, nonce, proof, HMAC material, or challenge lookup outcomes.
- **Dev gate and test seam:** default `AUTH_V2_OTP_HTTP_ENABLED` off; startup must reject enabled values unless `NODE_ENV=development`, `AUTH_V2_ENABLED`, and browser nonce are enabled and all origins/keys validate. Reject `test` and `production` explicitly. Require dedicated OTP and rate HMAC keys of at least 32 decoded bytes, distinct from each other and idempotency/origin keys. Use only `OtpProofProducer` with in-memory challenge/proof repositories; do not route through v1 OTP, its inbox, provider delivery, or persistence. A sink read API is dependency-injected for a test harness only; no HTTP retrieval, stdout, or delivery claim. `mobile` and malformed transport get the same generic restart response; there is no production claim.

## Failure and trust boundaries

A challenge may be inserted before an idempotency settlement failure, and a proof may be issued before verify settlement failure. That is acceptable only if the response and harness access remain withheld and the nonce/key cannot replay; orphaned records expire and are pruned. Wrong OTP attempts remain bounded by the producer’s five-attempt limit and successful verification consumes the challenge atomically. Proof purpose can only be `enrollment` or `stepup`; neither yields a principal, login proof, account creation, or session. Any future session exchange still needs the independent ST170b producer and review.

The current producer and nonce APIs already provide useful primitives, but the reference must not claim that current stores satisfy the new bounds: they do not. The metadata lookup, shared guard injection, dev-only config, and bounded store behavior are implementation requirements, not reasons to widen the accepted contract. Keep changes within the stated paths and preserve `/v1`, OpenAPI, schema, and provider behavior.
