## Concrete browser journey and client architecture

Keep the journey in the mounted `apps/web/components/onboarding/registration-flow.tsx` (`/{locale}/register`), with its existing single in-memory `csrf` ref, abort/generation fencing and terminal stop. The present `profile-saved` state follows PATCH and a separate `POST /v2/me/profile/read`; gate the next choice on **that returned** `profileComplete === true`, not PATCH success, local form validity or a profile inferred from cookies. If the reread says incomplete, leave profile editing possible and explain what is missing. Present one clear **Just me** action with no household side effect. The action posts exactly `{ "mode": "just-me" }`, waits for a committed result, then performs a distinct authoritative mode read. Only a reread of persisted `just-me` opens the owner list. A mode conflict/unknown response gets one mode read, never a blind second write; failure to establish mode leaves subsequent controls disabled and clears private projections. Keep the current session and CSRF through mode, list, selected detail, PATCH and final read; no manual UUID field, route query ID, imported fixture, automatic household choice, or mock Home/detail activation.

The list must be an owner-only, no-store `POST /v2/subscriptions/owner/read` with an initial empty JSON body. Use the reviewed opaque keyset cursor request for subsequent pages and the existing `SubscriptionPage` response shape (`items`, `nextCursor`, at most 50). Do not show an empty state until an authenticated authoritative page really returns `items:[]` with `nextCursor:null`; do not call a 50-row page complete when `nextCursor` exists. Show a named, keyboard operable row for every returned owner item, plus an explicit localized Next/Load more control when a cursor exists. Preserve existing rows while appending a validated next page, reject duplicate IDs or inconsistent pages, and stop with an error if pagination fails. A user selects an ID only by clicking its decoded row. The UI calls existing `POST /v2/subscriptions/{id}/read` with `{}` and renders only a strict `visibility:'owner'` projection; hidden/foreign/missing IDs are never distinguished in the UI. Detail presents status and only the legal targets for its currently reread status: `ACTIVE→PAUSED/CANCELLED/ARCHIVED`, `PAUSED→ACTIVE/CANCELLED/ARCHIVED`, `CANCELLED→ARCHIVED`; no status control for `DETECTED`, `TRIAL`, `ARCHIVED`, `REJECTED`. PATCH sends exactly `{status: target}` once, then a separate authoritative detail read confirms the displayed status. On 409 or lost/unknown PATCH response, reread once without retrying PATCH. If that read fails, clear detail and disable actions; never announce success from an uncertain response.

The old `apps/web/app/[locale]/home` and `[id]/subscription-detail.tsx` render sample data (`Spotify`, numeric amounts and fake history); they cannot be presented as the durable owner view. Prefer small private `JustMeStep`, `OwnerSubscriptionList` and `OwnerSubscriptionDetail` components hosted by `RegistrationFlow`, plus `apps/web/lib/mode-api.ts` and `subscription-api.ts` adapters. Their suggested signatures are `JustMeStep({locale,busy,onChoose})`, `OwnerSubscriptionList({locale,items,nextCursor,busy,onSelect,onMore})`, `OwnerSubscriptionDetail({locale,view,busy,uncertain,onTransition,onBack})`; parent owns the authoritative state machine and CSRF. These are proposed source roster names, not an alternate runtime authority. Reuse the `Button` and CSS token system, not `ReceiptCard`'s numeric mock amount path. `SubscriptionOwnerView.expectedAmountMinor` is a canonical integer string; parse to `bigint` and format with `@subtrack/money` `formatMinorUnits`, with locale, preserving the server-provided currency. Display `customName ?? merchantName ?? localized category label`, then localized cadence/status and amount. Where two rows share a visible name, retain distinct focusable rows and useful amount/status or row position in accessible names; never ask the person to type an ID.

## Contract and decoder freeze needed before source

The platform freeze names `POST /v2/me/mode` body `JustMeChoice` and known-committed 200 closed `ModeView` `{mode:'just-me'}`, plus `POST /v2/me/mode/read` body `{}` and closed `{mode:null|'just-me'}`. Incomplete/other stored mode is 409; repeating the same choice is a side-effect-free 200 readback. Current-authority failures, including uncertain COMMIT, collapse to 401; the client may attempt one fresh authenticated mode/detail read after an uncertain write, but success is never inferred from the 401. Both endpoints use the ST-237 exact Origin, access/binding/chain cookie set, one `X-Session-CSRF`, no query, strict JSON, bounded responses, `Cache-Control:no-store` and `Pragma:no-cache`. The list request has **only** optional opaque `cursor` (first call `{}`), with no client owner/scope/filter/limit; malformed cursor is 400. The fixed server query gets 51 rows, returns at most 50 in immutable `(created_at DESC,id DESC)` order and emits `nextCursor` only when a further row exists. Contract `SubscriptionPage` permits `VisibleSubscription`, so a dedicated owner-page schema or strict owner-only server projection plus client decoder must exclude its household arm on this mounted path. Existing browser detail contract also admits peer-safe view; private ST-238 presentation must reject peer projections and private source must have an explicit owner predicate. The older `browser-subscription-read/lifecycle` adapters are useful parser/problem references but use a separate Prisma/session authority; do not mount them here.

Implement narrow request helpers mirroring `profile-api.ts`: `chooseJustMe(csrf,signal)`, `readMode(csrf,signal)`, `readOwnerSubscriptions(csrf,signal,cursor?)`, `readOwnerSubscription(id,csrf,signal)`, `patchOwnerSubscription(id,status,csrf,signal)`. They require credentials, no-store, exact JSON media, bounded fatal UTF-8/JSON parsing, own-key strict shapes and exact problem mappings. Do not trust generated Zod's default object stripping alone: validate no extra keys, canonical UUIDs, owner discriminator, status/cadence/category enums, canonical signed minor string, currency/date, `items.length<=50`, unique IDs, cursor length, and no peer fields before rendering. Reuse `parseJustMeChoice` from `packages/contracts/profile.ts` and generated subscription types, but add narrow strict validators/tests where generated schemas are permissive. After a mutation's lost/401/409 response, attempt at most one authenticated authoritative reread to resolve persisted state; a failed reread, any independent 401/403, or missing volatile CSRF leads to the existing fresh verified-login stop. A generic 400/500 leaves no falsely confirmed private view. Server callback domain outcomes must be typed values mapped to 404/409 only after the authority commits; thrown callback errors and uncertain commit stay generic 401, never success.

Existing subscription RLS has been flagged as lacking FORCE and includes peer visibility. A current-owner SQL predicate is therefore required on list/detail/status regardless of policy; the platform freeze adds subscription FORCE in ordinary `0004_just_me_mode` and separately installed qualified SQL011, with policy/grant/catalog parity and startup pins. The browser must receive only owner projections. No transaction, charge, bank or detection evidence is needed for the card.

Add exact `onboarding.mode.*` keys for heading, explanation, Just me action, saving, confirming, persisted choice, incomplete-profile and uncertain states; `onboarding.ownerSubscriptions.*` for list title, truthful empty state, row name/category/cadence/status labels, loading, load more, detail/back, four target actions, conflict/recheck, unavailable and confirmation. Add to **both** `packages/i18n/catalogs/en.json` and `sv.json`; run parity. The 21 category codes, seven read statuses and six cadences need human-readable locale labels or a reviewed generic fallback, not raw enum codes as UX. Use heading focus on each step, real buttons, busy/disabled state for one submission, `role=status` for progress/confirmation and focused `role=alert` for error/uncertainty. Test keyboard selection, unique row accessibility, light/dark tokens and narrow viewport in both locales. The C28 nonblocking copy fix fits here: change `verifiedLoginRequired` in both catalogs to a generic fresh verified-login sentence covering reload and partial terminal credentials, without suggesting restore or exposing the editor.

## Actual proof and QA acceptance

The proof starts with a natural enrollment-created owner and retained live browser session on disposable PG16. It saves a complete profile and verifies a separate profile read; chooses Just me and verifies a separate mode read; shows a real persisted owner list, selects a row, reads owner detail, changes one allowed status once and rereads persisted detail. A synthetic subscription may be inserted directly **for that enrollment-created owner** in the disposable database as proof setup; no seeded identity, manual UUID UI or fake activation. Run a second naturally enrolled owner and show owner isolation, identical missing/foreign detail 404, no peer/list leakage and lifecycle owner enforcement. Empty owner list must display its true state; multiple rows must preserve stable ordering and select the intended row; >50 rows or a smaller test page must prove cursor continuation, duplicate/tampered cursor rejection and no stranded rows. Incomplete profile cannot choose; repeated mode choice/status request follows the frozen contract; forbidden status controls are absent and server rejects forged targets.

Use the ST-237 same-key PG/HTTPS/browser proof topology and its four `en/sv × light/dark` variants, source/executed-bundle pins, private receipt custody and cleanup. Add observed route counts and distinct phase receipts for profile, mode write/read, list, selected detail, PATCH and final detail read. Intercept a **committed then lost** mode write and PATCH response separately: each has exactly one mutation request, an authoritative reread, and no premature success. Test reread failure clears the private list/detail and disables controls. Preserve the actual reload navigation proof and partial terminal-cookie stop; after either, the old volatile CSRF is absent, private rows/editor/actions are absent and the generic bilingual login requirement is visible. Include duplicate/malformed headers/body, stale Origin/binding/chain/CSRF, rollback/unknown commit, second owner, pool role/GUC reset, process restart, ordinary/qualified catalog parity, and no-cache headers. Focused unit/component/contract tests and an actual browser/PG receipt are both required; visual screenshots alone do not prove persistence.
