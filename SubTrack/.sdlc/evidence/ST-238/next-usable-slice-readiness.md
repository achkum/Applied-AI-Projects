# Next usable private slice after ST-238 — readiness only

2026-10-11. ST-238 PR #283 is under validation; this is a read-only future proposal, not source GO or an acceptance claim. Begin only after its exact head passes independent reviews, actual PG/browser QA, applicable CI and Conductor merge audit.

## User-visible target

Deliver **returning-account fresh verified login to the persisted Just me subscriptions** in private development HTTPS. A person who previously completed enrollment, profile and explicit Just me chooses **Log in** on Welcome, completes a new trusted simulator verification, receives a new current durable web session, then sees an authoritative profile/mode read and the owner list/detail/status flow from ST-238. This closes the current dead end: `RegistrationFlow` sends reload and `ENROLLMENT_LOGIN_REQUIRED` to `verified-login-required`, while its identifier screen says login is unavailable. A new browser launch/reload must require fresh verification before private data appears. Empty list stays truthful. Existing account profile/mode are read, never overwritten or inferred from an OTP/contact.

This follows PRODUCT_SPEC F1.3 and USER_FLOWS UF-01 Welcome **Log in** and existing-subject **Log in instead?**. It is one coherent usable web path, not a proof-only or isolated helper slice. Native UF-01/02, household UF-02/03, bank connection UF-05, and a current-session CSRF recovery operation remain separate product work.

## Reusable trusted source and precise gaps

ST-237 supplies disposable PG16, pinned epoch, browser nonce/cookie/Origin/CSRF and current-owner transaction/session authority. ST-238 proposes profile/mode and owner subscription reads under that same authority. The accepted v2 contract already defines `POST /v2/auth/session` for a server-issued login proof. `DevelopmentSimulatorLoginProofProducer` is an **unregistered in-memory reference**, fixed to simulator `alice`, that resolves a registered subject server-side; it is not a durable HTTP login path. ADRs 0026/0027 specify separately purposed durable `issue_login`/`consume_login` and atomic session creation, but availability must be proved against the actual qualified fixture and current startup pins before reuse. Do not reinterpret enrollment continuation or OTP as a login proof.

Freeze a development-only trusted simulator verification endpoint and browser login session exchange in OpenAPI first: exact request/response/errors, new nonce chain, verified result provenance, one-use proof, transport/Origin/chain/binding, idempotency and no-store rules. The browser must never post a principal, identity UUID, HMAC, or asserted BankID outcome. Resolve only a live registered owner from the server-verified subject; a deleted/missing subject fails generically. Consume proof, lock the current owner, create session/family/credential/CSRF and settle burns in one durable transaction; no memory-authority fallback or separate commit. Return the existing cookie/CSRF shape only after known commit. Lost/uncertain response restarts with fresh verified login; no credential replay or partial private view.

Web work: a real bilingual accessible **Log in** entry and verified simulator handoff, strict API decoding/abort guards, then independent profile and mode reads before mounting ST-238's owner list. Route `ENROLLMENT_LOGIN_REQUIRED` to this entry without carrying enrollment authority. Reload clears volatile private state and offers fresh login; it does not silently recover CSRF. Keep sv/en and light/dark behavior and honest signed-out/expired states.
