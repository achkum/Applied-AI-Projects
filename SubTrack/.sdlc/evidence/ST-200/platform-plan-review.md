# ST200 platform plan review

**Decision: Approve with mandatory conditions.** Classify this as **Type 2a (architecture)** because it adds an internal resolver that composes the accepted v2 credential, principal, session repository, and a registered-contact port across authentication modules. It remains reversible and internal. On the stated scope, it is not Type 1: it does not change product scope, public API behavior, production deletion policy, persistence, providers, or the security model. Any proposal to expose this resolver over HTTP, alter who owns registered-contact data, add a production contact implementation, or weaken the established proof boundary must be reclassified and reviewed before implementation; a security-model or product-scope change would be Type 1.

The proposal is consistent with the accepted boundary if it only produces the existing deletion-only trusted assertion after independently establishing (1) a verified v2 token, (2) a real current mobile principal, (3) that principal's current, owned, full mobile session row, and (4) a server-owned registered contact for that exact identity. The assertion must not authorize general OTP use, account creation, or deletion by itself. It must not add an HTTP route, caller-selectable identity/contact/method, provider delivery, account deletion, or database implementation.

Mandatory conditions before coding:

1. **Sequence gate:** ST-199 must be accepted and merged to `main` before ST-200 source changes begin. Preserve the separate pending ST-198 mobile-bootstrap/idempotency decision. The supplied workspace did not contain `evidence/ST-199/platform-plan-review.md` or `evidence/ST-199/security-plan-review.md`, so this review cannot attest that the hard gate has already passed. Record and verify the accepted-main evidence before implementation.
2. **Current-principal binding:** Derive identity solely from the verified v2 access-token claims and the configured real `DevelopmentV2PrincipalResolver`; require exact mobile transport and consistency between returned principal and claims. Never accept identity, session, transport, contact identifier, or method selectors from a caller. Do not decode unverified claims or fall back to v1/web authentication.
3. **Registered-contact trust boundary:** Invoke a narrowly scoped server-owned port with only a freshly derived `{ userId: actualPrincipal.identityId }` context. The port returns only a strict plain own-data record containing the registered identifier hash and an allowed channel. Reject raw contact values, extra fields, accessors, malformed results, and thenable impostors. Keep test contact data server-owned and keyed only by the accepted identity. Production port implementation and its authority/source require separate review.
4. **Freshness and linearization:** Validate token claims and the owned full mobile row before querying contacts so stale or invalid principals cause no contact lookup. After every `await`, take a fresh monotonic time, reverify the token, revalidate expiry and claims, and synchronously reread and fully validate the current owned mobile row before constructing the assertion. Clock regression fails closed. The resulting owner check is valid at that final synchronous read's linearization point only; it does not guarantee the session remains current for the assertion's lifetime.
5. **Future unsafe use:** Any future HTTP adapter or consumer must freshly reauthenticate/recheck the current principal and owned row immediately before starting proof operations or other unsafe effects, and must independently enforce the accepted idempotency, TLS, exclusive Bearer/no-cookie, registered-contact, and throttling requirements. This resolver does not implement those controls or make an endpoint safe.
6. **Validation evidence:** Add meaningful tests for valid real v2 mobile resolution and proof production through the existing core, plus foreign/deleted/revoked/expired sessions, web/v1 rejection, invalid principal before lookup, revocation/deletion/expiry during each awaited boundary, hostile/malformed contact and repository records, captured-port mutation, and clock regression. Use the accepted v2 validation pattern without modifying accepted source. No raw identifiers or provider delivery in fixtures.

The plan may proceed as an internal Type 2a implementation only after the ST-199 accepted-main gate is evidenced and the conditions above are included in the task contract. This approval does not approve an HTTP route, production contact port, provider, real OTP delivery, account deletion, rollout, or any change to the accepted security model.
