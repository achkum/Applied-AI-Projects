# ST-045 preliminary authentication threat model

**Review state:** preliminary evidence inventory only. This is not a security approval, does not close ST-045, and is not evidence that an auth route is production-ready. Prepared from source on 2026-10-04 and reviewed for preliminary filing on 2026-10-05; accepted base `6cccc3bcb3acbb837d4dd10217983c626686c6c6`. No runtime behavior was exercised for this document.

## Scope and trust boundaries

This draft covers the OTP, identity-provider/BankID simulator, session/JWT, currently registered privacy and data-rights APIs, API logging, and database RLS boundaries. The accepted architecture uses NestJS, Prisma, and PostgreSQL RLS; ADR-0003 expects request-scoped transactions. The API contract says access JWTs last 15 minutes and rotating refresh credentials 30 days; web stores access credentials in an httpOnly cookie and mobile uses SecureStore. It does not specify mobile's HTTP credential transport or CSRF protections for cookie-authenticated browser requests (`docs/product/API_CONTRACT.md:7-10`).

Current module graph matters: `AppModule` registers `PrivacyModule` and `DataRightsModule` (`apps/api/src/app.module.ts:1-12`). It does not import `AuthModule`; AuthModule contains OTP, IdentityProvider and Sessions modules (`apps/api/src/auth/auth.module.ts:1-10`). Therefore OTP, simulator/BankID verify and session controllers are not currently reachable through this Nest application graph, while privacy/data-rights routes are. This limits immediate attack surface but does not make the unauthenticated header checks safe or authorize future auth-module registration.

ST-043 remains BACKLOG and expressly blocks implementation when official docs or approved credentials are unavailable (`.sdlc/tasks/ST-043.md:11-26`). Its test-mode certificate/docs prerequisites have not been evidenced in this source review. Consequently the BankID RP API v6 verification, QR/autostart flow, credential handling and production identity assurance are unverified; simulator behavior cannot satisfy those production claims.

## Risk register

Reachability qualifier: T2–T8 are latent source-level risks in OTP, identity-provider, session/JWT and DevInbox code while AuthModule is unregistered. They are not currently reachable through the checked Nest module graph; their exposure-dependent severities require re-review before any registration or deployment. T1/T9/T10 concern currently registered privacy/data-rights code, with database enforcement/exploitability still conditional on the unverified runtime role and context.

## Existing evidence and its limits

- OTP tests cover normal issue, cooldown/hourly limit, invalid code, 5-failure lockout, expiry, no pending challenge and one-time success (`apps/api/src/auth/otp/otp.service.spec.ts:43-215`). They are unit mocks; no database-concurrency, IP/global rate limiting, enumeration, retention or HTTP response-shape integration coverage is evidenced.
- Simulator/identity tests cover deterministic fixed identities, invalid tokens, deduplication and not persisting raw fictional personnummer (`identity-provider.spec.ts:16-119`). They do not test environment mode selection or prevention of simulator use in a real-data deployment.
- JWT tests cover issuance, signature tamper, expiry and different ephemeral keys (`jwt.service.spec.ts:16-61`). They do not validate claim shape, sid existence/revocation, production key configuration/rotation, audience, cookies/CSRF or middleware.
- Session service tests described in ST-044 cover standard refresh/reuse and caller filtering, but use mocks; no concurrent refresh or live RLS integration evidence is referenced (`.sdlc/tasks/ST-044.md:37-55`).
- API logger redacts request bodies and common credential headers (`apps/api/src/common/http-logger.ts:3-30`), but DevInbox separately writes PII and plaintext OTP to stdout.
- The checked API contract describes broader OTP/BankID/session routes, but current Nest module graph does not expose AuthModule. Contract route mismatches exist: contract uses `/v1/auth/otp/start` and `verify {challengeId, code}` while source uses `/request` and `verify {identifier, code}` (`API_CONTRACT.md:14-22`; `otp.controller.ts:12-35`). Session route paths likewise differ. Contract conformance must be resolved, not assumed.

## Review disposition and gates

**Preliminary disposition: BLOCK for a complete ST-045 security approval.** The registered caller-header trust boundary and non-proof deletion re-auth path are critical/high findings. Additional high risks remain in OTP brute-force/concurrency and enumeration controls, simulator mode isolation, refresh concurrency/revocation, signing-key/config lifecycle, and unverified RLS execution. Assign owners and evidence plans before any all-clear.

**ST-043 is not complete:** its task is BACKLOG, requires current official RP API v6 docs and approved test credentials, and explicitly says remain blocked when unavailable (`.sdlc/tasks/ST-043.md:11-26`). This draft therefore cannot certify BankID protocol correctness, QR/autostart secret handling, certificate storage, verified identity claims, or real-provider error handling. Do not create accounts/credentials or infer the protocol to close this gap.

Before changing any implementation, the separate SEC-FU1 contract must resolve principal source and module containment for currently registered routes, JWT mobile credential transport and cookie CSRF, `sid` ownership/revocation and key lifecycle, OTP/BankID bootstrap semantics, export bearer-token semantics, and an actual disposable-PostgreSQL RLS test role. These are unresolved contract/security decisions, not design choices made by this draft. Security/privacy reviewer must independently assess the final report; no approval is implied here.
