# ADR-0018: Default containment of legacy privacy and data-rights handlers

**Status:** Accepted for SEC-FU1f implementation; review and CI gates remain.
**Decision class:** Type 2a (reversible default runtime availability)
**Date:** 2026-10-10

## Context

The default AppModule imports PrivacyModule and DataRightsModule. Their six v1 handlers accept caller headers or export capability tokens without the required authenticated principal and data-scope/lifecycle integration. T1 remains open. The separately reviewed internal guard and storage proof do not authorize attaching these handlers to real user data.

ADR-0010 preserves v1 paths, schemas and behavior while adding opt-in v2 authentication. Default withdrawal therefore requires an explicit exception rather than treating versioned authentication as permission to retain unsafe reachability. Independent platform/security readiness approves this bounded containment; the Conductor adopts the reversible Type2a proposal. No seed ADR, product feature requirement or credential authority changes.

## Decision

Remove PrivacyModule and DataRightsModule from the default AppModule. Both default and configured v2 nonce/OTP graphs omit these six handlers:

- GET /v1/privacy/settings
- PATCH /v1/privacy/open-book
- GET /v1/privacy/preview-as/{householdId}
- POST /v1/data-rights/export
- GET /v1/data-rights/export/{token}
- DELETE /v1/data-rights/account

They return route-not-found in those graphs. There is no legacy enable flag or replacement identity-header authority. Retain their OpenAPI paths, parameters, request/response schemas, controllers, services and isolated implementation tests. Annotate each operation with `x-runtime-availability: unavailable-default` and its pending activation requirements. Operational endpoints and accepted opt-in v2 behavior remain unchanged.

This supersedes only ADR-0010's preservation of default runtime availability for these six operations. Its version separation, credential boundaries and all other preservation requirements remain in force. Authentication, owner/household scope, export semantics and deletion proofs require separate contracts and independent review before future activation.

OpenAPI metadata version advances from 1.1.0 to 1.1.1 for this availability decision. URLs, wire schemas and credential versions remain unchanged. This is an intentional withdrawal of default availability, not a backward runtime compatibility or rollout approval claim.

## Consequences and gates

Privacy/export/deletion product requirements remain required, but the unsafe implementations are unavailable through the default application graph. T1 remains open for authenticated activation and data-scope/lifecycle readiness; containment is not a High-risk acceptance or security all-clear. No production deployment, existing database operation, deletion, migration/history claim or new security model is authorized.

Record contract annotations and this decision before runtime edits. Acceptance requires actual HTTP 404 tests for all six valid synthetic requests under default and configured graphs, absent legacy controllers/services, zero feature/database access, positive ops checks, preserved feature/v2 regressions, contract regeneration/drift checks, independent source/QA reviews and exact-head required CI.
