# ADR 0038: Durable synthetic bank and detection in the isolated Android app

Status: proposed for ST-253 product completion batch, 2026-10-17. No migration has been applied by this change.

The delivered sandbox previously exposed only manual owner subscriptions. Reuse the accepted SyntheticBankProvider, IngestionWorker, bigint recurrence detector and durable confirm/reject/undo cores behind SandboxAuthority. Production enrollment/private-mobile routes and their database roles remain separate.

Connect creates an owner-bound Synthetic generation, ingests roughly two years of twelve fictional recurring streams and automatically scans them. Provider inputs include multiple categories, an annual stream, a recent price increase, groceries, a one-off, pending debit and refund. These are transactions through ingestion and detection, not subscription cards or verified market prices. Pending/refund/nonmerchant rows cannot become detection evidence. Confirmation persists ACTIVE; rejection and the server's existing ten-second Undo window retain durable feedback/idempotency receipts. A subsequent scan does not reset review decisions.

The additive `003-sandbox-bank-detection.sql` creates only isolated Synthetic tables, owner-scoped RLS, finite grants, capacity guards and exact existing detection constraints. It extends the existing subscription enum/columns without rewriting existing manual rows. Candidate source links are preserved until explicit owner-authorized bank-data removal; removal detaches bank account links while retaining subscriptions. Only the current owner sees transactions. Household membership never grants bank-history access.

The existing SQL allowlist expands by exact bank/detection statement names and owner-first parameters; the final detection fence uses `st250_auth.session`, never the production private-mobile namespace. The UI receives current committed bank/inbox/owner readbacks. A next expected date is persisted from latest attributed booked evidence and the detected calendar cadence; it is a forecast, never a paid charge. History is bounded to the latest 400 booked owner transactions with signed int64 minor units and actual source attribution.

Migration safety: the original two-file capability manifest remains unchanged. Startup additionally verifies every applied migration's checksum and the expanded FORCE RLS roster. The explicit one-shot `bootstrap.cjs upgrade` mode requires `SUBTRACK_SANDBOX_MIGRATION=preserve-owner-v1`, the exact isolated database/login/epoch, matching foundational checksums and a session advisory lock. It applies only unapplied 003/004 and does not generate keys, reset credentials or recreate identities. The normal initializer still refuses an existing database. No API request can invoke DDL or the bootstrap role.

PostgreSQL requires the new enum label to commit before its use. Migration 003 therefore commits the enum addition before its transactional schema expansion; `ADD VALUE IF NOT EXISTS` permits forward recovery if the later transaction fails. The previous API expects exactly two migration rows and cannot safely start after forward DDL. Before migration begins, a failed stop may restore the exact verified old API; once DDL may have begun, failures hold the API stopped with retained evidence and data until a reviewed forward-compatible recovery. Do not claim automatic rollback, drop data, delete enum labels, rewrite old migration checksums or restore an empty volume.

Before stopping the old API, the guarded upgrade helper captures a private PostgreSQL custom-format archive from the exact existing isolated database container as UID999. It bounds streaming bytes and time, writes an exclusive0600 staging file, verifies `pg_dump` success and a separate `pg_restore --list`, then retains only byte/hash/identity metadata in a receipt. This verifies archive creation and table-of-contents readability; it is not a demonstrated restore or an authorized automatic database rollback. The database and gateway containers/volumes remain unchanged. Actual review, capture and receipt verification precede any eventual additive application; source tests alone do not establish that a live backup exists.

Validation is authored, pending the consolidated batch: real provider/detector inputs, strict contract/transport tests, injected shared native screens, finite authority/startup checks, explicit upgrade planning, and the existing owned PostgreSQL qualification expanded with ingestion/review/replay/foreign denial and same-database restart readback. Actual installed combined screenshots and backend proof remain required before successor signing/delivery.
