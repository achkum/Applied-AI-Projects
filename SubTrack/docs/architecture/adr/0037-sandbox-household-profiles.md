# ADR0037 — Durable household profiles in the isolated Android sandbox

Status: proposed implementation for the founder-requested ST253 Android feature batch, 2026-10-17. Source implementation does not establish review, database execution, device acceptance or deployment approval.

The ordinary household service already implements household creation and profile-only dependants (ADR0021). Its Prisma tables and role policies are absent from the separate ADR0035 sandbox database. Calling that service through a production connection would cross the isolation boundary. Forward sandbox migration004 therefore installs the same household/member concepts in the existing isolated database; it does not rebuild or replace ordinary production household services or create fake identities.

Each workspace has one household, its authenticated installation identity is the sole admin, and up to19 additional non-login dependant profiles can be added. The canonical nullable identity/display-name pairing and unique active-admin constraint are retained. `created_by` and `owner_identity_id` bind the isolated household to its current capability principal with compound foreign keys, FORCE RLS and column-limited runtime grants. No request accepts a caller identity or household selector. Profile completion is required. Existing Just me subscription eligibility remains an internal owner-data guard; household creation is additive and does not silently grant shared subscription visibility.

Every operation runs inside the existing current-session transaction with the same owner lock and precommit token/revocation fence. Create is repeat-safe for an existing owner household. Dependant Add uses a fresh opaque UUID intent; an exact replay resolves the existing member, while a changed or retired replay conflicts. Edit/remove can target only active dependants in this owner household. Remove soft-retires a profile after removing its usage allocations; the admin cannot be removed or demoted. Retained member rows are capped80 per workspace and audit rows1000; active members are capped20. Capacity exhaustion fails closed rather than deleting old history.

An optional owner-entered subscription usage assignment links only this owner's existing subscription to this household's active profiles. A separate per-plan record stores an explicitly selected planned payer member; its default is null/unknown. Ownership never implies a payer or confirmed payment. Compound foreign keys and RLS prevent another owner's subscription/member targets. Empty usage assignment means owner-only usage attribution; it does not set a payer. This is cost attribution, not cross-account sharing consent, another person's transactions, a payment, a paid-charge claim or a settlement debt. Readback returns exact current member/assignment/planned-payer IDs only, while subscription names and amounts use the unchanged owner API. The UI normalizes active known-cadence SEK plans using the shared recurring-cost convention and allocates each monthly minor unit with existing `allocateEvenly`; ordering is stable by member UUID. Removing a dependant nulls their planned-payer links and removes usage allocations before retiring the member. No foreign/private bank records are read.

Household mutation audit stores only event kind and opaque target IDs, never profile/household names or bank data. A per-owner SHA256 chain binds previous hash/event/target; existing owner serialization orders the chain. Runtime has append/read rights, no audit update/delete rights. Existing transaction rollback covers profile, allocation and audit changes together.

The native screen follows the approved household layout: household/member avatars and metrics, member scope chips, payer distribution, exact monthly usage shares, editable family profiles, confirmation for removal and real subscription-user selection. User-facing language remains concise and bilingual. Readbacks after mutations, route focus and app restart are authoritative; mutation receipts never stand in for current state, and inactive/obsolete sessions hide all private members and subscriptions.

Adult external invitations, accepting another installation into a shared household, open-book/explicit cross-account sharing, admin transfer and settlement state remain separate unimplemented acceptance. This batch does not invent accounts, email/SMS, proof bypasses or fake payments to suggest completion. Required consolidated validation includes real PostgreSQL two-owner/RLS, rollback, retained-data migration and Android family/attribution/restart behavior before the single delivery build.
