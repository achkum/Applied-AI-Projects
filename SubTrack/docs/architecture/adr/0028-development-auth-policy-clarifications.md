## Authority and exact before/after
ADR0010 requires session-bound CSRF before unsafe web refresh and atomic same-family reuse revocation; ADR0026 requires locked live-owner/CSRF revalidation, atomic CSRF replacement/revocation and generic deleted/contact conflict without resurrection/relinking. ST229 retains these gates and leaves this interpretation unselected.
Actual `webContextForRefresh` resolves current OR consumed hash to the same immutable owner/session/browser scope; it does not return historical CSRF or mutation authority. `SessionCsrfGuard.mint` replaces the single identity/session token digest; `verify` checks only that current digest. HTTP verifies CSRF before reserving or refreshing. Existing tests demonstrate consumed refresh + newly minted current CSRF revokes the family; wrong CSRF leaves it intact.
Before→proposed after: keep those token acceptance/binding rules exactly; specify that consumed-token reuse means reuse admitted by mandatory web CSRF checks. Old refresh+predecessor CSRF is refused before burn/mutation and cannot trigger revocation. Raw core rotation without HTTP CSRF is not the web contract.
Actual HTTP rotation, CSRF mint and settlement are separate; consumed reuse currently removes family session rows but leaves the current CSRF digest (refresh-http.spec.ts:345-359). Durable after makes rotation/replacement/settlement OR reuse/revocation/invalidation/settlement one transaction, as already required by ADR0026; no claim the process-local reference already supplies it.
Actual erasure transaction clears `externalId`, `email`, `phone` and sets `deletedAt`; nullable unique columns no longer identify the erased row. Legacy provider lookup by subject then creates a fresh identity when unmatched, with separate lookup/create and no deleted-row predicate; it is evidence of identifier removal, not accepted durable enrollment/deletion implementation.
Before→proposed after: preserve cleared identifiers, live uniqueness and fresh unrelated identity after complete erasure, while making accepted durable deleted-row refusal/liveness and concurrency precise. No permanent registration ban, old-owner recovery, retired identifier table or additional retention follows from conflict prose.
## Proposed current-CSRF refresh rule (ADR0027 option A)
Preflight exact accepted web envelope/TLS/Origin/binding cookie, secret-hash matched current-or-consumed credential, epoch/time/bounds and current session-CSRF digest; access cookie contributes no authority. Bad/predecessor/missing CSRF fails generically without reservation, rotation, tombstone removal or revocation; valid current token is not consumed by preflight.
After valid preflight, independently commit the nonce-free globally unique Idempotency-Key burn using the pinned server-derived browser-chain authority/request digests and fresh opaque owner handle. Duplicate pending/completed/failed burns return generic409 without replay. Preflight is a snapshot, never sufficient mutation authority.
In the second transaction set both owner GUCs from the matched stored owner; lock epoch/owned reservation then live identity/family/session/credential/CSRF in ADR0027 order. Recompare complete immutable secret-bound tuple, active owner/session, configured Origin/cookie/chain/epoch/expiry and CURRENT noninvalidated CSRF digest under those locks; a rotation/revocation/deletion between checks fails closed, leaving the burn.
Current credential + current CSRF atomically consumes hash, inserts same-session/family successor with unchanged generation/original expiry, replaces current CSRF and settles completed. Never retain predecessor CSRF, mint a second family or disclose successor before known commit.
Consumed credential + current CSRF may only atomically revoke that matched live family/session, invalidate its CSRF and terminally settle the owned reservation failed; response is generic session-unavailable with no credential disclosure. Other families and their CSRF remain unchanged; already revoked/expired/deleted sessions fail generically without new authority.
After successful rotation an old refresh+old CSRF pair therefore causes no revocation; old refresh+current CSRF causes family-only revocation. Current refresh+predecessor CSRF also fails. Consumed hashes remain bounded through original family expiry for admitted reuse detection, never for historical-CSRF verification.
Known rollback retains burn and conditionally fails only its owned pending reservation; crash pending expires. Uncertain commit/lost response discloses/replays nothing, never automatically retries refresh or compensates by deleting identity/session; discard local credentials and obtain fresh verified login/nonce. Owner-manage known prior sessions; unknown orphans expire.
Without a separately reviewed current-session exact-Origin/cookie-bound CSRF replacement contract, reload/lost in-memory CSRF requires fresh verified login. No historical plaintext reconstruction, cached historical authority or new recovery endpoint is selected.
## Proposed post-erasure rule (ADR0027 detectable conflict + fresh identity)
Reject a detectable deleted row matched through legitimately stored subject/contact or an already server-derived old owner: generic restart, no resurrection, contact reassignment, profile overwrite or enrollment session. A contact retained by another live identity is a uniqueness conflict, not an identity-linking signal. Existing verified active subject yields only ENROLLMENT_LOGIN_REQUIRED and explicit later verified login.
After committed complete identifier erasure, the old values cannot identify the old row. A fresh OTP+mandatory verified simulator enrollment may create a NEW server-generated identity UUID if subject/contact are free and all continuation/session/idempotency gates pass; no old owner, session, household, consent, profile or audit ownership is linked, copied or revived.
Nullable global unique external_id/email/phone remain final arbiters for nonnull values, including any still-detectable deleted-row values. Do not add a live-only index that admits duplicate retained identifiers. Never use contact possession, UUID input, reservation or OTP alone as enrollment/login/deletion authority.
Concurrent enrollment/deletion must linearize under the same sorted subject/contact digest advisory locks THEN live identity row lock, before family/session/credential/CSRF locks. Deletion derives its old lock keys privately from its owned row before clearing; reread/revalidate under locks and restart if changed. These locks are transaction-only, never retained identifier records.
If enrollment observes the active old row first it returns login-required/conflict and creates no identity/session; if authorized deletion commits clearing first, enrollment rematches subject/contact and may create a distinct identity. Unique-race loser restarts without replay. Old-owner unsafe/session operations fail after deletion; no cached active-owner set.
This shared lock protocol and current-owner deletion/session invalidation are FUTURE separately reviewed durable prerequisites, absent from legacy v1 erasure. Keep accepted deletion authority: current same-principal session, web CSRF/Origin and independently consumed account-delete proof; no executor/provisioner deletion power, v1 reauthentication reuse or live-row maintenance deletion is authorized here.
## Affected typed predicates and feasibility gates
ADR0027 `match_refresh(...) RETURNS refresh_match` stays secret-hash-only, immutable tuple return with no state discriminator; `refresh_burn` stays trusted-adapter-only. `reserve_refresh(...)` retains full rematch and independently committed global burn. Transaction-bound async owner/session/CSRF ports must reread current noninvalidated CSRF and active session/identity under locks; settlement uses unchanged owned tuple. No predecessor_csrf_h column/function/grant.
`terminal_material(web,owned,verified_h)` retains private subject/contact locks and no retired lookup; provisioner SELECT(id,external_id)/INSERT stays unchanged. Ordinary owner context supplies locked deletedAt checks; contact writes use existing uniqueness and no relinking. Durable authorized erasure must share lock order and clear identifiers atomically with appropriate owner/session invalidation; exact deletion port/SQL predicates require their own narrow source proposal before implementation.
Small feasibility prerequisites: prove complete immutable refresh snapshot/validated digest producer and awaited transaction-bound ports, no client digest/owner selector; prove deletion can acquire shared locks and revalidate privately without new retention/lookup/deletion grants. Any unsupported predicate/authority must return to Conductor with exact before/after, not be invented.
Required future tests: current/current success; consumed/current family-only revoke+CSRF invalidate; current/predecessor and consumed/predecessor preflight refusal/no burn; between-preflight-and-lock CSRF rotation/revoke/delete; duplicate cross-operation burns; rollback/settle/capacity/expiry/clock/uncertain commit/restart; unrelated-family survival.
Erasure tests: detectable deleted subject/contact generic conflict; active subject login-required; live contact uniqueness; erased identifiers null; fresh enrollment distinct UUID/no old data linkage; both deletion/enrollment serial orders, changed-lock-key restart and unique-race loser; no old row resurrection/unsafe authority or broadened provisioner/executor grants. Actual qualified PG race/denial evidence is later, not mock proof here.
## Classification and adoption gate
Proposal changes documentary precision while preserving actual CSRF acceptance and identifier erasure; atomic invalidation/locks implement existing ADR0026 requirements and need later storage/port review. Independent platform/security must explicitly classify each delta and reconcile ADR0010/0026/ST229 wording; fresh planning QA and applicable exact-head CI are required before routine Type2a adoption.
If review finds a concrete security-model change, record that exact before/after as Type1 and obtain founder decision before implementation. Historical predecessor-CSRF acceptance/retention (ADR0027 B), erased subject/contact digest retention (C), permanent signup prohibition or added deletion/lookup authority are excluded alternatives, each needs its own concrete Type1 proposal if later selected.
No SQL/schema/grants/contracts/runtime/UI or policy activation is bundled; no legal compliance, production readiness or usable-account claim. Preserve ST230 historical artifacts and independent C3 reviews; their documentation approval does not select this proposal or waive new review.
