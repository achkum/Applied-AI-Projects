# ADR-0010: Opt-in versioned authentication contract

**Status: Accepted — contract-only**  
**Decision class:** Type 2a (API contract)  
**Date:** 2026-10-06

## Context

The existing v1 contract includes legacy caller identity headers and account deletion behavior. Replacing those semantics in place would mix a new credential model with existing consumers before deployment and consumer inventory is known. The approved ST170 proposal and platform/security reviews call for a versioned, additive contract; they do not approve runtime implementation, migration, rollout, or provider behavior.

## Decision

Add opt-in `/v2` authentication and session routes while preserving every existing v1 path, schema, and behavior. Derive principal and session only from a server-validated v2 credential. Keep v2 issuer, audience, and key namespace isolated from v1. Browser flows use exact-origin checks, a public one-use nonce paired with a distinct HttpOnly binding cookie, and a separate session-bound CSRF token for unsafe cookie calls. Mobile uses Bearer access credentials and the custom `Authorization: Refresh <opaque-secret>` refresh header. Credential branches are mutually exclusive; no mode fallback is allowed.

OTP verifies an identifier or performs restricted step-up only. Enrollment still requires verified BankID before an account is established. Server-owned proof producers are a separate required ST170b integration. Development OTP account-delete reauthentication is gated by explicit development mode and `AUTH_DELETE_OTP_DEV_ONLY=true`; production deletion requires recent BankID. Final account deletion requires both a current same-principal session and an independently consumed deletion-only proof.

Every mutating POST requires `Idempotency-Key` bound to operation, transport, browser chain or verified principal, and request hash. Duplicate pending/committed operations return generic `409 AUTH_RESTART_REQUIRED`, never secrets/proofs or another caller’s result. Lost one-use responses restart with a fresh nonce chain or challenge; uncertain refresh is never retried, and the caller discards local credentials for fresh verified login. Known prior sessions remain manageable only through owner-scoped listing/revocation; unknown orphans expire normally. Refresh rotation is atomic and same-family, with consumed-token reuse revoking the family. No database schema, provider, deployment, or runtime change is included in this contract slice.

## Consequences and gates

The v2 contract supports future independent implementation and review while existing v1 consumers remain unchanged. It makes no rollout-safety claim. Before runtime work, complete security/privacy review of nonce, CSRF, proof binding, storage and rotation; inventory databases before schema changes; confirm deployment origins, cookie host, trusted proxy hops, production keys, and development-only deletion configuration. Validate RLS only against disposable PostgreSQL using a qualified non-superuser, non-`BYPASSRLS` role. ST170b verified proof production is required before session exchange is client-ready. No BankID wire fields are specified here.

## Alternatives considered

- Replace v1 authentication in place: rejected because it changes established wire semantics and consumer compatibility without deployment inventory.
- Allow a v1 fallback: rejected because it would blur credential namespaces and permit identity confusion.
- Treat OTP as sufficient for enrollment/login: rejected because it violates the accepted UF-01 sequence and proof-purpose boundaries.

## Review

Proposal direction is approved by the supplied platform and security reviews. The actual contract and generated validation artifacts passed independent platform, client and security review plus local QA. Acceptance is limited to the versioned interface and validation models; runtime, provider, database, deployment and rollout gates remain.
