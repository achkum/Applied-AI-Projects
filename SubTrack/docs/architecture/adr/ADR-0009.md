# ADR-0009: Signature component placement — `packages/ui` for web, colocated for mobile; defer `packages/ui-native`

- Status: Accepted
- Class: Type 2a (architecture — new package / >1 consumer)
- Deciders: architect-client (Conductor breaks ties per DECISION_RULES §1)
- Date: 2026-09-30
- Blocking: ST-024, ST-026; informs ST-025, ST-027, ST-028

## Context

ST-024 (web) and ST-026 (mobile) both implement the same three signature components
(RollingNumber, ScopeSwitcher, ReceiptCard). Both stalled on attempt 1 against the same
class of defect: acceptance criteria written by ST-016 name paths and tooling that the
tasks' own `allowed_paths` exclude and that do not exist in the repo.

Verified state of the repo on `main` at `cc77e51`:

| Claim in AC | Actual state |
|---|---|
| `packages/ui` (ST-024 AC6) | **Exists** as a workspace package `@subtrack/ui`, but a bare scaffold: `package.json` + `tsconfig.json` only; `build`/`lint`/`test`/`typecheck` are no-op stubs; no `src/`. Owned by **ST-022** (`allowed_paths: SubTrack/packages/ui/**`). |
| `packages/ui-native` (ST-026 AC8) | **Does not exist.** Not referenced anywhere in `DESIGN_DIRECTION.md`, `ARCHITECTURE.md`, or `pnpm-workspace.yaml`. Introduced only by ST-016's AC refinement. |
| Storybook (web AC1/2/3, mobile AC1) | Absent repo-wide — no `.storybook/`, no `storybook` dependency. ST-022 (BACKLOG) owns it; ST-022 `depends_on: [ST-020]`, and ST-020 is **DONE**, so ST-022 is dispatchable today. |
| Playwright / axe-playwright / visual regression (web AC1/3/5) | Absent repo-wide. CI wiring is ST-017 (BACKLOG), whose `allowed_paths` is `.github/workflows/**` only — deliberately not dev-web's. |
| Maestro, iOS/Android devices (mobile AC1/3/5/7) | No binary, no simulator, no emulator in the execution environment. Not obtainable by an agent. |
| "Vitest unit tests" (mobile AC7) | Inverted. `apps/web` runs **vitest**; `apps/mobile` runs **jest** (`jest-expo`). ST-026 correctly used jest. |
| `packages/money` "shared money formatter" (all specs, §"visual component contract") | **Exists but is an empty scaffold** with no-op scripts. Every consumer is currently forced to write its own formatter. |

Two further conflicts were found that neither task reported, both consequences of the same
root cause:

1. **Lockfile.** ST-026 added `react-native-svg@15.2.0` and `expo-haptics@~13.0.1` to
   `apps/mobile/package.json` but could not update `pnpm-lock.yaml` (outside
   `allowed_paths`). `.github/workflows/subtrack-ci.yml:110` runs
   `pnpm install --frozen-lockfile`, which **fails** on the pushed branch
   (`ERR_PNPM_OUTDATED_LOCKFILE`, reproduced). Any task that adds a runtime dependency
   needs the lockfile in scope.
2. **Mobile has no working component-render test harness.** `main` contains no
   render-based test in `apps/mobile`; `@testing-library/react-native` was installed but
   never exercised. ST-026 is the first task to call `render()`, and all three component
   suites fail (`detectHostComponentNames` → `Unsupported param type … $ReadOnlyArray` from
   `DebuggingOverlayNativeComponent.js`) — a RN 0.74 / RNTL 12.9 incompatibility surfaced by
   the `^12.4.0` range floating to 12.9.0. Measured on `st/ST-026-mobile-signature-components`:
   **8 suites, 3 failed / 5 passed; 25 tests, 10 failed / 15 passed.** The 5 passing suites
   are pure-logic (`formatMoney`, `oklch`, `colors`, `useReducedMotion`, i18n parity); every
   failure is a `render()` call, not a component-logic defect. `apps/web`'s harness is
   unproven in the same way — `test/app.test.tsx` asserts on catalogs and a bare
   `document.createElement`, never mounting a React tree — but its
   vitest + jsdom + `@testing-library/react` + `jest-axe` set is installed and conventional.

The governing constraint is `DESIGN_DIRECTION.md` §7.3: *"Any new component must first exist
in `packages/ui` with a Storybook story and tests before it is used in a feature."* Note the
trigger is **use in a feature** (ST-028 hero screens), not authoring. §7 says `packages/ui`
and web Storybook; it says nothing about React Native or a native package. Amending §7 is
D-07 (founder); nothing in this ADR does so.

## Options considered

| Option | Pros | Cons |
|---|---|---|
| **A. Both platforms get real packages now** (`packages/ui` + create `packages/ui-native`) | Literal AC compliance; symmetric; no later move | Creates an unmandated RN package for exactly **one** consumer; Expo/Metro + pnpm symlinks need `metro.config.js` `watchFolders`, `transformIgnorePatterns` and a package-level jest project — all unbuilt; stacks a new package on a **demonstrably broken** render harness; discards working ST-026 code for zero behavioural gain |
| **B. Both platforms colocate in apps; defer both extractions** | Fastest; symmetric; keeps ST-026 work | Contradicts DESIGN_DIRECTION §7.3 for web, which is D-07 territory; guarantees a web move before ST-028; `packages/ui` already exists, so "defer the package" is fiction; ST-022 (which owns `packages/ui` and must render stories from it) would have nothing to point at |
| **C. `packages/ui` for web, colocated for mobile; defer `packages/ui-native`** (chosen) | Honours §7.3 where it applies; uses an **already-approved existing** package rather than creating one; gives ST-022 real stories to render; applies extract-at-second-consumer where no spec mandates otherwise; keeps ST-026's tested work in place | Asymmetric on its face and needs explaining to two dev roles; one AC rewrite per task |
| **D. Resequence ST-022 + ST-017 fully ahead, keep all ACs as written** | ACs achievable verbatim | ST-017 cannot deliver Maestro, iOS/Android devices or screen-reader sessions — those ACs are **unachievable by any agent in this environment**, not merely out of order; blocks all D1 component work behind CI plumbing; still leaves the `allowed_paths`, lockfile and harness defects unfixed |

## Decision

### 1. Placement (the Type 2a call)

The consistent principle, applied to both tasks: **extract to a shared package at the second
real consumer, unless an accepted spec already mandates the package.** Web meets the
exception; mobile does not.

- **Web — `packages/ui` (`@subtrack/ui`).** This is *not* a new-package decision: the package
  already exists in `pnpm-workspace.yaml`, DESIGN_DIRECTION §7.3 mandates it, ST-022 already
  owns it and needs components in it to render stories from, and it has a second consumer the
  moment Storybook and `apps/web` both import it. ST-024's components go there. `apps/web`
  adds `"@subtrack/ui": "workspace:*"` and consumes them.
- **Mobile — colocated in `apps/mobile/src/components/signature/`; `packages/ui-native` is
  NOT created.** One consumer, no spec mandate, and real integration cost (Metro
  `watchFolders`, pnpm symlink resolution, `transformIgnorePatterns`, a package jest project)
  that would land on top of a render harness that does not currently work. Revisit when a
  second RN consumer exists (a second Expo app, or an RN Storybook host that must resolve the
  package by name).

The asymmetry is deliberate and costs nothing in shared code, because almost nothing is
shareable between these two implementations: Framer Motion vs Reanimated, SVG vs
`react-native-svg`, CSS vs `StyleSheet`. What *is* genuinely shared is pure logic, and it
belongs in the **existing** packages, not in a new UI package:

- money formatting → implement `packages/money` (currently an empty scaffold, and already
  named as "the shared money formatter" by all seven component specs);
- `oklch()` → sRGB conversion → `packages/ui-tokens`' native generator should emit sRGB
  directly, so no native consumer needs ST-026's local `oklch.ts` workaround;
- member accent → already correct in `packages/ui-tokens` (`memberAccentForId`, ST-030).

### 2. Sequencing vs descoping (answer: both, split by whether an agent can actually do it)

Do not resequence everything, and do not descope everything. Split the ACs by achievability:

- **Resequence ahead of ST-024 (real prerequisites, achievable now):** **ST-022** —
  Storybook + visual-regression command in `packages/ui`. It is unblocked (`ST-020` DONE) and
  it owns the very package ST-024 must write into. Dispatch ST-022 first; ST-024 then only
  adds components + stories to a working toolchain. **ST-017** (CI wiring) may run in
  parallel — ST-024 needs the Storybook/Playwright *tooling*, not the CI job, and ST-017 AC2
  explicitly states it "does not block ST-022 implementation".
- **Descope to follow-ups (not achievable by an agent in this environment, at any point in
  the sequence):** Maestro E2E, iOS-simulator/Android-emulator runs, and VoiceOver/TalkBack
  device sessions. No binary, device or simulator is available. Keeping these as blocking ACs
  guarantees an indefinite BLOCKED loop and invites fabricated evidence. They become a
  human/CI-runner follow-up task (proposed **ST-033**, milestone D2).
- **New prerequisite task, mobile (proposed ST-032, blocks ST-026 and ST-027):** repair the
  mobile component-render harness — pin `@testing-library/react-native` to a version
  compatible with RN 0.74 (or apply the documented RNTL/RN interop fix), prove it with one
  rendering smoke test, and own the `pnpm-lock.yaml` update. Without this, no mobile component
  task can produce passing render tests, and ST-027 (Orbit, currently READY) will hit the
  identical wall.

Replacement evidence, for both platforms, until the descoped tooling exists: unit/behaviour
tests through each app's own runner — locale formatting, reduced-motion branch (frozen /
instant), accessibility props (`role`/`aria-*` on web, `accessibilityRole`/`accessibilityLabel`/
`accessibilityState` on mobile), token-only colour derivation, i18n sv/en parity via
`packages/i18n`' existing `check:parity`. Web additionally keeps `jest-axe` at unit level
(already installed) in place of `axe-playwright`.

### 3. ST-026's existing work: keep it

Keep the colocated implementation on `st/ST-026-mobile-signature-components`. Option C makes
its location correct as-is, so there is nothing to move. The three deviations it recorded are
all upheld:

- colocating rather than creating `packages/ui-native` — now the decided architecture;
- member-specific accent via `memberAccentForId` over AC2's literal "member=category" — correct;
  ST-030 was delivered precisely to resolve this, and `scope-switcher.md` prohibits
  substituting a category hue for member identity. **AC2's wording is the defect.**
- jest over AC7's "Vitest" — correct; `apps/mobile` has no vitest.

It is **not** complete and must not be closed on its current evidence: lint/typecheck/final
verification never ran, no HANDOFF was written, its render tests fail for the harness reason
above, and its lockfile omission breaks CI install. It needs one more attempt after ST-032,
not a rewrite.

## Consequences

+ ST-022 becomes the critical path for all web component work; it is unblocked today.
+ ST-026 keeps ~1,170 lines of written, reviewed-shape work; only verification is redone.
+ `packages/ui-native` is not created, so no Metro/pnpm shared-package plumbing is needed in D1.
+ ST-025 (web Orbit) and ST-027 (mobile Orbit), both currently READY with the *same*
  `allowed_paths`/Storybook defects, must get the same corrections before dispatch — otherwise
  they reproduce this block verbatim. ST-025 AC5 requires a Storybook story; ST-027 needs ST-032.
− Web components must exist in `packages/ui` before ST-028 consumes them, per §7.3; ST-028 is
  gated on ST-024 landing there (it already is, via `depends_on`).
− Mobile and web signature components will diverge stylistically until/unless extraction
  happens. Accepted: the shared surface is the token and money layer, not the view layer.
− Two new tasks (ST-032 harness, ST-033 device/E2E backfill) and a `packages/money`
  implementation task are added to the backlog.

## Verification (how we'll know it was right)

- ST-022 lands and its Storybook renders a story imported from `packages/ui` — confirms the
  web package choice was usable rather than ceremonial.
- ST-024 re-dispatch completes without a scope/`allowed_paths` block.
- After ST-032, `pnpm --filter @subtrack/mobile test` is green on
  `st/ST-026-mobile-signature-components` with all three component suites rendering.
- `pnpm install --frozen-lockfile` succeeds on both branches — the lockfile defect is closed.
- If a second RN consumer appears in D2 and extracting the three components to
  `packages/ui-native` proves cheap, the deferral was correct. If ST-027/ST-028 end up
  copy-pasting logic out of `apps/mobile/src/components/signature/`, revisit this ADR —
  that is the signal the second consumer arrived earlier than expected.
