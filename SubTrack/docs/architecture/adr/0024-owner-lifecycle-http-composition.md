# ADR-0024: Isolated owner lifecycle HTTP composition

Status: Proposed Type 2a architecture decision for ST-216 (2026-10-10). No runtime source authority until ST-215 PR244 is accepted on `main` and independent security/privacy readiness approves this boundary.

## Decision

Expose the accepted status-only `PATCH /v1/subscriptions/{id}` only in an explicitly enabled development Nest composition bound to numeric `127.0.0.1`. Keep `main.ts`, `AppModule`, the default graph, and accepted read-only launch unchanged. The dedicated graph registers the existing `AuthenticatedPrincipalGuard` as `APP_GUARD`, its V1 Bearer `PrincipalResolver`, real current-session `PrismaSessionOwnerReader`, existing read surface, and the private lifecycle writer. The guard's verified request context supplies the sole principal. No new issuer, client-selected owner/scope/action, public port, provider, or security model is introduced.

The route accepts a strict UUID path, no raw query string, and exactly one JSON field, `status: ACTIVE|PAUSED|CANCELLED|ARCHIVED`. Its target maps to resume/pause/cancel/archive respectively. The writer's locked owner row and transaction-local identical `app.user_id` and `app.current_user_id` bindings decide whether the pair is one of the seven in ADR-0023. The HTTP layer never reads an unlocked status to choose an action. Success exposes only `{id,status}`. A bounded RFC9457 filter projects malformed requests to 400, absent/invalid current principal to 401, missing and owner-invisible IDs to identical 404, stale/disallowed pairs to 409, and storage faults to masked 500. An uncertain success can produce 409 on retry, so the caller re-reads; no replay or exactly-once claim follows. No ordinary-action audit/replay persistence, new retention state, or broader edit/review/undo behavior is added.

## Fixture authority and verification

The private application factory accepts injected Prisma and verifier only from a trusted, fixture-verifying harness; it does not use ambient `DATABASE_URL` or treat a same-named database/role as proof of ownership. Before client construction or any listener, a direct launch verifies a private owner-only provenance record against Docker inspection: exact CID, fresh unique ST-216 label and creation time, running approved PG16 image, sole tmpfs data mount, and sole numeric-loopback ephemeral port. It matches the runtime URL role/database/port to that container and rejects credentials or selectors that diverge. The wrapper creates that container, records its CID before start, applies all canonical migrations as fixture owner, and grants only the ordinary non-superuser, non-BYPASSRLS LOGIN runtime role. Same-pool preflight checks RLS, role membership and necessary SELECT/UPDATE privilege before registration; names alone are insufficient. Cleanup verifies the exact labelled container was removed and the private temp directory is gone; PASS is emitted only afterward. All failures and responses are sanitized.

## Consequences and gates

Proof must traverse real HTTP, guard, session lookup, writer, and ordinary-role PostgreSQL for all seven pairs, access isolation, malformed/spoofed requests including parser-discarded query keys, revoked/wrong-subject sessions, races, rollback and pooled GUC cleanup. Changed runtime files need ≥80% coverage plus API lint/typecheck/regression, frozen build/container Node22 smoke, dedicated actual-PG CI, and independent platform/security/QA review at the exact head. If safe implementation needs an accepted source file outside ST-216's listed paths, request a minimal scope extension and renewed readiness before editing it. This decision does not complete ST-081, UF-06, or production/public release.
