# ADR-0020: Anonymous mobile enrollment OTP reservation binding

Status: Proposed; requires explicit founder approval. This document authorizes no runtime change.
Decision class: Type1 (security model), DECISION_RULES section1.
Date: 2026-10-10.

## Problem
Accepted mobile OTP envelopes carry Idempotency-Key, channel/identifier/purpose/transport on start and challengeId/code/transport on verify. Enrollment precedes a principal and mandatory BankID. ADR-0010 and the idempotency core permit browser-chain or verified-principal binding (plus a web-only nonce-bootstrap exception), so neither existing authority can honestly represent anonymous mobile initiation. IP, identifier, challenge possession and caller key are not verified principals.

## Proposed option A
Add a distinct internal reservation kind `anonymous-enrollment-otp` limited to operation startV2Otp or verifyV2Otp, transport mobile and enrollment purpose. It describes server-derived request isolation, never an authenticated principal. No wire header/secret, account/device identity or principal selector is added. Keep global keyed Idempotency-Key one-use uniqueness, owner-handle settlement and generic duplicate behavior unchanged.

The new kind requires a distinct internal discriminated input with literal `purpose: 'enroll_identifier'`. The core must validate kind, operation, transport and purpose at runtime as well as in its narrowed type. Its digest must have separate anonymous-request wording/types rather than reusing a verified-authority brand. Include the purpose in this new kind's binding while preserving existing authority inputs and binding bytes. The current core has no purpose field; this is a required future change, not an existing guarantee.

Require a dedicated server HMAC key of at least256 bits, copied immutably, with decoded bytes distinct from OTP, rate-limit, idempotency-core, origin and credential keys. Start and verify use different framed domains. Initially all stores and this configuration are process-local and development-only. No in-place key rotation: restart replaces the whole challenge, metadata, sink and reservation state, and clients start a fresh challenge. Durable storage or live rotation requires a separate reviewed design. This proposal creates no secret or configuration.

Capture one binding/input for reservation and settlement; never recompute it using changed configuration. Require mandatory configuration with no fallback or caller-provided key. Process-local restarts clear retained key burns; no distributed or durable one-use guarantee is claimed.

Start binding is a server HMAC over a domain/version, operation, transport, purpose, normalized identifier hash and channel, using unambiguous length framing. It remains explicitly unverified. Verify binding is a separately domain-framed HMAC over operation, transport, enrollment purpose, challengeId, stored normalized identifier hash and stored channel, obtained from the bounded server challenge record. No client authority field or value derived solely from IP/key is accepted. Request hash includes the full strict operation payload, including the code on verify; reservation storage retains only keyed digests. Code verification, not the reservation digest or challenge possession, establishes the restricted identifier proof.

The existing five-minute challenge/proof lifetimes and five-code-attempt maximum remain. Idempotency reservations stay bounded to10,000 and at most24 hours. Future adapter clock-regression, capacity and expiry handling must fail closed and be verified; this proposal does not claim the present producer already implements every gate. Start uses existing direct-IP and HMAC-identifier limits; verify shares the aggregate IP budget. Separate operation/transport/purpose/domain framing prevents this kind from being used by any browser, principal, session, refresh, step-up or deletion operation.

Reserve synchronously before producer mutation. Pending, completed and failed duplicates return generic409 without replaying challenge/code/proof. Complete settlement precedes sink publication or proof disclosure. Lost/uncertain responses require a fresh challenge and random fresh key under normal limits; consumed challenges/proofs are never revived. Settlement faults disclose nothing and leave burned reservations/bounded orphans. A future adapter must resolve purpose/identifier/channel only from its own bounded challenge metadata and ensure metadata/producer coherence through failures and concurrency.

Require a new process-owned `MobileEnrollmentChallengeMetadata` boundary: immutable challengeId, literal enrollment purpose/mobile transport, normalized identifier hash, channel, issuedAt and expiresAt, plus terminal lifecycle state. The present OTP repository has no metadata lookup and the web sink's browser-chain record cannot supply this tuple. The adapter must maintain this record from the same producer issuance and resolve it only internally, checking validity and coherence across awaits. Neither this metadata nor its digest proves identity.

Start must reserve bounded publication capacity before issuance, settle the owned idempotency reservation successfully, then publish metadata and the test-only code sink atomically in one synchronous store transition before responding. Publication failure must leave neither partially visible metadata nor a sink entry; disclose nothing, burn the reservation and let any unreachable producer challenge expire. Fault tests must prove this behavior, including settlement failure and capacity races. No producer challenge rollback or replay is assumed.

Completed settlement remains completed after publication or response failure; a failed-settle call must not undo it. Cleanup failure must still suppress disclosure and mark records unusable, with bounded expiry as fallback. The future metadata port must extend the producer/repository boundary or demonstrate an equivalent reviewed mechanism proving its immutable tuple agrees with the challenge the producer consumes; merely duplicating client fields does not suffice.

Verify resolves a valid immutable metadata snapshot, reserves before verification, and relies on the producer's atomic consume for at-most-one proof. Only successful settlement permits proof disclosure; after producer success, terminally remove metadata/sink even if settlement fails, so no consumed challenge is revived. Wrong-code failures burn that request key but retain expiry-bounded metadata so fresh keys may use the remaining producer-controlled attempts. An ambiguous producer exception must never reactivate or reconstruct producer state; subsequent attempts remain subject to its consumed/exhausted state. Concurrent snapshots cannot mint a second proof. Recheck time validity after awaits before disclosure; any resulting orphan proof remains bounded and undisclosed. These store/producer/cleanup properties require a separate implementation and fault/concurrency evidence.

Only enroll_identifier is allowed. Reject mobile otp_step_up until a separate current-principal decision. Successful proof remains bound to mobile transport, enrollment purpose, initiating challenge and normalized identifier hash; it cannot establish account/login/session/deletion authority and cannot replace mandatory BankID.

## Runtime gates after a decision
- Separate reviewed implementation task and core type/test update must restrict the new kind to these two operations/mobile/enrollment. No broad AuthorityKind cast, verified-principal alias or relaxation of existing bindings.
- Exact accepted mobile headers/body; reject Cookie, Authorization, Origin, browser nonce/CSRF, legacy authority selectors, duplicate/framing/query ambiguity and mixed transport. No additional mobile wire secret/header. Confirm contract descriptors remain accurate before any wire-affecting change.
- Start202 returns exactly challengeId, status accepted and nextBrowserNonce:null; verify200 returns exactly purpose enroll_identifier, proof and nextBrowserNonce:null. Preserve accepted no-store and generic error envelopes. Client keys use a trusted random generator with at least128 bits of randomness, within the accepted wire format.
- Direct TLS socket required; forwarded HTTPS assertions and cleartext browser loopback exceptions provide no mobile authority. Explicit development-only opt-in, absent from default and production graphs. No public port/deployment is approved.
- Standalone opt-in module initially; global browser middleware cannot be bypassed merely because Origin is absent. Any combined web/mobile middleware wiring requires separately reviewed discrimination and web regressions.
- Test-only process-local code sink, bounded and expiry-pruned. No HTTP retrieval, real delivery, code/token logging, provider or DB change. No source code or constructor mutation in this proposal.
- Actual HTTPS tests: both channels/normalization, mixed headers, plaintext/proxy spoof, cross-web/mobile challenges, wrong/expired/exhausted codes, concurrency at-most-one proof, pending/completed/failed duplicates, clocks/rates/capacity, reserve/settle/sink faults, no-store errors, restricted proof unable to redeem for login/deletion, and disabled/production404. Native/device and delivery evidence remain separate.

## Alternatives and decision request
Option A adopts the distinct anonymous enrollment request-binding model above and permits a subsequent reviewed development-only implementation task. It changes the security model; implementation is not bundled with approval.

After explicit adoption, the contract follow-up must narrowly update the API_CONTRACT requirement that every POST binds a browser chain or verified principal, documenting only these two anonymous mobile enrollment operations. Until adoption and that separately reviewed follow-up, ADR-0010 and the current contract remain authoritative. No accepted document is silently superseded by this Proposed ADR.

Option B keeps ADR-0010 unchanged and mobile OTP blocked; continue independently ready work. Requiring an existing Bearer principal would not implement anonymous enrollment in the accepted user flow.

Recommendation: A, provided independent platform/security reviewers approve this precise model and the founder explicitly adopts it. Approval does not waive runtime tests, mandatory BankID, data inventory or release gates. Until then this proposal remains unaccepted.
