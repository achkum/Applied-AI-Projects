# ADR-0025: Additive development browser subscription authority

Status: **Proposed for independent client/security readiness** (2026-10-10). Decision class: Type 2a, reversible API contract and isolated development composition. No runtime/source authority until reviewed and accepted.

## Context
Accepted v1 subscription GET/PATCH uses `AuthenticatedPrincipalGuard`, a v1 Bearer JWT and PostgreSQL `session`/`identity` current-owner lookup. Accepted v2 browser login creates HttpOnly cookies scoped to `/v2`, a separate in-memory development session and isolated JWT namespace. The v1 guard rejects v2 cookies. Accepted browser evidence requires exactly one `Origin`; same-origin GET can omit it, and JavaScript cannot set that forbidden header ([WHATWG Fetch origin-header algorithm](https://fetch.spec.whatwg.org/#append-a-request-origin-header)). `DevelopmentV2PrincipalResolver.resolve` checks current owner/session, origin and chain, but not binding-cookie hash; accepted `webContextForCurrentSession` supplies that additional check. The default application exposes neither subscription route nor a complete signed-in browser onboarding path.

## Proposal
Keep v1 behavior and authority unchanged. Add a contract-only opt-in `POST /v2/subscriptions/{id}/read` with exactly `{}` body, no query, current v2 web cookie, exact allowlisted Origin and session-bound `X-Session-CSRF`. It performs only the bounded owner detail read and never mutates a nonce, session, CSRF token or subscription, so ADR-0010's idempotency requirement for *mutating* POST does not apply. A later status-only `PATCH /v2/subscriptions/{id}` preserves the accepted seven-pair semantics and requires the same web authority and CSRF; it remains unavailable by default until separately contracted and activated. Runtime must verify access to derive `sid/sub`, hash the observed binding cookie, call accepted `webContextForCurrentSession(sid,{userId:sub},bindingCookieHash,exactOrigin,observedAt)`, then `DevelopmentV2PrincipalResolver.resolve(access,{transport:'web',exactOrigin,browserChainId})`, compare returned owner/session/chain, and call `SessionCsrfGuard.verify({identityId,sessionId},csrfHeader)` before passing that identity to subscription `RequestContext`. A disabled-by-default graph may pass it to the existing owner-scoped read and locked writer under ordinary-role PostgreSQL RLS. No Bearer fallback, token conversion, caller owner selector or shared v1/v2 issuer is allowed. A future proof may use a server-owned simulator proof and synthetic pre-registered identity in owned disposable PG; the in-memory v2 session reference supports only that limited proof, with no persistence or user onboarding.

## Consequences and gates
The next bounded task changes only the OpenAPI read-POST contract, generated bindings and contract tests; runtime/PATCH implementation is a later task after independent review. Independent architect-client/security review of cookie handling, current-owner linearization and transaction scope precedes runtime work; QA then requires real HTTPS browser + owned ordinary-role PG evidence at exact head. ST-217 user-facing binding remains NOT_READY until enrolled account, usable persistent session/runtime activation and browser proof are separately accepted. A design that changes v1 credential acceptance, substitutes identity headers, or replaces ADR-0010 isolation is Type 1 and needs a concrete founder decision before such work.
